03 Advanced stage capstone

Harden the task API: auth, tests, and rate limiting

Node.js · ties together everything in the Advanced stage

Rather than starting a new project, this stage's capstone is about taking the Learning-stage task API and making it production-worthy — which is a far more realistic picture of real backend work than always building something new. You'll add authentication so tasks belong to specific users, a real test suite that exercises both success and failure paths, and protections against abuse and crashes.

This project deliberately stacks the Advanced-stage topics on top of each other rather than treating them separately, because in a real codebase they interact: your auth middleware has to be tested, your error handling has to account for auth failures, and your rate limiting has to sit correctly in the middleware order relative to both.

By the end, every task in the database belongs to a specific authenticated user, nobody can see or modify anyone else's tasks, the whole API is covered by an automated test suite, and it can't be trivially hammered into the ground by a script making requests in a tight loop.

  • Authentication: JWT and session-based auth
  • Middleware architecture and error-handling patterns
  • Testing with Jest/Supertest
  • Async patterns at scale (queues, worker processes)
  • Basics of microservice architecture
Requirements
  • Registration and login routes: registration hashes the password with bcrypt before storing it, login verifies it with bcrypt.compare() and issues a JWT containing the user's id.
  • Every /tasks route is protected by authentication middleware that rejects requests with a missing or invalid token with 401, and every task is scoped to the authenticated user — a user can never read, update, or delete another user's task, not even by guessing an id.
  • A centralized error-handling middleware (four-parameter signature) that all routes funnel errors through, using an asyncHandler wrapper (or equivalent) so a thrown error inside an async route handler is actually caught instead of silently becoming an unhandled rejection.
  • At least one custom error class (e.g. NotFoundError, UnauthorizedError) carrying its own HTTP status code, used by at least two different routes.
  • A Jest + Supertest test suite covering, at minimum: successful task creation, a rejected request with a missing required field, a 401 on a protected route with no token, and a 404 for a task that doesn't belong to the requesting user.
  • Basic rate limiting on at least the login route (e.g. via express-rate-limit or a hand-rolled in-memory counter), returning 429 once a client exceeds the limit within a time window.
  • A process.on("unhandledRejection") safety-net listener that logs anything that still slipped past your error handling.
Suggested approach
  1. Add the auth routes and JWT middleware first, against your existing task routes, and manually verify with a REST client that protected routes reject requests with no token before doing anything else.
  2. Add the user-scoping to every existing task query next — this is the step most likely to have subtle bugs, so test it explicitly: create tasks as two different users and confirm neither can see the other's data.
  3. Refactor error handling into the centralized pattern (custom error classes, asyncHandler, one error middleware) before writing tests, since untangling ad hoc error handling after tests exist is more painful than doing it first.
  4. Write the test suite next, covering the specific success/failure paths listed in the requirements — run it against the real routes with Supertest, resetting any test data between runs.
  5. Add rate limiting last, since it's the most likely thing to interfere with your own test suite running many requests quickly — scope it narrowly (login only, or a generous limit) so your tests still pass.
Stretch goals
  • Add a refresh-token flow: a short-lived access token plus a longer-lived refresh token that can mint new access tokens without forcing a full re-login.
  • Move rate-limit state into Redis instead of in-memory, so it would survive a server restart and work correctly if you ever ran more than one instance.
  • Add a test that specifically confirms the 'missing return' double-response bug can't happen in any of your routes, by asserting each route sends exactly one response even on error paths.
