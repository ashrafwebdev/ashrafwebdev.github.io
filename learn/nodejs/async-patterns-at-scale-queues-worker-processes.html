03 Advanced stage

Async patterns at scale (queues, worker processes)

Node.js · part of the free zero-to-hero guide

Not all work belongs inside a request handler — sending emails, processing images, or generating reports can take seconds or minutes, far too slow to make a user wait on. A message queue (like BullMQ backed by Redis, or a cloud service like SQS) lets you hand off that work to be processed separately from the request/response cycle.

Worker processes pull jobs off the queue and execute them independently from your web server, which can then respond to the original request immediately (often with something like { status: "queued" }) and let the job finish whenever it finishes, entirely decoupled from how long the actual work takes.

Queues decouple 'accepting the request' from 'doing the slow work', keeping response times fast and predictable — and worker processes can be scaled independently from your web servers based on how deep the queue is getting, rather than scaling both together even when only one side is under load.

Failed jobs should be retried with backoff (waiting progressively longer between attempts) rather than immediately, and eventually moved to a dead-letter queue for manual inspection rather than retried forever — a job that fails because of a genuine bug will just keep failing no matter how many times it's retried, and silently retrying forever hides that problem instead of surfacing it.

Idempotency matters a great deal here — a job might run more than once (e.g. after a worker crashes mid-processing and the job gets picked up again), so jobs should be designed to produce the same end result whether they run once or several times, for example by checking 'has this already been done' before doing it, rather than assuming exactly-once execution.

Beyond one-off background jobs, queues also support delayed jobs (run this 24 hours from now) and repeating jobs (run every night at 2am) — useful for reminder emails, scheduled reports, or periodic cleanup tasks — and most queue libraries let you cap concurrency (how many jobs a single worker processes at once) to avoid overwhelming a downstream resource like a rate-limited third-party API.

A BullMQ job
const { Queue, Worker } = require("bullmq");

const emailQueue = new Queue("emails");

// In your route handler:
await emailQueue.add("welcome", { to: user.email });

// In a separate worker process:
new Worker("emails", async (job) => {
  console.log("Sending email to", job.data.to);
});
retries-and-idempotency.js
await emailQueue.add(
  "welcome",
  { to: user.email, userId: user.id },
  { attempts: 5, backoff: { type: "exponential", delay: 2000 } }
);

new Worker("emails", async (job) => {
  const alreadySent = await hasWelcomeEmailBeenSent(job.data.userId);
  if (alreadySent) return; // idempotent — safe if this job runs twice

  await sendEmail(job.data.to);
  await markWelcomeEmailSent(job.data.userId);
});
scheduled-and-limited.js
// Runs once, 24 hours from now
await reminderQueue.add("reminder", { userId: user.id }, { delay: 24 * 60 * 60 * 1000 });

// Repeats every night at 2am (cron syntax)
await reportQueue.add("nightly-report", {}, { repeat: { pattern: "0 2 * * *" } });

// Cap concurrency so we don't hammer a rate-limited API
new Worker("emails", processJob, { concurrency: 5 });
Key points
  • Queues decouple 'accepting the request' from 'doing the slow work', keeping response times fast and predictable.
  • Worker processes can be scaled independently from your web servers based on queue depth.
  • Failed jobs should be retried with backoff, and eventually moved to a dead-letter queue for manual inspection rather than retried forever.
  • Idempotency matters — a job might run more than once (e.g. after a crash mid-processing), so design jobs to handle that safely.
  • Queues support delayed jobs (run later) and repeating jobs (cron-like schedules), not just immediate background work.
  • Capping a worker's concurrency prevents it from overwhelming a downstream rate-limited resource, like a third-party API.
  • A job that fails due to a real bug will keep failing on every retry — a dead-letter queue surfaces that instead of hiding it behind silent infinite retries.
Try it yourself

Set up a simple BullMQ (or similar) queue and worker: a route that enqueues a job, and a separate worker script that processes it and logs the result. Then make the job idempotent by tracking completion state, configure retries with exponential backoff, and add a delayed job that fires a few seconds after being enqueued to confirm the delay option works.
