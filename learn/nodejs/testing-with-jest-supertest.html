Testing with Jest/Supertest

Node.js · part of the free zero-to-hero guide

Builds on: Middleware architecture and error-handling patterns

Jest is a full-featured JavaScript testing framework — test runner, assertion library, and mocking tools all in one. Supertest builds on top of it specifically for testing HTTP servers, letting you make requests against your Express app directly in tests without starting a real server on a port.

Testing routes this way catches integration-level issues (wrong status codes, malformed responses, middleware ordering bugs) that isolated unit tests of individual functions would miss entirely, since those functions might work correctly on their own but be wired together incorrectly.

Jest's beforeEach/afterEach (and beforeAll/afterAll) hooks are useful for resetting a test database between tests — each test should ideally start from a known, clean state, so tests don't accidentally depend on the order they happen to run in, which is a common source of flaky test suites.

Mock external services (third-party APIs, email sending, payment processors) in tests with jest.mock() so they run fast, deterministically, and don't depend on network access or real side effects like actually sending an email or charging a card every time the test suite runs.

Test both the success path and realistic failure paths for every route — missing required fields, a resource that doesn't exist, invalid authentication — not just the happy path where everything goes right. A route that only has one passing test for valid input often has untested, broken behavior for the inputs it will actually see in production.

Snapshot testing (asserting a response matches a previously saved snapshot) is convenient but easy to misuse — a snapshot that includes something that legitimately changes often, like a timestamp, will fail on every run for no real reason, and developers who get used to blindly running --updateSnapshot stop actually reviewing what changed.

server.test.js
const request = require("supertest");
const app = require("./app"); // exported Express app, not yet listening

test("GET /users/:id returns a user", async () => {
  const response = await request(app).get("/users/1");
  expect(response.status).toBe(200);
  expect(response.body).toHaveProperty("id", "1");
});
items.test.js (success and failure paths, with setup/teardown)
const request = require("supertest");
const app = require("./app");
const db = require("./db");

beforeEach(async () => {
  await db.reset(); // start each test from a clean, known state
});

test("POST /items creates an item", async () => {
  const res = await request(app).post("/items").send({ name: "Widget" });
  expect(res.status).toBe(201);
  expect(res.body.name).toBe("Widget");
});

test("POST /items without a name returns 400", async () => {
  const res = await request(app).post("/items").send({});
  expect(res.status).toBe(400);
  expect(res.body.error).toBeDefined();
});
email.test.js (mocking an external service)
jest.mock("./emailService"); // auto-mocks every exported function
const emailService = require("./emailService");
const request = require("supertest");
const app = require("./app");

test("registering a user sends a welcome email", async () => {
  emailService.sendWelcomeEmail.mockResolvedValue(true);

  await request(app).post("/register").send({ email: "a@example.com" });

  expect(emailService.sendWelcomeEmail).toHaveBeenCalledWith("a@example.com");
  // no real email was sent — fast, deterministic, no network needed
});
Key points
  • Supertest tests your actual Express app object directly, no need to bind it to a real port during tests.
  • Test both the success path and realistic failure paths (missing resource, invalid input) for every route.
  • Jest's beforeEach/afterEach hooks are useful for resetting a test database between tests.
  • Mock external services (third-party APIs, email sending) in tests so they run fast and don't depend on network access.
  • Each test should start from a known, clean state — order-dependent tests are a common source of flaky suites.
  • Snapshot tests are convenient but can rot silently if developers get used to blindly running --updateSnapshot.
  • Integration-level tests (a full route through Supertest) catch wiring/middleware-ordering bugs unit tests of individual functions would miss.
Try it yourself

Write Supertest tests for one of your Express routes, checking both the success path (correct status code and response shape) and at least one realistic failure path (bad input or missing resource). Then add a beforeEach hook that resets your test data, and mock any external service the route calls so the whole suite runs without real network access.
