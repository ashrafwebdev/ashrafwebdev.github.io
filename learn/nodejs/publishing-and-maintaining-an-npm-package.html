Publishing and maintaining an npm package

Node.js · part of the free zero-to-hero guide

Publishing to npm is as simple as npm publish once package.json has a unique name and version — but maintaining a package well requires ongoing care: semantic versioning, a changelog, and not breaking consumers without warning, since real projects will depend on your exact behavior, intentional or not.

Semantic versioning (major.minor.patch) is a contract with your users: a patch release should only contain bug fixes, a minor release adds backward-compatible functionality, and a major release can contain breaking changes — respecting that distinction is what lets consumers safely use version ranges like ^1.2.3 without manually reviewing every release.

The files field in package.json (or a .npmignore file) controls what actually ships in the published package, keeping it lean — without it, npm publishes essentially everything in the directory not excluded by .gitignore, which often means accidentally shipping test files, source maps, or internal scripts nobody consuming the package needs.

The main field (and increasingly the more expressive exports field) tells Node and bundlers which file to load when someone does require("your-package") or import ... from "your-package" — the exports field can also explicitly restrict which internal files are importable at all, preventing consumers from reaching into implementation details you might want to change freely later.

Automated tests and a CI pipeline that runs before publish prevent shipping a broken release to everyone depending on you — a broken patch release that reaches thousands of downstream projects overnight is a real, recurring failure mode in the npm ecosystem, and a CI gate is the standard defense against it.

A clear README with install instructions and a basic usage example is often the difference between a package getting adopted or ignored, and enabling two-factor authentication on your npm account (required for publishing popular packages, and a very good idea regardless) protects against a compromised account being used to publish malicious versions of your package to everyone who depends on it.

Terminal
npm login
npm version patch   # bumps the version and creates a git tag
npm publish
npm publish --dry-run   # preview exactly what would be published, without doing it
package.json (files and exports fields)
{
  "name": "my-utils",
  "version": "1.2.0",
  "main": "dist/index.js",
  "types": "dist/index.d.ts",
  "files": ["dist", "README.md"],
  "exports": {
    ".": "./dist/index.js",
    "./package.json": "./package.json"
  }
}
.github/workflows/publish.yml (CI gate before publish)
name: Publish
on:
  push:
    tags: ["v*"]
jobs:
  publish:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: "20", registry-url: "https://registry.npmjs.org" }
      - run: npm ci
      - run: npm test          # publish is blocked if tests fail
      - run: npm publish
        env: { NODE_AUTH_TOKEN: "${{ secrets.NPM_TOKEN }}" }
Key points
  • Semantic versioning (major.minor.patch) is a contract with your users — respect it, especially for major/breaking changes.
  • A .npmignore (or the files field in package.json) controls what actually ships in the published package, keeping it lean.
  • Automated tests and a CI pipeline before publish prevent shipping a broken release to everyone depending on you.
  • A clear README with install instructions and a basic usage example is often the difference between a package getting adopted or ignored.
  • The exports field can restrict which internal files consumers can import, protecting implementation details from becoming an accidental public API.
  • npm publish --dry-run lets you preview exactly what would ship before actually publishing it.
  • Two-factor authentication on your npm account protects against a compromised account publishing malicious versions to everyone who depends on your package.
Try it yourself

Package a small utility function, set up package.json correctly (name, version, main entry point, and a files field), and publish it to npm (or simulate the process locally with npm pack and inspect the resulting tarball's contents). Then bump the version with npm version minor after adding a backward-compatible feature, and write a short CHANGELOG entry describing what changed.
