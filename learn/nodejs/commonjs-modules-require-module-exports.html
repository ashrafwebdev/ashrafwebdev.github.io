CommonJS modules (require/module.exports)

Node.js · part of the free zero-to-hero guide

Builds on: npm and package.json basics

CommonJS is Node's original module system: module.exports defines what a file makes available, and require() pulls that into another file. It's synchronous and file-based, unlike the newer ES Modules standard that browsers and modern bundlers use natively.

Modern Node also supports ES Modules (import/export) via .mjs files or "type": "module" in package.json — new projects increasingly default to ESM, but a huge amount of existing Node code, and most older npm packages, are still CommonJS.

require() caches modules by their resolved file path — requiring the same file twice, from anywhere in the project, returns the exact same already-executed module object rather than re-running the file. This matters for anything with module-level state, like a shared database connection or an in-memory cache.

A common beginner mistake is confusing exports and module.exports. exports starts as a reference to the same object as module.exports, so exports.add = fn works fine — but reassigning exports = {...} breaks that link and exports nothing, since module.exports still points to the original (now-unused) object. Reassigning module.exports directly is always safe.

Circular requires — module A requiring module B while B is also requiring A — are possible in CommonJS but return a partially-completed export from whichever module hasn't finished executing yet, which can silently produce undefined values for functions or objects that haven't been defined yet at that point in the file. Restructuring to avoid the cycle is usually simpler than working around it.

Each CommonJS file also gets its own __dirname and __filename variables giving its absolute location on disk — useful for building file paths relative to the current module rather than relative to wherever the process happened to be started from. ES Modules don't have these automatically; they require import.meta.url instead.

math.js / index.js
// math.js
function add(a, b) { return a + b; }
module.exports = { add };

// index.js
const { add } = require("./math");
console.log(add(2, 3));
The exports vs module.exports pitfall
// BROKEN — reassigning exports breaks the link to module.exports
exports = { add: (a, b) => a + b };
// require("./this-file") will return {} — nothing was actually exported!

// CORRECT — either mutate exports, or reassign module.exports directly
exports.add = (a, b) => a + b;         // ok
module.exports = { add: (a, b) => a + b }; // also ok, and clearer
paths.js
const path = require("path");

console.log(__dirname);  // absolute directory of this file
console.log(__filename); // absolute path of this file

// Build a path relative to this module, not the process's cwd
const dataFile = path.join(__dirname, "data", "users.json");
Key points
  • module.exports can be a single value, a function, or (most commonly) an object of named exports.
  • require() caches modules by resolved file path — requiring the same file twice returns the same already-executed module.
  • Reassigning exports = {...} breaks its link to module.exports and silently exports nothing — mutate exports or reassign module.exports instead.
  • CommonJS require() is synchronous, which is part of why it doesn't work directly in browsers without a bundler.
  • Circular requires can return a partially-completed export from whichever module hasn't finished executing yet.
  • __dirname and __filename give a module's absolute location on disk — use them for module-relative paths.
  • Mixing CommonJS and ESM in one project is possible but adds real complexity — pick one per project where you can.
Try it yourself

Split a script into two CommonJS files — one exporting a couple of utility functions, one requiring and using them. Then deliberately trigger the exports-vs-module.exports bug by reassigning exports directly in one file, confirm the import breaks, and fix it.
