Event loop internals and performance tuning

Node.js · part of the free zero-to-hero guide

Builds on: Basics of microservice architecture

Node's event loop is what lets a single JavaScript thread handle thousands of concurrent connections — I/O operations (file, network, database) are delegated to the operating system (or libuv's internal thread pool) and handled asynchronously, so the main thread is never blocked waiting on them and can keep processing other work in the meantime.

The event loop actually runs in distinct phases each iteration — timers (due setTimeout/setInterval callbacks), pending callbacks, poll (retrieving new I/O events and running their callbacks), check (setImmediate callbacks), and close callbacks — cycling through them repeatedly for as long as the process has pending work.

Promise callbacks (microtasks) run at a higher priority than the phases above — after every synchronous chunk of code finishes and before the event loop moves to the next phase, all pending microtasks (resolved .then() callbacks, queueMicrotask) drain completely first. This is why a resolved promise's .then() reliably runs before a setTimeout(fn, 0) scheduled around the same time, even though both look 'immediate'.

setImmediate() and setTimeout(fn, 0) look similar but aren't guaranteed to run in the same order relative to each other outside I/O callbacks — inside an I/O callback specifically, setImmediate() is guaranteed to run before any timer, which is the one case where their ordering is deterministic.

The real danger for a Node server is CPU-bound work: a long synchronous loop or expensive computation (heavy JSON parsing, image processing, complex regex, cryptographic hashing) blocks the entire event loop, stalling every other request being handled by that same process, no matter how many concurrent connections there are — there's no free parallelism within a single Node process for CPU work the way there is for I/O.

worker_threads lets you run genuinely CPU-heavy code on a separate thread, off the main event loop, communicating with the main thread via message passing — this is the standard fix once profiling (with the --prof flag or the Chrome DevTools Node inspector) confirms a specific piece of synchronous computation is the actual bottleneck, rather than guessing.

Blocking vs. non-blocking
// Blocks the event loop — every other request waits
app.get("/bad", (req, res) => {
  let total = 0;
  for (let i = 0; i < 10_000_000_000; i++) total += i;
  res.json({ total });
});
worker.js and main.js (offloading real CPU work)
// worker.js
const { parentPort, workerData } = require("worker_threads");
let total = 0;
for (let i = 0; i < workerData.limit; i++) total += i;
parentPort.postMessage(total);

// main.js — the event loop stays free while this runs
const { Worker } = require("worker_threads");

app.get("/good", (req, res) => {
  const worker = new Worker("./worker.js", { workerData: { limit: 10_000_000_000 } });
  worker.on("message", (total) => res.json({ total }));
  worker.on("error", (err) => res.status(500).json({ error: err.message }));
});
ordering.js (microtasks vs. macrotasks)
console.log("1: sync");

setTimeout(() => console.log("4: setTimeout"), 0);

Promise.resolve().then(() => console.log("3: promise microtask"));

console.log("2: sync");

// Output order: 1, 2, 3, 4
// All synchronous code runs first, then ALL pending microtasks drain,
// and only then does the event loop move on to timer callbacks.
Key points
  • Node handles I/O concurrency well by design; CPU-bound work is where it needs deliberate help (worker threads, clustering).
  • The event loop cycles through distinct phases — timers, pending callbacks, poll, check, close — each iteration.
  • Microtasks (resolved promises) always drain completely before the event loop proceeds to its next phase — they run before timers, even setTimeout(fn, 0).
  • worker_threads lets you run genuinely CPU-heavy code off the main event loop.
  • The --prof flag and Chrome DevTools' Node inspector both help profile where time is actually going, rather than guessing.
  • A single slow synchronous operation can stall every concurrent request a Node process is handling — there's no free parallelism within one process.
  • setImmediate() is only guaranteed to run before timers specifically when called from inside an I/O callback.
Try it yourself

Write a route that does expensive synchronous computation and observe (with a second concurrent request in another terminal tab) how it blocks other requests entirely while it runs. Then move that computation to a worker_threads worker and confirm the second request now responds immediately regardless of how long the computation takes.
