npm and package.json basics

Node.js · part of the free zero-to-hero guide

Builds on: Running scripts with node

npm is Node's package manager, bundled with every Node install. package.json is a project's manifest — its name, version, dependencies, and custom scripts (like npm run build) all live there, making it the single source of truth for what a project needs to run.

npm install package-name downloads a package into node_modules and records it in package.json's dependencies. node_modules should never be committed to git — it's fully regenerated from package.json and package-lock.json, and can easily balloon to hundreds of megabytes.

Version numbers in package.json use semantic versioning ranges by default: a caret (^1.2.3) allows minor and patch updates but not a new major version, while a tilde (~1.2.3) allows only patch updates. An exact version with no prefix pins that dependency completely, which is sometimes desirable for critical packages.

The scripts field defines shortcuts (npm run dev, npm test) that every contributor can rely on without memorizing raw commands or tool-specific flags. Scripts named pretest or postinstall run automatically before/after their matching script, and npx runs a package's binary without installing it globally — handy for one-off tool usage like scaffolding a new project.

package-lock.json records the exact resolved version of every dependency (including nested ones), which is what makes installs reproducible across machines. npm ci installs strictly from the lock file, deleting node_modules first and failing if the lock file is out of sync with package.json — it's what CI pipelines and deployments should use instead of plain npm install.

dependencies are needed at runtime in production; devDependencies (test runners, linters, build tools) are only needed while developing. Keeping this split accurate matters because production installs can skip devDependencies entirely, shrinking deploy size and install time.

Terminal
npm init -y                    # creates a starter package.json
npm install express             # adds a runtime dependency
npm install --save-dev vitest   # adds a dev-only dependency
npm run start                   # runs the "start" script from package.json
npx create-vite my-app          # runs a package without installing it globally
package.json
{
  "name": "my-api",
  "version": "1.0.0",
  "main": "index.js",
  "scripts": {
    "start": "node index.js",
    "dev": "node --watch index.js",
    "test": "vitest run"
  },
  "dependencies": {
    "express": "^4.19.2"
  },
  "devDependencies": {
    "vitest": "^1.6.0"
  }
}
Terminal (CI vs local)
# On a laptop, exploring / adding packages:
npm install

# In CI or a deploy pipeline — fast, reproducible, strict:
npm ci

# Skip devDependencies in a production build:
npm ci --omit=dev
Key points
  • package.json is the source of truth for a project's dependencies and metadata — always commit it.
  • package-lock.json pins exact dependency versions for reproducible installs — commit this too.
  • node_modules belongs in .gitignore, always — it's fully regenerable from the lock file.
  • Caret (^) allows minor/patch updates, tilde (~) allows only patch updates, and no prefix pins an exact version.
  • The scripts field defines shortcuts (npm run dev, npm test) every contributor can rely on.
  • dependencies ship to production; devDependencies are dev-only tools like test runners and linters.
  • npm ci is the reproducible, strict install command CI/CD pipelines should use instead of npm install.
  • npx runs a package's CLI without a permanent global install — good for scaffolding tools you use rarely.
Try it yourself

Run npm init -y in a new folder, install a small package like chalk as a runtime dependency and vitest as a dev dependency, then add a custom npm script that runs a hello-world file. Finally, delete node_modules and recreate it using npm ci to see the difference from npm install.
