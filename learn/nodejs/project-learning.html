02 Learning stage capstone

A CRUD task API backed by a real database

Node.js · ties together everything in the Learning stage

This project takes the raw building blocks from the Zero stage and turns them into something that looks like real backend work: a REST API for managing tasks (create, list, get one, update, delete), served with Express, configured through environment variables, and backed by an actual database instead of an in-memory array that vanishes every time the process restarts.

The point isn't the task-list idea itself — it's deliberately boring so the difficulty stays where the Learning-stage topics live: correct routing and middleware, safe environment configuration, and real persistence with parameterized queries. A learner who can build this cleanly has crossed from 'wrote some JavaScript' to 'built a backend service'.

You get to choose MongoDB or PostgreSQL — pick whichever matches what you're more likely to use for a real project, since the underlying skills (connection pooling, safe querying) transfer either way.

  • Building REST APIs with Express
  • Routing, middleware, and request/response handling
  • Environment variables and configuration
  • Connecting to a database (MongoDB or PostgreSQL)
  • Streams and buffers basics
Requirements
  • An Express server with five routes: GET /tasks (list all), GET /tasks/:id (get one, 404 if missing), POST /tasks (create), PUT /tasks/:id (update, 404 if missing), and DELETE /tasks/:id (delete, 404 if missing).
  • express.json() middleware is registered before any route reads req.body, and every route that sends a response uses return so no handler ever tries to send two responses.
  • Real persistence to MongoDB or PostgreSQL — restarting the server must not lose any previously created tasks.
  • All database access uses parameterized queries or the equivalent safe query-builder/ORM pattern — no string concatenation of user input into a query, anywhere.
  • The database connection string comes from an environment variable (loaded via dotenv in development), never hardcoded in the source, and the server fails to start with a clear message if that variable is missing.
  • Correct status codes throughout: 201 for creation, 200 for successful reads/updates, 204 for a successful delete, 404 for a missing task, and 400 for a request missing required fields.
  • A .env.example file committed alongside the real (gitignored) .env, documenting every variable the app needs.
Suggested approach
  1. Start with the routes against a temporary in-memory array, exactly like the Zero-stage Express work, so you can verify routing, status codes, and the missing-return bug are all handled before database complexity enters the picture.
  2. Set up the database connection next, in its own module, reading the connection string from process.env with a fallback error if it's missing — get a single manual query working from a throwaway script before wiring it into any route.
  3. Swap the in-memory array for real queries one route at a time, starting with GET /tasks and POST /tasks, testing each with a REST client (curl, Postman, or Thunder Client) before moving to the next.
  4. Add the remaining routes (GET /tasks/:id, PUT, DELETE), making sure each checks for a missing task and returns 404 rather than assuming the row/document exists.
  5. Do a final pass with the server stopped and restarted between requests, confirming data really persists, and double-check every route's status codes against the requirements list.
Stretch goals
  • Add basic filtering via query strings (e.g. GET /tasks?completed=true), reading and validating req.query.
  • Split the routes into their own express.Router() file instead of keeping everything in one server file, even though that's technically an Advanced-stage topic — it's a natural next step once the routes start feeling crowded.
  • Add an index on whatever column/field you query most often (e.g. a 'completed' status) and compare query behavior with and without it on a table seeded with a few thousand fake rows.
