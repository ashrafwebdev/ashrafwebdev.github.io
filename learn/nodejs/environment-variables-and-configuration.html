Environment variables and configuration

Node.js · part of the free zero-to-hero guide

Builds on: Routing, middleware, and request/response handling

Environment variables keep configuration (database URLs, API keys, secrets) out of your source code, so different environments (local, staging, production) can run the same code with different settings — and secrets never end up committed to git in the first place.

process.env gives access to environment variables at runtime. The dotenv package loads variables from a local .env file during development, mimicking how they'd be set directly by the hosting platform in production — it should typically only be loaded when NODE_ENV isn't "production".

process.env.NODE_ENV is a widely-used convention (not built into Node itself, but respected by Express and most frameworks/libraries) for distinguishing "development", "test", and "production" behavior — for example, disabling verbose error stack traces in responses once in production.

process.env values are always strings, even when they look like numbers or booleans — process.env.PORT is the string "3000", not the number 3000, and process.env.DEBUG === false is always false since the left side is a string. Convert explicitly (Number(process.env.PORT), process.env.DEBUG === "true") rather than assuming JavaScript will coerce it usefully.

For anything beyond a couple of variables, validating configuration at startup — checking that required variables exist and parsing them into the right types, often with a schema library like zod — turns a missing or malformed environment variable into a clear startup error instead of a confusing runtime failure deep inside the app hours later.

Never log process.env wholesale, and be careful with error-reporting tools that might capture it automatically — a stray console.log(process.env) during debugging is a surprisingly common way secrets leak into log files or error-tracking dashboards.

.env / config.js
# .env (never commit this file)
DATABASE_URL=postgres://localhost/myapp
PORT=3000

// config.js
if (process.env.NODE_ENV !== "production") {
  require("dotenv").config();
}
const port = process.env.PORT || 3000;
config.js (validated with zod)
const { z } = require("zod");

const schema = z.object({
  PORT: z.coerce.number().default(3000),
  DATABASE_URL: z.string().url(),
  NODE_ENV: z.enum(["development", "test", "production"]).default("development"),
});

// Throws a clear error at startup if anything required is missing/invalid
const env = schema.parse(process.env);
module.exports = env;
.env.example (safe to commit)
# Copy this file to .env and fill in real values locally
DATABASE_URL=
PORT=3000
JWT_SECRET=
NODE_ENV=development
Key points
  • Never commit a real .env file — add it to .gitignore and commit a .env.example template instead.
  • process.env values are always strings — convert numbers/booleans explicitly (Number(process.env.PORT)).
  • Always provide sensible fallback defaults for non-secret configuration (process.env.PORT || 3000).
  • In production, environment variables are typically set by the hosting platform directly, not read from a .env file.
  • NODE_ENV is a widely-respected convention for switching behavior between development, test, and production.
  • Validate required environment variables at startup (with a schema library) so a missing secret fails fast and clearly, not deep inside a request handler.
  • Never log process.env wholesale — it's an easy way for secrets to leak into logs or error trackers.
Try it yourself

Add a .env file with a PORT and a fake DATABASE_URL variable, load it with dotenv only outside production, and use PORT (with a fallback default) when starting your Express server. Then add zod-based validation that throws a clear startup error if DATABASE_URL is missing, and confirm that removing it from .env actually produces that error.
