01 Zero stage capstone

wordcount — a file-reading CLI tool

Node.js · ties together everything in the Zero stage

The five Zero-stage topics — running scripts with node, npm and package.json, CommonJS modules, the fs module, and basic console programs — exist to get you comfortable outside the browser: no DOM, no build step, just a script, a terminal, and the filesystem. This project asks you to build wordcount, a small command-line tool that reads a text file and reports statistics about it: total words, total lines, and the five most frequent words.

The constraint that makes this a real test is that everything has to run from the terminal with zero external dependencies — no npm packages, just Node's built-in fs and process globals. That forces you to actually understand process.argv, file reading, and basic string processing rather than leaning on a library that hides the details.

By the end you'll have a real package.json-managed project (even with no dependencies, it should still have one) and a script you can run against any text file on your machine — README, novel chapter, or your own notes — and trust the numbers it gives you.

  • Running scripts with node
  • npm and package.json basics
  • CommonJS modules (require/module.exports)
  • Reading/writing files with the fs module
  • Basic console-based programs
Requirements
  • A package.json with a name, version, and a start script that runs your CLI file with node.
  • The script accepts a file path as a command-line argument (e.g. node wordcount.js notes.txt) via process.argv, not a hardcoded filename.
  • It reads the file with the fs module (either the sync or promise-based API is fine at this stage) using an explicit "utf-8" encoding so you get a string back, not a raw Buffer.
  • It correctly reports a total line count and a total word count, where 'word' is defined by splitting on whitespace after trimming — document your definition in a comment since edge cases (double spaces, trailing newlines) are easy to get subtly wrong.
  • It reports the five most frequent words, lowercased, with their counts, sorted from most to least frequent.
  • If the given file doesn't exist, the script prints a clear error message to console.error and exits with a non-zero code via process.exit(1), instead of crashing with a raw stack trace.
  • The whole thing is organized as at least two files using CommonJS require/module.exports — one file with the counting logic, one with the CLI entry point that calls it — not a single flat script.
Suggested approach
  1. Get the skeleton working first: read process.argv[2], log it, and confirm the script runs with node wordcount.js somefile.txt before writing any counting logic.
  2. Write the file-reading step next, wrapped in a try/catch that checks for a missing file and exits cleanly — get the failure path right early, since it's easy to forget once the happy path works.
  3. Write the counting logic (lines, words, frequency) in a separate module that exports a plain function taking a string and returning an object of results — keep it independent of fs or process entirely, so it's easy to test by hand with a short string.
  4. Wire the CLI file to require that module, call it with the file contents, and print the results in a readable format.
  5. Test it against a few different real files — an empty file, a file with only one line, a file with unusual spacing — and fix whatever breaks.
Stretch goals
  • Add a --top flag (e.g. --top 10) that changes how many frequent words are shown, hand-parsed from process.argv.
  • Add the Node 18+ --watch flag to your npm run start script so it re-runs automatically if you edit the file being analyzed... and notice why that particular use of --watch doesn't quite make sense once you think about what it actually watches.
  • Filter out a small hardcoded list of common 'stop words' (the, a, and, of, to) from the frequency count and compare how different the top five looks with and without them.
