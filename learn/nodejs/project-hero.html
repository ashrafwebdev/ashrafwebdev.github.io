04 Hero stage capstone

A multi-service backend with a queue, cache, and load-tested API

Node.js · ties together everything in the Hero stage

This is the capstone of the whole Node.js track, and it should feel genuinely hard: split your task API into two independently-running services — an API service and a worker service — communicating through a real job queue, backed by a cache layer, and proven under load rather than just 'working when you tried it once'. This is the project that turns 'I've used Express' into 'I can architect a backend system'.

Concretely: the API service accepts requests and enqueues slow work (e.g. generating a per-user activity report, or sending a notification) onto a Redis-backed queue instead of doing it inline; a separate worker process, run as its own script, pulls jobs off that queue and processes them independently, retrying with backoff on failure; and a cache layer (also Redis) sits in front of your most frequently-read, rarely-changed data so repeated reads don't hit the database every time.

The bar for 'done' here is deliberately close to what a small production team would actually expect: the API responds quickly regardless of how long background work takes, a crashed worker doesn't lose in-flight jobs, the whole system survives a load test without falling over silently, and it shuts down cleanly instead of dropping in-flight requests when told to stop.

  • Event loop internals and performance tuning
  • Clustering and horizontal scaling
  • Designing scalable, resilient service architectures
  • Publishing and maintaining an npm package
  • Contributing to Node core or a major framework
Requirements
  • Two separately runnable Node processes: an API service (Express) and a worker service, sharing a job queue (BullMQ or similar, backed by Redis) — starting only the API process must not process any queued jobs.
  • At least one route that enqueues a job instead of doing the work inline, returning immediately with a status like { status: "queued", jobId } rather than blocking the request until the job finishes.
  • The worker processes jobs idempotently — verified by manually re-queuing the same job id and confirming it doesn't duplicate its side effect (e.g. doesn't send a duplicate notification or double-increment a counter).
  • Jobs use retries with exponential backoff on failure, and a job engineered to always fail ends up somewhere inspectable (a dead-letter queue or a failed-jobs list) rather than retrying forever silently.
  • A cache layer (Redis) in front of at least one frequently-read endpoint, with a defined invalidation strategy (e.g. a write to the underlying data explicitly clears or updates the relevant cache key) — a stale cache after a write is a bug you need to explicitly avoid, not something left to chance.
  • A load test (using a tool like autocannon or k6) run against the API service, with a short written summary of throughput, latency at a couple of percentiles, and what — if anything — broke or degraded under load.
  • Both services handle SIGTERM gracefully: the API stops accepting new connections and finishes in-flight requests before exiting, and the worker finishes its current job (or explicitly marks it for retry) rather than exiting mid-job.
Suggested approach
  1. Start from your Advanced-stage API and pick one genuinely slow or non-critical piece of work to move to the queue (report generation, sending an email/notification) — get the queue and a trivial worker running end to end for that one case before touching anything else.
  2. Build the worker as its own separate entry-point script from day one, not a function called from the API process, so the architectural separation is real rather than simulated.
  3. Add idempotency and retry/backoff configuration to the job next, and deliberately break it (throw inside the worker) to confirm retries and eventual dead-lettering behave the way you intended, rather than assuming they do.
  4. Add the caching layer to a separate, unrelated read-heavy route, along with the invalidation logic for whatever write can make that cached data stale — verify by writing, reading immediately after, and confirming you don't see stale data.
  5. Do the load test and graceful-shutdown work last, once the system's behavior under normal conditions is solid — load testing against a half-finished system mostly just produces noise instead of useful signal.
Stretch goals
  • Add a second worker type on a different queue with its own concurrency limit, and confirm via the load test that a flood of one job type doesn't starve the other.
  • Put the API service behind the Node cluster module (or PM2) and re-run the load test to measure the actual throughput difference against a single process.
  • Add structured JSON logging with a request id that flows from the API request through to the corresponding worker job log line, so a single job's full lifecycle is traceable across both services.
