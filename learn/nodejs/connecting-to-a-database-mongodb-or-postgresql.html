Connecting to a database (MongoDB or PostgreSQL)

Node.js · part of the free zero-to-hero guide

MongoDB (via the official driver or Mongoose) stores flexible, JSON-like documents — a natural fit for JavaScript's own data shapes, and forgiving when your data's structure evolves over time. PostgreSQL (via pg or an ORM like Prisma) is a relational database, better suited when your data has clear structure, relationships, and needs strong consistency guarantees like multi-table transactions.

In both cases, use a connection pool rather than opening a fresh connection per request — establishing a database connection is comparatively expensive (a TCP handshake, authentication, sometimes TLS negotiation), and pools reuse a small set of existing connections across many requests instead of paying that cost every time.

Always use parameterized queries — placeholders like $1 in pg or a query builder/ORM's own parameter handling — never build SQL or query filters by concatenating raw, untrusted strings. String concatenation is exactly how SQL injection vulnerabilities happen, and it remains one of the most common real-world security bugs in web applications.

A transaction groups multiple operations so they either all succeed or all roll back together — essential whenever related writes must stay consistent, like debiting one account and crediting another. Skipping transactions for multi-step writes risks leaving data in a half-updated, inconsistent state if a later step fails.

Indexes dramatically speed up queries that filter or sort on a given column, at the cost of slightly slower writes and extra storage — a query that scans every row of a large table (a 'full table scan') gets progressively slower as the table grows, while an indexed lookup stays roughly constant. Watch for N+1 query patterns too: fetching a list, then querying once per item in a loop for related data, which an ORM's include/populate features (a single joined query) usually solve much more efficiently.

ORMs (Prisma, Mongoose, Sequelize) trade some raw SQL control for productivity and built-in protection against common mistakes like injection, and they typically also handle schema migrations — versioned, repeatable scripts that evolve a database's structure over time as the application changes.

db.js (PostgreSQL with pg)
const { Pool } = require("pg");
const pool = new Pool({ connectionString: process.env.DATABASE_URL });

async function getUser(id) {
  const result = await pool.query("SELECT * FROM users WHERE id = $1", [id]);
  return result.rows[0];
}
transfer.js (a transaction with pg)
async function transferFunds(fromId, toId, amount) {
  const client = await pool.connect();
  try {
    await client.query("BEGIN");
    await client.query("UPDATE accounts SET balance = balance - $1 WHERE id = $2", [amount, fromId]);
    await client.query("UPDATE accounts SET balance = balance + $1 WHERE id = $2", [amount, toId]);
    await client.query("COMMIT");
  } catch (err) {
    await client.query("ROLLBACK"); // undo both writes if either failed
    throw err;
  } finally {
    client.release(); // always return the connection to the pool
  }
}
user.js (Mongoose model)
const mongoose = require("mongoose");

const userSchema = new mongoose.Schema({
  name: { type: String, required: true },
  email: { type: String, required: true, unique: true },
});

const User = mongoose.model("User", userSchema);

async function createUser(name, email) {
  return User.create({ name, email }); // validated against the schema
}
Key points
  • Always use parameterized queries ($1, ?) — never build SQL by concatenating raw strings, which opens the door to SQL injection.
  • A connection pool reuses database connections across requests instead of creating a new one every time.
  • Wrap related multi-step writes in a transaction (BEGIN/COMMIT/ROLLBACK) so they succeed or fail together, keeping data consistent.
  • Indexes speed up filtered/sorted queries significantly, at the cost of slightly slower writes — add them for columns you query on often.
  • Watch for N+1 query patterns (a query per loop iteration) — an ORM's join/include features usually replace them with one efficient query.
  • ORMs (Prisma, Mongoose, Sequelize) trade some raw SQL control for productivity, built-in injection protection, and migration tooling.
  • Store the connection string in an environment variable, never hardcoded in source.
  • Always release a pooled connection back to the pool (in a finally block) even when a query fails, or the pool will eventually run dry.
Try it yourself

Connect a small Express app to a PostgreSQL or MongoDB instance and build one route that reads real data from it, using parameterized queries throughout. Then add a second route that performs two related writes inside a single transaction (PostgreSQL) or with appropriate error handling (MongoDB), and confirm that a forced error during the second write leaves the data unchanged rather than half-updated.
