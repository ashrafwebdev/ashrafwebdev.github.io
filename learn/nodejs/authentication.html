Authentication: JWT and session-based auth

Node.js · part of the free zero-to-hero guide

Builds on: Streams and buffers basics

Session-based auth stores a session identifier in a cookie, with the actual session data kept server-side (in memory, Redis, or a database) — simple and easily revocable (just delete the session record), but requires shared state accessible to every server instance handling requests.

JWT (JSON Web Token) auth encodes claims (like a user ID) directly into a signed token the client stores and sends with each request — stateless, which scales easily across servers with no shared session store needed, but harder to revoke before it naturally expires, since the server doesn't track which tokens are 'still valid' anywhere by default.

Passwords must always be hashed (with bcrypt or argon2, never a plain fast hash like MD5 or SHA-256 alone) before storage — never stored in plain text, ever. Bcrypt's deliberate slowness (controlled by a 'cost factor') is a feature, not a flaw: it makes brute-forcing a leaked password database computationally expensive.

Where you store a JWT on the client matters a lot for security: localStorage is readable by any JavaScript running on the page, so it's vulnerable to theft via XSS; an httpOnly cookie can't be read by JavaScript at all, which meaningfully reduces that specific risk, though it introduces its own concerns around CSRF that need separate mitigation (like SameSite cookie attributes).

A common production pattern combines a short-lived access token (minutes) with a longer-lived refresh token (days/weeks) stored more securely — the access token authenticates most requests and expiring quickly limits the damage if it leaks, while the refresh token is used only to obtain a new access token, and can itself be revoked server-side if needed.

Session stores that live only in a single server's memory (the default for something like express-session without configuration) silently break the moment you run more than one server instance or restart the process — a user's session vanishes. Backing sessions with Redis or a database is what makes session auth compatible with horizontal scaling.

auth.js (JWT)
const jwt = require("jsonwebtoken");

// After verifying login credentials:
const token = jwt.sign({ userId: user.id }, process.env.JWT_SECRET, { expiresIn: "1h" });

// Middleware to protect a route:
function requireAuth(req, res, next) {
  const token = req.headers.authorization?.split(" ")[1];
  try {
    req.user = jwt.verify(token, process.env.JWT_SECRET);
    next();
  } catch {
    res.status(401).json({ error: "Invalid token" });
  }
}
hashPassword.js (bcrypt)
const bcrypt = require("bcrypt");

async function register(email, plainPassword) {
  const passwordHash = await bcrypt.hash(plainPassword, 12); // cost factor 12
  return saveUser({ email, passwordHash });
}

async function login(email, plainPassword) {
  const user = await findUserByEmail(email);
  if (!user) return null;
  const valid = await bcrypt.compare(plainPassword, user.passwordHash);
  return valid ? user : null;
}
sessions.js (express-session with Redis)
const session = require("express-session");
const RedisStore = require("connect-redis").default;

app.use(session({
  store: new RedisStore({ client: redisClient }), // shared across instances
  secret: process.env.SESSION_SECRET,
  cookie: { httpOnly: true, secure: true, maxAge: 24 * 60 * 60 * 1000 },
  resave: false,
  saveUninitialized: false,
}));

app.post("/login", async (req, res) => {
  const user = await login(req.body.email, req.body.password);
  if (!user) return res.status(401).json({ error: "Invalid credentials" });
  req.session.userId = user.id; // stored server-side, cookie just holds the id
  res.json({ ok: true });
});
Key points
  • Session auth is stateful (server tracks sessions) and easy to revoke; JWT is stateless and scales more easily but is harder to revoke early.
  • Always set a reasonable expiresIn on JWTs — a token that never expires is a serious liability if it leaks.
  • Store JWT secrets in environment variables, never in source code.
  • Passwords must always be hashed (with bcrypt or argon2) before storage — never stored in plain text, ever.
  • An httpOnly cookie protects a token from being read by client-side JavaScript, reducing XSS-driven theft risk.
  • Combining a short-lived access token with a longer-lived, revocable refresh token limits damage from a leaked access token.
  • An in-memory session store breaks the moment you run more than one server instance — back it with Redis or a database for horizontal scaling.
  • bcrypt.compare(), not manual string comparison, must be used to check a password against its stored hash.

Add JWT-based login to an Express app: a route that hashes and stores a password with bcrypt on registration, a login route that verifies it and issues a token, and middleware that protects another route by requiring a valid token.
