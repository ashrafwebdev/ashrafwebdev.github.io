03 Advanced stage capstone

Making the storefront's slowest report actually fast

SQL · ties together everything in the Advanced stage

This project takes the normalized shop schema further, at real scale: instead of 20 orders, you'll generate thousands of rows so that performance differences are actually measurable, not imagined. You'll add a transactional checkout operation, a window-function-powered customer ranking, a view for a report you run often, and then hunt down and fix a genuinely slow query using EXPLAIN ANALYZE.

The rule for this project is simple and non-negotiable: every claim about performance has to be backed by a measurement. 'This should be faster' doesn't count — you run EXPLAIN ANALYZE before your change, run it again after, and the numbers either back up your fix or they don't.

This is also the first project where a mistake can corrupt data rather than just return a wrong answer, which is exactly why transactions matter here: a checkout that decrements inventory but fails to record the order, or vice versa, is worse than a checkout that fails cleanly and rolls back everything.

  • Indexes and reading query execution plans
  • Transactions and isolation levels
  • Window functions
  • Views and stored procedures
  • Query optimization for slow queries
Requirements
  • An expanded version of the Learning-stage schema (or an equivalent one) populated with at least 10,000 order_items rows, generated programmatically rather than typed by hand, so query timing differences are real.
  • A checkout operation written as an explicit transaction (BEGIN ... COMMIT) that decrements product inventory and inserts the order together, plus a demonstration of what happens on ROLLBACK when a deliberately insufficient-inventory case fails partway through.
  • A window-function query using RANK() or ROW_NUMBER() that ranks customers by total spend within each signup month or cohort, without collapsing the underlying order rows the way GROUP BY would.
  • A view (or materialized view, with a justification for the choice) that answers a report you expect to run repeatedly, such as monthly revenue by category.
  • One genuinely slow query in your schema identified by running EXPLAIN ANALYZE, along with a fix — a new index, a rewritten sargable condition, or a replaced correlated subquery — and a second EXPLAIN ANALYZE run proving the fix actually helped.
  • A short before/after write-up for that optimization: the original execution plan and timing, the change you made, and the new plan and timing side by side.
Suggested approach
  1. Generate a dataset an order of magnitude larger than anything you built in the Learning stage first, since small datasets can't expose real performance problems.
  2. Build the transactional checkout logic next, and deliberately test the failure path (insufficient inventory) to confirm ROLLBACK actually leaves the database untouched.
  3. Add the window-function ranking query, since it only depends on data that already exists.
  4. Create the view or materialized view for your chosen recurring report.
  5. Profile broadly with EXPLAIN ANALYZE across your heaviest queries to find the genuinely slow one, then fix it and re-measure — don't guess which query is slow before checking.
Stretch goals
  • Add a composite index and demonstrate the leftmost-prefix rule with two queries: one that can use the index and one that can't.
  • Convert a deep OFFSET-based report to keyset pagination and time both at a high page number to see the gap widen.
  • Run the checkout transaction at the SERIALIZABLE isolation level under simulated concurrent load and capture a serialization failure and retry.
