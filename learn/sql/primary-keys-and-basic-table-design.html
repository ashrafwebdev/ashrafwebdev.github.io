Primary keys and basic table design

SQL · part of the free zero-to-hero guide

Builds on: INSERT, UPDATE, DELETE basics

A primary key uniquely identifies each row in a table, is automatically indexed for fast lookups, and enforces uniqueness and non-null constraints by definition. A single auto-incrementing integer (or an equivalent identity/serial type) or a UUID column is the most common choice for new tables.

Auto-incrementing integers are compact, sort naturally by insertion order, and index efficiently, but they leak information about row count and creation order and don't work well across multiple independent write nodes. UUIDs avoid both problems and are easy to generate outside the database, but they're larger, don't sort meaningfully, and can fragment a B-tree index more than sequential integers do — the choice is a genuine tradeoff, not a default with one obviously correct answer.

A composite primary key, made of two or more columns together, is common on join tables that model a many-to-many relationship, such as a table pairing product IDs with tag IDs where no single column is unique on its own but the pair always is.

Each column is declared with a specific data type — INTEGER, VARCHAR(n), TEXT, BOOLEAN, DATE/TIMESTAMP, NUMERIC for exact decimal values like money — and choosing types that match the actual data (a fixed-length code versus free text, an exact decimal versus a floating-point approximation, a date versus a string) keeps storage efficient and prevents invalid data from ever being stored.

Constraints like NOT NULL, UNIQUE, and CHECK enforce data integrity rules directly in the database schema, which is more reliable than relying solely on application code to validate every write, since the constraint holds no matter which script, migration, or admin tool touches the table.

A sensible default value, set with DEFAULT, reduces the number of columns every INSERT statement has to specify explicitly and guarantees a consistent starting value — a created_at timestamp defaulting to now(), or a status column defaulting to 'pending', are typical examples.

schema.sql
CREATE TABLE products (
    id SERIAL PRIMARY KEY,
    name VARCHAR(200) NOT NULL,
    price NUMERIC(10, 2) NOT NULL CHECK (price >= 0),
    sku VARCHAR(50) UNIQUE NOT NULL,
    created_at TIMESTAMP NOT NULL DEFAULT now()
);
composite_key.sql
CREATE TABLE product_tags (
    product_id INTEGER NOT NULL REFERENCES products(id),
    tag_id INTEGER NOT NULL REFERENCES tags(id),
    added_at TIMESTAMP NOT NULL DEFAULT now(),
    PRIMARY KEY (product_id, tag_id)
);
Key points
  • A primary key uniquely identifies each row and is automatically indexed.
  • Auto-incrementing integers and UUIDs are the two most common key choices, each with real tradeoffs.
  • A composite primary key spans two or more columns, common on many-to-many join tables.
  • Column types should match the actual data to keep storage efficient and reject invalid values.
  • NOT NULL, UNIQUE, and CHECK constraints enforce data integrity at the database level, not just in app code.
  • DEFAULT values reduce boilerplate in INSERT statements and guarantee a consistent starting value.
  • NUMERIC (not floating point) is the correct type for exact values like currency.
