Replication, sharding, and partitioning strategies

SQL · part of the free zero-to-hero guide

Builds on: Database architecture and schema design at scale

Replication keeps copies of a database on multiple servers, most commonly one primary that accepts writes and one or more replicas that serve read traffic, improving both read throughput and fault tolerance if the primary fails. Replication can be synchronous (the primary waits for a replica to confirm before considering a write durable, safer but slower) or asynchronous (the primary doesn't wait, faster but with a small window where a crash could lose the most recent writes).

Replication lag is the delay between a write committing on the primary and that same write becoming visible on a replica; an application that writes data and then immediately reads it back from a lagging replica can see stale or missing data, a subtle bug commonly solved by reading recently-written data from the primary itself, at least for a short window.

Sharding splits a dataset horizontally across multiple independent database instances, each holding a subset of rows (often chosen by a hash or range of a shard key like customer_id), which lets write throughput scale beyond what a single machine can handle. The shard key choice is one of the most consequential decisions in a sharded system, since queries that don't filter by the shard key have to fan out across every shard and merge results, which is far more expensive than a single-shard query.

Partitioning is similar to sharding but stays within a single database instance, splitting one logical table into smaller physical pieces (commonly by date range) that queries can prune automatically, improving performance on very large tables without the operational complexity of a fully distributed sharded system. Range partitioning by date is especially common for time-series or event data, since old partitions can be archived or dropped wholesale once they age out.

Cross-shard operations — a transaction touching rows on two different shards, or a JOIN spanning shards — are either unsupported or significantly more expensive in a sharded system than in a single database, since there's no longer one engine that can enforce atomicity or optimize the join locally; this is one of the biggest hidden costs of moving to sharding and worth weighing carefully before committing to it.

Each technique trades operational complexity for a specific kind of scalability improvement, and they're not mutually exclusive: a mature large-scale system often layers all three, sharding for write scale, partitioning within each shard for query performance on huge tables, and replication within each shard for read scale and fault tolerance.

partitioning.sql
CREATE TABLE events (
    id BIGSERIAL,
    created_at TIMESTAMP NOT NULL,
    payload JSONB
) PARTITION BY RANGE (created_at);

CREATE TABLE events_2024 PARTITION OF events
    FOR VALUES FROM ('2024-01-01') TO ('2025-01-01');

CREATE TABLE events_2025 PARTITION OF events
    FOR VALUES FROM ('2025-01-01') TO ('2026-01-01');

Key points
  • Replication improves read throughput and fault tolerance via a primary and one or more read replicas.
  • Replication can be synchronous (safer, slower) or asynchronous (faster, with a small data-loss window).
  • Replication lag can cause a just-written row to appear missing on a stale replica.
  • Sharding splits data across independent database instances, scaling write throughput.
  • Shard key choice is critical; queries that don't filter by it must fan out across every shard.
  • Partitioning splits a table within one database instance, often by date range, easing query pruning.
  • Cross-shard transactions and joins are far more expensive or unsupported compared to a single database.
  • These techniques combine in large systems rather than being mutually exclusive choices.
