Foreign keys and referential integrity

SQL · part of the free zero-to-hero guide

A foreign key is a column (or set of columns) in one table that references a primary key in another, enforced by the database so you cannot insert an order with a customer_id that doesn't actually exist in the customers table — this guarantee is called referential integrity, and it holds regardless of which application or script performs the write.

When a referenced row would be deleted, the foreign key's ON DELETE behavior decides what happens to dependent rows: CASCADE deletes them too, SET NULL nulls out the reference (only valid if the foreign key column is nullable), SET DEFAULT resets it to a configured default value, and RESTRICT or NO ACTION (the strictest, often the default) blocks the delete entirely while dependents still exist.

ON UPDATE mirrors ON DELETE but triggers when the referenced primary key's value itself changes rather than being deleted — rare in practice since primary keys are usually immutable once assigned, but relevant for schemas that use a natural key that could plausibly change.

Enforcing these rules in the database, rather than only in application code, means the constraint holds no matter which application, script, or person is writing to the database — a much stronger guarantee than trusting every caller to remember to check first, and it catches bugs immediately at write time rather than surfacing as mysterious orphaned rows discovered much later.

Foreign key columns are commonly indexed too, and this matters for more than just JOIN speed: without an index on the referencing column, deleting a row from the referenced table can force a full scan of the dependent table to check whether any row still points at it, which gets slow fast as the dependent table grows.

A self-referencing foreign key, where a table references its own primary key, is a common pattern for hierarchical data such as an employee table with a manager_id column pointing back to another row in the same table, or a category table supporting nested subcategories.

schema.sql
CREATE TABLE orders (
    id SERIAL PRIMARY KEY,
    customer_id INTEGER NOT NULL REFERENCES customers(id) ON DELETE CASCADE,
    total NUMERIC(10, 2) NOT NULL,
    created_at TIMESTAMP NOT NULL DEFAULT now()
);
set_null_and_index.sql
CREATE TABLE reviews (
    id SERIAL PRIMARY KEY,
    product_id INTEGER NOT NULL REFERENCES products(id) ON DELETE CASCADE,
    reviewer_id INTEGER REFERENCES customers(id) ON DELETE SET NULL,
    body TEXT NOT NULL
);

CREATE INDEX idx_reviews_reviewer_id ON reviews (reviewer_id);
self_referencing.sql
CREATE TABLE employees (
    id SERIAL PRIMARY KEY,
    name VARCHAR(200) NOT NULL,
    manager_id INTEGER REFERENCES employees(id) ON DELETE SET NULL
);
Key points
  • A foreign key guarantees a column's value always matches an existing row in another table.
  • ON DELETE CASCADE, SET NULL, SET DEFAULT, and RESTRICT control what happens when a referenced row is deleted.
  • ON UPDATE mirrors ON DELETE but fires when the referenced key's value itself changes.
  • Enforcing integrity in the database protects data correctness regardless of which client writes to it.
  • Foreign key columns are commonly indexed too, both for JOIN speed and for fast delete-time checks.
  • SET NULL only works when the foreign key column is itself nullable.
  • A self-referencing foreign key models hierarchical data like org charts or nested categories.
