Query optimization for slow queries

SQL · part of the free zero-to-hero guide

Diagnosing a slow query starts the same way as any performance problem: measure first with EXPLAIN ANALYZE to see the actual execution plan and timing, rather than guessing which part is slow — intuition about which clause is expensive is wrong often enough that skipping this step wastes more time than it saves.

Common fixes include adding a missing index on filtered or joined columns, rewriting a correlated subquery as a JOIN, avoiding SELECT * when only a few columns are needed, and ensuring a WHERE clause doesn't wrap an indexed column in a function (which usually prevents the index from being used at all, since the database would have to evaluate that function against every row first).

A condition that can use an index directly is called sargable (search-argument-able); wrapping a column in a function, doing implicit type conversion, or using a leading wildcard in LIKE typically makes a condition non-sargable, and rewriting it into an equivalent sargable form — a range comparison instead of a function call, for example — is one of the highest-leverage optimizations available.

For queries joining several tables, join order and join type both affect performance: the database's query planner usually picks a good order automatically based on table statistics, but stale statistics or an unusual data distribution can lead it astray, in which case refreshing statistics (ANALYZE) is often a faster fix than manually restructuring the query.

Pagination with a large OFFSET gets progressively slower as the offset grows, since the database still has to compute and discard every skipped row; keyset pagination (also called seek-based pagination), which filters using WHERE id > last_seen_id instead of an offset, avoids that cost entirely and scales to arbitrarily deep pages.

For very large tables, techniques like partitioning (splitting one logical table into smaller physical pieces) or precomputing expensive aggregates into a materialized view can help when indexing alone isn't enough, though these add real complexity and are worth reaching for only once simpler fixes are exhausted and profiling actually points at them as necessary.

query.sql
-- Slow: function on an indexed column prevents index use
SELECT * FROM orders WHERE EXTRACT(YEAR FROM created_at) = 2024;

-- Faster: a sargable range condition can use the index
SELECT * FROM orders
WHERE created_at >= '2024-01-01' AND created_at < '2025-01-01';
keyset_pagination.sql
-- Slow at deep pages: OFFSET still walks past every skipped row
SELECT id, name FROM products ORDER BY id LIMIT 20 OFFSET 100000;

-- Fast at any depth: keyset pagination using the last seen id
SELECT id, name FROM products
WHERE id > 100020
ORDER BY id
LIMIT 20;
select_star_and_indexed_join.sql
-- Wasteful: pulls every column when only two are needed
SELECT * FROM orders JOIN customers ON customers.id = orders.customer_id;

-- Better: select only what's needed, and ensure customer_id is indexed
SELECT orders.id, customers.name
FROM orders
JOIN customers ON customers.id = orders.customer_id;
Key points
  • Always measure with EXPLAIN ANALYZE before attempting to fix a slow query.
  • Wrapping an indexed column in a function usually prevents the index from being used.
  • A sargable condition can use an index directly; rewriting non-sargable conditions is high-leverage.
  • Stale statistics can mislead the query planner; ANALYZE is a cheap fix worth trying early.
  • Keyset (seek-based) pagination avoids the growing cost of a large OFFSET on deep pages.
  • Rewriting correlated subqueries as JOINs is a common, effective optimization.
  • Partitioning and materialized views help at scale, once simpler fixes are exhausted.
Try it yourself

Rewrite a query that filters WHERE LOWER(email) = 'someone@example.com' into a form that can still use an index on the email column, and explain the tradeoff you chose. Then rewrite a deep OFFSET-based pagination query as keyset pagination and explain why it stays fast at page 10,000.
