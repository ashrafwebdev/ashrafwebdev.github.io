04 Hero stage capstone

A scale-out plan for the database your app outgrew

SQL · ties together everything in the Hero stage

This is the capstone of the whole SQL track, and it's deliberately half implementation and half written design decision — because at this scale, the hardest part of database work isn't writing a query, it's justifying a tradeoff. You'll take a large, high-write table (built on the storefront schema from earlier stages, or a fresh events-style table) that has genuinely outgrown a single instance, and produce both real, runnable partitioning SQL and a written architecture document defending your replication and sharding choices.

The bar here isn't 'it works on my laptop' — it's 'a staff engineer reading this document would understand exactly why you chose this shard key, this replica strategy, and this migration plan, and could poke at your reasoning.' Every decision has to be tied to an assumed scale you state up front, since a design with no stated numbers can't actually be evaluated.

This project pulls together every Hero-stage topic at once: schema design at scale, replication and sharding and partitioning, deep performance tuning, and the kind of engine-choice reasoning that comes up whenever a system has grown past its original assumptions.

  • Database architecture and schema design at scale
  • Replication, sharding, and partitioning strategies
  • Deep performance tuning under real production load
  • Choosing and migrating between database engines
Requirements
  • A written architecture document, at least several paragraphs long, that states an assumed scale up front (rows written per day, read-to-write ratio, expected growth) and uses those numbers to justify every choice that follows — no undefended 'this should scale better' claims.
  • Actual, runnable DDL implementing date-range partitioning on a large table (events, orders, or equivalent), with at least three partitions created, plus an EXPLAIN output demonstrating that a date-filtered query actually prunes to a single partition instead of scanning all of them.
  • A shard key decision for one clearly identified high-write table: which column you'd shard on, why, and a specific example of a query type that would become an expensive cross-shard fan-out as a direct result of that choice.
  • A read replica strategy naming which query types route to a replica versus the primary, and a concrete solution to the 'read your own write' problem for one specific user flow, such as a checkout confirmation page loading immediately after the order was placed.
  • A staged, backward-compatible migration plan (numbered steps, each independently safe to deploy) for a schema change specific to your new architecture — for example, adding a shard_id or region column to a large, actively-written table without downtime.
  • A monitoring section listing specific queries you'd run in production — against something like pg_stat_activity, pg_stat_user_tables, or your engine's equivalent — to catch replication lag, lock contention, or table bloat before they become an outage.
Suggested approach
  1. Start by writing down a concrete, invented-but-realistic scale scenario with real numbers before touching any SQL — every later decision needs something to be justified against.
  2. Implement the date-range partitioning first, since it's the one piece you can fully build and measure locally, and getting the pruning behavior to actually show up in EXPLAIN output will sharpen your intuition for the rest of the document.
  3. Work through the shard key decision next, actively looking for the query pattern that becomes painful under your chosen key — a shard key with no downside usually means you haven't looked hard enough.
  4. Write the replica strategy and the read-your-own-write solution together, since they're really the same problem viewed from two angles.
  5. Write the migration plan and monitoring section last, once the target architecture is settled, so both are grounded in the specific shape of the system you just designed rather than generic advice.
Stretch goals
  • Actually stand up two local database instances to simulate two shards, split your sample data across them by your chosen shard key, and write the application-level merge query a true cross-shard report would require.
  • Artificially simulate replication lag (a delayed batch job copying rows from primary to replica) and write the fallback logic a real application would need to solve read-your-own-write correctly.
  • Write a one-page engine comparison — your chosen engine versus one genuine alternative (a different relational engine, or a non-relational one) — naming the specific workload characteristics that would make you switch.
