02 Learning stage capstone

A normalized schema for a tiny online shop, and the reports it powers

SQL · ties together everything in the Learning stage

This project moves you from one table to a small, connected schema: customers, products, orders, and order_items, tied together with foreign keys and designed deliberately to reach third normal form. It's the first project where getting the schema wrong makes every later query harder, so the design step matters as much as the queries themselves.

Once the schema exists and is populated with realistic data, the second half of the project is writing the reports a small shop would actually want: which customers haven't ordered anything, which categories bring in the most revenue, which products have never sold. Those reports are exactly where JOIN, GROUP BY, and subqueries stop being separate lessons and start being one connected skill.

The deliberate constraint here is normalization: no column should store a fact that really belongs to a different table, and no comma-separated list should be hiding inside a single text column. If you find yourself duplicating a product's name and price onto every order line instead of joining back to products, that's the schema telling you something is still in first normal form when it should be in third.

  • JOINs: inner, left, right
  • GROUP BY and aggregate functions
  • Subqueries
  • Foreign keys and referential integrity
  • Basic normalization (1NF–3NF)
Requirements
  • At least four tables — customers, products, orders, and order_items — each with an appropriate primary key, and foreign keys connecting orders to customers and order_items to both orders and products, with a deliberately chosen ON DELETE behavior on each.
  • The order_items table stores only order_id, product_id, and quantity (plus its own key) — no product name or price duplicated there, since those belong to products and would violate normalization if copied.
  • At least 5 customers, 10 products, and 20 orders, populated so that at least one customer has zero orders and at least one product has never been ordered — the edge cases your JOIN queries need to actually exercise.
  • A LEFT JOIN query listing every customer alongside their total order count, including the customers with zero orders, without accidentally turning it back into an inner join.
  • A GROUP BY report showing total revenue per product category, using HAVING to keep only categories above a revenue threshold you choose.
  • At least one subquery (using IN, EXISTS, or a derived table in FROM) that answers a question a single-table query couldn't, such as which customers have never ordered from a specific category.
  • A one-paragraph write-up identifying which normal form (1NF, 2NF, or 3NF) each table satisfies and why, referencing at least one anomaly your design specifically avoids.
Suggested approach
  1. Sketch the entity-relationship model on paper before writing any SQL: which tables exist, which columns are foreign keys, and which table 'owns' each fact.
  2. Create the tables in dependency order — customers and products first, then orders, then order_items — so each foreign key has something to reference.
  3. Insert realistic sample data deliberately including the zero-order customer and the never-ordered product, so your JOIN queries have real edge cases to handle rather than a suspiciously clean dataset.
  4. Write and test the JOIN and GROUP BY reports first, since they follow mechanically once the foreign keys are in place.
  5. Write the subquery-based reports last, and sanity-check each result by reasoning out the expected answer from your own small dataset before trusting the query's output.
Stretch goals
  • Rewrite one IN-based subquery as an equivalent EXISTS query and compare how each reads.
  • Add a product_tags table with a composite primary key modeling a many-to-many relationship, and write a query returning all products with a given tag.
  • Add a discount_codes table referenced from orders, and write a report comparing revenue with and without discounts applied.
