Database architecture and schema design at scale

SQL · part of the free zero-to-hero guide

At scale, schema design decisions ripple outward: choosing surrogate keys (auto-generated IDs) versus natural keys (like an email address), deciding which relationships to fully normalize versus deliberately denormalize for read performance, and planning for schema migrations that can run safely against a live, high-traffic table without long locks.

Surrogate keys are generally preferred at scale because natural keys can change (a customer changes their email), can be composite and awkward to reference from other tables, and sometimes contain sensitive data that shouldn't be duplicated into every foreign key relationship; the tradeoff is one extra join or lookup to translate a surrogate ID back into something human-meaningful when needed.

Large systems often split a single conceptual database into bounded contexts that each own their own schema or database entirely, aligned with service boundaries in a microservice architecture, rather than one shared database everything reads and writes to directly — this avoids one service's schema change breaking another service unexpectedly, at the cost of needing some other mechanism (an API call, an event, a periodic sync) to share data across contexts.

Schema migrations at scale favor small, backward-compatible steps — add a nullable column, deploy code that writes to it, backfill existing rows, then make it required in a later migration — over one large blocking change, so the application can keep running throughout the rollout without downtime and so each step can be verified and rolled back independently if something goes wrong.

Adding a column is usually cheap, but altering an existing column's type, adding a NOT NULL constraint to an existing column, or adding certain kinds of indexes can lock a table for the duration of the operation on some engines — understanding which specific DDL operations your engine can perform online (without blocking reads and writes) versus which ones require a maintenance window is a core skill for schema work on a live production system.

Read replicas, connection pooling, and caching layers all sit adjacent to schema design proper, but the schema itself still shapes how well those layers can help: a schema with clear, stable access patterns and appropriately indexed foreign keys is far easier to scale horizontally than one that requires ad-hoc, unpredictable queries across many tables.

migration.sql
-- Step 1: add nullable column, deploy code that writes to it
ALTER TABLE orders ADD COLUMN currency VARCHAR(3);

-- Step 2 (later migration, after backfilling existing rows):
ALTER TABLE orders ALTER COLUMN currency SET NOT NULL;
backfill.sql
-- Backfill in batches to avoid one huge blocking transaction
UPDATE orders SET currency = 'USD'
WHERE currency IS NULL
  AND id IN (SELECT id FROM orders WHERE currency IS NULL LIMIT 1000);
-- repeat until zero rows are affected, then apply the NOT NULL constraint
Key points
  • Surrogate versus natural keys is a real design tradeoff worth deciding deliberately, not by default.
  • Bounded contexts let services own their own schema instead of sharing one large database.
  • Backward-compatible, staged migrations avoid downtime on high-traffic tables.
  • Not all DDL operations are equally safe online; some lock a table for their full duration.
  • Backfilling in small batches avoids one huge blocking transaction on a live table.
  • Denormalization for read performance should follow measurement, not precede it.
  • A well-indexed, predictable schema makes read replicas and caching layers far more effective.
