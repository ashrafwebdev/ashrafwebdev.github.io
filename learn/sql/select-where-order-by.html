01 Zero stage

SELECT, WHERE, ORDER BY

SQL · part of the free zero-to-hero guide

SQL's most basic statement is SELECT, which retrieves rows from a table. SELECT name, price FROM products; returns just those two columns for every row; SELECT * FROM products; returns every column, handy for exploration but best avoided in application code since it silently breaks if columns are later added, removed, or reordered, and it pulls more data over the wire than the caller actually needs.

The WHERE clause filters which rows come back, evaluated per row before any results are returned. Comparisons use the operators you'd expect — equals, not-equals, greater-than, less-than, greater-or-equal, less-or-equal — and SQL is declarative: you describe the result you want, not the steps to get it, leaving the database engine free to decide how to actually fetch the data.

NULL deserves special attention early, because it does not behave like an ordinary value. A column with no value is NULL, and comparing anything to NULL with an ordinary equals sign never returns true, not even NULL = NULL. To test for a missing value you must use IS NULL or IS NOT NULL instead of the equality operator, and this trips up nearly every beginner at least once.

ORDER BY sorts the result set, ascending by default (ASC) or descending with DESC, and can sort by multiple columns in sequence, such as by category first and then by price within each category. Where NULLs land in a sort is engine-specific by default — PostgreSQL sorts them last in an ascending sort, for instance — so an explicit NULLS FIRST or NULLS LAST is worth adding whenever the sort order actually matters.

LIMIT (or TOP/FETCH FIRST depending on the engine) caps how many rows come back, and combined with OFFSET it becomes the basis of simple pagination: skip the first N rows, then take the next page's worth. It's worth knowing this style of pagination degrades on very large offsets, since the database still has to walk past every skipped row.

Column aliases, written with AS, rename a column or computed expression in the output without touching the underlying table — useful for giving a calculated value like price * quantity AS subtotal a readable name that downstream code or a report can reference directly.

query.sql
SELECT name, price
FROM products
WHERE price > 20
ORDER BY price DESC;
pagination.sql
-- Second page of 10 results, cheapest first, missing prices sorted last
SELECT name, price AS current_price
FROM products
WHERE category = 'electronics'
ORDER BY price ASC NULLS LAST
LIMIT 10 OFFSET 10;
null_mistake.sql
-- Wrong: this never matches rows where discount really is NULL
SELECT * FROM products WHERE discount = NULL;

-- Correct
SELECT * FROM products WHERE discount IS NULL;
Key points
  • SELECT chooses which columns to return; avoid SELECT * in application code.
  • WHERE filters rows before they're returned, evaluated independently per row.
  • ORDER BY sorts results; ASC is the default, DESC reverses it, and multiple columns break ties in sequence.
  • NULL is never equal to anything, even itself; use IS NULL / IS NOT NULL, not =.
  • LIMIT and OFFSET implement basic pagination, though large offsets scale poorly on big tables.
  • AS gives a column or computed expression a readable alias in the output.
  • SQL is declarative: you describe the desired result, not the retrieval steps.
Try it yourself

Write a query against a products table that selects name and price for products over $15, sorted by price ascending. Then extend it to alias price as current_price, skip the first 5 matching rows, and return only the next 5 using LIMIT and OFFSET.
