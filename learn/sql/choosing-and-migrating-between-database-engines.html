Choosing and migrating between database engines

SQL · part of the free zero-to-hero guide

Builds on: Deep performance tuning under real production load

Choosing a database engine depends on the workload: PostgreSQL's rich feature set and strong consistency suit most general-purpose applications; MySQL remains extremely common for web applications and has a huge ecosystem of hosting and tooling; specialized engines (Cassandra for massive write throughput across many nodes, MongoDB for flexible document schemas, ClickHouse for analytical queries over huge datasets) fit narrower, specific needs better than a general-purpose relational database.

Beyond raw features, practical factors often decide the choice in the real world: team familiarity with an engine, managed hosting availability and cost on your cloud provider, the maturity of client libraries in your application's language, and how well an engine's operational tooling (backups, monitoring, replication setup) fits your team's existing practices.

A migration between engines is rarely a simple data dump-and-restore: differing SQL dialects (window function syntax, date arithmetic, string functions, auto-increment mechanics all vary), data type mappings (a numeric type in one engine may not map exactly to the equivalent type in another), and feature availability (stored procedures, specific index types, native JSON support) all need careful auditing before and during the move.

Application code itself often has implicit assumptions baked in about the source engine's specific behavior — how NULLs sort by default, what happens on a unique constraint violation, case sensitivity defaults for string comparisons — and these differences can cause correctness bugs that only surface after the migration, well past the point where they're easy to trace back to the engine change.

A common, lower-risk migration strategy runs both databases side by side temporarily — writing to both, reading from the old one, then gradually cutting reads over and verifying consistency — rather than a single risky cutover that can't easily be reversed if something goes wrong. This dual-write period also gives real production traffic time to surface subtle behavioral differences before the old system is decommissioned.

Always verify data consistency between old and new systems (row counts, checksums, or targeted spot-checks on business-critical tables) before decommissioning the old one, and keep the old system available in a read-only or backup capacity for some agreed period afterward, since some discrepancies only surface once every code path has actually exercised the new system under real load.

migration-plan.txt
1. Stand up the new database engine alongside the old one.
2. Audit SQL dialect differences: date functions, window functions, auto-increment syntax.
3. Dual-write: application writes to both databases.
4. Backfill historical data from old -> new.
5. Verify: compare row counts and checksums between the two.
6. Cut reads over gradually, monitoring for discrepancies.
7. Keep the old database available read-only for an agreed window.
8. Decommission the old database once fully confident.
dialect_differences.sql
-- PostgreSQL: auto-incrementing primary key
id SERIAL PRIMARY KEY

-- MySQL equivalent
id INT AUTO_INCREMENT PRIMARY KEY

-- PostgreSQL date arithmetic
created_at + INTERVAL '30 days'

-- MySQL equivalent
DATE_ADD(created_at, INTERVAL 30 DAY)
Key points
  • Engine choice should follow the actual workload: general-purpose, high write throughput, flexible schema, or analytics.
  • Practical factors like team familiarity, managed hosting, and tooling often decide as much as raw features.
  • SQL dialect differences and feature gaps make engine migrations more than a simple data dump-and-restore.
  • Application code often has implicit assumptions about the source engine's specific behavior that surface as bugs later.
  • Dual-write migrations with a gradual read cutover reduce the risk of a single irreversible cutover.
  • Always verify data consistency between old and new systems before decommissioning the old one.
  • Keep the old system available read-only for a window after cutover in case of late-surfacing discrepancies.
