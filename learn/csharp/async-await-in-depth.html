async/await in depth

C# · part of the free zero-to-hero guide

Builds on: Intro to ASP.NET Core

C#'s async/await lets you write asynchronous code that reads like synchronous code. A method marked async and returning Task or Task of T can use await to pause at an asynchronous operation without blocking the calling thread while it waits, which is essential for scalability — a web server can handle thousands of concurrent requests waiting on I/O using a small pool of threads instead of one thread per request.

Under the hood, awaiting a Task generates a state machine: the method returns control to its caller immediately, and the rest of the method resumes automatically once the awaited operation completes, typically on a thread-pool thread. This transformation is entirely compiler-generated — the readable, sequential-looking code you write is rewritten into callback-based continuations behind the scenes.

A common pitfall is blocking on async code with .Result or .Wait(), which can deadlock in UI or older ASP.NET (non-Core) contexts that have a synchronization context: the blocked thread is the very thread the continuation needs to resume on, so neither can proceed. The fix is to await consistently all the way up the call stack, often summarized as "async all the way", rather than mixing synchronous and asynchronous styles.

Task.WhenAll runs several tasks concurrently and completes when they all finish, which is dramatically faster than awaiting each one sequentially when the operations are independent; Task.WhenAny instead completes as soon as the first of several tasks finishes, useful for timeout patterns or racing multiple sources for the fastest response.

ConfigureAwait(false), seen often in library code, tells the runtime not to try to resume the continuation on the original synchronization context, avoiding unnecessary context-switching overhead and certain deadlock scenarios; it's generally unnecessary (and the default is fine) in modern ASP.NET Core, which has no synchronization context to begin with, but still matters in UI apps and reusable library code that might be called from either.

Exceptions thrown inside an async method are captured on the returned Task rather than thrown immediately, and only surface when the task is awaited (or its .Result/.Wait() is accessed, wrapped in an AggregateException in that case); an async method that's never awaited, sometimes called "fire and forget", silently swallows any exception it throws, which is a common source of bugs that are hard to trace.

Program.cs
static async Task<string> FetchDataAsync()
{
    await Task.Delay(500); // simulates network latency
    return "data loaded";
}

static async Task Main()
{
    Console.WriteLine("Fetching...");
    string result = await FetchDataAsync();
    Console.WriteLine(result);
}
ConcurrentTasks.cs
static async Task<string> FetchAsync(string name, int delayMs)
{
    await Task.Delay(delayMs);
    return $"{name} done after {delayMs}ms";
}

static async Task Main()
{
    var sw = System.Diagnostics.Stopwatch.StartNew();

    var taskA = FetchAsync("A", 300);
    var taskB = FetchAsync("B", 500);

    // Runs A and B concurrently -- total time is ~500ms, not 800ms
    string[] results = await Task.WhenAll(taskA, taskB);

    foreach (var r in results) Console.WriteLine(r);
    Console.WriteLine($"Elapsed: {sw.ElapsedMilliseconds}ms");
}
DeadlockAndFireForget.cs
// WRONG in a UI/classic-ASP.NET context: can deadlock
// string data = FetchDataAsync().Result;

// RIGHT: await all the way up
// string data = await FetchDataAsync();

// Fire-and-forget: exceptions here are silently lost!
static async Task RiskyAsync() => throw new InvalidOperationException("oops");

static void FireAndForget()
{
    _ = RiskyAsync(); // never awaited -- exception vanishes
}

static async Task Safe()
{
    await RiskyAsync(); // exception properly propagates and can be caught
}
Key points
  • async methods return Task or Task of T, letting callers await them.
  • await frees the calling thread instead of blocking it while the operation completes.
  • Avoid blocking on async code with .Result/.Wait(); it can deadlock in contexts with a synchronization context.
  • "Async all the way" — once a call is async, keep awaiting it up through every caller.
  • Task.WhenAll runs independent tasks concurrently instead of one after another; Task.WhenAny reacts to the first to finish.
  • ConfigureAwait(false) avoids unnecessary context-switching in library code, though it's largely moot in ASP.NET Core.
  • Exceptions in an async method live on the returned Task; an un-awaited "fire and forget" call can silently swallow them.
Try it yourself

Write two async methods that each simulate a delay with Task.Delay, run them concurrently with Task.WhenAll, and print how long the combined operation took using a Stopwatch. Then write a third async method that throws an exception, call it without awaiting it to observe the exception disappear, and then call it again properly awaited inside a try/catch to show the exception being caught correctly.
