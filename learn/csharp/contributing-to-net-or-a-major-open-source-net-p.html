Contributing to .NET or a major open-source .NET project

C# · part of the free zero-to-hero guide

Builds on: Cross-platform development with .NET MAUI

The .NET runtime, ASP.NET Core, and many popular libraries are fully open source on GitHub, and Microsoft actively documents contribution guidelines for the runtime itself, making it one of the more approachable major language ecosystems to contribute to; the dotnet/runtime, dotnet/aspnetcore, and dotnet/roslyn (the C# compiler itself) repositories are all publicly developed with the same pull request workflow anyone can use.

As with any large project, start by reading CONTRIBUTING.md, the coding style guidelines (often an .editorconfig file enforced automatically by the build), and "good first issue" or "help wanted" labeled tickets, which maintainers curate specifically to be approachable for newcomers without requiring deep familiarity with the whole codebase.

Before writing any code, it's worth searching existing issues and pull requests for the problem you're about to solve — large projects often already have a discussion, a rejected prior attempt with useful context on why it didn't work, or an in-progress fix, and duplicating that effort wastes both your time and a reviewer's.

A strong first pull request is small, includes tests, and clearly explains the problem it solves and how the fix addresses it; running the project's full test suite locally before submitting avoids the most common source of review friction, since CI failures on a first-time contribution often get far less patient attention than a green build with a clear description.

Code review on large .NET projects is typically thorough and can involve several rounds of feedback even for a small change — this is normal, not a sign the contribution is unwelcome, and responding promptly and respectfully to review comments (rather than getting defensive) is what turns a first contribution into an ongoing relationship with the project.

Beyond code, open-source .NET projects also need help with documentation, triaging issues (reproducing a reported bug, asking clarifying questions, labeling), and reviewing other people's pull requests — often a lower-friction way to build context and trust with a project's maintainers before attempting a larger code change yourself.

workflow
$ git clone https://github.com/you/runtime-fork.git
$ cd runtime-fork
$ git checkout -b fix-string-format-edge-case

# make the change, then run the relevant test project
$ dotnet test src/libraries/System.Runtime/tests

$ git commit -m "Fix edge case in string formatting for negative zero"
$ git push origin fix-string-format-edge-case
# open a pull request against the upstream repository
pr-checklist.md
## Before opening the PR
- [ ] Searched existing issues/PRs for duplicates or prior context
- [ ] Read CONTRIBUTING.md and matched the project's coding style
- [ ] Added or updated tests covering the change
- [ ] Ran the full relevant local test suite -- not just the new test
- [ ] Wrote a PR description explaining the problem AND the fix
- [ ] Linked the PR to the issue it resolves, if one exists

## After opening the PR
- [ ] Responded to review feedback within a reasonable time
- [ ] Rebased/updated the branch if CI flags a merge conflict
upstream-sync.sh
# Keeping a fork in sync before starting new work
$ git remote add upstream https://github.com/dotnet/runtime.git
$ git fetch upstream
$ git checkout main
$ git merge upstream/main
$ git push origin main

# Now branch from an up-to-date main for the next contribution
$ git checkout -b my-next-fix
Key points
  • Most core .NET projects are open source with documented contribution guidelines.
  • "Good first issue" labels are curated entry points for new contributors.
  • Search existing issues and PRs before starting work to avoid duplicating effort.
  • Small, well-tested pull requests with a clear problem statement are easiest to review.
  • Run the relevant local test suite before submitting to avoid obvious review friction.
  • Multiple rounds of code review are normal on large projects, not a rejection signal.
  • Triage, documentation, and reviewing others' PRs are lower-friction ways to build trust with maintainers.
Try it yourself

Find a .NET open-source repository on GitHub, locate its CONTRIBUTING.md, and list three specific expectations it sets for contributors. Then find one issue labeled "good first issue" or "help wanted" in that repository, summarize what it's asking for in your own words, and outline the steps you would take (branch, test, PR description) before opening a pull request for it.
