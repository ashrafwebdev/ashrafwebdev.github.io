Entity Framework Core

C# · part of the free zero-to-hero guide

Builds on: ASP.NET Core Web APIs

Entity Framework Core (EF Core) is Microsoft's object-relational mapper: you define C# classes representing your data, and EF Core translates LINQ queries against a DbContext into SQL, mapping rows back into objects automatically, so most day-to-day database access never requires writing raw SQL by hand.

A DbContext subclass exposes DbSet of T properties, one per table, and EF Core tracks changes to loaded entities (this is called the change tracker) so calling SaveChanges() generates the appropriate INSERT, UPDATE, or DELETE statements for everything that changed since the entities were loaded, without you writing any SQL yourself.

Loading related data requires deliberate choices: by default EF Core does not load navigation properties (a customer's orders, say) unless you ask via .Include(c => c.Orders) (eager loading), access them lazily with a proxy (lazy loading, which must be explicitly enabled and can cause subtle N+1 query performance problems if overused), or query them separately. The N+1 problem — issuing one query per row of an outer result instead of one combined query — is one of the most common EF Core performance mistakes in real applications.

Queries that will only be read, never modified, should use .AsNoTracking(), which skips the overhead of change tracking and can meaningfully improve performance for read-heavy endpoints like API GET actions where nothing is ever saved back.

Migrations let you evolve your database schema alongside your C# model classes in version control: dotnet ef migrations add generates a migration file (both an Up and Down method) describing the schema change based on differences EF Core detects between your model and the last migration, and dotnet ef database update applies pending migrations to the actual database.

A DbContext is intentionally lightweight and not thread-safe, and is meant to be short-lived — typically one instance per web request in ASP.NET Core, registered with a Scoped lifetime, rather than a single long-lived shared instance, which would cause both threading bugs and an ever-growing change-tracker memory footprint.

AppDbContext.cs
public class Product
{
    public int Id { get; set; }
    public string Name { get; set; } = "";
    public decimal Price { get; set; }
}

public class AppDbContext : DbContext
{
    public DbSet<Product> Products => Set<Product>();
    protected override void OnConfiguring(DbContextOptionsBuilder options)
        => options.UseSqlite("Data Source=app.db");
}

using var db = new AppDbContext();
var cheap = db.Products.Where(p => p.Price < 20).ToList();
RelatedDataAndNoTracking.cs
public class Customer
{
    public int Id { get; set; }
    public string Name { get; set; } = "";
    public List<Order> Orders { get; set; } = new();
}

public class Order
{
    public int Id { get; set; }
    public decimal Total { get; set; }
    public int CustomerId { get; set; }
}

// Eager loading avoids the N+1 problem: one query, not one-per-customer
var withOrders = db.Customers
    .Include(c => c.Orders)
    .ToList();

// Read-only query: skip change tracking overhead entirely
var readOnly = db.Products
    .AsNoTracking()
    .Where(p => p.Price > 50)
    .ToList();

Key points
  • A DbContext subclass with DbSet of T properties models your database tables.
  • EF Core translates LINQ queries against a DbContext into SQL automatically.
  • SaveChanges() commits tracked insertions, updates, and deletions in one call, using the change tracker.
  • Related data isn't loaded automatically — use .Include(...) for eager loading and watch out for N+1 query problems.
  • .AsNoTracking() skips change-tracking overhead for read-only queries.
  • Migrations version-control schema changes alongside your C# model classes.
  • A DbContext should be short-lived and registered with a Scoped lifetime, typically one per web request.
Try it yourself

Define a DbContext with a Customer entity (Id, Name, Email), and write a LINQ query against it that returns customers whose email ends in a specific domain. Then add an Order entity with a foreign key to Customer, write a query using .Include to eagerly load each customer's orders, and write a second read-only version of the query using .AsNoTracking().
