04 Hero stage capstone

A production-grade order-processing API with CI/CD and live monitoring

C# · ties together everything in the Hero stage

This is the roadmap's own capstone framing made literal: architect a production-grade .NET API with CI/CD and monitoring. The project is an order-processing API for a small e-commerce-style domain (customers, products, orders) built with Clean Architecture layering, deployed automatically on every push, and observable in production — not just "working on my machine", but demonstrably running, tested, and watched the way a real backend service would be.

The project deliberately combines everything from earlier stages under real constraints: the domain layer must have zero dependency on EF Core or ASP.NET Core, async and LINQ are used throughout the application and infrastructure layers, generics show up in at least one genuinely reusable abstraction (a generic repository or result type), and the whole thing is proven correct by an automated test suite that a CI pipeline runs on every commit, not by hand-testing before a demo.

What separates this from the Advanced-stage API is scope and rigor, not new unfamiliar tools: it needs a real architectural boundary between business rules and infrastructure, it needs to survive being deployed and left running (which is what monitoring is for), and it needs a pipeline that would catch a regression before it ever reaches production, since that's the difference between a project that merely works and one a hiring manager would call portfolio-worthy.

  • Performance and memory tuning
  • Designing large-scale .NET architectures
  • Cross-platform development with .NET MAUI
  • Contributing to .NET or a major open-source .NET project
Requirements
  • A solution split into at least Domain, Application, Infrastructure, and Api projects, where Domain has no project reference to EF Core, ASP.NET Core, or any other framework package.
  • At least one generic abstraction used for real (e.g. a generic repository interface constrained with where T : class, or a generic Result of T type used consistently for success/failure across the application layer).
  • EF Core migrations checked into source control, with the API able to apply pending migrations automatically on startup in a development environment.
  • A CI pipeline (GitHub Actions or equivalent) that runs on every push: restores, builds, runs the full xUnit suite, and fails the build on any test failure — configured as an actual workflow file in the repository, not described in prose.
  • A CD step that deploys the API automatically on a successful build to some real, reachable environment (a cloud VM, a container platform, or a PaaS free tier all count).
  • Structured logging (not Console.WriteLine) plus at least one health-check endpoint and one basic metric or dashboard (request count, error rate, or response time) visible for the running deployed instance.
  • At least 70% of the Application and Domain layers covered by automated tests, verified by a coverage tool and enforced (or at least reported) in the CI pipeline.
Suggested approach
  1. Design the Domain and Application layers first, entirely without a database or a web framework in the picture — write the entities, the interfaces the application layer needs (like IOrderRepository), and unit tests against fakes before any infrastructure code exists.
  2. Build the Infrastructure layer's EF Core implementation next, wiring it to the interfaces already defined inward, and confirm migrations apply cleanly to a real database instance.
  3. Build the thin Api layer last of the application code, keeping controllers minimal and pushing all real logic down into Application-layer handlers you already tested in isolation.
  4. Get the CI pipeline running early, even before the app is feature-complete — a pipeline that only ever runs against a growing, real feature set is far more trustworthy than one bolted on at the end.
  5. Add CD, logging, health checks, and monitoring only once the core API is stable and its tests are green, since instrumenting a moving target wastes effort re-doing the same wiring repeatedly.
Stretch goals
  • Add the outbox pattern for a domain event (like "OrderPlaced") so an event is only published after the database transaction that created the order actually commits.
  • Add a load test (using a tool like k6 or NBomber) against the deployed instance and use the results to justify one concrete performance change, backed by dotnet-counters or dotnet-trace output.
  • Extend CI with a required code-review gate and branch protection rules, and document the full deployment runbook (rollback steps included) as if handing the project to another engineer.
