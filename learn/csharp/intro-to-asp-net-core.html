Intro to ASP.NET Core

C# · part of the free zero-to-hero guide

Builds on: Working with files

ASP.NET Core is Microsoft's cross-platform framework for building web apps and APIs in C#. A minimal API can be just a few lines: WebApplication.CreateBuilder configures the app (reading configuration, setting up dependency injection), and app.MapGet/MapPost wire URL routes directly to handler functions without any controller class needed.

ASP.NET Core is built around a request pipeline of middleware — small components that each handle one concern (logging, authentication, static files, routing, error handling) and pass the request to the next one in sequence, configured explicitly in your startup code with calls like app.UseAuthentication() or app.UseStaticFiles(). Order matters: middleware registered earlier runs first on the way in and last on the way out, so authentication middleware, for example, needs to run before any middleware that assumes the user is identified.

Dependency injection is baked into the framework from the start: services are registered with the builder (builder.Services.AddScoped<IMyService, MyService>()) with a lifetime — Singleton (one instance for the app's whole lifetime), Scoped (one instance per HTTP request), or Transient (a new instance every time it's requested) — and are then automatically supplied wherever a constructor or minimal API handler asks for that type as a parameter.

Route parameters like {name} bind automatically to matching handler parameters by name and type, and more complex data (a JSON body on a POST) can be bound the same way by declaring a parameter of the model's type; the framework infers from context whether to read it from the route, the query string, or the body.

Configuration flows from multiple sources layered in a defined precedence order — appsettings.json, an environment-specific appsettings.{Environment}.json, environment variables, and command-line arguments — with later sources overriding earlier ones, which is how the same published app behaves differently across development, staging, and production without a rebuild.

Larger applications typically use the MVC or Controller pattern instead of minimal APIs, grouping related endpoints into a controller class annotated with routing attributes, but both approaches sit on the same underlying ASP.NET Core pipeline and can even be mixed within a single application.

Program.cs
var builder = WebApplication.CreateBuilder(args);
var app = builder.Build();

app.MapGet("/", () => "Hello, ASP.NET Core!");
app.MapGet("/greet/{name}", (string name) => $"Hello, {name}!");

app.Run();
ProgramWithDI.cs
var builder = WebApplication.CreateBuilder(args);

// Register a service with a Scoped lifetime (one instance per request)
builder.Services.AddScoped<IGreeter, FriendlyGreeter>();

var app = builder.Build();

// The handler simply asks for IGreeter and DI supplies it
app.MapGet("/greet/{name}", (string name, IGreeter greeter) =>
    greeter.Greet(name));

app.Run();

interface IGreeter { string Greet(string name); }
class FriendlyGreeter : IGreeter
{
    public string Greet(string name) => $"Hey there, {name}!";
}
MiddlewareOrder.cs
var app = builder.Build();

// Order matters: each middleware runs before the ones after it
app.Use(async (context, next) =>
{
    Console.WriteLine($"Request: {context.Request.Path}");
    await next(); // pass control to the next middleware
    Console.WriteLine($"Response: {context.Response.StatusCode}");
});

app.UseAuthentication();
app.UseAuthorization();
app.MapGet("/secure", () => "only for authenticated users");
Key points
  • Minimal APIs let you wire routes directly to handlers with very little boilerplate.
  • ASP.NET Core processes every request through a configurable pipeline of middleware, and registration order controls execution order.
  • Dependency injection is built in; services are registered with a Singleton, Scoped, or Transient lifetime.
  • Route parameters like {name} bind automatically to matching handler parameters.
  • Configuration layers appsettings.json, environment-specific overrides, environment variables, and command-line args, each overriding the last.
  • Larger apps commonly organize endpoints into controller classes using the MVC pattern, on the same pipeline as minimal APIs.
