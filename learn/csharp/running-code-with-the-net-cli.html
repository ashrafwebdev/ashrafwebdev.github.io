01 Zero stage

Running code with the .NET CLI

C# · part of the free zero-to-hero guide

Builds on: Arrays and lists

The dotnet command-line tool is the primary way to create, build, run, and publish .NET projects, independent of any IDE. dotnet new console -o MyApp scaffolds a new console project with a .csproj file describing its dependencies and target framework; dotnet new list shows every template installed, and there are templates for web APIs, class libraries, test projects, and more.

dotnet run compiles and runs a project in one step during development, while dotnet build just compiles (producing DLLs in bin/Debug/...), and dotnet publish produces a self-contained, deployable output for a target platform — optionally bundling the .NET runtime itself so the target machine doesn't need it preinstalled.

Dependencies are added with dotnet add package, which updates the .csproj file and restores the package from NuGet, .NET's central package repository, similar to npm for JavaScript or pip for Python. dotnet restore re-downloads all listed dependencies, which is useful after cloning a repository or when packages are missing.

Multiple related projects (a web API, a class library, a test project) are typically grouped in a solution file (.sln), created with dotnet new sln and populated with dotnet sln add; commands like dotnet build and dotnet test run against every project in the solution when invoked from its directory.

The .csproj file is plain XML and is meant to be hand-edited when needed — changing the target framework, adding a project reference, or excluding files from compilation are all just XML edits, unlike the heavier project file formats .NET used before the SDK-style projects introduced in .NET Core.

Configuration commonly lives in appsettings.json plus environment-specific overrides like appsettings.Development.json, and the environment is selected via the DOTNET_ENVIRONMENT or ASPNETCORE_ENVIRONMENT variable, letting the same published binary behave differently in development, staging, and production without a rebuild.

terminal
$ dotnet new console -o MyApp
$ cd MyApp
$ dotnet run
Hello, World!

$ dotnet add package Newtonsoft.Json
$ dotnet build
$ dotnet publish -c Release -o ./out
terminal-solution.sh
$ dotnet new sln -o MyBank
$ cd MyBank
$ dotnet new classlib -o MyBank.Domain
$ dotnet new xunit -o MyBank.Tests
$ dotnet sln add MyBank.Domain MyBank.Tests
$ dotnet add MyBank.Tests reference MyBank.Domain
$ dotnet test              # runs every test project in the solution
$ dotnet restore           # re-fetches all NuGet packages
MyApp.csproj
<Project Sdk="Microsoft.NET.Sdk">

  <PropertyGroup>
    <OutputType>Exe</OutputType>
    <TargetFramework>net8.0</TargetFramework>
    <Nullable>enable</Nullable>
    <ImplicitUsings>enable</ImplicitUsings>
  </PropertyGroup>

  <ItemGroup>
    <PackageReference Include="Newtonsoft.Json" Version="13.0.3" />
  </ItemGroup>

</Project>
Key points
  • dotnet new scaffolds new projects from built-in or installed templates.
  • dotnet run builds and runs; dotnet build only compiles; dotnet publish produces deployable output.
  • Project dependencies and metadata live in the plain-XML .csproj file, which is safe to hand-edit.
  • NuGet is the standard package repository, managed via dotnet add package and dotnet restore.
  • A .sln solution file groups related projects so build and test commands can run across all of them at once.
  • dotnet add ... reference ... wires up a project-to-project dependency inside a solution.
  • The active environment (appsettings.Development.json vs production) is selected via an environment variable, not a rebuild.
Try it yourself

Scaffold a new console project with dotnet new console, add a package of your choice with dotnet add package, and run the project with dotnet run. Then create a solution file, add both your console project and a new class library project to it, add a project reference from the console app to the library, and confirm dotnet build succeeds for the whole solution.
