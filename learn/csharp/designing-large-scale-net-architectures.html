Designing large-scale .NET architectures

C# · part of the free zero-to-hero guide

Large .NET systems commonly follow Clean Architecture or a similar layered approach: a core domain layer with no external dependencies, surrounded by application logic, then infrastructure (database, external APIs) and presentation (Web API, UI) layers that depend inward, never the reverse. This inversion is what lets you swap a database provider or a UI framework without touching the domain's business rules, since nothing in the domain layer even references those outer layers.

CQRS (Command Query Responsibility Segregation) combined with the MediatR library is a popular .NET pattern for separating write operations (commands) from read operations (queries), keeping each handler focused on a single responsibility; taken further, some systems use entirely separate models (and even separate databases) for reads versus writes, though that level of separation is usually reserved for genuinely high-scale or complex-reporting scenarios rather than every project.

Dependency injection is the mechanism that makes the inward-pointing dependency rule practical: infrastructure classes implement interfaces defined in the application or domain layer, and are only wired together at the composition root (typically Program.cs), so the domain layer can define "I need something that saves an order" as an interface without knowing or caring that the concrete implementation happens to use EF Core and SQL Server.

As systems grow past a single deployable, patterns from the broader microservices world apply equally in .NET: message queues (Azure Service Bus, RabbitMQ) for asynchronous communication between services, the outbox pattern for reliably publishing an event only after a database transaction commits, and API gateways for presenting a single entry point over several backend services.

Domain-Driven Design concepts — entities (objects with identity that persists across changes), value objects (immutable objects compared by their values, a natural fit for C# records), and aggregates (a cluster of entities and value objects treated as a single unit for consistency, with one designated root that's the only object outside code is allowed to reference directly) — give a shared vocabulary for modeling complex business rules that a purely data-centric, table-driven design tends to lose.

None of this is free: layering, CQRS, and DDD all add indirection and ceremony that a small CRUD application doesn't need. The judgment call is matching architectural investment to actual complexity — a simple internal tool is often better served by a straightforward three-layer app than a full Clean Architecture solution with a dozen projects.

layout
src/
  Domain/          # entities, value objects, no external dependencies
  Application/      # use cases, commands, queries, interfaces
  Infrastructure/    # EF Core, external API clients, implementations
  Api/              # controllers, composition root, DI setup

# dependency direction: Api -> Application -> Domain
#                     Infrastructure -> Application -> Domain
CqrsHandler.cs
// Application layer: defines the interface, knows nothing about EF Core
public interface IOrderRepository
{
    Task SaveAsync(Order order);
}

public record PlaceOrderCommand(string Customer, decimal Amount) : IRequest<int>;

public class PlaceOrderHandler : IRequestHandler<PlaceOrderCommand, int>
{
    private readonly IOrderRepository _repository;
    public PlaceOrderHandler(IOrderRepository repository) => _repository = repository;

    public async Task<int> Handle(PlaceOrderCommand cmd, CancellationToken ct)
    {
        var order = new Order(cmd.Customer, cmd.Amount);
        await _repository.SaveAsync(order);
        return order.Id;
    }
}

// Infrastructure layer: the only place that knows about EF Core
public class EfOrderRepository : IOrderRepository
{
    private readonly AppDbContext _db;
    public EfOrderRepository(AppDbContext db) => _db = db;
    public async Task SaveAsync(Order order)
    {
        _db.Orders.Add(order);
        await _db.SaveChangesAsync();
    }
}
CompositionRoot.cs
// Program.cs: the composition root -- the only place that wires
// interfaces (defined inward) to implementations (defined outward)
var builder = WebApplication.CreateBuilder(args);

builder.Services.AddScoped<IOrderRepository, EfOrderRepository>();
builder.Services.AddMediatR(cfg =>
    cfg.RegisterServicesFromAssemblyContaining<PlaceOrderHandler>());

var app = builder.Build();
app.MapPost("/orders", async (PlaceOrderCommand cmd, IMediator mediator) =>
    Results.Ok(await mediator.Send(cmd)));
app.Run();
Key points
  • Clean Architecture keeps the domain layer free of dependencies on infrastructure or frameworks.
  • CQRS with MediatR separates command handlers from query handlers for clearer responsibilities.
  • Dependencies should always point inward toward the domain, never outward.
  • The composition root (typically Program.cs) is the only place interfaces get wired to concrete implementations.
  • Message queues decouple services and support asynchronous, resilient communication at scale.
  • DDD's entities, value objects, and aggregates give shared vocabulary for modeling complex business rules.
  • Layering and DDD add real ceremony — match the architecture's complexity to the problem's actual complexity.
