03 Advanced stage capstone

A tested, async, EF-Core-backed habit tracker API

C# · ties together everything in the Advanced stage

The Advanced stage is where the roadmap's own blurb points directly at the deliverable: a tested ASP.NET Core Web API backed by Entity Framework Core. This project builds that API around a habit tracker — a small backend where a client can create habits, log a completion for a habit on a given day, and query a habit's streak — because the streak calculation gives you a genuine reason to reach for LINQ aggregation and async database queries rather than just wrapping CRUD around a table.

Every endpoint must be a real [ApiController] action (not a minimal API route) so you exercise attribute routing, model binding, and validation attributes together, and every database access must go through an injected, EF-Core-backed repository interface rather than a controller talking to a DbContext directly — that separation is exactly what makes the accompanying xUnit test suite possible without a real database.

The bar for "done" on this project is not just that the API responds correctly by hand-testing in a browser or Postman, but that an xUnit test suite proves the important behavior (streak calculation, validation, not-found handling) automatically, and that every I/O-bound method is genuinely async rather than fake-async wrapping over synchronous EF calls.

  • async/await in depth
  • Generics and advanced LINQ
  • ASP.NET Core Web APIs
  • Entity Framework Core
  • Testing with xUnit
Requirements
  • An EF Core DbContext with at least a Habit and a related HabitCompletion entity, connected by a foreign key, using SQLite so the whole project runs with zero external setup.
  • Controller actions (using [ApiController] and attribute routing, not minimal APIs) for creating a habit, logging a completion, listing habits, and getting a single habit's current streak, each returning the correct status code (200, 201, 400, or 404) for its outcome.
  • A request model with at least two validation attributes (e.g. [Required] on the habit name, [Range] or similar on any numeric input) that produces an automatic 400 response on invalid input.
  • A repository interface (e.g. IHabitRepository) with an EF-Core-backed implementation, injected into controllers via constructor injection — no controller may reference DbContext directly.
  • Every repository method that touches the database is async and awaited correctly all the way up to the controller action.
  • An xUnit test project with at least five tests covering the streak calculation logic and at least one 404/400 case, using a fake or in-memory implementation of the repository interface rather than a real database.
  • dotnet test passes for the whole solution from a clean checkout.
Suggested approach
  1. Model the domain first: write Habit and HabitCompletion as plain classes, then wire up the DbContext and confirm dotnet ef migrations add and dotnet ef database update succeed before writing any controller code.
  2. Build the repository interface and its EF-backed implementation next, writing a couple of throwaway console calls against it to confirm creating a habit and logging a completion actually persist correctly.
  3. Wire up the controller actions for create and list first, since they're the simplest, and confirm them manually before moving to anything streak-related.
  4. Implement the streak calculation as a method on the repository (or a small dedicated service) that you can unit test in isolation with an in-memory fake, before ever calling it from a controller action.
  5. Write the xUnit test project last against the fake repository, then go back and add validation attributes and proper status codes to any controller action the tests reveal is returning the wrong thing on bad input.
Stretch goals
  • Add pagination to the "list habits" endpoint using Skip/Take, and test that it returns the correct page.
  • Add a second, read-optimized endpoint that returns every habit's streak in one call using a single query with .AsNoTracking() instead of one query per habit, and confirm you avoided an N+1 by reasoning through what SQL EF Core would generate.
  • Add a [Theory]-based test suite with several date-range scenarios (a broken streak, a same-day double log, a streak spanning a month boundary) to pressure-test the streak logic beyond the happy path.
