Testing with xUnit

C# · part of the free zero-to-hero guide

xUnit is one of the most widely used testing frameworks in the .NET ecosystem. A test method is marked with [Fact] for a single fixed test case, or [Theory] combined with [InlineData] to run the same test logic against multiple sets of inputs, avoiding copy-pasted near-identical test methods that differ only in their input values.

Assertions live in the Assert class — Assert.Equal, Assert.True, Assert.Throws, Assert.Contains — and tests generally follow the Arrange-Act-Assert structure: set up the objects under test, perform the action being tested, then verify the outcome, kept as three clearly separated sections even in a short test.

xUnit creates a fresh instance of the test class for every test method by default, which keeps tests naturally isolated from each other without needing explicit setup/teardown attributes for common cases; anything you'd normally put in a setup method instead goes in the test class's constructor, and anything for teardown implements IDisposable on the test class itself.

Shared, expensive setup that must persist across multiple tests (like spinning up a test database once) uses a fixture: a class implementing IClassFixture of TFixture for sharing across tests within one class, or ICollectionFixture combined with a [Collection] attribute for sharing across multiple test classes — a deliberate opt-in, since the framework's default of per-test isolation is usually what you want.

Good unit tests isolate the code under test from its dependencies using fakes, stubs, or mocking libraries like Moq, so a test failure points precisely at the class being tested rather than at a database, network call, or file system it happens to depend on; dependency injection (registering interfaces rather than concrete classes) is what makes substituting a fake implementation practical in the first place.

dotnet test runs the whole suite from the command line or CI, and supports filtering with --filter to run a subset of tests by name, trait, or namespace, which is essential once a test suite grows past a few dozen tests and running everything on every save becomes slow.

CalculatorTests.cs
public class CalculatorTests
{
    [Theory]
    [InlineData(2, 3, 5)]
    [InlineData(-1, 1, 0)]
    public void Add_ReturnsSum(int a, int b, int expected)
    {
        var calc = new Calculator();
        Assert.Equal(expected, calc.Add(a, b));
    }

    [Fact]
    public void Divide_ByZero_Throws()
    {
        var calc = new Calculator();
        Assert.Throws<DivideByZeroException>(() => calc.Divide(1, 0));
    }
}
ConstructorSetupAndFixture.cs
public class OrderServiceTests : IDisposable
{
    private readonly OrderService _service;

    // Runs before every test method -- this IS the setup step
    public OrderServiceTests()
    {
        _service = new OrderService(new InMemoryOrderRepository());
    }

    [Fact]
    public void PlaceOrder_IncreasesCount()
    {
        // Arrange is done in the constructor above
        _service.PlaceOrder("Widget", 3);          // Act
        Assert.Equal(1, _service.OrderCount);       // Assert
    }

    // Runs after every test method -- teardown
    public void Dispose() => _service.Dispose();
}
MockedDependency.cs
public interface IEmailSender { void Send(string to, string body); }

public class SignupServiceTests
{
    [Fact]
    public void Signup_SendsWelcomeEmail()
    {
        var mockSender = new Mock<IEmailSender>();
        var service = new SignupService(mockSender.Object);

        service.Signup("amina@example.com");

        mockSender.Verify(
            s => s.Send("amina@example.com", It.IsAny<string>()),
            Times.Once);
    }
}
Key points
  • [Fact] marks a single test case; [Theory] with [InlineData] parameterizes one across inputs.
  • Assert.Equal, Assert.True, and Assert.Throws cover most verification needs.
  • A fresh test class instance per test method keeps tests isolated by default; use the constructor for setup and IDisposable for teardown.
  • Shared expensive setup across tests uses a fixture (IClassFixture or ICollectionFixture) as a deliberate opt-in.
  • Mocking a dependency's interface isolates the code under test so failures point at the right class.
  • Arrange-Act-Assert keeps each test readable even as the scenario grows more complex.
  • dotnet test runs the whole suite from the command line or CI, with --filter to run a subset.
Try it yourself

Write an xUnit test class for a StringUtils.IsPalindrome method with a Theory covering a palindrome, a non-palindrome, and an empty string. Then write a second test class with constructor-based setup for a small service of your choice, and add one test that uses a mocked dependency (or a simple hand-written fake) to verify the service calls that dependency correctly.
