Performance and memory tuning

C# · part of the free zero-to-hero guide

.NET's garbage collector manages heap memory in generations: short-lived objects are collected cheaply and often from generation 0, while long-lived objects get promoted to generation 1 and 2, which are collected less frequently, based on the same "most objects die young" observation used across managed runtimes. A generation-0 collection is fast precisely because it only has to scan a small, recently-allocated region, not the whole heap.

The Span of T and Memory of T types let you work with contiguous memory (arrays, strings, stack-allocated buffers) without extra allocations or copies, which matters a great deal in performance-sensitive parsing or I/O code; Span of T is a stack-only ref struct, so it can't be stored in a field or captured in a lambda/async method, while Memory of T can, at the cost of slightly more overhead.

Large object allocations (85,000 bytes or more) bypass the normal generational scheme and go straight into the Large Object Heap, which is collected less predictably and, historically, wasn't compacted the way the rest of the heap is, so applications that repeatedly allocate large arrays or buffers can suffer from heap fragmentation if they're not careful.

Value types avoid heap allocation and GC pressure entirely when used as locals or fields of another value type, which is one reason structs can be a meaningful performance win in hot paths — but only when kept small, since large structs get expensive to copy on every assignment or method call, trading one cost for another.

String concatenation in a loop is a classic accidental performance trap: each + allocates a brand-new string, so a loop building up a large string via repeated concatenation is quadratic in the string's final length; StringBuilder avoids this by mutating an internal buffer and only materializing the final string once.

Tools like dotnet-trace, dotnet-counters, and Visual Studio's profiler measure real allocation and CPU hotspots; as with any language, the right first step in tuning is always profiling to find the actual bottleneck, not guessing — intuition about what's "probably slow" is wrong often enough that skipping measurement wastes real engineering time on the wrong fix.

StringBuilderVsConcat.cs
// Quadratic: each += allocates a new string of growing size
string BuildBad(int n)
{
    string result = "";
    for (int i = 0; i < n; i++)
        result += i.ToString();
    return result;
}

// Linear: one growable internal buffer, materialized once at the end
string BuildGood(int n)
{
    var sb = new StringBuilder();
    for (int i = 0; i < n; i++)
        sb.Append(i);
    return sb.ToString();
}

readonly struct Point3D

    public readonly double X, Y, Z;
    public Point3D(double x, double y, double z) => (X, Y, Z) = (x, y, z);
}

Key points
  • The GC organizes the heap into generations, collecting short-lived objects far more often and cheaply.
  • Span of T lets you slice and process memory without extra allocations, but can't be stored in a field or async state.
  • Allocations of 85,000 bytes or more go to the Large Object Heap, which is collected differently and can fragment.
  • Small structs avoid heap allocation and GC pressure but get expensive to copy once they grow large — there's a real tradeoff.
  • String concatenation in a loop is quadratic; use StringBuilder for building strings incrementally.
  • Profile with tools like dotnet-trace and dotnet-counters before changing code for performance reasons.
  • Reducing allocations in hot paths is often the highest-leverage .NET performance win.
Try it yourself

Read about the difference between Gen 0, Gen 1, and Gen 2 garbage collections in .NET and summarize in two or three sentences why generational collection improves throughput. Then write two small methods that build a 10,000-character string, one using string concatenation in a loop and one using StringBuilder, and time each with a Stopwatch to observe the difference.
