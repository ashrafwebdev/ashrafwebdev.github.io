Exception handling

C# · part of the free zero-to-hero guide

C# uses try/catch/finally, structurally similar to Java's model. Code that might throw goes in try, a specific catch (ExceptionType e) handles that failure, and finally runs unconditionally — whether the try block succeeded, threw, or even returned early — making it the natural place for cleanup that must always happen.

Unlike Java, C# has no checked exceptions — the compiler never forces you to catch or declare any exception, so you decide by convention which failures are worth handling explicitly versus letting propagate up to a caller better positioned to deal with them. This makes documentation and XML doc comments (<exception>) more important in C#, since the compiler won't remind you what a method might throw.

Multiple catch blocks can be stacked for different exception types, and they're evaluated top to bottom, so more specific exception types must be listed before more general ones (like Exception itself) or the specific catch becomes unreachable and the compiler flags it as an error. A catch with a when clause (an exception filter) can further narrow which instances of a type get handled, without losing the original stack trace the way re-throwing and re-catching would.

Rethrowing with bare throw; inside a catch block preserves the original stack trace, while throw ex; resets it to the rethrow point, erasing information about where the exception actually originated — a subtle but important distinction when debugging production failures from logs.

The using statement (or using declaration, its more concise C# 8+ form without braces) automatically calls Dispose() on any IDisposable resource at the end of its scope, even if an exception is thrown, which is C#'s equivalent to Java's try-with-resources. This matters for anything holding an unmanaged resource — file handles, database connections, network sockets — since the garbage collector alone doesn't reliably release those in a timely way.

Custom exceptions should derive from Exception (or a more specific existing type) and typically add fields relevant to the failure, plus the standard constructors so the type plays well with re-throwing and serialization; a good custom exception name and message save significant debugging time compared to throwing a generic Exception everywhere.

Program.cs
static int Divide(int a, int b)
{
    try
    {
        return a / b;
    }
    catch (DivideByZeroException e)
    {
        Console.WriteLine($"Cannot divide: {e.Message}");
        return 0;
    }
    finally
    {
        Console.WriteLine("Attempt finished.");
    }
}
CustomExceptionAndFilter.cs
public class InsufficientFundsException : Exception
{
    public decimal Shortfall { get; }
    public InsufficientFundsException(decimal shortfall)
        : base($"Short by {shortfall:C}")
    {
        Shortfall = shortfall;
    }
}

static void Withdraw(decimal balance, decimal amount)
{
    if (amount > balance)
        throw new InsufficientFundsException(amount - balance);
}

try
{
    Withdraw(50, 75);
}
catch (InsufficientFundsException e) when (e.Shortfall > 100)
{
    Console.WriteLine("Severe shortfall: " + e.Message);
}
catch (InsufficientFundsException e)
{
    Console.WriteLine("Minor shortfall: " + e.Message);
}
RethrowGotcha.cs
static void Inner() => throw new InvalidOperationException("boom");

static void Outer_Good()
{
    try { Inner(); }
    catch (Exception e)
    {
        // 'throw;' preserves the original stack trace
        throw;
    }
}

static void Outer_Bad()
{
    try { Inner(); }
    catch (Exception e)
    {
        // 'throw ex;' resets the stack trace to here -- loses origin info
        throw e;
    }
}
Key points
  • finally always runs, whether or not an exception was thrown or the block returned early.
  • C# has no checked exceptions; catching is a matter of convention, not compiler enforcement.
  • Catch blocks are checked top to bottom — list more specific exception types before general ones.
  • An exception filter (catch (T e) when (...)) narrows which instances get handled without discarding the stack trace.
  • throw; preserves the original stack trace; throw ex; resets it — almost always prefer throw;.
  • using automatically disposes of IDisposable resources, even during an exception.
  • Catch the most specific exception type you can meaningfully act on; avoid blanket catch (Exception) unless you're logging and rethrowing.
  • Custom exceptions should carry the data relevant to the failure and use a descriptive message.
Try it yourself

Write a method that parses a string to an int with int.Parse inside a try/catch for FormatException, returning -1 on failure, and test it with valid and invalid input. Then define a custom InsufficientFundsException carrying a Shortfall amount, throw it from a Withdraw method, and catch it with two catch blocks distinguishing a severe shortfall from a minor one using a when clause.
