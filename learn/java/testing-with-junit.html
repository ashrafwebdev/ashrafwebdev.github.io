Testing with JUnit

Java · part of the free zero-to-hero guide

JUnit (currently JUnit 5, also called Jupiter) is the standard framework for writing automated tests in Java. A test method is annotated with @Test and typically calls methods from org.junit.jupiter.api.Assertions, such as assertEquals, assertTrue, and assertThrows, to verify expected behavior; the test runner reports each method's pass/fail status independently.

Good tests follow the Arrange-Act-Assert pattern: set up the inputs and objects needed, perform the action being tested, then assert the outcome matches expectations. Each test should focus on one specific behavior so that when a test fails, the failure message alone tells you roughly what broke, without needing to read the whole test body to figure out which assertion actually failed.

@BeforeEach and @AfterEach let you run shared setup and teardown code around every test method, keeping test bodies focused on the specific behavior being verified rather than repeated boilerplate; @BeforeAll/@AfterAll (which must be static, unless the test class uses per-class lifecycle) run once for the whole test class instead of once per test.

@ParameterizedTest combined with a source annotation like @ValueSource or @CsvSource runs the same test logic against a whole table of different inputs, which catches far more edge cases than writing one hand-written test method per case and keeps the test file from growing unwieldy as more cases are added.

For code that depends on external collaborators (a database, a network call, another service), tests often use a mocking library like Mockito to substitute a fake, controllable stand-in for the real dependency, letting you test a class's logic in complete isolation without needing a real database or network connection just to run a unit test.

Test coverage tools (like JaCoCo) report what percentage of lines or branches your tests actually execute, but high coverage alone doesn't guarantee good tests — a test that calls a method without asserting anything meaningful about its result gets "credit" for coverage while verifying nothing at all, so coverage is a useful signal, not a target to chase for its own sake.

CalculatorTest.java
import org.junit.jupiter.api.*;
import static org.junit.jupiter.api.Assertions.*;

class CalculatorTest {
    private Calculator calc;

    @BeforeEach
    void setUp() {
        calc = new Calculator();
    }

    @Test
    void addsTwoPositiveNumbers() {
        assertEquals(5, calc.add(2, 3));
    }

    @Test
    void divisionByZeroThrows() {
        assertThrows(ArithmeticException.class, () -> calc.divide(1, 0));
    }
}
StringUtilsTest.java
import org.junit.jupiter.api.Test;
import org.junit.jupiter.params.ParameterizedTest;
import org.junit.jupiter.params.provider.CsvSource;
import static org.junit.jupiter.api.Assertions.*;

class StringUtilsTest {

    @ParameterizedTest
    @CsvSource({
        "racecar, true",
        "hello, false",
        "'', true",
        "A man a plan a canal Panama, false" // case-sensitive, spaces count
    })
    void isPalindromeAcrossManyInputs(String input, boolean expected) {
        assertEquals(expected, StringUtils.isPalindrome(input));
    }

    @Test
    void nullInputThrowsIllegalArgumentException() {
        assertThrows(IllegalArgumentException.class,
            () -> StringUtils.isPalindrome(null));
    }
}
Key points
  • @Test marks a method as an automatically-run test case, reported pass/fail independently of other tests.
  • Assertions.assertEquals, assertTrue, and assertThrows verify expected outcomes.
  • @BeforeEach runs shared setup before every test, keeping tests DRY and focused; @BeforeAll runs once per class.
  • @ParameterizedTest with @ValueSource or @CsvSource runs one test method against many input cases.
  • Mocking libraries like Mockito substitute fake collaborators so a unit test can isolate the logic under test.
  • Each test should verify one behavior, making a failing test easy to pinpoint.
  • High code coverage doesn't guarantee good tests; a test must actually assert meaningful outcomes to be worth anything.
Try it yourself

Write a StringUtils class with an isPalindrome method, then write three JUnit tests covering a palindrome, a non-palindrome, and an empty string. Then convert those three cases into a single @ParameterizedTest using @CsvSource, add a case for null input that expects an IllegalArgumentException, and add a @BeforeEach that logs which test is about to run.
