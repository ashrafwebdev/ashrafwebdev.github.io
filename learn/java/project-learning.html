StockRoom: an inventory tracker with real persistence

Java · ties together everything in the Learning stage

This project moves from a single-run demo to something that behaves like a real tool: a small-warehouse inventory tracker that actually remembers its contents after the program exits. It's the first project that has to bring together all five Learning-stage topics at once — inheritance and interfaces, the Collections framework, exception handling, file I/O, and a real build tool — because each one solves a problem the others can't.

The inventory holds more than one kind of item, so you'll use interfaces and inheritance to model what they have in common and where they differ. You'll store items in a Map for fast lookup by SKU instead of scanning an array by hand. You'll define your own exception types for the failure cases that matter to this domain, rather than leaning on generic ones. And the whole thing gets built with Maven or Gradle instead of hand-typed javac commands, because that's how real Java projects are actually compiled and packaged.

The test that actually matters here is restart survival: close the program, run it again, and the inventory you had before should still be there — loaded from disk, not lost the moment the JVM exits.

  • OOP principles: inheritance, polymorphism, interfaces
  • The Collections framework (List, Map, Set)
  • Exception handling
  • File I/O
  • Build tools: Maven or Gradle basics
Requirements
  • A Sellable interface with a totalValue() method, implemented by an Item base class holding private SKU, name, quantity, and price fields; two subclasses that extend Item — for example PerishableItem (adds an expiration date) and ElectronicItem (adds a warranty length) — each overriding at least one inherited method meaningfully.
  • A Map from SKU (a String) to Item as the primary in-memory store, iterated through its values as Item references to print a report — and a one- or two-sentence comment explaining why a Map was the right structure here instead of a List.
  • A custom checked DuplicateSkuException, thrown and handled when code tries to add an item whose SKU already exists, plus at least one other exception (custom or built-in, such as IllegalArgumentException) handled for a second distinct failure case like a negative quantity.
  • Saving the full inventory to a plain-text or CSV file using java.nio.file.Files (or a BufferedWriter) inside try-with-resources, and loading it back into the Map at startup, so the inventory that exists after restarting the program is the same one that existed before it was closed.
  • The load step tolerates both a missing save file (first run ever) and a corrupted line in an existing file (a value that isn't a valid number) without crashing — catch IOException and NumberFormatException separately, print what happened, and continue with whatever could be loaded.
  • A scripted sequence of operations in main that exercises the whole system end to end: add several items (including a deliberate duplicate SKU to trigger the exception), remove one, save to disk, then reload from disk into a fresh Map and print the result to prove persistence actually worked.
  • The project is set up as a buildable Maven or Gradle project (a working pom.xml or build.gradle) rather than compiled by hand, with at least one declared dependency, and it builds successfully with mvn package or ./gradlew build.
Suggested approach
  1. Design the Item hierarchy first in isolation — the interface, the base class, and the two subclasses — and write a small throwaway main that just creates a few objects and prints them polymorphically, before touching collections at all.
  2. Introduce the Map-based store and the custom exceptions next, testing the duplicate-SKU and negative-quantity cases with hardcoded calls so you can see each exception actually fire before moving on.
  3. Add save-to-file logic first, since it's easier to verify: write the file, then open it yourself in a text editor to confirm its contents look right before writing a single line of load code.
  4. Deliberately break the save file by hand — delete it, corrupt one line — and confirm your load code degrades gracefully in both cases before wiring loading into normal program startup.
  5. Set up the Maven or Gradle project structure last: move your classes into src/main/java, add the build file, and confirm the build tool compiles and packages everything correctly from a clean checkout.
Stretch goals
  • Add a low-stock Set of SKUs, recalculated after every change to the inventory, and print it as part of the report.
  • Swap the flat text format for real CSV (splitting on commas, handling a header row), and write a short comment on what got easier and what got harder compared to your original format.
  • Split the file-persistence code into its own module in your build tool, so you get hands-on practice with a small multi-module Maven or Gradle project.
