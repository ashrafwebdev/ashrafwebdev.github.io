Designing microservice architectures

Java · part of the free zero-to-hero guide

Builds on: JVM internals, garbage collection, and performance tuning

A microservice architecture splits an application into small, independently deployable services, each owning its own data and communicating with others over the network, typically via REST or messaging, rather than in-process calls. This trades the simplicity of a single deployable (a monolith) for independent scalability, independent deployment cadence, and team autonomy — but it also introduces network latency, partial failure, and data-consistency challenges that simply don't exist inside a single process.

Because services are distributed, failures must be expected rather than assumed away: patterns like circuit breakers (stop calling a failing dependency temporarily, failing fast instead of piling up slow requests), retries with exponential backoff, and timeouts keep one failing service from cascading into a system-wide outage where every service is stuck waiting on the one that's down.

Each service owning its own data ("database per service") means you generally cannot use a single ACID database transaction across two services the way you could within one monolith's database. Multi-step operations that span services instead rely on patterns like the saga pattern — a sequence of local transactions, each with a defined compensating action to undo it if a later step fails — to achieve eventual consistency across service boundaries.

Service discovery, centralized configuration, and distributed tracing (following a single logical request as it hops across multiple services, using a shared trace ID propagated through each call) become necessary infrastructure once you have more than a handful of services, which is why most production microservice systems rely on a platform like Kubernetes plus an observability stack (metrics, logs, and traces) rather than ad-hoc scripts and manual monitoring.

An API gateway sitting in front of the services provides a single entry point for external clients, handling cross-cutting concerns like authentication, rate limiting, and request routing in one place, so individual services don't each need to reimplement that logic themselves.

Deciding service boundaries well is arguably the hardest part of microservice design: services split along the wrong lines (for example, purely by technical layer instead of by business capability) tend to require constant coordinated cross-service changes for even simple new features, which erases most of the independence microservices were supposed to provide in the first place — a sign that the boundaries need rethinking, not that microservices themselves were the wrong choice.

order-service.yaml
# Simplified service definition
service: order-service
endpoints:
  - POST /orders
  - GET /orders/{id}
dependsOn:
  - inventory-service   # checked via REST, guarded by a circuit breaker
  - payment-service     # called async via a message queue
resilience:
  timeoutMs: 2000
  retries: 2
  circuitBreaker: true
CircuitBreakerSketch.java
// Simplified illustration of a circuit breaker's core state machine
// (in practice, use a library like Resilience4j rather than hand-rolling this)
enum CircuitState { CLOSED, OPEN, HALF_OPEN }

class SimpleCircuitBreaker {
    private CircuitState state = CircuitState.CLOSED;
    private int consecutiveFailures = 0;
    private static final int FAILURE_THRESHOLD = 5;

    boolean allowRequest() {
        return state != CircuitState.OPEN;
    }

    void recordSuccess() {
        consecutiveFailures = 0;
        state = CircuitState.CLOSED;
    }

    void recordFailure() {
        consecutiveFailures++;
        if (consecutiveFailures >= FAILURE_THRESHOLD) {
            state = CircuitState.OPEN; // stop calling the failing dependency
        }
    }
}
Key points
  • Each microservice should own its data and be independently deployable from the others.
  • Circuit breakers, retries with backoff, and timeouts contain failures instead of letting them cascade across services.
  • Database-per-service means cross-service multi-step operations need patterns like sagas with compensating actions instead of a single ACID transaction.
  • Service discovery and centralized configuration become necessary as the number of services grows.
  • Distributed tracing lets you follow one logical request across many service boundaries using a shared trace ID.
  • An API gateway centralizes cross-cutting concerns like authentication and rate limiting for external clients.
  • Service boundaries drawn along business capabilities, not technical layers, are what actually preserve team and deployment independence.
