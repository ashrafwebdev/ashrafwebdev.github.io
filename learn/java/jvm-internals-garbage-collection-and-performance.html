JVM internals, garbage collection, and performance tuning

Java · part of the free zero-to-hero guide

The JVM manages memory in distinct regions: the heap (where objects live, shared across all threads), the stack (per-thread, holding local variables and method call frames), and metaspace (class metadata, replacing the old fixed-size "PermGen" region since Java 8). Understanding this layout explains why some errors are StackOverflowError (deep or infinite recursion exhausting a single thread's stack) versus OutOfMemoryError (heap or metaspace exhaustion, which is a much more serious, application-wide problem).

Garbage collection automatically reclaims heap memory occupied by objects that are no longer reachable from any live reference, so Java developers don't manually free memory the way C/C++ developers do. This trades a small amount of runtime overhead and occasional pause time for the elimination of a huge class of bugs — use-after-free and double-free errors simply cannot happen in ordinary Java code.

Most collectors use a generational strategy, splitting the heap into a young generation (for newly created, usually short-lived objects) and an old generation (for objects that have survived multiple collections). This is based on the empirical observation that most objects die young, so collecting the young generation frequently and cheaply, while collecting the old generation rarely, gives much better overall throughput than treating the whole heap uniformly.

The default collector since Java 9, G1 (Garbage First), divides the heap into many equally-sized regions and prioritizes collecting the regions with the most garbage first, aiming for predictable, bounded pause times rather than the absolute shortest possible pause. ZGC and Shenandoah are newer low-latency collectors that keep pause times in the single-digit milliseconds even on very large heaps, at the cost of somewhat higher CPU overhead, which matters for latency-sensitive applications where a multi-hundred-millisecond GC pause would be unacceptable.

Performance tuning typically starts with measurement, not guessing: tools like JFR (Java Flight Recorder, built into the JVM with very low overhead) and VisualVM profile CPU and memory usage over time, revealing where time is actually spent rather than where you assume it's spent. Flags like -Xmx (max heap size), -Xms (initial heap size), and -XX:+UseG1GC let you tune heap size and collector choice once you know where the actual bottleneck is.

A common performance mistake is over-allocating short-lived objects in a hot loop (for example, building Strings with + inside a loop instead of a StringBuilder), which creates unnecessary GC pressure; the fix is usually algorithmic (allocate less, reuse buffers) rather than reaching for GC tuning flags first, since no amount of collector tuning fixes a program that's fundamentally allocating too much.

terminal
# Run with a max heap of 512MB using the G1 collector
$ java -Xmx512m -XX:+UseG1GC -jar app.jar

# Capture a short profiling recording
$ java -XX:StartFlightRecording=duration=60s,filename=out.jfr -jar app.jar

# Print detailed GC activity to stdout (useful for a quick first look)
$ java -Xlog:gc*:stdout:time,level,tags -jar app.jar
AllocationPressure.java
public class AllocationPressure {
    public static void main(String[] args) {
        long start = System.nanoTime();

        // Bad: creates a new String object on every iteration
        String result = "";
        for (int i = 0; i < 50_000; i++) {
            result += i; // O(n^2) copying, heavy GC pressure
        }

        long slowMs = (System.nanoTime() - start) / 1_000_000;

        start = System.nanoTime();
        // Good: one mutable buffer, far fewer allocations
        StringBuilder sb = new StringBuilder();
        for (int i = 0; i < 50_000; i++) {
            sb.append(i);
        }
        long fastMs = (System.nanoTime() - start) / 1_000_000;

        System.out.println("String concat: " + slowMs + "ms, StringBuilder: " + fastMs + "ms");
    }
}
Key points
  • The JVM heap holds objects; the stack holds per-thread call frames and local variables; metaspace holds class metadata.
  • StackOverflowError and OutOfMemoryError point to different memory regions being exhausted.
  • Garbage collectors focus effort on young, short-lived objects, since most objects never survive long (generational GC).
  • G1 is the modern default collector, prioritizing bounded pause times; ZGC/Shenandoah target very low, consistent latency on large heaps.
  • Tune based on profiler data (JFR, VisualVM), not intuition, before changing heap or GC flags.
  • -Xmx/-Xms control heap size; -XX:+UseG1GC and similar flags select the collector.
  • Excessive short-lived allocation (like string concatenation in a loop) creates GC pressure; fix the allocation pattern before reaching for GC tuning flags.
Try it yourself

Research the difference between the G1 and ZGC garbage collectors and write two or three sentences on when you would pick one over the other. Then write a small program that builds a large string two ways — with + concatenation in a loop and with StringBuilder — time both approaches, and explain in a comment why the StringBuilder version generates far less garbage for the collector to clean up.
