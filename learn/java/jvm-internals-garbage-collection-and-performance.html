JVM internals, garbage collection, and performance tuning

Java · part of the free zero-to-hero guide

The JVM manages memory in distinct regions: the heap (where objects live), the stack (per-thread, holding local variables and method call frames), and metaspace (class metadata). Understanding this layout explains why some errors are StackOverflowError (deep or infinite recursion) versus OutOfMemoryError (heap exhaustion).

Garbage collection automatically reclaims heap memory occupied by objects that are no longer reachable. Modern collectors like G1 and ZGC divide the heap into regions and collect young, short-lived objects far more often than old, long-lived ones, based on the empirical observation that most objects die young.

Performance tuning typically starts with measurement, not guessing: tools like JFR (Java Flight Recorder) and VisualVM profile CPU and memory usage, and flags like -Xmx and -XX:+UseG1GC let you tune heap size and collector choice once you know where the actual bottleneck is.

terminal
# Run with a max heap of 512MB using the G1 collector
$ java -Xmx512m -XX:+UseG1GC -jar app.jar

# Capture a short profiling recording
$ java -XX:StartFlightRecording=duration=60s,filename=out.jfr -jar app.jar
Key points
  • The JVM heap holds objects; the stack holds per-thread call frames and local variables.
  • Garbage collectors focus effort on young, short-lived objects, since most objects never survive long.
  • StackOverflowError and OutOfMemoryError point to different memory regions being exhausted.
  • Tune based on profiler data (JFR, VisualVM), not intuition, before changing heap or GC flags.
Try it yourself

Research the difference between the G1 and ZGC garbage collectors and write two or three sentences on when you would pick one over the other.
