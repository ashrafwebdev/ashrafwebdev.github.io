Concurrency: threads and the executor framework

Java · part of the free zero-to-hero guide

Java has built-in support for concurrency: a Thread represents an independent path of execution, created either by extending Thread or, more commonly, by passing a Runnable (or Callable, if you need a return value) to a new Thread and calling start(). Calling run() directly instead of start() is a classic beginner mistake: it just executes the code synchronously on the current thread, with no new thread created at all.

Creating raw threads by hand does not scale well — each OS thread carries real memory and scheduling overhead — so the executor framework (java.util.concurrent) provides thread pools via Executors.newFixedThreadPool(n), letting you submit many tasks that get run across a bounded, reusable set of worker threads instead of spawning a new thread per task.

ExecutorService.submit returns a Future, which represents a result that will become available later; calling future.get() blocks the calling thread until the task completes and returns its result (or rethrows its exception, wrapped in an ExecutionException). CompletableFuture extends this idea to let you chain asynchronous steps together without blocking at every stage.

Shared mutable state accessed from multiple threads needs coordination to avoid race conditions, where the final result depends unpredictably on thread timing. The synchronized keyword ensures only one thread at a time can execute a block of code or method, using the object's intrinsic lock, but it can also introduce contention (threads waiting) or, if locks are acquired in inconsistent order across methods, deadlock.

java.util.concurrent.atomic classes like AtomicInteger provide lock-free, thread-safe operations on a single variable (such as incrementing a shared counter) that are typically faster than a full synchronized block for that narrow case, because they rely on low-level compare-and-swap CPU instructions instead of locking.

Thread-safe collections like ConcurrentHashMap allow safe concurrent reads and writes without external synchronization and generally scale far better under contention than manually wrapping a plain HashMap with synchronized, because they use fine-grained internal locking (or lock-free algorithms) rather than one lock guarding the entire structure.

PoolDemo.java
import java.util.concurrent.*;

public class PoolDemo {
    public static void main(String[] args) throws InterruptedException {
        ExecutorService pool = Executors.newFixedThreadPool(3);

        for (int i = 1; i <= 5; i++) {
            int taskId = i;
            pool.submit(() -> {
                System.out.println("Running task " + taskId +
                    " on " + Thread.currentThread().getName());
            });
        }

        pool.shutdown();
        pool.awaitTermination(5, TimeUnit.SECONDS);
    }
}
SafeCounter.java
import java.util.concurrent.*;
import java.util.concurrent.atomic.AtomicInteger;

public class SafeCounter {
    private static final AtomicInteger safeCount = new AtomicInteger(0);
    private static int uncoordinatedCount = 0; // NOT thread-safe, for comparison

    public static void main(String[] args) throws InterruptedException {
        ExecutorService pool = Executors.newFixedThreadPool(8);
        int increments = 10_000;

        for (int i = 0; i < increments; i++) {
            pool.submit(() -> {
                safeCount.incrementAndGet();       // atomic, always correct
                uncoordinatedCount++;               // race condition, likely wrong total
            });
        }

        pool.shutdown();
        pool.awaitTermination(10, TimeUnit.SECONDS);

        System.out.println("Atomic result: " + safeCount.get() + " (expected " + increments + ")");
        System.out.println("Unsynchronized result: " + uncoordinatedCount + " (often less than expected)");
    }
}
Key points
  • A Thread runs a Runnable's code independently of the main program flow; call start(), never run() directly, to actually spawn a new thread.
  • The executor framework manages a pool of reusable threads instead of creating one thread per task.
  • Future represents a result available later; get() blocks until the task finishes or throws an ExecutionException.
  • Shared mutable state across threads requires synchronization to avoid race conditions.
  • synchronized guarantees mutual exclusion but can introduce contention or, with inconsistent lock ordering, deadlock.
  • Atomic classes like AtomicInteger offer lock-free thread-safe updates for single variables, often faster than synchronized for that case.
  • ConcurrentHashMap and similar concurrent collections scale better under contention than manually synchronizing a plain HashMap.
Try it yourself

Write a program that submits 10 tasks to a fixed thread pool of size 4, where each task prints its task number and the current thread's name, then shuts the pool down cleanly. Then write a second version that has many tasks increment both a plain int field and an AtomicInteger concurrently, print both final totals, and explain in a comment why they usually differ.
