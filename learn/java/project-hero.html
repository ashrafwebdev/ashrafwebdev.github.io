Order and Stock: a two-service Spring Boot system with monitoring built in

Java · ties together everything in the Hero stage

This is the capstone of the Java track, and it deliberately doesn't fit in one Spring Boot application. Order and Stock is a small two-service system — an Order Service and an Inventory Service, each with its own database, talking to each other over HTTP — built to prove you can do more than write code that works: you can design a system that keeps working when a piece of it fails, and you can see what it's actually doing once it's running.

Every Hero-stage topic earns its place here. JVM and garbage-collection tuning matters once you have two long-running services instead of a script that exits in a second. Microservice design patterns — circuit breakers, timeouts, sagas — matter the moment two services can fail independently of each other, which they will. Advanced design patterns matter because a two-service system has real duplication and real fragility to manage, not just an excuse to use patterns for their own sake. And the discipline of writing documentation a stranger could follow, the same discipline expected of a real open-source contribution, is what turns a personal project into something you could actually hand to someone else.

The honest goal for this project is that a stranger could clone it, read your write-up, run both services locally, and understand not just what they do but why they're built the way they are — including what happens when one of them falls over.

  • JVM internals, garbage collection, and performance tuning
  • Designing microservice architectures
  • Advanced design patterns at scale
  • Contributing to a major Java open-source project
Requirements
  • Two independently runnable Spring Boot services (an Order Service and an Inventory Service), each with its own database and its own REST API, communicating with each other over HTTP rather than sharing a process or a database.
  • A resilience mechanism protecting at least one cross-service call — a circuit breaker (Resilience4j, or a hand-rolled state machine following the closed/open/half-open pattern) combined with a timeout, so a slow or unreachable Inventory Service degrades the Order Service instead of hanging or crashing it.
  • At least one saga-style compensating action: if an order is placed and a later step fails partway through (for example, stock was reserved but payment then fails), the system runs a compensating step that undoes the earlier one (releasing the reserved stock) rather than leaving the two services in an inconsistent state.
  • Spring Boot Actuator enabled on both services, exposing health and metrics endpoints, plus at least one custom application metric you added yourself (for example, a counter of orders successfully placed) — real monitoring you built, not just the untouched defaults.
  • At least two advanced design patterns used deliberately and identifiably in the codebase (for example, a Builder for constructing Order objects, a Strategy for pricing or shipping calculation, or a Decorator adding logging or retry behavior around a service call), each with a short comment explaining what problem it's actually solving there.
  • Evidence of at least one deliberate JVM or performance decision: a documented choice of garbage collector or heap flags for how the services are run, and a short before/after note describing a real hot path you found with a profiler (JFR or VisualVM) and what you changed to improve it.
  • A written, README-quality account inside the project documenting both services' APIs, how to run the whole system locally, and the architecture decisions above — written with the same care and context you'd put into a pull request description on a serious open-source project, clear enough that a stranger could run it without asking you questions.
Suggested approach
  1. Build the two services independently first, each fully working and independently testable against its own database, before making them call each other at all.
  2. Wire the Order Service to call the Inventory Service over HTTP for one simple case (checking stock availability), and get that path solid end to end before adding any resilience around it.
  3. Add the circuit breaker, the timeout, and the saga compensating action once the happy path genuinely works — none of that logic means anything until there's a real failure mode for it to protect against.
  4. Add Actuator and your custom metric, then deliberately introduce a slow endpoint or a thread-pool bottleneck so you have something real to observe with a profiler before you tune anything.
  5. Go back through both codebases, find two places where a design pattern would meaningfully reduce duplication or fragility, apply it there deliberately, and write the README-quality documentation last, once the architecture has actually settled.
Stretch goals
  • Add a third service (for example, a Notification service) purely to practice designing a service boundary from scratch, including deciding what it should and shouldn't be responsible for.
  • Put both services behind a simple API gateway that handles routing and one shared concern, like request logging, in a single place instead of duplicating it in each service.
  • Find one real, well-scoped issue in a Java open-source project you actually use, and apply what this project taught you about writing a clear, well-tested, well-documented change to open a real pull request.
