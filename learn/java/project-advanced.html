TaskFlow: a Spring Boot task-tracking API with a database

Java · ties together everything in the Advanced stage

This is the project where Java stops being a language you run from a terminal and starts being a language that serves other programs. TaskFlow is a small task-tracking REST API, built with Spring Boot and backed by a real database, that exercises every Advanced-stage topic together: generics, streams and lambdas, concurrency, Spring Boot itself, and JUnit.

A REST API is also the first project in this track where correctness under bad input actually matters to someone besides you — a caller sending a malformed request or asking for a task that doesn't exist needs a sensible HTTP response, not a leaked stack trace. And because Spring Boot apps run indefinitely rather than executing once and exiting, this is also the first natural place to use the executor framework or Spring's async support for work that shouldn't block the response.

The bar for this project isn't just "it returns JSON" — it's an API you could hand someone a URL for and a short set of curl commands, and they could exercise every important behavior, including the ones that go wrong on purpose.

  • Generics
  • Streams and lambda expressions
  • Concurrency: threads and the executor framework
  • Spring Boot fundamentals
  • Testing with JUnit
Requirements
  • A Spring Boot application exposing full CRUD for a Task resource through a controller class using @GetMapping, @PostMapping, @PutMapping, and @DeleteMapping, backed by a repository interface extending JpaRepository against a real database (an embedded H2 instance is fine).
  • At least one endpoint that uses the Stream API to transform or aggregate data before returning it — for example a summary endpoint that groups tasks by status using Collectors.groupingBy and returns a count per status — rather than looping over the results by hand.
  • A generic response wrapper type you write yourself (its own type parameter, not a built-in generic) used across at least two different endpoints, showing you can design and use your own generic type, not only consume ones from the standard library.
  • At least one piece of work that runs asynchronously without blocking the HTTP response — using either the executor framework or Spring's @Async — for something that genuinely doesn't need to finish before the response is sent, such as simulating a notification when a task is marked done.
  • A JUnit test suite covering both layers of the application: at least one test using @WebMvcTest to exercise a controller in isolation against a mocked service, and at least one test using @SpringBootTest (or a focused repository test) that exercises real persistence end to end.
  • Meaningful error handling that returns the correct HTTP status for each failure case — 404 for a task that doesn't exist, 400 for invalid input — through an @ExceptionHandler or a ResponseEntity built with the right status, instead of letting an unhandled exception produce a raw stack trace response.
  • The project builds and runs with Maven or Gradle, and every endpoint is documented well enough (a short set of example curl commands, at minimum) that someone else could run it locally and try every behavior without asking you how.
Suggested approach
  1. Scaffold the smallest possible Spring Boot app: one entity, one repository, one working GET endpoint against the embedded database. Confirm it starts and returns real data before adding anything else.
  2. Fill out the rest of CRUD, then immediately add the not-found and invalid-input error handling, so the API behaves sensibly under bad input before you build anything more elaborate on top of it.
  3. Add the stream-based summary endpoint and the generic response wrapper once core CRUD is solid — these are refinements layered on a working API, not something to design the foundation around.
  4. Wire in the asynchronous background work, and prove to yourself with logging or a deliberate delay that the HTTP response really does return before the background work finishes.
  5. Write the JUnit test suite last, once the shape of the API has stabilized, covering both the isolated controller layer and at least one real path through the database.
Stretch goals
  • Add pagination and sorting to the list endpoint using Spring Data's built-in Pageable support.
  • Swap the embedded H2 database for a real PostgreSQL instance running in a container, and note what configuration actually had to change.
  • Add a simple request-logging filter or interceptor in front of the API and use it to time every request, printing the ones that are unexpectedly slow.
