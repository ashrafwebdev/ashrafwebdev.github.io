01 Zero stage

Compiling and running with javac/java

Java · part of the free zero-to-hero guide

Builds on: Arrays

Java source code (.java) is compiled by javac into platform-independent bytecode (.class files), which the Java Virtual Machine then executes with the java command. This two-step compile-then-run model is what lets the same compiled bytecode run unchanged on Windows, Linux, or macOS, as long as a compatible JVM is installed.

For a single file with one public class, javac Main.java produces Main.class, and java Main runs it — note you pass the class name to java, not the file name. If a source file contains multiple top-level classes, javac produces one .class file for each of them, though only one class in the file may be public and it must match the file name.

The CLASSPATH tells the JVM where to look for compiled classes and any JAR dependencies at runtime. For anything beyond a single-file toy program, you'll organize source under a package directory structure that mirrors the package declaration (com.example.app.Main lives in com/example/app/Main.java), and compile/run with -d and -cp flags pointing at those directories.

Modern JDKs (11+) also support running a single source file directly with java Main.java, which compiles the file in memory and runs it immediately without ever writing a .class file to disk — ideal for quick scripts, throwaway experiments, or teaching examples, though not something production builds rely on.

The JDK includes several other command-line tools worth knowing: jar packages compiled classes and resources into a distributable .jar archive, javadoc generates HTML API documentation from specially formatted comments, and jshell (since Java 9) gives you an interactive REPL for trying out snippets of Java without creating a file at all.

Real projects almost never compile files by hand; they use a build tool such as Maven or Gradle (covered in a later lesson) to manage compilation, dependencies, and packaging into a distributable JAR file, but understanding the raw javac/java workflow underneath is what makes build-tool output and error messages make sense.

terminal
$ javac Main.java
$ ls
Main.class  Main.java

$ java Main

terminal-packages
# Package-based project layout
$ find . -name '*.java'
src/com/example/app/Main.java
src/com/example/app/util/StringHelper.java

# Compile into an 'out' directory, preserving package structure
$ javac -d out src/com/example/app/Main.java src/com/example/app/util/StringHelper.java

# Run using the fully-qualified class name and the classpath
$ java -cp out com.example.app.Main

# Package everything into a runnable JAR
$ jar --create --file app.jar --main-class com.example.app.Main -C out .
$ java -jar app.jar
Key points
  • javac compiles source into bytecode; java runs that bytecode on the JVM.
  • Bytecode is platform-independent — "write once, run anywhere" — given a compatible JVM.
  • The public class name must match the source file name exactly; other, non-public classes in the same file get their own .class files too.
  • java is invoked with a class name (or JAR), not a file name, once code has been compiled.
  • Package declarations must match the folder structure on disk (com.example.app lives under com/example/app).
  • JDK 11+ supports running a single .java file directly for quick experiments, with no .class file written to disk.
  • jar packages compiled output into a distributable archive; jshell gives an interactive REPL.
Try it yourself

Write a small Main.java on your machine, compile it with javac, run the resulting class file with java, then try the single-file java Main.java shortcut and compare. Next, move it into a com.example package folder, recompile with -d, run it with the fully-qualified class name and -cp, and package the result into a runnable app.jar with the jar tool.
