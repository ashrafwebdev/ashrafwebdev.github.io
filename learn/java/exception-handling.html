Exception handling

Java · part of the free zero-to-hero guide

Builds on: The Collections framework (List, Map, Set)

Java uses try/catch/finally blocks to handle errors without letting them crash the program. Code that might fail goes in try; code that responds to a specific failure goes in a matching catch; code in finally always runs, whether or not an exception occurred (even if the try block returns), making it ideal for cleanup, though try-with-resources has mostly replaced manual finally-based cleanup for resources.

Java distinguishes checked exceptions (subclasses of Exception other than RuntimeException, which the compiler forces you to catch or declare with throws, like IOException) from unchecked exceptions (subclasses of RuntimeException, which are optional to catch, like NullPointerException or IllegalArgumentException). Checked exceptions are meant for recoverable conditions the caller should plan for; unchecked exceptions usually signal programmer bugs.

You can define your own exception types by extending Exception (checked) or RuntimeException (unchecked), which is useful when a generic exception type doesn't communicate enough domain meaning; a custom InsufficientFundsException is far more informative to a caller than a bare IllegalStateException.

Catch blocks can be ordered from most specific to most general, and Java lets you catch several unrelated exception types in one block with the pipe syntax, catch (IOException | SQLException e), avoiding duplicated handling code when the response is identical for multiple exception types.

Since Java 7, try-with-resources automatically closes any resource implementing AutoCloseable (file streams, database connections, and the like) at the end of the block, even if an exception is thrown, eliminating a whole class of resource-leak bugs that used to require careful nested try/finally blocks.

A common anti-pattern is catching Exception (or worse, Throwable) broadly and silently swallowing it with an empty catch block; this hides real bugs and makes debugging painful. Catch the most specific exception type you can meaningfully handle, and if you must catch broadly, at least log the exception rather than discarding it.

SafeDivide.java
public class SafeDivide {
    static int divide(int a, int b) {
        try {
            return a / b;
        } catch (ArithmeticException e) {
            System.out.println("Cannot divide by zero: " + e.getMessage());
            return 0;
        } finally {
            System.out.println("Division attempt finished.");
        }
    }

    public static void main(String[] args) {
        System.out.println(divide(10, 2));
        System.out.println(divide(10, 0));
    }
}
InsufficientFundsException.java
class InsufficientFundsException extends Exception { // checked: caller must handle it
    InsufficientFundsException(String message) { super(message); }
}

class Account {
    private double balance;
    Account(double balance) { this.balance = balance; }

    void withdraw(double amount) throws InsufficientFundsException {
        if (amount > balance) {
            throw new InsufficientFundsException(
                "Requested " + amount + " but balance is only " + balance);
        }
        balance -= amount;
    }
}

public class BankDemo {
    public static void main(String[] args) {
        Account acc = new Account(100.0);
        try {
            acc.withdraw(250.0);
        } catch (InsufficientFundsException e) {
            System.out.println("Withdrawal failed: " + e.getMessage());
        }
    }
}
Key points
  • finally always executes, making it the right place for cleanup logic that must never be skipped.
  • Checked exceptions must be caught or declared with throws; unchecked (RuntimeException) exceptions are optional to catch.
  • Custom exception classes give domain-specific meaning that generic exception types can't communicate on their own.
  • Multi-catch with the pipe syntax handles several exception types identically without duplicating code.
  • Try-with-resources closes AutoCloseable resources automatically, even when an exception is thrown.
  • Never silently swallow exceptions with an empty catch block; at minimum, log what was caught.
  • Catch the most specific exception type you can meaningfully handle, rather than a broad catch-all.
Try it yourself

Write a method that parses a String into an int using Integer.parseInt, catches NumberFormatException, and returns a default value of -1 when parsing fails; test it with valid and invalid input. Then define a custom checked ValidationException, throw it from a method that rejects negative numbers, and write a caller that handles both exceptions with a single multi-catch block where the response is the same for both.
