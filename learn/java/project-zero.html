01 Zero stage capstone

Checkouts and late fees: a library catalog on the command line

Java · ties together everything in the Zero stage

The five Zero-stage topics for Java — syntax and types, control flow and methods, classes and objects, arrays, and the javac/java workflow — all exist to answer one question: can you model a small piece of the real world as objects and make them behave correctly? This project asks you to model a neighborhood library: books that can be checked out and returned, and members who borrow them, entirely as plain Java classes with no external libraries.

You're deliberately restricted to what this stage has actually taught you. That means fixed-size arrays instead of the Collections framework, no file saving (the catalog resets every time the program runs), and no interactive keyboard input — instead, your main method seeds the catalog with sample data and runs a fixed sequence of actions, printing a formatted report of what happened. That constraint is the whole point: everything has to work through classes, methods, arrays, and control flow alone.

By the end you'll have a small set of .java files that compile cleanly with javac and produce a readable console report when run with java, with two classes that know how to describe themselves properly instead of printing the default, unhelpful object representation.

Requirements
  • A Book class with private fields for title, author, ISBN, and a checked-out flag; a constructor that sets them all; and checkOut() and returnBook() methods that update the flag and report whether the action actually succeeded (a book that's already checked out can't be checked out again).
  • A Member class with a private name field and a fixed-size array (for example, room for 3 books) tracking which Book objects that member currently has borrowed, with methods to add and remove a book from that array.
  • Both Book and Member override toString() so printing an instance shows readable information instead of the default class-and-hashcode text; Book also overrides equals() and hashCode() so two Book objects with the same ISBN are considered equal.
  • A Main class whose main method builds an array of at least 5 Book objects and an array of at least 3 Member objects with hardcoded sample data, then runs through a checkout, a second attempt to check out that same already-borrowed book, and a return.
  • At least one overloaded method — for example a findBook method that can be called with either a title or an ISBN — showing you understand that Java resolves overloads by parameter type at compile time.
  • The whole thing compiles cleanly with javac and runs with java Main, ending with a formatted console report listing every book, its checked-out status, and (when applicable) which member currently holds it.
  • Every failure case — book not found, book already checked out, member's borrowed-books array already full — is handled with plain if checks and a printed message, not by letting the program throw an uncaught exception and crash.
Suggested approach
  1. Start with the Book class alone: fields, constructor, checkOut()/returnBook(), and toString(). Compile it with a throwaway main that creates one Book and prints it before writing anything else.
  2. Add the Member class next, including its fixed-size borrowed-books array, and test creating a couple of members standalone before connecting them to books at all.
  3. Wire Book and Member together inside Main with hardcoded sample arrays, and implement the overloaded findBook method so you have a way to look items up by either title or ISBN.
  4. Add the checkout/return workflow logic, including the already-checked-out and not-found cases, testing each branch by hand with a scripted sequence of calls in main.
  5. Finish with the formatted console report, and only then go back and add equals/hashCode to Book, confirming with a quick test that two Book objects built with the same ISBN but different object identity now compare as equal.
Stretch goals
  • Add a simple daysBorrowed int field to the checkout process and print a late fee for any book held past a hardcoded threshold, using nothing but arithmetic and conditionals.
  • Make a member's borrowed-books array grow instead of staying fixed at 3 slots: track a count separately, and when the array fills up, use Arrays.copyOf to allocate a bigger array and copy the existing entries into it.
  • Split Book, Member, and Main into three separate files, and practice the multi-file javac invocation that compiles all of them together in one command.
