Testing with pytest

Python · part of the free zero-to-hero guide

Builds on: Async Python with asyncio

pytest is the most widely used Python testing framework — test functions are just functions prefixed with test_ in a file named test_*.py or *_test.py, and assertions use plain assert statements instead of a special assertion API like self.assertEqual(...) from the built-in unittest module.

Plain assert statements work directly because pytest rewrites them at test-collection time to give detailed, readable failure output automatically — showing you the actual values on both sides of a failed comparison, not just 'AssertionError' with no context, which is a big part of why pytest feels friendlier than unittest.

Fixtures (@pytest.fixture) provide reusable setup — like a database connection, a temp file, or sample data — that tests can request simply by naming the fixture as a parameter; pytest handles calling it and passing the result in. Fixtures can themselves depend on other fixtures, and have a scope (function, class, module, session) controlling how often they're recreated.

pytest.raises(ValueError) used as a context manager is how you test that a specific exception is raised — the test fails if the code inside the block doesn't raise that exception, and you can further inspect the exception's message via the object it yields.

@pytest.mark.parametrize runs the same test function multiple times with different input/expected-output pairs, which avoids copy-pasting near-identical test functions and makes it trivial to add one more edge case later — just add one more row of data, not one more function.

Fixtures with scope="function" (the default) run fresh for every single test, giving each test a clean, isolated starting point — this test isolation is one of pytest's core value propositions, since a test that depends on leftover state from a previous test is fragile and order-dependent in exactly the way tests shouldn't be.

test_math.py
import pytest
from mymodule import add

def test_add_positive_numbers():
    assert add(2, 3) == 5

def test_add_negative_numbers():
    assert add(-2, 5) == 3

@pytest.fixture
def sample_data():
    return [1, 2, 3]

def test_sum_of_sample(sample_data):
    assert sum(sample_data) == 6
test_parametrize_and_raises.py
import pytest
from mymodule import divide

@pytest.mark.parametrize("a, b, expected", [
    (10, 2, 5),
    (9, 3, 3),
    (-6, 2, -3),
])
def test_divide(a, b, expected):
    assert divide(a, b) == expected

def test_divide_by_zero_raises():
    with pytest.raises(ZeroDivisionError):
        divide(10, 0)
test_fixture_scope.py
import pytest

@pytest.fixture(scope="module")
def db_connection():
    print("opening connection")   # runs once for the whole test file
    conn = {"connected": True}
    yield conn                     # tests receive this value
    print("closing connection")   # teardown after all tests finish

def test_query_users(db_connection):
    assert db_connection["connected"]

def test_query_orders(db_connection):
    assert db_connection["connected"]   # reuses the SAME connection
Key points
  • pytest test functions just need a test_ prefix — no need to subclass anything, unlike Python's built-in unittest.
  • Plain assert statements work directly — pytest rewrites them to give detailed failure output automatically.
  • Fixtures let you share setup across many tests, and can themselves depend on other fixtures.
  • A fixture's scope (function, class, module, session) controls how often it's recreated — the default, function scope, gives every test a clean slate.
  • pytest.raises(ValueError) as a context manager tests that a specific exception is raised.
  • @pytest.mark.parametrize runs one test function against many input/output pairs, avoiding near-duplicate test functions.
  • A fixture using yield instead of return can run teardown code after the test finishes, similar to a context manager.
  • Run pytest -v for verbose per-test output, or pytest -k "add" to run only tests whose name matches a keyword.
Try it yourself

Write three pytest test functions for a function you've already built, covering a normal case, an edge case, and a case that should raise an exception (using pytest.raises). Then convert the normal-case tests into a single parametrized test using @pytest.mark.parametrize with at least three input/expected-output pairs.
