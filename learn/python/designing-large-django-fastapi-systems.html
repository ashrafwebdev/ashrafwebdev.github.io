Designing large Django/FastAPI systems: architecture, caching, queues

Python · part of the free zero-to-hero guide

Builds on: Packaging and publishing to PyPI

At scale, a web application's architecture matters as much as any individual line of code: separating concerns into services, caching expensive or frequently-accessed data (often with Redis), and offloading slow work to background task queues (Celery, RQ, or FastAPI's built-in background tasks for simpler cases) so incoming requests stay fast and the web server thread isn't blocked doing something the user isn't actually waiting to see.

Cache expensive, frequently-read data rather than recomputing it on every request — but caching introduces its own hard problem: invalidation. A cache that's never updated when the underlying data changes serves stale results, so every cache needs an explicit strategy (a time-to-live, an explicit invalidation on write, or both) for when its entries stop being trustworthy.

Background task queues move slow work — sending an email, processing an uploaded file, generating a report — out of the request/response cycle so users aren't left waiting on something that could just as easily happen a few seconds later. The trade-off is added complexity: now you need a message broker (commonly Redis or RabbitMQ) and worker processes running separately from your web server, plus a way to track and report a background job's eventual success or failure back to the user.

Database access patterns become critical at scale in ways they simply don't with a handful of users. The N+1 query problem — issuing one query to fetch a list, then one more query per item to fetch each item's related data — silently turns a single page load into hundreds of database round-trips; Django's select_related/prefetch_related and SQLAlchemy's eager loading both exist specifically to collapse that into one or two queries.

Connection pooling reuses a fixed number of database connections across many requests instead of opening a brand-new one per request, which is both faster and keeps the database from being overwhelmed by connection churn under load; read replicas let read-heavy traffic (which is most traffic, for most apps) be served from a copy of the database that isn't competing with writes on the primary.

Horizontal scaling — running more copies of the app server behind a load balancer instead of making one server bigger — requires the app itself to be stateless between requests: session data, uploaded-file staging, and anything else that used to live safely in one process's memory needs to move to a shared store (Redis, the database, object storage) that every instance of the app can reach identically.

A background task in FastAPI
from fastapi import FastAPI, BackgroundTasks

app = FastAPI()

def send_welcome_email(email: str):
    # slow work, runs after the response is already sent
    ...

@app.post("/signup")
def signup(email: str, background_tasks: BackgroundTasks):
    background_tasks.add_task(send_welcome_email, email)
    return {"message": "Signed up!"}
Caching a slow query with Redis
import json
import redis

cache = redis.Redis()

def get_dashboard_stats(user_id):
    cache_key = f"dashboard:{user_id}"
    cached = cache.get(cache_key)
    if cached:
        return json.loads(cached)

    stats = compute_expensive_stats(user_id)   # slow DB aggregation
    cache.setex(cache_key, 300, json.dumps(stats))  # 5 minute TTL
    return stats
N+1 query problem, Django ORM
# BAD: 1 query for authors, then N more, one per book, to fetch each author
for book in Book.objects.all():
    print(book.title, book.author.name)

# GOOD: select_related does a SQL JOIN, fetching everything in 1 query
for book in Book.objects.select_related("author").all():
    print(book.title, book.author.name)
Key points
  • Cache expensive, frequently-read data (Redis is the common choice) rather than recomputing it on every request, but always pair it with an invalidation strategy.
  • Background task queues (Celery, RQ) move slow work out of the request/response cycle so users aren't left waiting.
  • Watch for N+1 query problems — Django's select_related/prefetch_related and SQLAlchemy's eager loading both exist specifically to fix this.
  • Connection pooling reuses database connections across requests instead of opening a new one each time.
  • Read replicas let read-heavy traffic be served without competing with writes on the primary database.
  • Horizontal scaling (more app server instances) requires the app itself to be stateless — session data belongs in a shared store, not local memory.
  • A background job needs a way to report its eventual success or failure back to the user, since the original request has already returned.
