01 Zero stage capstone

Convertible: a terminal calculator and unit converter that never quits mid-task

Python · ties together everything in the Zero stage

The five Zero-stage topics — syntax and data types, control flow, functions with default arguments, the core collection types, and reading input while printing formatted output — all exist to support one basic shape of program: read something from the user, decide what to do with it, and print a result, over and over, until the user is done. This project makes you build that shape for real, as a single command-line program that acts as both a calculator and a unit converter.

The twist that makes this a genuine test of the stage rather than a toy exercise is the menu loop: the program has to keep running, showing the same set of options, until the user explicitly chooses to quit — which forces you to actually use a while loop for something with real state (a running history of results) instead of a single pass through some code.

Nothing here needs a class, a file, or a library beyond the built-ins. That's deliberate — the constraint proves you can structure a non-trivial, stateful program using nothing but functions, conditionals, loops, and Python's built-in collection types.

  • Syntax, variables, and data types
  • Control flow: if/elif/else, loops
  • Functions and default arguments
  • Lists, dictionaries, tuples, sets
  • Reading input and printing output
Requirements
  • A menu, printed every time the loop repeats, listing numbered options: at least four arithmetic operations (add, subtract, multiply, divide), at least three unit conversions (for example kilometers to miles, Celsius to Fahrenheit, and kilograms to pounds), a "view history" option, and a "quit" option.
  • Every operation and every conversion is its own function — no operation's logic is written directly inline in the menu loop. Function names should read clearly, like fahrenheit_to_celsius, not calc2.
  • The divide function checks for a zero denominator using if/else and prints a friendly message instead of letting the program crash with a ZeroDivisionError.
  • Every value read with input() that's meant to be a number is explicitly converted with int() or float() before being used in a calculation.
  • A running history: every completed calculation or conversion is appended to a list (as a formatted string, or as a small tuple of the inputs and result), and choosing "view history" prints all of them so far, most recent last.
  • Results are printed using an f-string with a format spec that fixes the number of decimal places shown, so a result like 3.333333333333 prints as 3.33.
  • The program only exits when the user selects the quit option from the menu, at which point it prints a goodbye message and stops — no other way to end the program should be required.
Suggested approach
  1. Write and test one calculation function on its own first — for example add(a, b) — calling it directly with hardcoded numbers, before building any menu around it.
  2. Build the menu loop next, but keep every branch trivial at first (just a print("picked option 1") placeholder for each choice) so you can confirm the loop reads a choice, dispatches correctly, and quits cleanly before any real logic exists.
  3. Fill in the arithmetic functions one at a time, wiring each into its menu branch and testing it before moving to the next, adding the zero-division guard as you write divide.
  4. Add the unit conversion functions the same way, one at a time, converting the input string to a float before passing it in.
  5. Add the history list last: append to it inside each branch that successfully completes a calculation, then wire up the "view history" option to print it.
Stretch goals
  • Let the user type a whole expression on one line, like 12 + 5, and write a small function that splits the string on spaces and figures out which operation to call.
  • Add a "clear history" menu option, and a "undo last" option that removes the most recent history entry using list.pop().
  • Revisit the safe_input.py pattern from the Reading Input and Printing Output lesson and wrap your numeric conversions in try/except ValueError so mistyped input produces a friendly re-prompt instead of a crash.
