Object-oriented Python: classes, inheritance

Python · part of the free zero-to-hero guide

A class is a blueprint for creating objects. __init__ is the constructor, run automatically when a new instance is created, and self refers to the specific instance a method is being called on — it must be the first parameter of every instance method, and Python supplies it automatically when you call instance.method().

Inheritance lets a class reuse and extend another class's behavior with class Dog(Animal):. Overriding a method in the subclass replaces the parent's version for instances of that subclass, and calling super().__init__(...) from the subclass's constructor lets it extend the parent's setup logic instead of fully duplicating it.

Instance attributes (set on self inside __init__) belong to each individual object, while class attributes (defined directly in the class body) are shared by every instance — a subtle but important distinction, since mutating a shared mutable class attribute from one instance can unexpectedly affect every other instance.

Python supports a handful of special/'dunder' methods beyond __init__ that let your objects work naturally with built-in syntax: __str__ controls what print(obj) shows, __eq__ controls what == does between two instances, and __repr__ controls the unambiguous, developer-facing representation shown in a debugger or REPL.

'Properties' (@property) let a method be accessed like a plain attribute — obj.area instead of obj.area() — which is useful for computed values that should look read-only from the outside, and lets you add validation logic to attribute access later without breaking every caller's existing code.

Python supports multiple inheritance, and resolves ambiguous method lookups using the Method Resolution Order (MRO), computed with the C3 linearization algorithm — but deep or diamond-shaped inheritance hierarchies get hard to reason about fast, so most experienced Python developers favor composition (an object holding a reference to another) over deep inheritance chains whenever it's a reasonable option.

classes.py
class Animal:
    def __init__(self, name):
        self.name = name

    def speak(self):
        return f"{self.name} makes a sound."

class Dog(Animal):
    def speak(self):
        return f"{self.name} barks."

rex = Dog("Rex")
print(rex.speak())
dunder_and_property.py
class Rectangle:
    def __init__(self, width, height):
        self.width = width
        self.height = height

    @property
    def area(self):
        return self.width * self.height

    def __repr__(self):
        return f"Rectangle({self.width}, {self.height})"

    def __eq__(self, other):
        return (self.width, self.height) == (other.width, other.height)

r = Rectangle(4, 5)
print(r)          # Rectangle(4, 5) -- uses __repr__
print(r.area)     # 20 -- looks like an attribute, runs like a method
print(r == Rectangle(4, 5))  # True
super_and_shared_state.py
class Vehicle:
    def __init__(self, make, model):
        self.make = make
        self.model = model

class Car(Vehicle):
    def __init__(self, make, model, doors):
        super().__init__(make, model)  # extend, don't duplicate
        self.doors = doors

car = Car("Toyota", "Corolla", 4)
print(car.make, car.doors)
Key points
  • self must be the first parameter of every instance method — Python passes it automatically when you call instance.method().
  • __init__ runs once, automatically, right after a new instance is created.
  • super().__init__(...) calls the parent class's constructor, useful when a subclass needs to extend rather than fully replace it.
  • Instance attributes belong to one object; class attributes are shared across all instances of the class, which can be a subtle bug source if they're mutable.
  • @property makes a method accessible like a plain attribute, useful for computed, read-only-looking values.
  • __repr__, __str__, and __eq__ are the dunder methods most worth overriding — they control debugging output, printing, and equality checks respectively.
  • Python supports multiple inheritance, resolved via the Method Resolution Order, but keep hierarchies shallow — deep inheritance trees get hard to reason about fast.
  • Favor composition (an object holding a reference to another) over deep inheritance when either would reasonably solve the design problem.
Try it yourself

Create a Shape base class with an area() method returning 0, then Circle and Rectangle subclasses that override it with the correct formula. Then add a __repr__ method to each subclass so printing an instance shows something readable, and write a small script that sorts a list of mixed Circle/Rectangle instances by area using sorted(shapes, key=lambda s: s.area()).
