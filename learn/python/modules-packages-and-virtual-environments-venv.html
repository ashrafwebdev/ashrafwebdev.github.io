Modules, packages, and virtual environments (venv)

Python · part of the free zero-to-hero guide

A module is just a .py file you can import from another file. A package is a folder of modules — traditionally marked with an __init__.py file, though it's optional for a 'namespace package' since Python 3.3 — letting you organize related code into a hierarchy like myapp.utils.strings.

import module_name pulls in a whole module, and you access its contents with module_name.thing; from module_name import thing pulls in one specific name directly into your file's namespace. from module_name import * exists but is generally discouraged in real code — it makes it unclear where a given name actually came from when you're reading the file later.

A virtual environment (venv) is an isolated Python installation for a single project, with its own site-packages directory, so its installed package versions don't conflict with another project's different — and possibly incompatible — versions of the same libraries. Without one, installing packages globally on your machine is a recipe for one project quietly breaking another.

requirements.txt, generated with pip freeze > requirements.txt, lets anyone recreate your exact dependency set with pip install -r requirements.txt — this reproducibility is what lets a teammate, a CI server, or a production deployment install the exact same package versions you developed and tested against.

Modern projects increasingly use pyproject.toml to declare both project metadata and dependencies in one standardized place, paired with faster tools like uv or poetry that resolve dependencies and manage the virtual environment together, rather than treating pip and venv as two separate manual steps.

Python finds modules by searching sys.path, which includes the current script's directory, installed site-packages, and anything listed in the PYTHONPATH environment variable — understanding this list is the key to debugging a mysterious ModuleNotFoundError for a module you're sure you installed (it's very often installed into the wrong environment).

Terminal
python -m venv .venv
source .venv/bin/activate   # on Windows: .venv\Scripts\activate
pip install requests
pip freeze > requirements.txt
mypackage/__init__.py + usage
# mypackage/greetings.py
def hello(name):
    return f"Hello, {name}!"

# main.py, in the same project root as mypackage/
from mypackage.greetings import hello
import mypackage.greetings as greetings

print(hello("Amina"))
print(greetings.hello("Yusuf"))
Terminal (checking your environment)
which python           # confirm it points inside .venv, not the system Python
pip list                # packages visible in the ACTIVE environment only
deactivate               # leave the virtual environment
Key points
  • Always work inside a virtual environment per project — installing packages globally leads to version conflicts across projects.
  • requirements.txt (from pip freeze) lets anyone recreate your exact dependency set with pip install -r requirements.txt.
  • import module_name pulls in a whole module; from module_name import thing pulls in one specific name.
  • Avoid from module import * in real projects — it obscures where each name in your file actually came from.
  • Python resolves imports by searching sys.path; a mysterious ModuleNotFoundError is usually a sign the package was installed into the wrong environment.
  • Modern projects increasingly use pyproject.toml and tools like uv or poetry instead of raw pip + requirements.txt.
  • A package needs (traditionally) an __init__.py file in its folder to be treated as a package rather than a plain directory.
Try it yourself

Create a virtual environment, activate it, install the requests library, and confirm it's isolated by comparing pip list before and after activation. Then create a small local package with two modules that import from each other, and write a main.py at the project root that imports and uses functions from both.
