WeatherLog: a self-updating weather report that remembers every run

Python · ties together everything in the Learning stage

This project moves you from a single script into something closer to a small, real program: a command-line tool that calls a live public weather API, models the response as a proper Python object, and appends the result to a growing local history file every time you run it — rather than throwing the data away the moment the script ends.

It's built specifically to force all five Learning-stage topics to work together: classes and inheritance to model the data, the requests library to fetch it, try/except to survive the network actually failing (which it will, eventually), JSON or CSV file I/O to persist it, and a real virtual environment with a requirements.txt so the project can be handed to someone else and just work.

You are not allowed to hardcode the weather data or fake the API call — this has to hit a real, no-key-required public endpoint (for example Open-Meteo) and handle whatever it actually returns, including the times it doesn't return anything at all.

  • Object-oriented Python: classes, inheritance
  • File I/O and working with JSON/CSV
  • Modules, packages, and virtual environments (venv)
  • Calling APIs with the requests library
  • Basic error handling with try/except
Requirements
  • A call to a real public API (no API key required) made with requests, using a timeout= argument and response.raise_for_status(), wrapped in a try/except that catches requests.exceptions.RequestException and prints a friendly message instead of crashing when the network fails or the API errors out.
  • At least one class (for example WeatherReport) whose __init__ is populated from fields in the parsed API response, plus a method that returns a readable one-line summary string — and at least one subclass of it that adds or overrides something, demonstrating real inheritance rather than a single flat class.
  • The location to check the weather for is provided by the user (via input() or a command-line argument), not hardcoded, and the program handles the case where that location produces no results from the API.
  • Every run appends its report to a local history file in JSON or CSV format rather than overwriting it — meaning the program reads whatever history already exists at startup, adds the new entry, and writes the combined result back, so running it five times produces a five-entry history.
  • The code is split across at least two of your own modules (for example api.py and models.py, imported into a top-level main.py) rather than living in a single file.
  • The project has its own virtual environment and a requirements.txt generated with pip freeze, and you can prove it works by installing from that file into a fresh venv and running the script successfully.
Suggested approach
  1. Get the raw API call working as a standalone script first, printing the parsed JSON response directly, before writing any classes around it.
  2. Wrap that call in try/except and add raise_for_status() next, deliberately breaking the URL once to confirm your error handling actually triggers.
  3. Design the report class (and its subclass) once you know exactly what fields the real API response contains — don't guess at the shape ahead of time.
  4. Split the working script into modules, then set up the virtual environment and requirements.txt around the code that's now known to work.
  5. Add the persistent history file last: write the read-existing, append-new, write-combined logic as its own function so it's easy to test independently of the API call.
Stretch goals
  • Fetch a second endpoint (for example a multi-day forecast) and merge it into the same report using a second subclass or a composed object.
  • Add a "compare to last run" feature that reads the previous history entry and prints whether the temperature went up or down since then.
  • Reimplement the history storage in the other format (swap JSON for CSV or vice versa) and write a short comment on which was simpler for this particular data shape and why.
