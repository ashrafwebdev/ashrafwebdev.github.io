03 Advanced stage capstone

Shrtn: a tested REST API for shortening links, built with FastAPI or Flask

Python · ties together everything in the Advanced stage

This is the project where you stop writing scripts and start writing a real service: a URL-shortener REST API with routes to create, redirect, inspect, and delete short links, backed by tests that prove it actually works rather than a manual click-through in a browser.

The scope is deliberately narrow — a URL shortener has almost no domain complexity to get lost in — so the project can focus entirely on proving out the Advanced-stage skills themselves: a generator that never hands out the same short code twice, a decorator that logs every request, a context manager that guarantees clicks get recorded even when something goes wrong mid-request, at least one genuinely asynchronous route, and a pytest suite that exercises the whole thing through the framework's own test client.

In-memory storage (a plain dict) is fine here — the point of this stage is the API layer, the concurrency model, and the tests around it, not database design, which comes later.

  • Decorators and context managers
  • Generators and iterators
  • Async Python with asyncio
  • Testing with pytest
  • Web frameworks: Flask/FastAPI (or Django) fundamentals
Requirements
  • At least four routes: create a short code for a submitted URL (returning 201), redirect a request for a short code to its original URL (returning 302 or similar, and 404 for an unknown code), return click-count stats for a code, and delete a code — each with the correct HTTP status code for its outcome.
  • Short codes are produced by a generator function that yields a fresh, never-repeating code each time it's called (for example a base62 counter, or a random generator that checks the existing store for collisions) — not a hardcoded counter variable incremented inline in the route.
  • A decorator you wrote yourself, applied to at least two of your route functions, that logs the request path and how long the function took to run.
  • A custom context manager (either a class with __enter__/__exit__, or a generator function using @contextmanager) wrapping the "increment this code's click count and log the click" step, so the log always happens — even if an exception is raised partway through handling that request.
  • At least one route defined with async def that awaits something (asyncio.sleep() as a stand-in for a slow downstream call is fine), with a code comment explaining why this doesn't block other requests from being handled while it waits.
  • A pytest suite of at least five tests, run through the framework's own test client, covering: successful creation, a successful redirect, a 404 on an unknown code, the click count actually incrementing after a redirect, and deletion actually removing a code.
  • A short README describing how to create the virtual environment, install from requirements.txt, run the app, and run the test suite — someone else should be able to follow it and get the whole thing running without asking you a question.
Suggested approach
  1. Get the simplest possible route working first — a hardcoded redirect from one fixed short code to one fixed URL — and confirm you can reach it before adding any real logic.
  2. Build the code generator and wire up the create and redirect routes around it, using a plain in-memory dict as storage.
  3. Add the stats and delete routes, then layer the decorator and the context manager on top of the request handling you already have working.
  4. Add the async route and the pytest suite in the same pass — the tests will immediately tell you whether the async version is actually behaving correctly.
  5. Write the README last, once the install-and-run steps have actually been verified from a clean virtual environment on their own.
Stretch goals
  • Swap the in-memory dict for a small SQLite-backed store so the data survives a restart, without changing any route's external behavior.
  • Add simple per-IP rate limiting to the create route, implemented as another decorator so the pattern you built stays reusable.
  • Write a Dockerfile so the whole service runs identically with a single command on any machine that has Docker installed.
