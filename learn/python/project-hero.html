04 Hero stage capstone

Shiplog: a production-grade task API with auth, caching, and a background worker

Python · ties together everything in the Hero stage

This is the capstone of the whole Python track, and it's meant to be portfolio-worthy on its own: a task-management REST API that a real team could plausibly run — protected by authentication, fast because of a real caching layer with an explicit invalidation strategy, and resilient because slow work happens in a background queue instead of blocking the request that triggered it.

The bar here is different from every earlier stage. It's not "does it work when I run it once on my machine" — it's "could a stranger read the README, stand this up, understand the architectural decisions, and trust it enough to build on top of." That means the profiling, the packaging, and the written explanation of your own tradeoffs are just as much a required part of this project as the code.

Start from your Advanced-stage API rather than from a blank file if it's a reasonable foundation — this stage is about extending a working service into a production-shaped one, not proving you can start over from zero a fourth time.

  • Performance profiling and optimization (cProfile, Cython, PyPy)
  • Packaging and publishing to PyPI
  • Designing large Django/FastAPI systems: architecture, caching, queues
  • Contributing to CPython or a major open-source Python project
Requirements
  • Token-based authentication (API keys or JWTs) protecting every write route, returning a 401 for any request missing or presenting an invalid token.
  • A cache (Redis, or an equivalent in-memory cache with the same shape) placed in front of at least one genuinely expensive read endpoint, with an explicit time-to-live and a written explanation of exactly what invalidates it and when.
  • At least one slow operation (sending a notification, processing an uploaded file, generating a report — anything that would take a user-noticeable amount of time) offloaded to a background task queue, so the API response returns immediately and the work finishes afterward.
  • A documented before-and-after profiling result: run cProfile (or an equivalent load-testing pass) against your API, find one real bottleneck the data actually points to, fix it, and record the timing difference — not a bottleneck you merely assumed existed.
  • One genuinely reusable piece of the service (for example the caching wrapper or the auth-checking decorator) extracted into its own installable package with a pyproject.toml, built, and uploaded to TestPyPI.
  • A pytest suite covering authentication (both an accepted and a rejected token), the caching behavior (a way to observe a cache hit versus a cache miss), and the background task path (confirming the response returns before the background work is complete) — runnable with a single command.
  • A written architecture section in the README explaining your caching strategy, why you chose a background queue instead of handling that work synchronously, and specifically what you'd change first to handle ten times the current load.
Suggested approach
  1. Start from a working, already-tested API rather than a blank project — extending something proven is the point of this stage.
  2. Add authentication first, since the caching and background-task layers you'll add next both need to know who's making the request.
  3. Add caching to exactly one specific, measurably slow endpoint, and prove the improvement with a real before-and-after timing number, not a guess.
  4. Add the background task queue next, and write a test that specifically confirms the API response returns before the background work finishes.
  5. Profile the whole service under a simple synthetic load, fix whatever the profiling data actually shows is slow, then extract and publish the most reusable piece last, once its interface has stopped changing.
Stretch goals
  • Containerize the entire service — API, background worker, and cache — with Docker Compose, so the whole thing comes up with a single command on any machine.
  • Add structured logging and a health-check endpoint suitable for a real deployment behind a load balancer or uptime monitor.
  • Open a real documentation or bug-fix pull request against one of the open-source libraries your service depends on, following the contribution workflow from the Contributing to CPython or a Major Open-Source Python Project lesson.
