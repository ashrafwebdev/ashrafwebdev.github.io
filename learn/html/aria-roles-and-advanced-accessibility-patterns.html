ARIA roles and advanced accessibility patterns

HTML · part of the free zero-to-hero guide

ARIA (Accessible Rich Internet Applications) attributes fill gaps semantic HTML can't cover on its own — mostly for custom, JavaScript-driven widgets like tabs, modals, and dropdowns that don't have a native HTML equivalent.

The first rule of ARIA is: don't use ARIA if a native element already does the job. A <button> is already a button; adding role="button" to a <div> just to save a bit of styling effort throws away built-in keyboard support you'd have to rebuild by hand — Enter and Space activation, focusability, and correct screen reader announcement all come free with the real element and all have to be manually reimplemented (and easily gotten wrong) with a div.

ARIA works in three broad categories: roles (role="tablist", role="dialog") declare what a custom widget is; properties (aria-label, aria-required) describe characteristics that mostly don't change; and states (aria-expanded, aria-selected, aria-checked) describe conditions that change as the user interacts, and which your JavaScript is responsible for keeping in sync with the actual visible state — an aria-expanded="false" left stale after a menu opens is worse than no ARIA at all, because it actively lies to the screen reader user.

aria-live regions solve a real problem: content that changes without a page reload — a form validation error, a "3 items added to cart" toast, a chat message arriving — needs to be announced to a screen reader even though focus never moves there. aria-live="polite" waits for a natural pause before announcing; aria-live="assertive" interrupts immediately and should be reserved for genuinely urgent, time-sensitive messages.

Building a fully correct custom widget from scratch is deceptively hard: a proper tab interface needs arrow-key navigation between tabs, Home/End key support, correct tabindex roving so only the active tab is in the normal tab order, and aria-selected kept in sync — all documented in the WAI-ARIA Authoring Practices Guide (APG), which provides tested reference patterns for exactly this reason. Reaching for that guide, or a well-tested existing library, is usually smarter than inventing a new keyboard interaction model from scratch.

It's worth internalizing that ARIA attributes change absolutely nothing about behavior — they are purely announcements to assistive technology. Adding role="button" and aria-pressed="false" to a <div> makes a screen reader describe it as a toggle button, but the div still won't respond to a Tab key or an Enter press unless you add tabindex="0" and your own keydown event handlers for both.

A custom tab widget needs ARIA
<div role="tablist">
  <button role="tab" aria-selected="true" id="tab-1" aria-controls="panel-1">Profile</button>
  <button role="tab" aria-selected="false" id="tab-2" aria-controls="panel-2" tabindex="-1">Settings</button>
</div>
<div role="tabpanel" id="panel-1" aria-labelledby="tab-1">Profile content...</div>
<div role="tabpanel" id="panel-2" aria-labelledby="tab-2" hidden>Settings content...</div>
a live region announcing a toast
<div aria-live="polite" class="visually-hidden-until-populated">
  <!-- JS inserts text here; screen readers announce it automatically -->
</div>

<script>
  function announce(message) {
    document.querySelector('[aria-live]').textContent = message;
  }
  announce('3 items added to cart');
</script>
common mistake: ARIA without behavior
<!-- Wrong: announced as a button, but not keyboard-operable at all -->
<div role="button" aria-pressed="false">Toggle</div>

<!-- Right: use a real <button>, which gets keyboard behavior for free -->
<button aria-pressed="false">Toggle</button>
Key points
  • Rule one of ARIA: no ARIA is better than bad ARIA — prefer native elements whenever one exists.
  • aria-label and aria-labelledby give accessible names when visible text isn't enough.
  • aria-live regions announce dynamic content changes (like a form error or toast) to screen readers.
  • Custom widgets built with ARIA must also handle keyboard interaction manually — ARIA alone changes nothing about behavior.
  • ARIA states like aria-expanded and aria-selected must be kept in sync with the real UI state by your JavaScript, or they actively mislead users.
  • The WAI-ARIA Authoring Practices Guide has tested reference patterns for common widgets — use it instead of inventing keyboard behavior from scratch.
  • aria-live="assertive" interrupts immediately and should be reserved for genuinely urgent messages; default to "polite".
Try it yourself

Find a custom dropdown or tab component on a site you use, open dev tools, and inspect what ARIA attributes it uses. Then build your own minimal two-tab widget by hand with role="tablist"/role="tab"/role="tabpanel", wire up aria-selected and a hidden attribute correctly with JavaScript, and add arrow-key navigation between the two tabs.
