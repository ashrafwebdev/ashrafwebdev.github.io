Authoring reusable Web Components / design-system primitives

HTML · part of the free zero-to-hero guide

Builds on: Progressive enhancement principles

At the hero stage, Web Components stop being a curiosity and become a real tool for building a design system — a small set of reusable, framework-agnostic primitives (buttons, cards, tooltips) that any team can drop into any project, React or not.

This means thinking about public API design: which attributes should be configurable, which internal details should stay hidden behind the Shadow DOM, and how consumers style your component from the outside using CSS custom properties you expose deliberately.

CSS custom properties (variables) are the primary styling bridge across the Shadow DOM boundary, because unlike ordinary CSS rules, they inherit through shadow roots. A component author defines an internal style using var(--btn-bg, #1F4E44) with a sensible default, and a consumer overrides just that one value from outside without ever needing to pierce the component's internals or use fragile, framework-specific escape hatches like ::part for every property.

For the handful of cases custom properties don't cover — styling a specific internal element structurally rather than just a color or spacing value — the ::part pseudo-element is the deliberate, sanctioned escape hatch: the component author tags an internal element with part="icon", and only elements explicitly exposed that way become stylable from outside, keeping everything else genuinely encapsulated.

A reusable primitive also needs to handle the same states a native element would: disabled, focus-visible, loading, and error, at minimum. Skipping these is the most common way a hand-rolled component ends up feeling worse than the native HTML element it's replacing — a custom <app-button> that doesn't dim and reject clicks when disabled, or doesn't show a visible focus ring, is a regression compared to a plain <button disabled>.

Versioning discipline matters as soon as more than one project consumes your components: a renamed attribute or a changed default value is a breaking change exactly like it would be in any published library, and should be communicated the same way — semantic versioning, a changelog entry, and ideally a deprecation warning logged to the console for at least one version before the old behavior is removed.

Exposing a styling hook
class AppButton extends HTMLElement {
  connectedCallback() {
    const shadow = this.attachShadow({ mode: 'open' });
    shadow.innerHTML = `
      <style>
        button {
          background: var(--btn-bg, #1F4E44);
          color: var(--btn-fg, white);
        }
        button:disabled { opacity: 0.5; cursor: not-allowed; }
        button:focus-visible { outline: 3px solid var(--btn-focus-ring, #94b8ac); }
      </style>
      <button part="button" ?disabled="${this.hasAttribute('disabled')}">
        <slot></slot>
      </button>
    `;
  }
}
customElements.define('app-button', AppButton);
consumer overriding the hook, and using ::part
<style>
  /* Overrides the exposed custom property, no internals touched */
  .danger-zone app-button { --btn-bg: #b3261e; }

  /* Styles the internal button element via the explicitly exposed part */
  app-button::part(button) { border-radius: 999px; }
</style>

<div class="danger-zone">
  <app-button>Delete account</app-button>
</div>
Key points
  • Design-system components should expose intentional CSS custom-property "hooks", not require overriding internal styles.
  • CSS custom properties inherit through Shadow DOM boundaries — they're the primary styling bridge for encapsulated components.
  • ::part is the sanctioned escape hatch for structural styling of internals the component author explicitly exposes.
  • Keep the public attribute API small and well-documented — every attribute is a promise you have to maintain.
  • Handle disabled, focus-visible, loading, and error states — skipping them makes a custom component feel worse than the native element it replaces.
  • Framework-agnostic components (Web Components) can sit alongside React, Vue, or plain HTML in the same org.
  • Treat attribute renames and default-value changes as breaking changes with real versioning and deprecation warnings.
Try it yourself

Design a small component library (3-4 components: button, card, badge) with consistent, documented CSS custom-property hooks for theming. Give at least one component a part-exposed internal element for structural styling, implement a disabled and a focus-visible state on the button, and write a short changelog entry as if you'd just renamed one attribute.
