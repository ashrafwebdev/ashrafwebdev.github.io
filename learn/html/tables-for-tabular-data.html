Tables for tabular data

HTML · part of the free zero-to-hero guide

Builds on: Semantic HTML5: header, nav, main, article, section, footer

Tables exist for one job: real tabular data with rows and columns, like a price list or a schedule. They are not a layout tool — that misuse from the 1990s and 2000s is exactly what CSS Grid and Flexbox replaced.

A table is built from <table>, with <tr> for each row, <th> for header cells, and <td> for data cells. Wrapping the header row in <thead> and the data rows in <tbody> is good practice for larger tables.

A quick way to tell if content genuinely belongs in a table: read it aloud row by row. "Basic plan: $5 a month, 10 gigabytes of storage" makes sense spoken aloud, because it's real tabular data. If reading the layout aloud produces nonsense — because it was really just three boxes arranged side by side for visual effect — a table is the wrong tool, and a flex or grid layout is the right one.

The scope attribute on a <th> — scope="col" or scope="row" — tells a screen reader exactly which cells that header applies to, so as it reads down a data row it can announce "Price: $15 per month" instead of just a bare number. Without scope, a screen reader has to guess the association from position alone, which breaks down fast on any table more complex than a simple grid.

<caption>, placed immediately after the opening <table> tag, gives the table an accessible title that's announced before its contents — this is different from putting a heading above the table, because a caption stays programmatically tied to that specific table even if the surrounding page structure changes.

Tables can span cells across multiple rows or columns using the colspan and rowspan attributes on a <td> or <th>, which is common in schedules and pricing grids where one label applies to several cells at once. Complex spanning tables are exactly the case where scope and even headers/id attribute pairing become important — otherwise the visual layout and the announced structure drift apart.

index.html
<table>
  <caption>Subscription plans</caption>
  <thead>
    <tr>
      <th scope="col">Plan</th>
      <th scope="col">Price</th>
      <th scope="col">Storage</th>
    </tr>
  </thead>
  <tbody>
    <tr>
      <th scope="row">Basic</th>
      <td>$5/mo</td>
      <td>10 GB</td>
    </tr>
    <tr>
      <th scope="row">Pro</th>
      <td>$15/mo</td>
      <td>100 GB</td>
    </tr>
  </tbody>
</table>
a spanning schedule table
<table>
  <caption>Weekly class schedule</caption>
  <thead>
    <tr><th scope="col">Time</th><th scope="col">Monday</th><th scope="col">Tuesday</th></tr>
  </thead>
  <tbody>
    <tr>
      <th scope="row">9-11am</th>
      <td colspan="2">Studio time (both days)</td>
    </tr>
    <tr>
      <th scope="row" rowspan="2">1-3pm</th>
      <td>Painting</td>
      <td>Sculpture</td>
    </tr>
  </tbody>
</table>
common mistake: table used for layout
<!-- Wrong: three unrelated boxes forced into a table just for a
     side-by-side layout — meaningless when read row by row -->
<table>
  <tr><td>Fast shipping</td><td>24/7 support</td><td>Free returns</td></tr>
</table>

<!-- Right: use CSS for layout, keep tables for tabular data -->
<ul class="feature-grid">
  <li>Fast shipping</li>
  <li>24/7 support</li>
  <li>Free returns</li>
</ul>
Key points
  • Only use <table> for genuinely tabular data — never for page layout.
  • <th> marks header cells and is announced differently by screen readers than <td>.
  • The scope attribute (scope="col" / scope="row") improves accessibility on complex tables.
  • <caption> gives a table an accessible title, right after the opening <table> tag.
  • colspan/rowspan merge cells for schedules and pricing grids, but need extra care to stay accessible.
  • A good sanity check: if reading the content row by row aloud doesn't make sense, it probably isn't real tabular data.
  • <thead> and <tbody> aren't required, but they make larger tables easier to style and to scan.
Try it yourself

Build a table comparing three products you know (rows) across price, and two other features (columns), with proper thead/tbody structure, a caption, and scope attributes on every header cell. Then add one cell that uses colspan to span two columns and check with a screen reader (or your browser's accessibility inspector) that it still announces sensibly.
