Basic MySQL queries

PHP · part of the free zero-to-hero guide

Builds on: Embedding PHP in HTML

PHP and MySQL have historically gone hand in hand — the mysqli extension (or, better, PDO covered in the next lesson) connects to a MySQL database and runs SQL queries directly from PHP code. Both extensions support prepared statements, and both are actively maintained, but mysqli is MySQL-specific while PDO works with multiple database engines through one API.

The single most important rule: never build a SQL query by concatenating raw user input into a string. Always use prepared statements with placeholders, which separate the query structure from the data and prevent SQL injection entirely, because the database driver sends the query and the values as two separate pieces rather than one interpolated string the database has to parse.

Connecting with mysqli can either throw exceptions on failure or fail silently depending on configuration — calling mysqli_report(MYSQLI_REPORT_ERROR | MYSQLI_REPORT_STRICT) near the top of a script makes connection and query errors throw catchable exceptions instead of requiring you to manually check a return value after every single call.

bind_param() requires a type string as its first argument, one character per bound value: i for integer, d for double/float, s for string, and b for binary blob data. Getting the type character wrong doesn't usually cause an error, but MySQL will coerce the value, which can silently produce subtly wrong results.

Beyond SELECT, the same prepared-statement pattern applies to INSERT, UPDATE, and DELETE — after an INSERT, $mysqli->insert_id (or $stmt->insert_id) gives you the auto-incremented primary key of the row you just created, useful for immediately referencing the new record without a second query.

Each web request typically opens its own short-lived database connection and lets PHP close it automatically at the end of the request (or does so explicitly with $stmt->close() and $mysqli->close()) — PHP does not keep a long-running connection pool between requests the way some server-based languages do, though persistent connections (mysqli_pconnect) exist for specific use cases.

query.php (mysqli, prepared statement)
<?php
$mysqli = new mysqli("localhost", "user", "password", "mydb");

$stmt = $mysqli->prepare("SELECT * FROM users WHERE id = ?");
$stmt->bind_param("i", $userId);
$stmt->execute();
$result = $stmt->get_result();
?>
insert.php (mysqli, prepared INSERT)
<?php
mysqli_report(MYSQLI_REPORT_ERROR | MYSQLI_REPORT_STRICT);
$mysqli = new mysqli("localhost", "user", "password", "mydb");

$stmt = $mysqli->prepare("INSERT INTO users (name, email) VALUES (?, ?)");
$stmt->bind_param("ss", $name, $email);
$stmt->execute();

echo "New user id: " . $mysqli->insert_id;
$stmt->close();
$mysqli->close();
?>
vulnerable_vs_fixed.php (a real SQL injection mistake)
<?php
// DANGEROUS: never do this — raw string concatenation of user input
$id = $_GET['id'];
$result = $mysqli->query("SELECT * FROM users WHERE id = $id");
// An attacker could pass ?id=1 OR 1=1 to dump every row,
// or ?id=1; DROP TABLE users to destroy data.

// SAFE: same query with a prepared statement
$stmt = $mysqli->prepare("SELECT * FROM users WHERE id = ?");
$stmt->bind_param("i", $_GET['id']);
$stmt->execute();
?>
Key points
  • Prepared statements with placeholders (?) are non-negotiable — never concatenate user input into a raw SQL string.
  • bind_param("i", $userId) tells mysqli the parameter's type (i for integer, s for string).
  • Always close database connections/statements or let PHP's garbage collection handle it — don't leave them open across requests.
  • PDO (next lesson) is generally preferred over mysqli today for its more consistent, database-agnostic API.
  • mysqli_report(MYSQLI_REPORT_ERROR | MYSQLI_REPORT_STRICT) turns silent failures into catchable exceptions, which is far easier to debug.
  • After an INSERT, $mysqli->insert_id gives you the new row's auto-increment primary key without a second query.
  • String concatenation of user input directly into SQL is the classic SQL injection vulnerability — prepared statements exist specifically to eliminate this risk.
  • Getting a bind_param type character wrong usually doesn't error loudly; MySQL coerces the value instead, which can produce quietly wrong results.
