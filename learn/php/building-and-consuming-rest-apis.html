Building and consuming REST APIs

PHP · part of the free zero-to-hero guide

Builds on: Testing with PHPUnit

A PHP REST API returns structured data (usually JSON) instead of HTML — set the response's content type explicitly and use json_encode()/json_decode() to convert between PHP arrays and JSON. Unlike a normal HTML page, an API's "view" is really just its response format, so most of the meaningful logic lives in validating the request and shaping the output correctly.

Consuming an external API from PHP typically uses curl or, more conveniently, an HTTP client library like Guzzle, which wraps curl with a much friendlier interface — handling things like automatic JSON encoding/decoding, timeouts, retries, and exceptions on non-2xx responses without you manually configuring cURL options for each request.

Meaningful REST APIs use HTTP status codes deliberately rather than always returning 200: 201 Created after successfully creating a resource, 204 No Content for a successful action with nothing to return, 400 Bad Request for malformed input, 401 Unauthorized when authentication is missing or invalid, 404 Not Found for a resource that doesn't exist, and 422 Unprocessable Entity for validation failures — these let API consumers handle different outcomes programmatically without parsing the response body just to find out what happened.

Most real APIs require authentication — common approaches include a static API key sent in a header, a Bearer token (often a JWT) sent as Authorization: Bearer <token>, or full OAuth2 for delegated third-party access. Whichever scheme is used, credentials should travel over HTTPS only and never be accepted as a URL query parameter, since query strings tend to end up logged in server access logs and browser history.

When a client sends a JSON request body (common for POST/PUT/PATCH to an API), that body doesn't arrive in $_POST the way an HTML form submission does — $_POST is only populated for form-encoded submissions. Instead, you read the raw request body from the php://input stream and decode it yourself with json_decode($raw, true).

Designing for the long term means thinking about versioning (commonly a /v1/ URL prefix or an Accept header) so you can change an API's shape later without breaking existing consumers, and rate limiting so a single misbehaving client can't overwhelm the service for everyone else.

api.php (plain PHP)
<?php
header("Content-Type: application/json");

$users = [["id" => 1, "name" => "Amina"]];
echo json_encode($users);
?>
create_user.php (reading a JSON body, using status codes)
<?php
header("Content-Type: application/json");

$raw = file_get_contents("php://input");
$data = json_decode($raw, true);

if (!isset($data['name']) || trim($data['name']) === '') {
    http_response_code(422);
    echo json_encode(["error" => "name is required"]);
    exit;
}

// ...save the user, get back a new id...
$newId = 42;

http_response_code(201);
echo json_encode(["id" => $newId, "name" => $data['name']]);
?>
consuming_api.php (Guzzle client)
<?php
require "vendor/autoload.php";

use GuzzleHttp\Client;
use GuzzleHttp\Exception\RequestException;

$client = new Client(['base_uri' => 'https://api.example.com', 'timeout' => 5]);

try {
    $response = $client->get('/users/1', [
        'headers' => ['Authorization' => 'Bearer ' . $apiToken],
    ]);
    $user = json_decode($response->getBody(), true);
} catch (RequestException $e) {
    echo "API call failed: " . $e->getMessage();
}
?>
Key points
  • Always set Content-Type: application/json explicitly when returning a JSON response.
  • Use appropriate HTTP status codes (http_response_code(404)) rather than always defaulting to 200.
  • Guzzle is the de facto standard HTTP client library for consuming external APIs from PHP.
  • Frameworks provide dedicated API resource/response classes (Laravel's API Resources, for instance) for more consistent JSON output.
  • A JSON request body doesn't populate $_POST — read it from php://input and decode it manually.
  • Never accept API credentials as a URL query parameter — they end up in logs and browser history; use headers over HTTPS instead.
  • Distinguish status codes purposefully: 201 for created, 204 for no content, 401 for missing/invalid auth, 422 for validation errors.
  • Version an API (e.g. a /v1/ prefix) from the start so its shape can evolve later without breaking existing consumers.
Try it yourself

Build a plain-PHP endpoint that returns a JSON array of items, setting the correct content type and status code. Then add a second endpoint that accepts a JSON POST body (read via php://input), validates a required field, and returns 201 with the created resource on success or 422 with an error message on invalid input. Finally, write a short script using curl or Guzzle that calls your own endpoint and prints the decoded response.
