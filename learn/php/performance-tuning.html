Performance tuning: OPcache, query profiling

PHP · part of the free zero-to-hero guide

Builds on: Caching and query optimization

OPcache is a built-in PHP extension that caches compiled bytecode in memory, skipping the parse-and-compile step on every request — enabling it in production is one of the single highest-leverage PHP performance changes you can make, often improving throughput dramatically for essentially no code changes.

opcache.memory_consumption sets how much memory OPcache can use for cached bytecode, and opcache.max_accelerated_files caps how many distinct PHP files it will cache — if either limit is set too low for the size of your codebase, OPcache starts evicting and recompiling files, which quietly erases most of the benefit. Monitoring OPcache's hit rate (via opcache_get_status()) reveals whether these limits are actually large enough.

opcache.validate_timestamps=0 in production means PHP stops checking whether a source file has changed since it was cached, squeezing out a bit more performance — but the tradeoff is that a code deploy afterward has no effect until the cache is manually cleared or the PHP-FPM/web server process is reloaded, which is why this setting should only be used alongside a deploy process that clears OPcache automatically.

Query profiling goes beyond a single EXPLAIN — MySQL's slow query log records every query that exceeds a configured time threshold from real production traffic, which surfaces problems you'd never think to test manually, since real usage patterns and data volumes are often very different from what you exercise locally.

Application-level profilers like Blackfire or Xdebug's built-in profiler go further than the database layer, showing exactly which PHP function calls consume the most wall-clock time and memory across a real request — this is what reveals bottlenecks that have nothing to do with the database at all, like an inefficient loop, excessive object creation, or a slow third-party library call.

The right general approach is to profile before optimizing, since the actual bottleneck is often not where intuition points — it's easy to spend hours hand-optimizing a piece of code that turns out to account for a tiny fraction of total request time, while the real cost (an N+1 query, a missing index, a synchronous call to a slow external API) sits somewhere else entirely. PHP 7.4+ also supports opcode preloading (opcache.preload), which loads specific frequently-used files into shared memory once at server startup rather than on first request, useful for framework core files that are always needed.

php.ini
opcache.enable=1
opcache.memory_consumption=128
opcache.max_accelerated_files=10000
opcache.validate_timestamps=0  ; disable in production, requires manual cache clear on deploy
my.cnf (enabling MySQL's slow query log)
[mysqld]
slow_query_log = 1
slow_query_log_file = /var/log/mysql/slow.log
long_query_time = 1  ; log any query taking longer than 1 second
log_queries_not_using_indexes = 1
Checking OPcache's hit rate at runtime
<?php
$status = opcache_get_status();

printf("Hit rate: %.2f%%\n", $status['opcache_statistics']['opcache_hit_rate']);
printf("Cached scripts: %d\n", $status['opcache_statistics']['num_cached_scripts']);
printf("Memory used: %.1f MB\n", $status['memory_usage']['used_memory'] / 1024 / 1024);
// A low hit rate or frequent restarts usually means memory_consumption
// or max_accelerated_files is set too low for this codebase.
?>
Key points
  • OPcache should always be enabled in production — the performance difference is substantial and the setup cost is minimal.
  • opcache.validate_timestamps=0 in production means you must clear the cache manually on every deploy.
  • MySQL's slow query log surfaces genuinely slow queries from real production traffic, not just what you think to test manually.
  • Profile before optimizing — the actual bottleneck is often not where intuition points.
  • opcache.memory_consumption and opcache.max_accelerated_files set too low will cause silent cache evictions that erase most of OPcache's benefit.
  • opcache_get_status() exposes the current hit rate at runtime, the most direct way to tell if OPcache is actually configured well.
  • Application profilers (Blackfire, Xdebug) reveal PHP-level bottlenecks — like inefficient loops or slow external calls — that a database-only view like EXPLAIN can't show.
  • Opcode preloading (opcache.preload, PHP 7.4+) loads frequently-used files into shared memory once at server startup rather than per-request.
Try it yourself

Enable OPcache in a local PHP environment and compare request response times for a moderately complex script before and after. Then enable MySQL's slow query log with a low long_query_time threshold, run your application for a bit, and inspect the log for any surprisingly slow queries you wouldn't have found just by reading the code.
