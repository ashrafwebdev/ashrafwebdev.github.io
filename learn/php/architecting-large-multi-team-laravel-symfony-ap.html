Architecting large, multi-team Laravel/Symfony applications

PHP · part of the free zero-to-hero guide

Builds on: Building and maintaining a framework or reusable package

At large scale, a single Laravel or Symfony app serving many teams benefits from clear internal boundaries — organizing code by domain/feature rather than only by technical layer (all models together, all controllers together), so teams can work on their area with minimal collision. A folder structure grouped by domain (Billing, Shipping, Catalog) makes it obvious which team owns which code, whereas a purely layer-based structure (all Models/, all Controllers/) scatters one team's feature across several unrelated top-level folders.

Techniques like modular service providers, well-defined internal APIs between domains, and strict code ownership boundaries (enforced by CI, not just convention) keep a large monolithic codebase maintainable as team size grows. A service provider scoped to one domain can register only that domain's routes, config, and bindings, keeping the framework's bootstrapping process itself organized along the same domain lines as the code.

Clear internal APIs between domains prevent every team's code from becoming tightly, invisibly coupled to every other team's — instead of the Billing domain reaching directly into Shipping's internal classes and database tables, it calls a small, deliberate interface (a service class or an internal event) that Shipping controls and can change its own internals behind. This is the same discipline microservices enforce via network boundaries, just applied inside one codebase.

A 'modular monolith' often captures microservices' organizational benefits — clear ownership, enforced boundaries, independent internal evolution — without their operational complexity, since there's still just one deployment, one database connection pool, and no network calls between domains. Many teams find this the right stopping point, splitting a domain out into a real separate service only once it has a genuinely distinct scaling, deployment, or team-ownership need that the monolith can no longer accommodate gracefully.

Domain events are a useful pattern for reducing coupling further: instead of the Billing domain calling directly into Shipping's code when an order is paid, it dispatches an OrderPaid event, and Shipping (along with anything else that cares — email notifications, analytics) listens for that event independently. Neither domain needs to know the other exists at the call-site level, only that a shared event contract exists.

CI checks — not just code review — can enforce architectural boundaries automatically, for example failing a build if static analysis detects one domain's code importing another domain's internal (non-public) classes directly. Relying on code review alone to catch this consistently across a large, fast-moving team tends to fail eventually; an automated check makes the boundary a fact about the codebase rather than a matter of individual reviewer diligence.

A domain-oriented folder structure
src/
  Billing/
    Models/
    Services/
    Http/Controllers/
    BillingServiceProvider.php
  Shipping/
    Models/
    Services/
    Http/Controllers/
    ShippingServiceProvider.php
Billing/BillingServiceProvider.php (a domain-scoped service provider)
<?php

namespace App\Billing;

use Illuminate\Support\ServiceProvider;

class BillingServiceProvider extends ServiceProvider
{
    public function boot(): void
    {
        $this->loadRoutesFrom(__DIR__ . '/routes.php');
        $this->loadMigrationsFrom(__DIR__ . '/Migrations');
    }
}
// Registering this in config/app.php keeps Billing's bootstrapping
// self-contained instead of scattered across shared global files.
Decoupling two domains with a domain event
<?php
// Billing/Services/PaymentService.php
namespace App\Billing\Services;

use App\Billing\Events\OrderPaid;

class PaymentService
{
    public function markPaid(int $orderId): void
    {
        // ...update the order's payment status...
        event(new OrderPaid($orderId)); // Billing has no idea who's listening
    }
}

// Shipping/Listeners/StartFulfillment.php
namespace App\Shipping\Listeners;

use App\Billing\Events\OrderPaid;

class StartFulfillment
{
    public function handle(OrderPaid $event): void
    {
        // Shipping reacts independently, with no direct call from Billing
    }
}
Key points
  • Organizing by domain/feature rather than purely by technical layer scales much better once multiple teams share one codebase.
  • Clear internal APIs between domains prevent every team's code from becoming tightly, invisibly coupled to every other team's.
  • A 'modular monolith' often captures microservices' organizational benefits without their operational complexity — worth considering before splitting into real services.
  • CI checks (not just code review) can enforce architectural boundaries, like preventing one domain from importing another's internals directly.
  • Domain-scoped service providers keep each domain's routes, config, and bindings self-contained rather than scattered through shared global files.
  • Domain events (like an OrderPaid event) let one domain react to another's changes without either domain calling into the other's code directly.
  • Split a domain into a genuinely separate service only once it has a distinct scaling, deployment, or ownership need the monolith can no longer serve well.
  • Relying only on code review to enforce a boundary tends to erode over time on a large, fast-moving team — automated static analysis in CI makes the rule durable.
Try it yourself

Take an existing Laravel/Symfony app organized by technical layer and reorganize one feature into a self-contained domain folder (models, services, controllers together). Then add a domain-scoped service provider for that folder, and replace one direct cross-domain method call with a dispatched domain event and a listener in the other domain, so the two domains no longer call each other's classes directly.
