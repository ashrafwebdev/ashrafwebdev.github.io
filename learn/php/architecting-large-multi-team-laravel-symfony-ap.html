Architecting large, multi-team Laravel/Symfony applications

PHP · part of the free zero-to-hero guide

At large scale, a single Laravel or Symfony app serving many teams benefits from clear internal boundaries — organizing code by domain/feature rather than only by technical layer (all models together, all controllers together), so teams can work on their area with minimal collision.

Techniques like modular service providers, well-defined internal APIs between domains, and strict code ownership boundaries (enforced by CI, not just convention) keep a large monolithic codebase maintainable as team size grows.

A domain-oriented folder structure
src/
  Billing/
    Models/
    Services/
    Http/Controllers/
  Shipping/
    Models/
    Services/
    Http/Controllers/
Key points
  • Organizing by domain/feature rather than purely by technical layer scales much better once multiple teams share one codebase.
  • Clear internal APIs between domains prevent every team's code from becoming tightly, invisibly coupled to every other team's.
  • A 'modular monolith' often captures microservices' organizational benefits without their operational complexity — worth considering before splitting into real services.
  • CI checks (not just code review) can enforce architectural boundaries, like preventing one domain from importing another's internals directly.
Try it yourself

Take an existing Laravel/Symfony app organized by technical layer and reorganize one feature into a self-contained domain folder (models, services, controllers together).
