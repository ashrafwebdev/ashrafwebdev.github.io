Contributing to PHP core or PHP RFCs

PHP · part of the free zero-to-hero guide

PHP itself evolves through a formal RFC (Request for Comments) process — anyone can propose a language change, and PHP internals developers discuss and vote on it publicly on the php.internals mailing list. A complete RFC typically includes a stated problem, a concrete proposal, backward compatibility impact, and alternatives that were considered and rejected, so the proposal can be evaluated on its full trade-offs rather than just its surface idea.

Voting rules differ by the kind of change being proposed: language changes generally require a two-thirds supermajority to pass, while changes that don't affect the language itself (like adding a new function to the standard library) can pass with a simple majority — a deliberate design to make backward-incompatible or far-reaching changes harder to sneak through than smaller, additive ones.

PHP RFCs are public and archived at php.net/rfc — reading past RFCs and their discussions teaches you a great deal about language design trade-offs, since the debate around a proposal (not just its final accepted text) usually surfaces the real reasoning: what alternatives were considered, what backward-compatibility concerns almost sank a proposal, and why the community ultimately landed where it did. Features like named arguments, enums, and the match expression all went through this exact public process.

For most developers, contributing to a major framework (Laravel, Symfony) or widely-used package is a more approachable path than PHP core itself — the C-level engine work has a steeper barrier to entry than most application-level PHP work, since php-src is written in C and requires understanding the Zend Engine's internals, not just PHP the language.

Getting a local build of php-src running is itself a useful first step even before writing any code — it lets you test a proposed patch, reproduce a reported core bug precisely, or simply see how a language feature is actually implemented under the hood, which is a different (and often more illuminating) kind of understanding than reading the RFC text alone.

A well-written bug report against php-src (with a minimal, reliably reproducing example and the exact PHP version it occurs on) is valuable even without a code fix attached — maintainers can triage and often fix a clearly reported bug far faster than a vague one, and clear reproductions are frequently the actual bottleneck, not available maintainer time. Major frameworks like Laravel and Symfony have active, welcoming contributor communities and clearly labeled beginner-friendly issues (often tagged "good first issue"), which is usually the most practical entry point into open source PHP contribution.

Terminal (building php-src from source)
git clone https://github.com/php/php-src.git
cd php-src
./buildconf
./configure --disable-all --enable-cli
make -j4

# Test your freshly built binary against a script:
./sapi/cli/php -v
./sapi/cli/php test.php
A language feature that went through the RFC process (named arguments, PHP 8.0)
<?php
function createUser(string $name, string $role = 'member', bool $active = true) {
    // ...
}

// Before named arguments: had to pass every positional arg in order
createUser('Amina', 'member', false);

// After the RFC was accepted: skip defaults, name only what you need
createUser('Amina', active: false);
Key points
  • PHP RFCs are public and archived — reading past RFCs and their discussions teaches you a great deal about language design trade-offs.
  • PHP core contributions require C knowledge; framework/package contributions generally don't.
  • A well-written bug report against php-src (with a minimal reproduction) is valuable even without a code fix.
  • Major frameworks like Laravel and Symfony have active, welcoming contributor communities and clearly labeled beginner-friendly issues.
  • Language-affecting RFCs need a two-thirds supermajority vote; smaller additive changes (like a new standard library function) need only a simple majority.
  • A complete RFC states the problem, the proposal, backward compatibility impact, and alternatives considered — not just the feature itself.
  • Building php-src locally lets you test a patch or reproduce a core bug precisely, which is often more illuminating than reading about the feature alone.
  • Features like named arguments, enums, and match all became part of PHP through this exact public RFC and voting process.
Try it yourself

Read one accepted PHP RFC from start to finish (php.net/rfc) and summarize the problem it solved and the trade-offs the community debated. Then find one currently open beginner-friendly issue on the Laravel or Symfony GitHub repository, read through its discussion, and write a short note on what a fix would need to address and why the maintainers haven't simply merged one yet.
