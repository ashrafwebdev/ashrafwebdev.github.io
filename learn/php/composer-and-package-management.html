Composer and package management

PHP · part of the free zero-to-hero guide

Composer is PHP's dependency manager — it installs libraries into a vendor folder and generates an autoloader so you can use any installed class without manually requiring each file. It solves the problem every non-trivial PHP project eventually hits: pulling in other people's well-tested code (a logging library, an HTTP client, a database toolkit) without hand-managing file includes and version conflicts.

composer.json declares your project's dependencies (and metadata like name, description, and autoloading rules); composer.lock pins the exact resolved versions of every dependency and sub-dependency, ensuring everyone on a team (and your production server) installs identical package versions rather than whatever happens to satisfy the version constraints at install time.

Version constraints in composer.json use symbols with specific meaning: an exact version like 1.2.3 pins that one version; a caret constraint like ^1.2 allows any 1.x release that's 1.2.0 or newer (following semantic versioning, no breaking changes expected); a tilde constraint like ~1.2 is similar but slightly stricter about how much of the version can change. Understanding these matters because composer update will happily jump to a newer version within the allowed range and potentially introduce behavior changes.

composer require adds a new dependency and updates both files at once; composer require --dev adds a development-only dependency (like PHPUnit) that won't be installed when a production deploy runs composer install --no-dev. composer dump-autoload regenerates the autoloader without touching any package versions — needed after adding a new class to your own PSR-4-mapped source folder if the autoloader hasn't picked it up yet (rare with modern Composer, but still useful to know).

PSR-4 autoloading (configured in the autoload section of composer.json) maps your own namespaces to folders, so your own classes autoload too, not just installed packages — this is what makes new App\Models\User() work without a manual require, as long as the class lives at the folder path matching its namespace.

vendor/ itself should be gitignored and regenerated with composer install, which reads composer.lock and installs the exact pinned versions — never edit anything inside vendor/ directly, since any change is lost the next time someone runs a fresh install.

Terminal
composer init
composer require monolog/monolog
composer require --dev phpunit/phpunit

# In your PHP entry file:
require "vendor/autoload.php";
composer.json
{
  "name": "yourname/blog",
  "require": {
    "php": ">=8.1",
    "monolog/monolog": "^3.0"
  },
  "require-dev": {
    "phpunit/phpunit": "^10.0"
  },
  "autoload": {
    "psr-4": {
      "App\\": "src/"
    }
  }
}
Using an autoloaded class
<?php
require "vendor/autoload.php";

use Monolog\Logger;
use Monolog\Handler\StreamHandler;

$log = new Logger('app');
$log->pushHandler(new StreamHandler(__DIR__ . '/app.log'));
$log->info('Application started.');
?>
Key points
  • require "vendor/autoload.php"; at the top of your entry file is what makes Composer-installed classes available via use.
  • Commit both composer.json and composer.lock — the lock file guarantees reproducible installs.
  • vendor/ itself should be gitignored and regenerated with composer install.
  • PSR-4 autoloading (configured in composer.json) maps your own namespaces to folders, so your own classes autoload too, not just installed packages.
  • Caret (^1.2) and tilde (~1.2) version constraints allow different amounts of automatic version drift on composer update.
  • composer require --dev keeps development-only tools (like PHPUnit) out of a production install run with --no-dev.
  • Never hand-edit files inside vendor/ — a fresh composer install discards any such changes.
  • composer dump-autoload regenerates the autoloader without changing any dependency versions.
Try it yourself

Run composer init in a new project, require a small utility package, and use one of its classes in a script. Then add a dev-only dependency like phpunit/phpunit with --dev, inspect the differences between the require and require-dev sections of the resulting composer.json, and confirm that composer install --no-dev skips installing the dev dependency.
