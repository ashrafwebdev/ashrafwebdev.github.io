Testing with PHPUnit

PHP · part of the free zero-to-hero guide

PHPUnit is the standard PHP testing framework — test classes extend TestCase, and test methods (prefixed test, or marked with a #[Test] attribute in modern versions) use assertion methods like assertEquals() and assertTrue() to check expected behavior. Running vendor/bin/phpunit discovers and runs every test class in the configured test directory, reporting pass/fail per test and a summary at the end.

Good tests are isolated and repeatable — a test shouldn't depend on another test's side effects, and database-touching tests typically run against a separate test database that gets reset between runs (often wrapped in a transaction that's rolled back after each test, so nothing persists between test methods).

setUp() runs before every test method in a class, and tearDown() runs after — a natural place to create shared test fixtures (like a fresh object under test) and clean them up, so each test method starts from the same known state rather than depending on execution order.

Real-world code often depends on things you don't want a unit test to actually invoke — an external API call, sending an email, or a slow database query. PHPUnit's mocking support ($this->createMock(SomeInterface::class)) lets you create a fake stand-in object that returns configured values for specific method calls, so you can test your code's logic in isolation without its real dependencies actually running.

Data providers let one test method run against many different input/expected-output pairs without duplicating the test body: a method marked #[DataProvider('provider')] (or the older @dataProvider annotation) pulls its arguments from another method that returns an array of argument sets, so adding a new case is just adding a new row rather than writing a whole new test method.

PHPUnit distinguishes assertEquals() (loose comparison, similar to ==) from assertSame() (strict comparison, similar to ===) — using the wrong one can let a test pass when it actually shouldn't, for example when comparing 0 and "" with assertEquals in older PHPUnit versions. Code coverage reports (generated with Xdebug or PCOV enabled) show which lines your test suite actually exercises, which is useful for finding untested logic but is not by itself proof the tests are meaningful.

CalculatorTest.php
<?php
use PHPUnit\Framework\TestCase;

class CalculatorTest extends TestCase {
    public function testAddsTwoNumbers(): void {
        $result = add(2, 3);
        $this->assertEquals(5, $result);
    }
}
DiscountTest.php (a data provider)
<?php
use PHPUnit\Framework\TestCase;
use PHPUnit\Framework\Attributes\DataProvider;

class DiscountTest extends TestCase {
    #[DataProvider('priceProvider')]
    public function testDiscountApplies(float $price, float $expected): void {
        $this->assertSame($expected, applyDiscount($price));
    }

    public static function priceProvider(): array {
        return [
            'below threshold' => [40.0, 40.0],
            'at threshold'    => [50.0, 45.0],
            'above threshold' => [100.0, 90.0],
        ];
    }
}
OrderServiceTest.php (mocking a dependency)
<?php
use PHPUnit\Framework\TestCase;

class OrderServiceTest extends TestCase {
    public function testPlaceOrderSendsConfirmationEmail(): void {
        $mailer = $this->createMock(MailerInterface::class);
        $mailer->expects($this->once())
               ->method('send')
               ->with($this->stringContains('Order confirmed'));

        $service = new OrderService($mailer);
        $service->place(['id' => 1, 'email' => 'a@example.com']);
        // No real email is sent — we only verify send() was called correctly.
    }
}
Key points
  • Test methods must be public and prefixed with test (or use a #[Test] attribute in modern PHPUnit).
  • setUp() runs before every test method in a class — a natural place for shared test fixtures.
  • Laravel and Symfony both provide testing helpers on top of PHPUnit for testing routes, database state, and HTTP responses directly.
  • Aim to test behavior and edge cases, not just the obvious happy path.
  • Data providers let one test method cover many input/output cases without duplicating test code.
  • Mocking (createMock()) isolates the code under test from slow or external real dependencies like APIs, email, or the filesystem.
  • assertSame() is strict (like ===); assertEquals() is loose (like ==) — picking the wrong one can hide a real bug.
  • Tests that touch a database should run against an isolated test database, often reset via a rolled-back transaction after each test.
Try it yourself

Write a PHPUnit test class with three test methods for a function you've written, covering a normal case, an edge case, and an invalid-input case. Then convert those three cases into a single test method driven by a data provider, and add one test that mocks a dependency (like a mailer or logger interface) to verify your code calls it correctly without invoking the real thing.
