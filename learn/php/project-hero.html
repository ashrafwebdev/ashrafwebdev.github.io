04 Hero stage capstone

An admin platform built like another team has to take it over

PHP · ties together everything in the Hero stage

This is the capstone of the whole PHP track: a production-shaped Laravel or Symfony app organized as a modular monolith, with at least two clearly separated domains, a real CI/CD pipeline, a documented architecture, and one piece of it extracted into its own installable Composer package. It touches every Hero-stage topic on purpose — performance tuning, package maintenance, and multi-team architecture — not as separate exercises but as one coherent piece of work.

The bar isn't "it works on my machine." It's "a new engineer could clone this, read one file, and know where to make a change safely — and a CI pipeline would catch them automatically if they broke a boundary or a test without them having to ask anyone."

This is meant to be genuinely portfolio-worthy: the kind of project you can walk an interviewer through and point at specific files as evidence of judgment, not just working code.

  • Performance tuning: OPcache, query profiling
  • Building and maintaining a framework or reusable package
  • Architecting large, multi-team Laravel/Symfony applications
  • Contributing to PHP core or PHP RFCs
Requirements
  • The app is organized as a modular monolith with at least two distinct domains, each in its own top-level namespace and folder with its own models, controllers/routes, and service provider or bundle registration — not one flat, app-wide Models/Controllers structure.
  • The two domains communicate only through a defined internal interface or a dispatched domain event and listener pair, never by one domain directly calling or importing the other's internal classes.
  • A CI pipeline (for example GitHub Actions) runs the full test suite and a PSR-12 style check on every push, and the build fails if either one fails.
  • A deploy step, triggered by CI on merge to the main branch, builds a deployable artifact or deploys to a real staging target and runs any pending database migrations automatically.
  • OPcache is enabled and confirmed active in the deploy target by checking opcache_get_status() there — not just set in a config file and assumed to be working.
  • At least one genuinely slow query is found, via EXPLAIN or the slow query log, and fixed, with before-and-after timings or query counts documented.
  • One domain's standalone logic is extracted into its own Composer package with its own composer.json, PSR-4 namespace, and at least one test, and installed back into the main app via composer require.
  • A short ARCHITECTURE.md explains the domain boundaries and what a new engineer needs to know before touching either domain's code.
Suggested approach
  1. Decide the two domain boundaries and the single interface or event contract between them before writing any feature code — retrofitting a boundary onto already-tangled code is far harder than starting with one.
  2. Build each domain fully — models, routes, a couple of tests — end to end before starting the second, so you have a working pattern to repeat rather than two half-finished domains at once.
  3. Get CI green on tests and the PSR-12 check first, on an unremarkable feature branch, before adding any deploy step, so a broken pipeline never has the chance to deploy broken code.
  4. Add the deploy step and confirm OPcache is actually active in that target, not merely configured.
  5. Profile the app under a realistic amount of seeded data, fix one real slow query, and only then extract one domain's logic into its own versioned package, once that domain's public boundary has proven stable enough to commit to.
Stretch goals
  • Add a static-analysis check to CI that fails the build if one domain's code imports another domain's non-public classes.
  • Enable OPcache preloading for the framework's core files and measure the boot-time difference with opcache_get_status() before and after.
  • Find one real, currently open "good first issue" on the Laravel or Symfony GitHub repository, submit a fix, and note what the maintainers' review taught you.
