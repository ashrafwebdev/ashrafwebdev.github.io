Caching and query optimization

PHP · part of the free zero-to-hero guide

Caching avoids redoing expensive work — storing a computed result (in memory via Redis/Memcached, or even a local file) and reusing it until it's stale, rather than recalculating or re-querying on every request. The performance gain can be dramatic for anything expensive and frequently requested, since reading from memory is orders of magnitude faster than a database round-trip.

Cache invalidation (knowing when to expire or update cached data) is often harder than the caching itself, and is famously called one of the two hard problems in computer science. A short time-to-live (TTL) is the simplest strategy — accept slightly stale data in exchange for simplicity — while explicitly clearing a cache key whenever the underlying data changes is more precise but requires remembering to do it everywhere that data can change.

Query optimization starts with knowing what's actually slow: EXPLAIN on a MySQL query shows how the database plans to execute it, revealing whether it's using indexes effectively or scanning entire tables. A query plan showing type: ALL on a large table is a red flag — it means MySQL is reading every single row rather than using an index to jump straight to the relevant ones.

Indexes speed up reads but slow down writes and use extra storage — every insert or update also has to update every index on that table, so add them deliberately on columns actually used in WHERE, JOIN, and ORDER BY clauses, not on every column just in case.

A very common and specifically PHP-and-ORM-flavored performance trap is the N+1 query problem: fetching a list of N records, then looping over them and running one more query per record to fetch related data (an author, a category), resulting in N+1 total queries instead of 2. Eager loading — telling the ORM up front to fetch the related data in the same batch, like Eloquent's with('author') — collapses this back down to a small, fixed number of queries regardless of how many rows are returned.

Caching can happen at several different layers, and picking the right one matters: a full page cache (caching entire rendered HTML output) saves the most work per request but is the least flexible, since any dynamic per-user content breaks it; an object or query cache (caching one expensive query's result) is more precise and composable; and HTTP-level caching (Cache-Control headers, letting the browser or a CDN cache a response) offloads work away from your server entirely for content that doesn't need to be regenerated per request.

A simple cache pattern with Redis
<?php
$cacheKey = "user:$userId";
$cached = $redis->get($cacheKey);

if ($cached) {
    $user = json_decode($cached, true);
} else {
    $user = fetchUserFromDatabase($userId);
    $redis->setex($cacheKey, 300, json_encode($user)); // cache 5 minutes
}
?>
EXPLAIN and adding a missing index
-- Before: MySQL scans the whole table (type: ALL)
EXPLAIN SELECT * FROM orders WHERE customer_email = 'a@example.com';

-- Add an index on the column used in the WHERE clause
CREATE INDEX idx_orders_customer_email ON orders (customer_email);

-- After: EXPLAIN now shows type: ref, using the new index
EXPLAIN SELECT * FROM orders WHERE customer_email = 'a@example.com';
n_plus_one.php (a common ORM performance mistake)
<?php
// BAD: 1 query for posts, then 1 more query PER post for its author = N+1 queries
$posts = Post::all();
foreach ($posts as $post) {
    echo $post->author->name; // triggers a separate query each time
}

// GOOD: eager-load the relationship up front = 2 queries total, regardless of N
$posts = Post::with('author')->get();
foreach ($posts as $post) {
    echo $post->author->name; // already loaded, no extra query
}
?>
Key points
  • Cache invalidation (knowing when to expire or update cached data) is often harder than the caching itself — plan for it deliberately.
  • EXPLAIN SELECT ... reveals whether MySQL is using an index or performing a full table scan.
  • Indexes speed up reads but slow down writes and use extra storage — add them deliberately, not everywhere.
  • Cache at the layer that gives the best return: a full page cache saves the most work, but an object/query cache is more precise.
  • The N+1 query problem is one of the most common PHP/ORM performance mistakes — one query per row in a loop instead of a single batched query.
  • Eager loading (like Eloquent's with()) fixes N+1 problems by fetching related data in the same small batch of queries.
  • A query plan showing type: ALL on a large table is a strong signal a useful index is missing.
  • HTTP-level caching (Cache-Control headers) can offload repeat work to the browser or a CDN entirely, bypassing your server.
Try it yourself

Add a Redis (or file-based) cache in front of a slow database query, and confirm the second request is significantly faster than the first. Then run EXPLAIN on a query against a table without an index on its WHERE column, add the missing index, and compare the EXPLAIN output before and after. Finally, find or construct an N+1 query pattern in a loop and fix it with eager loading, counting the actual number of queries run before and after.
