Sessions, cookies, and basic auth

PHP · part of the free zero-to-hero guide

Builds on: Working with MySQL via PDO

Cookies store small pieces of data directly in the browser, sent with every subsequent request to the same site. Sessions store data server-side, with only a session ID cookie sent to the browser — better for anything sensitive, since the actual data never leaves the server. Cookies are also what make sessions work in the first place: without the session ID cookie, PHP would have no way to associate a request with previously stored session data.

A basic login flow: verify submitted credentials against a hashed password in the database, then store the user's ID in $_SESSION to mark them as logged in for subsequent requests. Every protected page then checks whether $_SESSION['user_id'] is set before allowing access, redirecting to the login page otherwise.

A real security detail often missed: call session_regenerate_id(true) immediately after a successful login, which issues the user a brand-new session ID while keeping their session data. This defends against session fixation attacks, where an attacker tricks a victim into using a session ID the attacker already knows, then hijacks the now-authenticated session once the victim logs in.

Cookies accept several security-relevant attributes when set: Secure (only sent over HTTPS), HttpOnly (invisible to JavaScript, blocking a whole class of cookie-theft via XSS), and SameSite (controls whether the cookie is sent on cross-site requests, helping prevent CSRF). PHP's session cookie can be configured with all three via session_set_cookie_params() before session_start(), or in php.ini.

setcookie(name, value, expire, path, domain, secure, httponly) sets an ordinary cookie directly, independent of sessions — useful for things like a "remember this browser" flag or a non-sensitive user preference. Like any other header, setcookie() must be called before any output is sent to the browser, the same constraint that applies to header().

Logging out means both destroying the server-side session data with session_destroy() and clearing the session cookie itself — destroying the session alone leaves a now-useless cookie in the browser, and forgetting to clear it is a common incomplete-logout bug.

login.php
<?php
session_start();

// After verifying credentials against the database:
if (password_verify($submittedPassword, $hashedPasswordFromDb)) {
    session_regenerate_id(true); // defend against session fixation
    $_SESSION['user_id'] = $user['id'];
    header("Location: /dashboard.php");
    exit;
}
?>
logout.php
<?php
session_start();

$_SESSION = [];

// Also clear the session cookie itself, not just server-side data
if (ini_get("session.use_cookies")) {
    $params = session_get_cookie_params();
    setcookie(session_name(), '', time() - 42000,
        $params["path"], $params["domain"], $params["secure"], $params["httponly"]);
}

session_destroy();
header("Location: /login.php");
exit;
?>
secure_cookie_example.php
<?php
session_set_cookie_params([
    'lifetime' => 0,
    'path' => '/',
    'secure' => true,   // only sent over HTTPS
    'httponly' => true, // invisible to JavaScript
    'samesite' => 'Lax',
]);
session_start();

// A plain, non-session cookie for a low-stakes preference
setcookie('theme', 'dark', time() + 60 * 60 * 24 * 30, '/', '', true, true);
?>
Key points
  • Always hash passwords with password_hash() and verify with password_verify() — never store or compare plain-text passwords.
  • Call exit; right after a header("Location: ...") redirect — code after it still executes otherwise.
  • Session data lives server-side; only an opaque session ID is stored in the visitor's cookie.
  • Set the session cookie's Secure and HttpOnly flags in production to reduce interception and script-access risk.
  • Call session_regenerate_id(true) right after login to prevent session fixation attacks.
  • Logging out should clear both the server-side session data (session_destroy()) and the cookie itself — clearing only one leaves an incomplete logout.
  • setcookie(), like header(), must be called before any output is sent to the browser.
  • The SameSite cookie attribute helps mitigate CSRF by controlling whether a cookie is sent along with cross-site requests.
Try it yourself

Build a minimal login script that checks a submitted password with password_verify against a stored hash, and sets a session variable on success. Add session_regenerate_id(true) right after a successful login, then write a matching logout.php that clears both the session data and the session cookie, and confirm that visiting a protected page after logout correctly redirects back to the login form.
