Classes, prototypes, and inheritance

JavaScript · part of the free zero-to-hero guide

JavaScript's class syntax is a cleaner, more familiar-looking way to write what the language has always done under the hood through prototypes: every object carries a hidden internal link to another object (its prototype), and looking up a property or method that isn't found directly on the object falls back to searching that linked prototype, and so on up what's called the prototype chain, until it either finds a match or reaches the end.

A class's regular methods (anything defined without special syntax inside the class body) live on the class's prototype object, not copied individually onto every instance — this is memory-efficient, since a thousand instances of the same class share one single copy of each method rather than each carrying its own duplicate. Instance fields set inside the constructor with this.name = ..., by contrast, do live directly on each individual instance, since they hold data that's genuinely different per object.

extends sets up inheritance between two classes, and inside a subclass constructor, super(...) must be called — and called before any use of this — because it's what actually runs the parent class's constructor and initializes the inherited part of the instance; using this before calling super() throws a ReferenceError. Outside the constructor, super.methodName() calls the parent class's version of an overridden method, useful when a subclass wants to extend rather than completely replace the parent's behavior.

Overriding a method in a subclass — giving it a method with the same name as one on the parent, so the subclass's version takes precedence — is called method overriding. JavaScript does not support method overloading (defining multiple versions of the same method name that differ only by parameter types or count, as some other languages allow); a class can only have one method of a given name, and any parameter-count flexibility has to be handled manually inside that single method.

Modern JavaScript classes also support private fields and methods, written with a # prefix (#balance), which are genuinely inaccessible from outside the class — not just discouraged by convention, but enforced by the language itself, unlike a regular property that anyone can still reach even if you name it with a leading underscore as a hint not to touch it. Static members (static keyword) belong to the class itself rather than to instances, useful for utility methods or shared configuration that doesn't need a specific instance to make sense.

instanceof checks whether an object's prototype chain includes a given class's prototype, which is useful for runtime type checks, though it has real limits — it can give surprising answers across different execution contexts (like different iframes or worker threads, where each has technically distinct built-in prototypes), and it says nothing about an object's actual shape beyond that inheritance chain.

classes.js
class Animal {
  constructor(name) { this.name = name; }
  speak() { return `${this.name} makes a sound.`; }
}

class Dog extends Animal {
  speak() { return `${this.name} barks.`; }
}

const rex = new Dog("Rex");
console.log(rex.speak());
private-fields-and-super.js
class BankAccount {
  #balance; // truly private, not reachable from outside the class

  constructor(openingBalance) {
    this.#balance = openingBalance;
  }

  deposit(amount) {
    this.#balance += amount;
    return this.#balance;
  }

  get balance() { return this.#balance; } // read-only public view
}

class SavingsAccount extends BankAccount {
  constructor(openingBalance, rate) {
    super(openingBalance); // must run before using `this`
    this.rate = rate;
  }
  applyInterest() {
    return this.deposit(this.balance * this.rate); // extends parent behavior
  }
}

const acct = new SavingsAccount(1000, 0.05);
console.log(acct.applyInterest()); // 1050
// console.log(acct.#balance); // SyntaxError: private field, inaccessible here
prototype-chain-under-the-hood.js
// What `class` is doing under the hood, roughly, with plain prototypes
function Animal(name) {
  this.name = name;
}
Animal.prototype.speak = function () {
  return `${this.name} makes a sound.`;
};

const cat = new Animal("Whiskers");
console.log(cat.speak());                     // found via the prototype chain
console.log(cat.hasOwnProperty("speak"));      // false — it's on the prototype
console.log(Object.getPrototypeOf(cat) === Animal.prototype); // true
Key points
  • Under the hood, class methods live on the prototype, shared across all instances — not copied onto each object.
  • extends sets up inheritance; super() must be called before using this in a subclass constructor.
  • Overriding a method in a subclass (like speak() above) is called method overriding, not overloading — JS doesn't support true overloading.
  • Private fields (#balance) are genuinely inaccessible from outside the class, unlike a conventionally-named-but-still-public underscore property.
  • static members belong to the class itself, not to instances — useful for utility methods that don't need instance data.
  • instanceof checks whether an object's prototype chain includes a given class, but gives unreliable answers across different execution contexts like iframes.
  • Instance fields set with this.field = ... in the constructor live on each individual instance; regular methods live once on the shared prototype.
