The event loop, microtasks, and macrotasks in depth

JavaScript · part of the free zero-to-hero guide

JavaScript runs on a single thread — only one piece of JavaScript code executes at any given moment — yet it never blocks the whole program on slow operations like network requests or timers, because of the event loop. The mental model: all currently-queued synchronous code runs to completion first, then the entire microtask queue is drained completely (every microtask, including any new ones queued by earlier microtasks), then exactly one macrotask is picked up and run, then the microtask queue is drained again, and the cycle repeats indefinitely.

Promise callbacks (.then(), .catch(), .finally(), and anything after an await) are microtasks. setTimeout(), setInterval(), and I/O callbacks (like a completed file read in Node, or a UI event dispatch) are macrotasks. This ordering explains a classic, genuinely surprising result: a Promise.resolve().then(fn) queued before a setTimeout(fn, 0) always runs first, even though both superficially look like they should run 'immediately' — the entire microtask queue must fully drain before the event loop is even allowed to look at the next macrotask.

This distinction matters practically, not just as trivia: code that depends on execution order across a mix of promises and timers can behave unexpectedly if you assume 'whatever was scheduled first runs first' without accounting for which queue each callback actually lands in. A common real bug: expecting a setTimeout(fn, 0) to run before a chain of several .then() callbacks, when in fact every one of those microtasks runs first, no matter how many are queued, because the timeout is stuck waiting for its turn as a macrotask.

A genuinely rare but real footgun: a microtask that queues another microtask (for example, a .then() handler that itself returns a promise which schedules further .then() handlers, recursively) can, in principle, starve macrotasks indefinitely, since the microtask queue must be fully emptied before any macrotask gets a turn — if microtasks keep refilling the queue faster than it drains, timers, rendering, and I/O callbacks are all delayed behind them.

The browser also inserts rendering (style recalculation, layout, paint) at specific points in this cycle, generally after the microtask queue drains and before the next macrotask, though the precise timing is more nuanced and partly implementation-defined — a practical consequence is that even a synchronous loop packed with many DOM writes won't visually update the page until that whole script finishes and the microtask queue is empty, which is why long synchronous work makes a page feel frozen even though the DOM was, technically, already being updated in memory the whole time.

Node.js has its own extra wrinkles worth knowing if you work there: process.nextTick() queues a callback that runs even before the regular microtask queue (including before promise callbacks), and Node's event loop is organized into distinct phases (timers, pending callbacks, poll, check, close callbacks) that don't map exactly onto the simpler browser model — worth a dedicated look once you're doing real backend work in Node.

eventloop.js
console.log("1: sync");

setTimeout(() => console.log("2: macrotask (setTimeout)"), 0);

Promise.resolve().then(() => console.log("3: microtask (promise)"));

console.log("4: sync");

// Actual order: 1, 4, 3, 2
chained-microtasks-vs-timeout.js
console.log("start");

setTimeout(() => console.log("timeout"), 0);

Promise.resolve()
  .then(() => console.log("promise 1"))
  .then(() => console.log("promise 2"))
  .then(() => console.log("promise 3"));

console.log("end");

// Order: start, end, promise 1, promise 2, promise 3, timeout
// All three chained microtasks drain before the single macrotask runs,
// no matter how many .then() links are in the chain.
await-pauses-at-microtask-boundaries.js
async function demo() {
  console.log("A");
  await null; // yields, resuming as a microtask
  console.log("C"); // runs after any synchronous code that follows the call
}

console.log("start");
demo();
console.log("B");

// Order: start, A, B, C
// `await` splits the async function: everything before the first await
// runs synchronously; everything after resumes later as a microtask.
Key points
  • Order of execution: all synchronous code, then the entire microtask queue drains, then one macrotask, then the microtask queue drains again, repeat.
  • Promise callbacks (.then, .catch, code after await) are microtasks; setTimeout/setInterval/I-O callbacks are macrotasks.
  • A chain of any number of .then() callbacks fully drains before a competing setTimeout(fn, 0) ever runs, regardless of chain length.
  • A microtask that keeps queuing more microtasks can starve macrotasks indefinitely — a real, if rare, footgun.
  • Code before the first await in an async function runs synchronously; everything after it resumes later as a microtask.
  • Understanding this ordering explains most 'why did this run in that order' bugs in code mixing promises and timers.
  • Node.js's process.nextTick() runs even before the regular microtask queue, and Node's event loop has distinct phases that don't map directly onto the browser's simpler model.
