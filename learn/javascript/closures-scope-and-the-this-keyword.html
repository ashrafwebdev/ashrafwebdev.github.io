Closures, scope, and the 'this' keyword

JavaScript · part of the free zero-to-hero guide

Builds on: Promises and async/await in depth

A closure is what happens whenever a function is defined inside another function and keeps access to that outer function's variables even after the outer function has already finished running and returned. This isn't a special feature you opt into — every function in JavaScript forms a closure over the scope it was defined in, automatically; it's just usually invisible until you return an inner function from an outer one and only then notice the outer variables are still alive.

Closures are the mechanism behind private state in JavaScript before (and still alongside) classes with private fields: a variable declared inside an outer function is completely inaccessible from outside it, but an inner function returned from that outer function can still read and modify it, giving you a controlled, encapsulated piece of mutable state with no way to reach in and corrupt it directly.

A classic closure pitfall involves loops and var: because var is function-scoped, not block-scoped, a closure created inside a var-based for-loop captures the same single variable, not a fresh one per iteration, so all the closures end up seeing the final value of the loop variable after the loop finishes. Switching to let fixes this automatically, since let creates a genuinely new binding for each iteration of the loop.

this is unlike ordinary variables — it isn't determined by where a regular function is written, but by how it's called at the call site. Calling obj.method() binds this to obj. Calling the same function as a bare, unattached function binds this to undefined in strict mode (or the global object in loose mode) — which is exactly why passing a method as a bare callback, like setTimeout(obj.method), silently loses its intended this and is one of the single most common sources of confusion for people learning JavaScript.

Arrow functions sidestep this entire problem by design: they don't have their own this binding at all, and instead capture this lexically from the scope they were written in, exactly like a closure captures any other outer variable. This is precisely why arrow functions are the standard choice for callbacks inside class methods and event handlers — they automatically keep referring to the surrounding object's this, with nothing extra required.

When you do need to explicitly control what this refers to, three methods exist: .call(thisArg, ...args) and .apply(thisArg, argsArray) both invoke the function immediately with a given this (differing only in how arguments are passed), while .bind(thisArg) returns a new function permanently locked to that this, which can then be called (or passed around as a callback) later without losing its binding.

closures.js
function makeCounter() {
  let count = 0; // captured by the closure
  return function () {
    count += 1;
    return count;
  };
}

const counter = makeCounter();
console.log(counter(), counter(), counter()); // 1 2 3
var-loop-closure-bug.js
// Bug: var is function-scoped, so all three closures share one `i`
const broken = [];
for (var i = 0; i < 3; i++) {
  broken.push(() => console.log("var:", i));
}
broken.forEach((fn) => fn()); // var: 3, var: 3, var: 3

// Fix: let creates a fresh binding per iteration
const fixed = [];
for (let j = 0; j < 3; j++) {
  fixed.push(() => console.log("let:", j));
}
fixed.forEach((fn) => fn()); // let: 0, let: 1, let: 2
this-binding.js
const counter = {
  count: 0,
  increment() { this.count++; },
};

counter.increment();       // fine, `this` is `counter`
console.log(counter.count); // 1

const bareIncrement = counter.increment;
// bareIncrement(); // TypeError-ish bug: `this` is undefined here

// Fix with bind:
const bound = counter.increment.bind(counter);
bound(); // works, `this` is locked to counter
console.log(counter.count); // 2

// Arrow functions avoid the problem entirely by inheriting `this`:
const counterWithArrow = {
  count: 0,
  incrementLater() {
    setTimeout(() => { this.count++; }, 100); // `this` still counterWithArrow
  },
};
Key points
  • A closure keeps a reference to its outer variables alive as long as the closure itself is reachable, even after the outer function returns.
  • Closures are the classic way to build private state in JavaScript: outer variables are invisible from outside, but reachable and mutable through returned inner functions.
  • A var-based for-loop shares one variable across every iteration's closures; let creates a fresh binding per iteration, which is usually what you actually want.
  • Arrow functions inherit this from where they're defined, not how they're called — this is why they're preferred inside class methods and callbacks.
  • A regular function's this depends entirely on the call site: obj.method() binds this to obj; a bare function call binds it to undefined in strict mode.
  • Passing a method as a bare callback (setTimeout(obj.method)) silently loses its this — bind it first, or wrap it in an arrow function.
  • .call()/.apply() invoke a function immediately with a chosen this; .bind() returns a new function permanently locked to that this for later use.
Try it yourself

Write a makeCounter-style closure that supports increment, decrement, and reset, each remembering the same private count variable. Then reproduce the classic var-in-a-loop closure bug with three functions pushed into an array, fix it by switching to let, and finally write an object with a method that loses its this when passed as a bare callback to setTimeout, fixing it with both .bind() and an arrow function.
