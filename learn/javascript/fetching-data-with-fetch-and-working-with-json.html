Fetching data with fetch() and working with JSON

JavaScript · part of the free zero-to-hero guide

Builds on: Array/object methods: map, filter, reduce, destructuring

fetch() makes an HTTP request from JavaScript and returns a Promise that resolves to a Response object once the response headers have arrived — the body itself hasn't necessarily been read yet at that point. Most APIs communicate in JSON, so you almost always chain a call to .json(), which reads and parses the response body into a plain JavaScript object or array; .json() returns its own Promise too, since reading the body is itself an asynchronous operation.

A critical and frequently-missed detail: fetch() only rejects its promise on genuine network failure — DNS resolution failing, no connectivity, a CORS block. It does not reject on HTTP error status codes like 404 or 500; a failed request with a 500 status still resolves successfully as far as fetch() is concerned. That means you must check response.ok (or response.status) yourself and throw an error explicitly if the request wasn't actually successful, or your error handling will silently never trigger for failed requests.

Sending data (POST, PUT, PATCH) requires passing a second options object to fetch() with at least method, a headers object including "Content-Type": "application/json", and a body that is a JSON string — plain JavaScript objects are not automatically serialized, so you need JSON.stringify() yourself before sending, and correspondingly JSON.parse() (or .json()) on the way back.

JSON.stringify() and JSON.parse() are the underlying tools for converting between JavaScript values and JSON text more broadly, useful even outside of networking — for example, persisting an object to localStorage, which only stores strings. Be aware JSON can't represent everything JavaScript can: functions, undefined values, and symbols are silently dropped when stringifying, dates become plain strings (not Date objects) and need to be re-parsed manually, and circular references throw an error outright.

Real network calls need genuine error handling on two separate fronts: network-level failures (wrap the fetch/await in a try/catch to handle offline states, timeouts, or DNS errors gracefully) and application-level failures (check response.ok and read the error body, since a well-built API often returns a useful JSON error message alongside a 4xx/5xx status that's worth surfacing to the user or the logs).

For requests that might hang indefinitely, pass an AbortController's signal into the fetch options — this lets you cancel an in-flight request, either after a timeout you set yourself, or when the user navigates away or triggers a newer request that should supersede the old one (a common pattern in live search-as-you-type inputs, to avoid an old, slow response overwriting a newer one).

api.js
async function getUser(id) {
  const response = await fetch(`https://api.example.com/users/${id}`);
  if (!response.ok) {
    throw new Error(`Request failed: ${response.status}`);
  }
  return response.json();
}
posting-json-with-error-handling.js
async function createUser(user) {
  try {
    const response = await fetch("https://api.example.com/users", {
      method: "POST",
      headers: { "Content-Type": "application/json" },
      body: JSON.stringify(user),
    });

    if (!response.ok) {
      const errorBody = await response.json().catch(() => null);
      throw new Error(errorBody?.message || `Request failed: ${response.status}`);
    }

    return await response.json();
  } catch (err) {
    console.error("createUser failed:", err.message);
    throw err;
  }
}
cancelling-with-abortcontroller.js
async function searchUsers(query) {
  const controller = new AbortController();
  const timeoutId = setTimeout(() => controller.abort(), 5000);

  try {
    const response = await fetch(
      `https://api.example.com/search?q=${encodeURIComponent(query)}`,
      { signal: controller.signal }
    );
    return await response.json();
  } catch (err) {
    if (err.name === "AbortError") {
      console.warn("Search request timed out");
      return [];
    }
    throw err;
  } finally {
    clearTimeout(timeoutId);
  }
}
Key points
  • fetch() does NOT reject on HTTP error statuses (404, 500) — always check response.ok yourself and throw explicitly if needed.
  • .json() itself returns a Promise too, so it needs its own await — reading the body is an async step separate from receiving the headers.
  • POST/PUT requests need a method, headers with a content-type, and a JSON.stringify()-ed body in the fetch options object.
  • JSON.stringify() silently drops functions, undefined, and symbols, and turns dates into plain strings that need manual re-parsing.
  • Wrap fetch calls in try/catch to handle genuine network failures (offline, DNS errors, CORS blocks) separately from application-level HTTP errors.
  • AbortController lets you cancel an in-flight fetch — useful for timeouts and for cancelling stale requests in live-search style inputs.
  • A well-designed API often returns a useful JSON error body alongside a 4xx/5xx status — read and surface it instead of only logging the status code.
Try it yourself

Write an async function that fetches data from a free public API (like https://jsonplaceholder.typicode.com/users) and logs each user's name. Then extend it to POST a new resource with a JSON body and proper headers, checking response.ok and throwing a descriptive error on failure, and finally add an AbortController-based timeout so the request gives up after 5 seconds instead of hanging indefinitely.
