03 Advanced stage capstone

A tiny validation library, shipped as tested ES modules

JavaScript · ties together everything in the Advanced stage

This project moves you from building visible pages to building a piece of reusable, general-purpose code meant to be imported and used by other code — a small form-validation library that any project could import and run against a set of field values. It's the first project in this track that isn't really "about" a UI at all; its correctness is proven entirely by an automated test suite, the way real production JavaScript libraries are actually judged.

The library has to genuinely use everything this stage covers: it's organized as real ES modules with proper import/export boundaries, its core class relies on prototypal behavior and correctly scoped this, at least one validation rule is asynchronous and must be properly awaited, and every piece of behavior — not just the happy path — is backed by a Jest or Vitest test.

The constraint that makes this a genuine test of the stage: nothing gets marked done by eyeballing console output. If a behavior isn't covered by an automated test, for the purposes of this project it doesn't count as working yet.

  • Promises and async/await in depth
  • Closures, scope, and the 'this' keyword
  • Classes, prototypes, and inheritance
  • ES Modules and code organization
  • Error handling patterns and unit testing (Jest/Vitest)
Requirements
  • The library is split across at least three real ES modules (for example rules.js, validator.js, and index.js) connected with genuine import/export statements — not one file containing everything.
  • A Validator class whose instances are constructed as new Validator(rules), where rules maps field names to arrays of validation functions to run against that field.
  • At least one built-in synchronous rule (like required or minLength) and at least one asynchronous rule that returns a real Promise (for example, a simulated "is this username already taken" check using a delayed Promise) — validate() must correctly await every rule, sync and async alike, before deciding pass or fail.
  • A closure is used somewhere in the library to keep genuine internal state private — for example a cache of recent validation results — that is not exposed as a public property a consumer could accidentally read or overwrite.
  • A Jest or Vitest test suite covering at minimum: a fully passing case, a failing synchronous-rule case, a failing asynchronous-rule case, and at least one edge case such as an empty input or a field with no rules attached.
  • Every failure the library reports is a real Error object with a specific, readable message — never a bare string, a silent false, or an unhandled rejection.
  • A short comment block at the top of index.js documents the library's public API — how to construct a validator, what validate() returns, and what shape the errors take — written so a stranger could use it without reading the implementation.
Suggested approach
  1. Sketch the public API on paper before writing any implementation — what does calling code actually look like when it constructs a validator and reads the result — since this is a library other code will consume, not a page you're styling as you go.
  2. Build the core Validator class and the synchronous rules first, and get simple passing and failing tests green before introducing anything asynchronous.
  3. Add the asynchronous rule and update validate() to properly await every rule (reaching for Promise.all() is worth it here) before it resolves with a final result.
  4. Add the closure-based private state once the core validation logic is solid and already covered by tests, so you can be confident the caching layer isn't hiding a bug in the logic underneath it.
  5. Go back through the test suite deliberately looking for the edge cases you skipped on the first pass — empty objects, missing fields, fields with zero rules — and add tests for each one you find.
Stretch goals
  • Introduce a real class hierarchy — a base Rule class with subclasses for each rule type — using prototypal inheritance intentionally instead of plain validator functions.
  • Run your test suite with coverage reporting turned on, and push every module toward full branch coverage, not just full line coverage.
  • Install the library into a separate throwaway project with npm link (or as a local file dependency) and confirm the module boundaries actually work when consumed from outside your own test runner.
