Console debugging

JavaScript · part of the free zero-to-hero guide

Builds on: Arrays and objects basics

console.log() is the fastest feedback loop in JavaScript — print a value and see exactly what it is, right now, without setting up any tooling. But the console object has a whole family of more specialized methods worth knowing: console.table() renders arrays of objects as an actual readable table, console.error() and console.warn() print with distinct severity styling and, crucially, a full stack trace, and console.group()/console.groupEnd() let you visually nest related log output.

console.log() accepts multiple arguments and prints them space-separated on one line, so console.log("user:", user) is both clearer and faster to type than building a concatenated string. It also supports format specifiers (%s, %d, %o) and, in browsers, %c for CSS-styled output — rarely necessary, but occasionally useful for making a specific log stand out.

The debugger; statement is a real breakpoint written directly in your source code: when DevTools is open, execution pauses right there, and you can inspect every variable in scope, step line by line, and watch the call stack — a far more powerful way to understand a bug than sprinkling console.log calls everywhere and guessing where to put them next.

Browser DevTools also let you set breakpoints without touching the source at all, including conditional breakpoints (only pause when a specific expression is true) and DOM breakpoints (pause when a specific element is modified or removed) — both are enormously useful once a bug depends on something happening many iterations into a loop or deep in a rendering cycle.

For asynchronous code, console.trace() prints the call stack at the point it's called, which helps answer 'who called this function, and from where' — a question that plain console.log can't answer on its own, especially once callbacks and promises are involved and the call stack no longer matches the code's visual layout.

It's easy to forget stray debugging output in code that ships. Treat console.log as a temporary tool, not application output — a linter rule (like no-console) or a quick project-wide search before committing catches most leftover calls before they reach production.

debug.js
const users = [
  { name: "Amina", age: 27 },
  { name: "Yusuf", age: 30 },
];

console.table(users); // renders a readable table in DevTools
console.error("This looks like a problem");
grouping-and-trace.js
function processOrder(order) {
  console.group(`Order #${order.id}`);
  console.log("Customer:", order.customer);
  console.log("Item count:", order.items.length);
  if (order.items.length === 0) {
    console.warn("Empty order — check the cart flow");
  }
  console.groupEnd();
}

function whoCalledThis() {
  console.trace("call stack at this point");
}
debugger-statement.js
function calculateDiscount(price, coupon) {
  debugger; // execution pauses here when DevTools is open
  const rate = coupon === "SAVE10" ? 0.1 : 0;
  return price * (1 - rate);
}

// Open DevTools, then call calculateDiscount(100, "SAVE10")
// and step through line by line, watching `rate` change.
Key points
  • console.table() is far more readable than console.log() for arrays of objects.
  • console.error()/console.warn() print a full stack trace alongside styled output — more informative than plain log for problems.
  • debugger; in your code pauses execution right there if DevTools is open — a real breakpoint without clicking anything.
  • DevTools conditional and DOM breakpoints let you pause exactly when a specific expression becomes true or a specific element changes, without editing source.
  • console.trace() answers 'who called this, and from where' — invaluable once callbacks and async code obscure the visual call structure.
  • console.group()/console.groupEnd() visually nest related log lines, making busy output much easier to scan.
  • Remove stray console.log calls before shipping — they're a debugging tool, not application output; a lint rule catches most stragglers automatically.
  • The Network tab (not just Console) is often where real debugging of API issues actually happens.
Try it yourself

Add a debugger statement inside a function, open DevTools, trigger the function, and step through it line by line watching a local variable change. Then rewrite the same function's logging using console.group to nest related messages, and add a console.table call to inspect an array of objects it produces.
