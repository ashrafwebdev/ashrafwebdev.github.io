The Bundle Diet: a full performance audit of a real app

JavaScript · ties together everything in the Hero stage

This is the capstone of the JavaScript track, and it's deliberately not a new app — it's a rigorous performance audit and optimization pass on a real one, ideally one you already built earlier in this track (the weather dashboard or the validation library's demo both work well). The point isn't to learn a new topic; it's to prove that everything from this stage — event loop internals, memory profiling, design patterns, and build tooling — comes together as one coherent skill: making a real piece of software measurably faster and smaller.

Every claim in this project has to be backed by a number. "I think it's faster now" doesn't count — you need a captured baseline, a specific change, and a re-measured result, for runtime behavior, memory, and bundle size alike. This is exactly the discipline production performance work actually requires, and it's a different muscle than writing correct code in the first place.

The bar for this project, like the rest of the Hero stage, is portfolio-worthy: a stranger reading your before/after report should come away trusting that you genuinely understand why each change helped, not just that you tried something and it happened to work.

  • The event loop, microtasks, and macrotasks in depth
  • Memory management and performance profiling
  • Common design patterns (module, observer, factory) in JS
  • Build tooling internals: bundlers, transpilers, tree-shaking
  • Contributing to an open-source JavaScript library
Requirements
  • A real, non-trivial JavaScript app of your own — reused from an earlier stage or otherwise — with a measurable production bundle and at least a few hundred lines of application code to work with.
  • A recorded trace in DevTools' Performance tab that identifies at least one concrete point where the actual ordering of a microtask (like a .then() callback) and a macrotask (like a setTimeout() callback) surprised you against what you predicted — documented with the real observed order, not a guess.
  • At least one genuine memory issue found using heap snapshots and fixed — for example a never-removed event listener, a closure retaining more than it needs to, or an array that grows without ever being trimmed — confirmed by re-taking a snapshot after the fix.
  • A measured bundle size before any changes (from your bundler's build output or a tool like source-map-explorer), followed by at least two real tree-shaking or code-splitting changes, with the resulting before/after size reported in actual kilobytes.
  • At least one place in the app identified as following, or refactored to follow, a recognizable design pattern — module, observer, or factory — with a short explanation of why that pattern is the right fit there.
  • A written before/after report covering every issue: what the profiler actually showed, exactly what you changed, and the measured improvement in milliseconds, kilobytes, or retained objects.
  • Nothing regresses: if the app has existing tests they still pass after every change, and if it doesn't, you add basic smoke tests covering the specific areas you touched.
Suggested approach
  1. Capture a full baseline first, on everything — bundle size, a recorded Performance-tab trace of typical usage, and a heap snapshot — before changing a single line, so every later comparison has real numbers behind it.
  2. Investigate the event loop finding next, since it's usually the fastest to understand fully, and it often turns out to explain a real bug, not just a slowdown.
  3. Chase the memory issue using multiple heap snapshots taken before and after repeating the same user action several times in a row — a genuine leak shows up as objects that should have been collected but keep accumulating across snapshots.
  4. Tackle the bundle size last, since it usually needs the most exploration of what your bundler actually produced before you can decide what's worth splitting out or tree-shaking away.
  5. Write each section of the before/after report at the moment you take the measurement, rather than trying to reconstruct exact numbers from memory once every change is already made.
Stretch goals
  • Add a CI check or pre-commit script that fails the build if the bundle size regresses past a threshold you set, so the improvement can't quietly be undone later.
  • Find a genuine open issue in a real open-source JavaScript library you depend on — ideally one related to performance or a bug you now understand deeply — and open a real pull request against it.
  • Turn your before/after report into a short public write-up aimed at another intermediate JavaScript developer, explaining the investigation the way you'd have wanted to read it before you started.
