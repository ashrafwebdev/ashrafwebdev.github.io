Memory management and performance profiling

JavaScript · part of the free zero-to-hero guide

Builds on: The event loop, microtasks, and macrotasks in depth

JavaScript manages memory automatically through garbage collection — you never manually free an object the way you would in a lower-level language; instead, the engine periodically identifies objects that are no longer reachable from any live reference (starting from global variables, the current call stack, and closures still in scope) and reclaims their memory. The core idea to internalize is that garbage collection only frees what's actually unreachable — an object with even one lingering reference anywhere, however accidental, stays alive in memory indefinitely.

Memory leaks in JavaScript happen when references linger unintentionally, not because the engine failed at its job. The most common real-world sources: event listeners attached to long-lived objects (like window) but never removed when the feature they belong to is torn down; caches or maps that grow without any eviction strategy; timers (setInterval) that are never cleared and keep their callback's closed-over variables alive forever; and closures that capture a large object just to reference one small property from it, unintentionally keeping the whole object alive.

Detached DOM nodes are a particularly sneaky, classic leak: if you remove an element from the page with .remove() but a JavaScript variable (or, more commonly, a stale closure) still holds a reference to it, that node is no longer visible or part of the page, yet it and everything still attached to it (its children, its listeners) stay in memory, invisible to a casual look at the running app but visible as a growing count in a heap snapshot.

The Chrome DevTools Memory panel lets you take heap snapshots — a complete picture of every object currently alive and reachable — and compare two snapshots taken before and after repeating some action (like opening and closing a modal ten times). If the object count for a particular type keeps climbing snapshot over snapshot instead of returning to roughly its starting point, that's the concrete signature of a leak, and the snapshot comparison view shows you exactly which objects are accumulating and, often, the retaining path explaining why they're still reachable.

The Performance panel's flame chart is the tool for a different, related question: not 'what's leaking' but 'where is time actually being spent'. Recording a session while interacting with a slow page shows exactly which functions consumed the most time, distinguishing scripting time, layout/reflow time, painting time, and idle time — frequently revealing that a perceived 'JavaScript is slow' problem is actually a layout thrashing problem (interleaved DOM reads and writes forcing repeated synchronous layout recalculation) rather than genuinely slow logic.

Profiling and fixing performance issues should always start with measurement, not guessing — it's easy to 'optimize' a piece of code that was never actually the bottleneck while the real slow path goes untouched. Recording a baseline profile, identifying the actual hot path from real data, fixing that specific thing, then re-profiling to confirm the fix actually helped, is a far more reliable loop than intuition alone.

A common leak: forgotten listener
// Leak: listener keeps a reference to `bigData` alive forever
function attach(bigData) {
  window.addEventListener("resize", () => console.log(bigData.length));
}

// Fix: keep a reference so it can be removed later
function attach(bigData) {
  const handler = () => console.log(bigData.length);
  window.addEventListener("resize", handler);
  return () => window.removeEventListener("resize", handler);
}
uncleared-interval-and-unbounded-cache.js
// Leak: interval keeps running (and its closure alive) forever
function startPolling(onUpdate) {
  const id = setInterval(() => onUpdate(fetchLatest()), 5000);
  // never cleared — if the component using this goes away, this keeps running
}

// Fix: return a cleanup function and actually call it when done
function startPollingFixed(onUpdate) {
  const id = setInterval(() => onUpdate(fetchLatest()), 5000);
  return () => clearInterval(id);
}

// Leak: a cache that only ever grows, never evicts
const cache = new Map();
function getCached(key, compute) {
  if (!cache.has(key)) cache.set(key, compute());
  return cache.get(key); // fine for a bounded key space, a leak otherwise
}
// Fix: cap the size, evicting the oldest entry once the limit is hit
function getCachedBounded(key, compute, maxSize = 100) {
  if (!cache.has(key)) {
    if (cache.size >= maxSize) cache.delete(cache.keys().next().value);
    cache.set(key, compute());
  }
  return cache.get(key);
}
Key points
  • Garbage collection is automatic, but only frees memory nothing still references — dangling listeners and timers are the most common leak source.
  • Heap snapshots taken before/after repeating an action, then compared, reveal exactly what's accumulating instead of returning to baseline.
  • The Performance panel's flame chart shows where CPU time is actually being spent — scripting, layout, painting, idle — not just where you assume it is.
  • Detached DOM nodes (removed from the page but still referenced by a lingering variable or closure) are a classic, easy-to-miss leak.
  • Uncleared setInterval timers keep their entire closure alive indefinitely — always pair a started interval with a way to clearInterval it.
  • An unbounded cache (a Map or object that only ever grows) is a slow, steady leak — cap its size and evict old entries.
  • Always measure with a real profile before optimizing — fixing code that was never the actual bottleneck wastes effort while the real slow path stays untouched.
Try it yourself

Take two heap snapshots in Chrome DevTools before and after repeatedly triggering an action in an app, and look for objects that keep growing in count. Then write a startPolling function using setInterval that leaks by never being cleared, fix it by returning a cleanup function, and separately implement a simple bounded cache that evicts its oldest entry once it exceeds a maximum size.
