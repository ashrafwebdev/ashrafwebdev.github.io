DOM selection and manipulation

JavaScript · part of the free zero-to-hero guide

Builds on: Console debugging

The DOM (Document Object Model) is the browser's live, in-memory representation of your HTML as a tree of objects that JavaScript can read and change. When JavaScript modifies the DOM, the browser re-renders the affected part of the page immediately — this is the entire mechanism behind every dynamic web page that doesn't reload to show new content.

document.querySelector() finds the first element matching any valid CSS selector and returns null if nothing matches; querySelectorAll() finds every matching element and returns a NodeList. Older methods like getElementById() and getElementsByClassName() still exist and are marginally faster in hot code paths, but querySelector/querySelectorAll are far more flexible since they accept any CSS selector, including combinators and pseudo-classes.

Once you've selected an element, you can change its text content (.textContent), its rendered HTML (.innerHTML), its attributes (.getAttribute()/.setAttribute()), inline styles (.style.color = "red"), and its classes via .classList, which has .add(), .remove(), .toggle(), and .contains().

.textContent is safer than .innerHTML whenever you're inserting plain text, because innerHTML parses whatever string you give it as HTML — if that string ever comes from user input and you don't sanitize it, you've built a cross-site scripting (XSS) vulnerability. Only use innerHTML when you genuinely need to insert markup, and never with untrusted content.

Creating new elements programmatically uses document.createElement(), followed by setting properties and then attaching it to the tree with .appendChild(), .append(), or .insertBefore(). When building many elements at once, building them inside a DocumentFragment and appending that fragment once avoids triggering a separate reflow for every individual insertion, which matters for performance in loops.

DOM lookups and DOM writes both cost real time — they're not free operations like a plain variable read. Cache a selected element in a variable rather than re-querying it on every use, and batch multiple style/attribute changes together rather than interleaving them with reads (reading .offsetHeight right after a write forces the browser to recalculate layout early, a performance trap known as layout thrashing).

dom.js
const heading = document.querySelector("h1");
heading.textContent = "Updated title";

const items = document.querySelectorAll(".item");
items.forEach((item) => item.classList.add("visible"));
creating-elements.js
const list = document.querySelector("#todo-list");
const fragment = document.createDocumentFragment();

const todos = ["Buy milk", "Write report", "Call Amina"];
for (const text of todos) {
  const li = document.createElement("li");
  li.textContent = text; // safe: plain text, not parsed as HTML
  li.classList.add("todo-item");
  fragment.appendChild(li);
}

list.appendChild(fragment); // one DOM write instead of three
innerHTML-xss-risk.js
// Dangerous: inserting untrusted input as HTML
function showComment(comment) {
  const el = document.querySelector("#comment");
  el.innerHTML = comment; // if comment contains a script tag, it can run
}

// Safe: textContent never parses its input as markup
function showCommentSafely(comment) {
  const el = document.querySelector("#comment");
  el.textContent = comment;
}
Key points
  • textContent is safer than innerHTML for plain text — innerHTML parses its input as HTML, a common XSS risk if the content is user-supplied.
  • querySelectorAll returns a static NodeList, not a true array — most modern browsers support .forEach() on it directly, but use Array.from() if you need array methods it lacks, like .map().
  • classList.toggle() is the cleanest way to flip a class on/off, e.g. for a menu or an active state.
  • Build multiple elements inside a DocumentFragment and append it once, instead of appending each element individually, to avoid repeated reflows.
  • DOM lookups aren't free — cache a selected element in a variable rather than re-querying it repeatedly.
  • Interleaving DOM writes with layout-triggering reads (like .offsetHeight) causes layout thrashing — batch reads together, then batch writes together.
  • querySelector() returns null when nothing matches — always guard against that before calling a method on the result.
Try it yourself

Build a button that, when clicked, toggles a 'highlighted' CSS class on a paragraph elsewhere on the page. Then build a small to-do list: given an array of strings, create a list item for each one inside a DocumentFragment and append it to the page in a single DOM write, and explain in a comment why textContent is the right choice over innerHTML for the item text.
