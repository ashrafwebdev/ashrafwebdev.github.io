ES Modules and code organization

JavaScript · part of the free zero-to-hero guide

Builds on: Classes, prototypes, and inheritance

ES Modules let you split code across multiple files, explicitly choosing what should be public with export and pulling specific pieces into another file with import — replacing older, less structured approaches like relying on global variables, or Node's CommonJS require/module.exports system, which is still common in older Node code but works differently under the hood (synchronous, dynamic, not statically analyzable the way ES Modules are).

A module can have exactly one default export (the one 'main' thing it offers, imported without curly braces and under any name you choose) alongside any number of named exports (imported with curly braces, by their exact exported name, though you can rename them locally with the as keyword). Whether to use a default export, named exports, or a mix is a real design decision — named exports make renaming and refactoring safer across a codebase (tools can trace exactly what's used where) and are generally the more common recommendation in modern style guides, though default exports still make sense for a module that clearly represents one primary thing, like a single React component file.

Modules are automatically deferred (they don't block page parsing the way a classic blocking script tag does) and execute in strict mode by default, and — importantly — a given module only ever executes once no matter how many other files import it; every importer receives references to the exact same live bindings, not separate copies, so if one file changes an exported mutable value, every other file that imported it sees the updated value too.

In the browser, <script type="module"> is required to use import/export directly — a plain <script> tag doesn't understand module syntax and will throw a syntax error. In Node.js, module support depends on either using a .mjs file extension or setting "type": "module" in package.json; Node also supports dynamic imports (await import("./module.js")), which load a module lazily at runtime rather than eagerly at the top of the file — useful for code-splitting or conditionally loading something only when it's actually needed.

Circular imports (module A imports from module B, which imports back from module A) are technically supported but can produce confusing partially-initialized values, since one side of the cycle may still be executing when the other side tries to read from it — this is a real, if uncommon, source of hard-to-debug 'why is this undefined' bugs, and generally worth restructuring code to avoid rather than working around.

Splitting code into small, focused modules with a clear single responsibility makes it dramatically easier to test in isolation, easier to understand at a glance (a well-named file with a handful of related exports tells you more at a glance than a thousand-line file with everything mixed together), and easier for a bundler to tree-shake unused code out of the final production build.

math.js / main.js
// math.js
export function add(a, b) { return a + b; }
export const PI = 3.14159;
export default function multiply(a, b) { return a * b; }

// main.js
import multiply, { add, PI } from "./math.js";
console.log(add(2, 3), multiply(2, 3), PI);
renaming-and-shared-state.js
// config.js
export let requestCount = 0;
export function trackRequest() { requestCount++; }

// analytics.js — imports the same live binding, not a copy
import { requestCount, trackRequest } from "./config.js";
trackRequest();
console.log(requestCount); // 1 — sees the update made through the import

// Renaming an import to avoid a naming collision
import { add as sum } from "./math.js";
console.log(sum(2, 3));
dynamic-import.js
// Load a heavy module only when it's actually needed
async function showChart(data) {
  const { renderChart } = await import("./chart-library.js");
  renderChart(data);
}

document.querySelector("#show-chart-btn")
  .addEventListener("click", () => showChart(myData));
Key points
  • A module can have exactly one default export but any number of named exports.
  • <script type="module"> in HTML is required to use import/export in the browser directly.
  • Modules execute exactly once, and every importer shares the same live bindings — not separate copies — so changes to an exported mutable value are visible everywhere it's imported.
  • Named exports can be renamed on import with as, and are generally easier to trace and refactor across a codebase than default exports.
  • Dynamic import("./module.js") loads a module lazily at runtime, returning a Promise — useful for code-splitting and conditional loading.
  • Node.js requires either a .mjs extension or "type": "module" in package.json to use ES Module syntax, as opposed to older CommonJS require().
  • Circular imports are supported but can yield partially-initialized values mid-cycle — worth restructuring code to avoid rather than debugging around.
  • Splitting code into focused modules makes it dramatically easier to test, understand, and tree-shake in isolation.
Try it yourself

Split a small script into two modules — one exporting utility functions, one that imports and uses them — and load it via a script type=module tag. Then add a mutable exported variable to the utility module, mutate it from the main module, and confirm both modules see the same updated value through their live binding. Finally, add a button that dynamically imports a third module only when clicked, and confirm in the network tab that it doesn't load until then.
