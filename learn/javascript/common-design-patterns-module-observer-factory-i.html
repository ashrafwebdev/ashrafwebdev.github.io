Common design patterns (module, observer, factory) in JS

JavaScript · part of the free zero-to-hero guide

Builds on: Memory management and performance profiling

Design patterns are named, reusable solutions to problems that come up again and again in software — learning their names is less important than recognizing the underlying shape of the problem they solve, since you'll often reach for one instinctively before ever having a name for it. The module pattern, observer pattern, and factory pattern are three of the most common in everyday JavaScript, each solving a genuinely different kind of problem.

The module pattern uses a closure to create private internal state alongside a small, deliberately exposed public interface — an immediately-invoked function expression (IIFE) that returns an object containing only the methods meant to be public, with everything else trapped inside the closure and permanently unreachable from outside. This predates ES Modules by years and was, for a long time, the primary way JavaScript simulated privacy and encapsulation before the language had real modules or private class fields; it's largely superseded now for organizing whole files, but the same closure-based technique is still genuinely useful for creating a single self-contained object with private internal state.

The observer pattern (also called publish/subscribe, or pub/sub) decouples the code that produces an event from the code that reacts to it — a subject maintains a list of subscriber functions and calls every one of them whenever something notable happens, without needing to know anything about what those subscribers actually do with that information. This is the foundational idea behind DOM events, Node's built-in EventEmitter class, and the internal mechanics of most reactive UI frameworks and state-management libraries, even when they don't use the word 'observer' anywhere in their own documentation.

The factory pattern centralizes object-creation logic behind a single function instead of scattering new ClassName(...) calls with construction logic all over a codebase. This is especially valuable when the exact type of object to create depends on some input (returning different subclasses based on a config value, say), when construction genuinely involves nontrivial setup logic worth naming and isolating, or simply when you want every call site to go through one place so that changing how objects get built later only requires editing one function instead of hunting down every scattered constructor call.

These three patterns compose naturally rather than competing with each other — it's entirely normal for a factory function to internally use the module pattern to give each created object its own private state, and for that created object to itself be an observer-pattern emitter that other code subscribes to. Recognizing the shape of the problem in front of you (need to hide state? reach for closures. need to decouple producers from consumers of an event? reach for observer. need centralized, flexible creation logic? reach for a factory) matters far more than memorizing pattern names.

Patterns are tools for solving a real problem you actually have in front of you, not a checklist to apply for its own sake — reaching for the observer pattern to decouple two pieces of code that will only ever have one fixed relationship, for instance, adds a layer of indirection that makes the code harder to trace for no real benefit. The best guide is need, not novelty.

observer.js
function createEmitter() {
  const listeners = [];
  return {
    on(fn) { listeners.push(fn); },
    emit(data) { listeners.forEach((fn) => fn(data)); },
  };
}

const events = createEmitter();
events.on((data) => console.log("Got:", data));
events.emit("hello");
module-pattern-and-factory.js
// Module pattern: closure-based private state, public interface only
function createCounter(start = 0) {
  let count = start; // private, unreachable from outside
  return {
    increment() { return ++count; },
    reset() { count = start; },
    get value() { return count; },
  };
}

// Factory pattern: centralizes creation logic that varies by input
function createShape(type, size) {
  switch (type) {
    case "circle":
      return { type, area: () => Math.PI * size ** 2 };
    case "square":
      return { type, area: () => size ** 2 };
    default:
      throw new Error(`Unknown shape type: ${type}`);
  }
}

const counter = createCounter(10);
console.log(counter.increment(), counter.value); // 11 11
console.log(createShape("circle", 2).area().toFixed(2)); // 12.57
decoupling-with-observer.js
// A form and a notification banner, decoupled through an emitter,
// instead of the form directly calling banner-specific code.
const events = createEmitter();

function setupForm(formEl) {
  formEl.addEventListener("submit", (e) => {
    e.preventDefault();
    events.emit({ type: "success", message: "Saved successfully" });
  });
}

function setupNotificationBanner(bannerEl) {
  events.on(({ message }) => {
    bannerEl.textContent = message;
    bannerEl.classList.add("visible");
  });
}
// Neither function knows the other exists — both only know about `events`.
Key points
  • The module pattern predates ES Modules and uses a closure to fake private state — largely superseded for organizing whole files, but still useful for a single object with private internals.
  • The observer pattern is everywhere: DOM events, Node's EventEmitter, and most reactive UI frameworks under the hood.
  • A factory function centralizes and hides object-creation complexity, especially useful when the type or setup of the created object varies by input.
  • These patterns compose naturally — a factory can internally use a closure for private state, and produce objects that are themselves observer-pattern emitters.
  • Design patterns are named recognitions of a recurring problem shape, not a checklist to apply on principle — reach for one because it solves a real problem in front of you.
  • Recognize the underlying need (hide state -> closures; decouple producer from consumer -> observer; centralize flexible creation -> factory) rather than memorizing pattern names.
  • Adding a pattern where a simpler, direct call would do just adds indirection without benefit — need should drive the choice, not novelty.
Try it yourself

Build a small createEmitter-style pub/sub utility from scratch and use it to decouple two unrelated pieces of code (e.g. a form and a notification banner). Then write a createCounter factory function using the module pattern for private state, and a separate createShape factory function that returns a differently-shaped object depending on a type argument, throwing a clear error for an unrecognized type.
