02 Learning stage capstone

A live weather dashboard backed by a real public API

JavaScript · ties together everything in the Learning stage

This project is where the DOM, events, array/object methods, fetch(), and modern ES6+ syntax stop being separate topics and become one working feature: a page where a visitor types a city, submits a form, and sees a real short-range forecast rendered on the page — pulled live from a public weather API, not hardcoded data.

Nothing about this project reloads the page. Submitting the form is intercepted with JavaScript, the network request happens asynchronously, and the DOM is updated in place — which means you'll have to handle three states honestly: loading, success, and failure, since a real API call can do any of the three and a good UI never pretends otherwise.

The forecast data coming back from the API is a nested structure of arrays and objects, exactly like the kind you've been practicing with map, filter, and destructuring — this project is the first time you'll shape real, externally-owned data instead of data you invented yourself.

  • DOM selection and manipulation
  • Events and event listeners
  • Array/object methods: map, filter, reduce, destructuring
  • Fetching data with fetch() and working with JSON
  • ES6+ syntax: arrow functions, template literals, spread/rest
Requirements
  • A form with a city or location input; submitting it calls event.preventDefault() and reads the value via DOM selection rather than letting the browser navigate.
  • On submit, the app calls fetch() against a free, no-API-key public weather service and explicitly checks response.ok before parsing the JSON, throwing a real error when the request wasn't successful.
  • The forecast is rendered as a list of DOM elements built with document.createElement() and appended to the page inside a single DocumentFragment write, not one appendChild() call per item.
  • The raw API response is shaped with .filter() and/or .map() before rendering (for example, narrowing to the next several days or daytime hours) rather than looped over by hand.
  • At least one destructuring assignment is used to pull the specific fields you need (temperature, condition, date, etc.) out of each forecast entry.
  • The page shows a visible loading state while the request is in flight, and a clear, specific error message — with no stale forecast left on screen — if the city can't be found or the network request fails.
  • Template literals and at least one arrow function with an implicit return are used somewhere in the rendering code.
Suggested approach
  1. Build the static HTML shell first — the input, the submit button, and an empty results container — with no JavaScript at all, so you know the page has something correct to attach behavior to.
  2. Wire up the submit listener with preventDefault(), call fetch(), and just console.log() the parsed JSON to confirm you're actually getting real data back before writing any rendering code.
  3. Once you can see the real response shape in the console, write the filter/map/destructuring logic that turns it into exactly the small, clean list of values your rendering function needs.
  4. Build the DOM-rendering function that turns that shaped data into elements inside a DocumentFragment, appended to the page in one write.
  5. Add the loading and error states last — you need the successful path fully working first so you know exactly what "idle, not loading, no error" is supposed to look like before you build the other two states around it.
Stretch goals
  • Use navigator.geolocation to pre-fill the user's current location automatically on page load, falling back to the manual input if permission is denied.
  • Cache the last few successful lookups in a plain object keyed by city name, so re-searching a recent city skips the network request entirely.
  • Add a Celsius/Fahrenheit toggle that re-renders the already-fetched data on the client without triggering a new fetch() call.
