Error handling patterns and unit testing (Jest/Vitest)

JavaScript · part of the free zero-to-hero guide

Builds on: ES Modules and code organization

try/catch lets you handle errors gracefully at the point where they occur instead of letting them crash the whole program. A finally block, if present, always runs after the try/catch resolves, whether an error was thrown or not — the natural place to put cleanup code, like closing a connection or clearing a loading spinner, that needs to happen regardless of the outcome.

Always throw actual Error objects (or subclasses of Error), never plain strings or other values — an Error automatically captures a stack trace at the point it was created, which is often the single most useful piece of information for tracking down where and why something went wrong; throwing a bare string discards that entirely.

Custom error classes, created by extending Error, let calling code distinguish between different failure categories programmatically — a ValidationError versus a NetworkError versus a NotFoundError — rather than having to parse an error's message text to figure out what actually went wrong, which is brittle and breaks the moment the message wording changes.

Unit tests verify that a specific, isolated piece of code behaves correctly, independent of the rest of the system. Jest and Vitest (a newer, notably faster alternative built for projects already using Vite, with a nearly identical API) both provide a describe() function to group related tests, a test()/it() function to define one specific case, and an expect() assertion API with matchers like .toBe(), .toEqual(), .toThrow(), and .toHaveBeenCalledWith() for spies and mocks.

Good tests are independent of each other — one test's outcome must never depend on another test having run first, since test runners can execute tests in any order or in parallel, and a hidden dependency between tests produces flaky, order-dependent failures that are miserable to debug. Aim to test observable behavior ('adds two numbers correctly', 'throws on negative input') rather than internal implementation details that might legitimately change even when the actual behavior hasn't.

Mocking replaces a real dependency (a network call, the current date, a random number generator) with a controlled stand-in, so a test can exercise the code under realistic-but-deterministic conditions without needing a live server, a real database, or genuine randomness — both Jest and Vitest include built-in mocking utilities (vi.fn() in Vitest, jest.fn() in Jest) for exactly this purpose.

math.test.js (Vitest/Jest)
import { describe, it, expect } from "vitest";
import { add } from "./math.js";

describe("add", () => {
  it("adds two positive numbers", () => {
    expect(add(2, 3)).toBe(5);
  });
  it("handles negative numbers", () => {
    expect(add(-2, 5)).toBe(3);
  });
});
custom-errors-and-finally.js
class ValidationError extends Error {
  constructor(message, field) {
    super(message);
    this.name = "ValidationError";
    this.field = field;
  }
}

function createUser(data) {
  if (!data.email) {
    throw new ValidationError("Email is required", "email");
  }
  return { id: 1, ...data };
}

function safeCreateUser(data) {
  try {
    return createUser(data);
  } catch (err) {
    if (err instanceof ValidationError) {
      console.warn(`Validation failed on ${err.field}: ${err.message}`);
      return null;
    }
    throw err; // re-throw anything we don't specifically know how to handle
  } finally {
    console.log("createUser attempt finished"); // always runs
  }
}
mocking-and-error-tests.test.js
import { describe, it, expect, vi } from "vitest";
import { createUser, ValidationError } from "./users.js";

describe("createUser", () => {
  it("throws a ValidationError when email is missing", () => {
    expect(() => createUser({})).toThrow(ValidationError);
  });

  it("calls the logger mock exactly once on success", () => {
    const logger = vi.fn();
    createUser({ email: "a@b.com" }, logger);
    expect(logger).toHaveBeenCalledTimes(1);
    expect(logger).toHaveBeenCalledWith("user created");
  });
});
Key points
  • Throw Error objects (or subclasses), not plain strings — they carry a stack trace that's often the most useful debugging clue you have.
  • Custom error classes (extending Error) let calling code branch on error type with instanceof, instead of fragile string-matching on a message.
  • A finally block always runs whether an error was thrown or not — the natural place for cleanup code.
  • Tests should be independent — one test's outcome must never depend on another test having run first.
  • describe() groups related tests; it()/test() defines one specific case; expect() asserts on the result.
  • Aim to test observable behavior ("adds two numbers correctly") not internal implementation details that might change without the behavior actually changing.
  • Mocking (vi.fn()/jest.fn()) replaces real dependencies like network calls or randomness with controlled, deterministic stand-ins for tests.
  • expect(fn).toThrow(ErrorClass) tests that a function throws the right kind of error, not just any error.
Try it yourself

Write three Vitest/Jest test cases for a function you've already built, covering a normal case, an edge case, and an invalid-input case that should throw. Then create a custom error class extending Error, throw it from that function on invalid input, and write a test asserting the function throws specifically that error class rather than any generic error. Finally, use a mock function to verify a side-effect callback (like a logger) is called exactly once with the expected argument on success.
