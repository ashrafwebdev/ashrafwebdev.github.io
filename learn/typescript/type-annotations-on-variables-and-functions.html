Type annotations on variables and functions

TypeScript · part of the free zero-to-hero guide

Builds on: Basic types: string, number, boolean, array, any

Function signatures benefit the most from annotations: typing each parameter and the return value documents the contract directly in the code, and TypeScript will flag any call site that doesn't match it — no separate documentation, no reading the implementation to guess what's expected, just the signature itself.

When a variable's initial value already makes its type obvious, explicit annotation is optional — TypeScript's inference handles it automatically. Annotate when the type isn't obvious from the right-hand side, when you're declaring a variable before assigning it a value, or when you deliberately want a wider type than inference would pick on its own.

Parameters must always be annotated, because TypeScript has no call site to infer them from at the point the function is defined — without an annotation, an unannotated parameter in a non-strict config silently becomes any, quietly reintroducing the exact unsafety typed code is meant to prevent. Enabling noImplicitAny (bundled into strict) turns this into a compile error instead of a silent gap.

Return types are inferred from a function's body by default, which is usually fine for small private functions, but explicitly annotating the return type on anything exported or public is good practice: it acts as a safety net that catches you accidentally returning the wrong thing after refactoring, rather than letting the inferred return type silently drift to match a bug.

Object and array destructuring parameters need their own annotation syntax, since the types can't simply follow each destructured name the way they would for a plain parameter — the type goes after the whole destructuring pattern, describing the shape being pulled apart.

Widening is a subtlety worth knowing: a let variable initialized to a string literal like "active" is inferred as the general string type, not the narrow literal type "active", because let variables are assumed reassignable. A const with the same initializer, by contrast, infers the narrower literal type, since it can never change.

annotations.ts
function calculateTotal(price: number, quantity: number): number {
  return price * quantity;
}

// Error caught at compile time, not runtime:
// calculateTotal("10", 2);

let count = 0; // inferred as number, no annotation needed
destructuring-and-widening.ts
function printCoords({ x, y }: { x: number; y: number }): void {
  console.log(`(${x}, ${y})`);
}

let status1 = "active";       // inferred as string (widened, since let is reassignable)
const status2 = "active";     // inferred as "active" (the exact literal type)

let pending: number; // declared before assignment, annotation required here
pending = 5;
implicit-any-mistake.ts
// Without noImplicitAny, this parameter silently becomes 'any':
function double(x) {
  return x * 2;
}

double("hello"); // no compile error, but produces NaN at runtime

// With noImplicitAny (part of strict mode) this is a compile error instead,
// forcing you to write: function double(x: number) { ... }
Key points
  • Annotate function parameters always — TypeScript can't infer them from a call site the way it can for a variable's initializer.
  • Return type annotations are optional (TypeScript infers them) but valuable as explicit documentation and a safety net on exported or public functions.
  • Over-annotating obvious variables adds noise without adding safety — trust inference where the right-hand side already makes the type clear.
  • noImplicitAny (part of strict) turns an unannotated parameter into a compile error instead of a silent any.
  • A type error is caught the moment you save the file or run the compiler, long before the code ever executes.
  • Destructured parameters are annotated by placing the type after the whole destructuring pattern, not after each individual name.
  • let initializers widen to the general type (string); const initializers keep the narrow literal type, since they can never be reassigned.
  • Declaring a variable before assigning it a value (let x: number;) requires an explicit annotation, since there's no initializer to infer from.
Try it yourself

Write a fully-annotated function that takes a name (string) and an age (number) and returns a greeting string, then try calling it with wrong argument types to see the compiler error. Afterward, declare the same greeting as both a let and a const variable and use hover-info or a type query to confirm the let version widens to string while the const version keeps its literal type.
