03 Advanced stage

Strict mode and gradually typing a large codebase

TypeScript · part of the free zero-to-hero guide

Builds on: Decorators

Migrating a large existing JavaScript codebase to strict TypeScript all at once is rarely realistic — the number of type errors that surface the moment strict mode is enabled on unconverted code is typically enormous, and trying to fix them all before shipping anything else brings feature work to a halt for far too long to be practical on a real team.

TypeScript supports incremental adoption by design: start with loose settings (allowJs and a non-strict config), convert files one at a time from .js to .ts, and tighten individual tsconfig.json flags gradually as coverage and confidence grow, rather than flipping every strict check on at once across the whole project on day one.

noImplicitAny is usually the single most valuable individual flag to turn on early, even before full strict mode, since it catches the exact case where an unconverted or under-annotated function is silently providing zero type safety at all — flushing those out first tends to surface the highest-value, lowest-effort fixes early in a migration.

// @ts-expect-error and per-file // @ts-nocheck comments let you silence specific known issues temporarily during migration without blocking the whole build, while still actively tracking what's left to fix — critically, // @ts-expect-error itself becomes an error if the line it's suppressing stops actually having a type error, which prevents these suppression comments from silently going stale and hiding a real problem that's since resurfaced differently.

checkJs, paired with allowJs, lets you type-check plain .js files using JSDoc comments instead of converting them to .ts syntax outright — this is a genuinely useful intermediate step for files that are too risky or too large to rewrite immediately, letting you add real type safety without touching the file's actual runtime code at all.

Migration progress is worth tracking with dedicated tooling (a type-coverage report, or simply counting remaining anys and suppression comments over time) rather than relying on team memory of what's left — a large migration that loses visibility into its own progress is at real risk of stalling out somewhere in the middle, with the codebase left in a permanently half-migrated, worst-of-both-worlds state.

A staged tsconfig.json
{
  "compilerOptions": {
    "allowJs": true,
    "checkJs": false,
    "strict": false,
    "noImplicitAny": true
  }
}
suppressing-a-known-issue.ts
// @ts-expect-error — legacy payload shape, tracked in JIRA-1234
const total: number = legacyApi.getTotal();

// If legacyApi.getTotal() is later fixed to actually return a number,
// this comment itself becomes a compile error: "Unused '@ts-expect-error'
// directive" -- forcing you to notice and remove the now-stale suppression.
typed-jsdoc-in-plain-js.js
// @ts-check
/**
 * @param {number} price
 * @param {number} quantity
 * @returns {number}
 */
function calculateTotal(price, quantity) {
  return price * quantity;
}

calculateTotal("10", 2); // flagged by tsc even though this is a plain .js file
Key points
  • allowJs lets .js and .ts files coexist during a gradual migration.
  • Turn on individual strict flags (noImplicitAny first, usually) rather than flipping strict: true all at once on a large codebase.
  • // @ts-expect-error documents a known, temporary issue and will itself error if the underlying problem gets fixed and the comment becomes stale.
  • checkJs plus allowJs type-checks plain .js files via JSDoc comments, without needing to convert them to .ts syntax outright.
  • Track migration progress with tooling (type-coverage reports, or counting remaining suppressions over time) rather than relying on memory of what's left.
  • A stalled, half-migrated codebase combines the worst of both worlds — real conversion effort spent, but without full type safety to show for it.
  • // @ts-nocheck silences an entire file, useful for very large or risky files you aren't ready to fix piece by piece yet.
Try it yourself

Take an existing JavaScript file, rename it to .ts, and fix type errors one at a time until it compiles cleanly under strict mode. Then, on a separate plain .js file, add a @ts-check comment and JSDoc type annotations instead, and confirm tsc still catches a deliberately introduced type mismatch without any file rename at all.
