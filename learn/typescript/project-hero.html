04 Hero stage capstone

Publish a fully-typed npm package with zero any types

TypeScript · ties together everything in the Hero stage

This is the project the entire TypeScript track has been building toward: design, build, and actually publish a small, genuinely useful npm package with real consumers in mind, and hold it to a standard the earlier stages only asked you to approach — zero any anywhere, a deliberately designed public API, and at least one place where real type-level programming earns its keep rather than just showing off.

The bar here mirrors the Advanced-stage declaration-file project from the other direction: there, you described someone else's untyped code from the outside; here, you're the original author, and your exported types are exactly as much of a contract with your users as your runtime behavior is. A breaking type change is a breaking change, whether or not any test ever catches it.

This should feel like something you could genuinely point to afterward: a real package, a real README, and real proof — via type-only tests — that its public API does what you say it does.

  • Type-level programming (recursive conditional types, template literal types)
  • Designing type-safe public APIs for a library
  • Contributing types to DefinitelyTyped
  • Working with the TypeScript Compiler API
Requirements
  • A small library, published to npm (or npm-ready, with a public GitHub repo, a version tag, and clear install instructions) that solves one specific, genuine problem — not a toy 'hello world' package.
  • Zero any anywhere in your own source, and zero any leaking into the .d.ts files tsc actually emits for consumers — confirmed by reading the generated declarations directly, not just your source.
  • Every consumer-facing export is a named, documented interface or type (matching the practice of designing type-safe public APIs) — no anonymous inline shape buried in a function signature that a consumer would need to reconstruct by hand.
  • At least one genuinely load-bearing use of type-level programming — a template literal type or a recursive conditional type — solving a real problem inside your API, not included purely to demonstrate the technique.
  • A type-only test file (using a tool like tsd or expect-type, in the same spirit as DefinitelyTyped's required test format) asserting the exact resolved type of at least three real calls into your public API.
  • A README documenting every exported function and type clearly enough that a stranger could use the package correctly without ever reading your implementation.
  • The package builds cleanly under strict mode, and a broken type is actually capable of failing your build — not just flagging a squiggly line in your own editor.
Suggested approach
  1. Write the README and the public export signatures first, before any implementation — if you can't describe an export in one clear sentence, its API probably isn't ready yet.
  2. Implement the simplest, least generic pieces first, and get them compiling and testable before tackling the one load-bearing type-level feature.
  3. Build the type-level feature — the template literal or conditional type — once you have a concrete, real use for it inside the library, not before; retrofit it onto working code rather than designing around it from day one.
  4. Write the type-only test file once the public API feels stable, so it locks in the exact guarantee you intend to make to consumers from that point forward.
  5. Finish with a pass reading the emitted .d.ts output directly, confirming nothing quietly widened to any along the way, then publish.
Stretch goals
  • Use the TypeScript Compiler API (directly, or through a wrapper like ts-morph) to write a small companion script that checks every code example in your README still compiles against your published types, so your docs can't silently drift out of sync with your real API.
  • Find a related package on npm that's missing types entirely, and apply what you learned about DefinitelyTyped's process to attempt a real (or practice) type-declaration contribution for it.
  • Add function overloads to one exported function so that a specific literal argument narrows the returned type more precisely than a single generic signature could on its own.
