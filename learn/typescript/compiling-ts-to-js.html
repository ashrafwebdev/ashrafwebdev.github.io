01 Zero stage

Compiling TS to JS

TypeScript · part of the free zero-to-hero guide

Browsers and Node.js can't run TypeScript directly — the tsc compiler (or a faster tool like esbuild or SWC) strips out the type annotations entirely and transforms modern syntax down to plain JavaScript your runtime actually understands. This transformation happens purely at the syntax level; it never inspects whether your program does anything sensible at runtime, only whether the types you wrote are internally consistent beforehand.

In practice, most projects don't call tsc directly for their final production build — bundlers like Vite handle transpilation internally using a much faster tool (esbuild, under the hood, in Vite's case) purely for speed, while tsc --noEmit is run as a separate step purely for type checking, decoupled entirely from the build pipeline that actually produces JavaScript.

This split matters because fast transpilers like esbuild and SWC compile each file in isolation, without ever building a full type-aware model of your project — which means they can strip types and rewrite syntax extremely quickly, but they physically cannot catch a type error, since doing so requires knowledge that spans multiple files. A project relying only on a fast bundler and skipping tsc --noEmit can genuinely ship broken code that a normal tsc build would have blocked.

TypeScript type annotations are erased completely at compile time and have precisely zero runtime footprint — there's no performance cost to types, and no way to inspect a TypeScript type from within running JavaScript, because by the time the code executes, that information simply no longer exists. This is different from some other typed-to-JS languages that keep runtime type metadata around.

By default, tsc still emits JavaScript even when it reports type errors, unless noEmitOnError is explicitly set to true — which surprises people expecting a type error to behave like a hard build failure the way it would in many other compiled languages. CI pipelines that only check the exit status of a plain tsc build (without noEmitOnError) can miss this distinction, since tsc's own exit code does reflect errors even though a .js file still gets written.

Source maps, enabled with "sourceMap": true, let you debug the original .ts file directly in the browser or Node's inspector even though the runtime is actually executing the emitted .js — the source map is a separate file mapping each position in the compiled output back to its original location in your TypeScript source.

Terminal
npx tsc index.ts          # compiles index.ts to index.js
npx tsc --noEmit          # type-check only, don't output files
npx tsc --watch           # recompile automatically on save
Before and after erasure
// input.ts
function add(a: number, b: number): number {
  return a + b;
}
const total: number = add(2, 3);

// output.js (after tsc strips every type annotation)
function add(a, b) {
  return a + b;
}
const total = add(2, 3);
noEmitOnError-gotcha.ts
// broken.ts
function greet(name: string): string {
  return 123; // type error: number not assignable to string
}

// `tsc broken.ts` reports the error AND still writes broken.js by default.
// Add "noEmitOnError": true in tsconfig.json to stop the .js file
// from being emitted at all when a type error is present.
Key points
  • TypeScript type annotations are erased entirely at compile time — they have zero runtime footprint or performance cost.
  • tsc --noEmit is how most projects use the compiler purely as a type checker alongside a faster, non-type-checking bundler.
  • Fast transpilers like esbuild/SWC strip types per-file without cross-file type analysis, so they cannot catch genuine type errors — only tsc can.
  • A type error doesn't necessarily stop tsc from emitting JavaScript unless noEmitOnError is set.
  • Source maps ("sourceMap": true) let you debug the original .ts file even though the runtime executes the emitted .js.
  • There's no way to inspect a TypeScript type at runtime — by execution time, the type information has been fully discarded.
  • A CI pipeline that skips a real tsc check and relies only on a fast bundler's build success can ship code with real type errors.
Try it yourself

Compile a small .ts file with tsc, inspect the output .js file, and confirm the type annotations are completely gone. Then introduce a deliberate type error, run tsc again without noEmitOnError, and check whether the .js file was still written despite the reported error — then add noEmitOnError and see how the behavior changes.
