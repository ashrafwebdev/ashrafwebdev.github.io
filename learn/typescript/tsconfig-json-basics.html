tsconfig.json basics

TypeScript · part of the free zero-to-hero guide

Builds on: Interfaces and type aliases

tsconfig.json configures how the TypeScript compiler behaves — which files to include, which JavaScript version to output, where to emit that output, and how strict the type checking should be. Running tsc --init from a project's root generates a sensible starting file with most options present but commented out, ready to be uncommented as needed.

The single most valuable setting is "strict": true, which enables a whole bundle of stricter checks at once — including strictNullChecks, noImplicitAny, and strictFunctionTypes — that together catch far more real bugs than TypeScript's default, looser configuration. Turning it on individually flag by flag is possible, but starting a new project with the bundled strict flag is almost always the right call.

target controls which version of JavaScript features the compiler is allowed to emit directly versus needing to down-level (rewrite) into older equivalents — targeting ES2020 or newer lets modern syntax like optional chaining pass through untouched, while an older target rewrites it into more verbose, broadly compatible code. module separately controls which module system the output uses (CommonJS's require/module.exports versus ESM's import/export), and mismatching it against your actual runtime is a very common source of confusing 'module not found' errors.

include and exclude control which files the compiler actually processes — a glob like "src/**/*" in include scopes the project to just that directory, while exclude (commonly node_modules, which is excluded by default anyway) keeps generated or third-party files out of type checking.

Project references ("references": [...] paired with "composite": true) let a large codebase be split into multiple tsconfig.json files that build incrementally and depend on each other, which matters once a monorepo grows large enough that a single full type check on every save becomes too slow.

Most modern build tools (Vite, esbuild, SWC) read tsconfig.json for module resolution and path mapping, but they typically strip types without actually checking them, for speed — meaning a broken type can still produce a working build. Running tsc --noEmit as a separate step (often in CI or a pre-commit hook) is how most projects catch what the fast bundler alone would silently let through.

tsconfig.json
{
  "compilerOptions": {
    "target": "ES2020",
    "module": "ESNext",
    "strict": true,
    "outDir": "./dist"
  },
  "include": ["src/**/*"]
}
a-more-complete-config.json
{
  "compilerOptions": {
    "target": "ES2020",
    "module": "ESNext",
    "moduleResolution": "Bundler",
    "strict": true,
    "noUnusedLocals": true,
    "noUnusedParameters": true,
    "esModuleInterop": true,
    "skipLibCheck": true,
    "outDir": "./dist",
    "rootDir": "./src"
  },
  "include": ["src/**/*"],
  "exclude": ["node_modules", "dist"]
}
Key points
  • Turn on "strict": true from day one on a new project — retrofitting it onto a large, already-loose codebase later is far more painful.
  • target controls which JavaScript version features are emitted directly versus rewritten for compatibility.
  • module controls the module system used in the output — mismatching it against the actual runtime is a common source of confusing errors.
  • include/exclude control which files the compiler processes; node_modules is excluded by default.
  • skipLibCheck skips type checking inside .d.ts files (including third-party ones), which meaningfully speeds up compilation on most real projects.
  • Project references (composite + references) split a large codebase into independently, incrementally buildable pieces.
  • Most modern bundlers strip types for speed without truly checking them — running tsc --noEmit separately (often in CI) is how real type errors still get caught.
Try it yourself

Run tsc --init in a new folder, turn on strict mode, and confirm a deliberately null-unsafe snippet gets flagged as an error. Then add skipLibCheck and noUnusedLocals to the config and observe how each one changes what the compiler reports on the same project.
