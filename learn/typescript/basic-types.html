01 Zero stage

Basic types: string, number, boolean, array, any

TypeScript · part of the free zero-to-hero guide

TypeScript adds a type system on top of JavaScript, checked at compile time rather than runtime. The basic types map directly onto JavaScript's own categories: string, number, and boolean correspond exactly to what typeof would report on the equivalent JavaScript value, so nothing about the underlying data changes — only what the compiler is willing to let you do with it before your code ever runs.

Arrays are written as string[] — a type name followed by square brackets — which is by far the most common style in everyday code and style guides. You'll meet an alternative angle-bracket spelling for the exact same thing a little later in this track, once generics are introduced; for now, T[] is all you need.

number covers every numeric value TypeScript knows about, integers and floating point alike — there's no separate int or float, because JavaScript itself only has one general-purpose numeric type under the hood. Arbitrary-precision whole numbers use the distinct bigint type instead, written with an n suffix like 10n, and TypeScript will not let you mix number and bigint in the same arithmetic expression without an explicit conversion.

any is the type system's escape hatch: a value typed any can be assigned to anything, read as anything, and called as anything, with zero compile-time checking performed on it at all. That flexibility is exactly the problem — assigning an any-typed value into a strongly typed variable silently disables checking on that variable too, and the unsafety keeps spreading through every place the value travels afterward, often resurfacing as a runtime crash far from where the any was introduced.

It's worth knowing that arrays typed with a specific element type are still mutable containers — pushing a value of the wrong type into a number[] is caught at compile time just as reliably as assigning it directly, since TypeScript tracks the array's element type through every method that adds to it, including push, unshift, and spread.

Reaching for any out of impatience is one of the most common ways a new TypeScript codebase ends up barely safer than the plain JavaScript it replaced. A handful of well-placed anys at the boundary of untyped legacy code or a third-party library is a reasonable pragmatic choice; scattering them through new code you're writing from scratch generally isn't, and it's worth treating each one as a small debt to pay down later.

basics.ts
let username: string = "amina";
let age: number = 27;
let isAdmin: boolean = false;
let scores: number[] = [88, 92, 75];

let anything: any = "careful with this one";
anything = 42; // allowed, but you've lost all safety
arrays-and-checking.ts
let scores: number[] = [88, 92, 75];
scores.push(100);       // OK, matches the element type
// scores.push("A");   // Error: string is not assignable to number

let bigCount: bigint = 9007199254740993n;
// let mixed = bigCount + 1; // Error: cannot mix bigint and number
let mixedFixed = bigCount + 1n; // OK, both bigint
any-spreads-unsafety.ts
function parseConfig(raw: any) {
  return raw.settings.timeout; // no error here, even if this is wrong
}

const config = parseConfig(JSON.parse("{}"));
let timeoutMs: number = config; // no error either — 'any' infected this too
console.log(timeoutMs.toFixed(2)); // crashes at runtime: undefined has no toFixed
Key points
  • Basic types mirror JavaScript's runtime types, checked before your code ever runs, not while it runs.
  • Prefer unknown over any when you genuinely don't know a type — unknown forces you to check or narrow before using it, while any lets you do anything unchecked.
  • Prefer the T[] array syntax in everyday code — you'll meet an equivalent angle-bracket spelling once generics are introduced later in this track.
  • number covers integers and floats alike; use the separate bigint type for arbitrary-precision whole numbers.
  • TypeScript can usually infer types automatically from a variable's initial value — you don't need to annotate every single declaration.
  • Array methods that add elements (push, unshift, spread) are still type-checked against the array's declared element type.
  • An any value contaminates every variable it flows into, silently disabling checks well beyond the original line where it appeared.
  • Treat any as a deliberate, temporary escape hatch at code boundaries, not a default choice when a type is merely inconvenient to figure out.
Try it yourself

Declare typed variables for a user's name, age, admin status, and a list of their favorite numbers, without using any. Then write a small function that intentionally accepts an any-typed parameter, pass a value of the wrong shape through it, and observe where the mistake actually surfaces at runtime rather than at compile time.
