Contributing types to DefinitelyTyped

TypeScript · part of the free zero-to-hero guide

DefinitelyTyped is the massive community repository behind the @types/* packages on npm — when a JavaScript library has no built-in types of its own, this is almost always where the community-maintained types live instead, and it's one of the largest, most actively maintained open-source repositories in existence purely due to how many packages it covers.

Contributing means writing or improving a .d.ts file for a real, untyped (or under-typed) package, following DefinitelyTyped's contribution guidelines closely, including their required test file format that verifies the types actually behave correctly when exercised, rather than merely compiling without error — a declaration file that compiles cleanly can still describe the wrong shape entirely, so the test file is what actually catches that.

Start with a small, well-scoped package rather than a massive, actively-changing one for a first contribution — a large, popular package's types tend to already be extensively maintained by several regular contributors with strong opinions about API design decisions, which makes for a much harder first pull request to land than a smaller, less-attended package with an open, uncontested gap.

Existing @types packages with open issues are often a genuinely easier entry point than starting a brand-new package's types entirely from scratch — an existing declaration file gives you a working structure and test format to extend, and a specific, already-reported problem gives you a clear, scoped goal rather than needing to reverse-engineer an entire library's public API surface yourself from its source or documentation.

The DefinitelyTyped review process typically involves both automated checks (the type tests, plus dtslint or the newer tsc-based linting it's since migrated toward) and human maintainer review, and it can take real back-and-forth before a contribution merges — this is normal for a shared community resource where a mistake in a widely-used declaration file would affect a large number of downstream projects at once.

This is genuinely high-leverage, low-glamour work: a good type definition helps every downstream user of that package silently, forever, without ever needing to thank the original contributor or even know their declaration file exists — it's a form of open-source contribution that's easy to overlook precisely because, when done well, nobody notices it at all.

Key points
  • DefinitelyTyped requires a companion test file (using dtslint or a similar tool) proving your types behave correctly, not just that they compile.
  • Start with a small, well-scoped package rather than a massive, actively-changing one for your first contribution.
  • Existing @types packages with open issues are often an easier entry point than starting a brand-new package's types from scratch.
  • A declaration file that compiles cleanly can still describe the wrong shape entirely — the required test file is what actually catches that.
  • The review process combines automated type-testing tools with human maintainer review, and can take genuine back-and-forth before merging.
  • This is genuinely high-leverage, low-glamour open-source work — a good type definition helps every downstream consumer silently and permanently.
  • A large, popular package's types are typically already actively maintained, making a smaller or less-attended package an easier first contribution target.
Try it yourself

Find a small npm package you use that lacks TypeScript types, check if an @types package already exists with open issues, and attempt a fix or a new minimal declaration file. Write the accompanying type test file the contribution guidelines require, and note in your own words what it verifies that a plain successful compile would not have caught on its own.
