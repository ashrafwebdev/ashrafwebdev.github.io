Designing type-safe public APIs for a library

TypeScript · part of the free zero-to-hero guide

Builds on: Type-level programming (recursive conditional types, template literal types)

When you're the one authoring a library others will depend on, your exported types ARE your API contract — a breaking type change is exactly as disruptive to consumers as a breaking runtime change, even though no runtime test might ever catch it, since the break only shows up when a consumer's own project fails to compile against the new version.

Good library type design favors clarity and stability over cleverness: minimal generic complexity at the surface, well-named exported types (not just inline anonymous object shapes buried in a function signature), and function overloads used only when they genuinely improve the calling experience, rather than as a way to paper over a poorly-designed single signature.

Exporting named interfaces and types for anything a consumer will reference directly is worth the extra effort even when an inline anonymous type would technically work — a consumer trying to write their own function that accepts your library's options object needs an actual named type to reference, and forcing them to reconstruct or copy an anonymous shape by hand is a real usability cost most library authors underestimate.

Keeping the generic surface of a public API as simple as it can be while still being genuinely useful matters because complexity compounds for every single consumer: a library author who deals with one confusing generic constraint once, while designing the API, is trading that one-time cost against every consumer having to understand the same complexity, repeatedly, for as long as they use the library.

Function overloads (multiple signatures for the same function name, each handling a different combination of argument types) are a genuinely useful tool for a public API when a single generic signature would produce a confusing or overly permissive result type — but they add real maintenance burden, since every overload needs to be kept consistent with the single actual implementation signature underneath them, and it's easy for overloads to drift out of sync as a library evolves.

Testing your published types deliberately, the same way you'd test runtime behavior, catches a category of regression that ordinary unit tests miss entirely — tools like tsd or expect-type let you write assertions purely about what type a given expression resolves to, which is the only way to reliably catch an accidental type-signature regression before it reaches consumers.

A clear public API
// Exported, named, documented — this IS the contract
export interface FetchOptions {
  retries?: number;
  timeoutMs?: number;
}

export function fetchWithRetry(url: string, options?: FetchOptions): Promise<Response> {
  /* ... */
  return fetch(url);
}
overloads-for-a-clearer-result-type.ts
// A single generic signature here would force every caller to get back
// `Element | null`, even when they already know the specific tag.
export function createElement(tag: "input"): HTMLInputElement;
export function createElement(tag: "div"): HTMLDivElement;
export function createElement(tag: string): HTMLElement {
  return document.createElement(tag);
}

const input = createElement("input"); // typed as HTMLInputElement, not HTMLElement
type-testing-the-public-api.ts
import { expectType } from "expect-type";
import { fetchWithRetry } from "./index";

// This test file never runs the function — it only checks the TYPE
// that fetchWithRetry resolves to, catching accidental signature regressions.
expectType<Promise<Response>>(fetchWithRetry("https://example.com"));
Key points
  • Exported types are as much a stability contract as your runtime API — treat type changes with the same care as breaking changes.
  • Export named interfaces/types for anything consumers will reference directly, rather than leaving them anonymous and inferred.
  • Keep the generic surface of a public API as simple as it can be while still being useful — complexity compounds for every consumer, repeatedly.
  • Function overloads can produce a clearer, more specific result type than a single generic signature, at the cost of extra maintenance burden.
  • Overload signatures must be kept consistent with the single real implementation signature underneath them as the library evolves.
  • Test your published types the same way you test runtime behavior — tools like tsd or expect-type exist for exactly this.
  • A breaking type change surfaces only when a consumer's project fails to compile, not through any runtime test, making it an easy category of regression to miss.
Try it yourself

Design and document the exported TypeScript interface for a small hypothetical library function, considering what should be required vs. optional. Then add two function overloads to the same function that narrow the return type based on a specific literal argument, and write a short type-only test asserting the resolved type of a call to it.
