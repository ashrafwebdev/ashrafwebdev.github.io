02 Learning stage capstone

A type-safe fetch() wrapper for a public API you choose

TypeScript · ties together everything in the Learning stage

This project takes the Learning-stage topics — generics, union and intersection types, enums and literal types, narrowing, and the built-in utility types — and applies all five to one real, useful piece of code: a small typed wrapper around fetch() for a public API you choose. It echoes the JavaScript track's weather-app project, but the point here is different — it's not about getting data on screen, it's about making it impossible for a caller of your client to accidentally treat a failed request as a successful one, or misuse a response's shape.

The core deliverable is a generic function that any part of your program can call and ask, right at the call site, for the specific shape it expects back — rather than writing a slightly different, hand-duplicated fetch call for every single endpoint you touch.

A constraint worth holding yourself to throughout: no bare any anywhere in code you write, including inside the fetch wrapper itself. Every result the library hands back to a caller should already carry real, specific type information by the time it reaches them.

  • Generics
  • Union and intersection types
  • Enums and literal types
  • Type narrowing and type guards
  • Built-in utility types (Partial, Pick, Omit, Record)
Requirements
  • A generic helper — something like fetchJson<T>(url: string): Promise<T> — that lets each call site ask for its own specific result type instead of getting back a bare, unchecked any.
  • A discriminated union result type (a shared literal field such as a kind property set to "success" or "error") returned by at least one function, narrowed correctly with a type guard or a switch statement before the caller ever touches the data.
  • At least one enum or string literal type union used for a fixed, small set of values — for example the HTTP methods your client sends, or a status category taken from the API's own response data.
  • At least one built-in utility type applied somewhere it removes real duplication: Partial<RequestOptions> for optional request configuration, Pick<ApiResponse, "id" | "name"> or Omit<ApiResponse, "internalId"> for a smaller display type derived from a larger response, or Record<string, ApiResponse> for a simple response cache.
  • Interfaces describing the actual JSON shape of at least two distinct responses from the real public API you're calling — written to match a response you've genuinely inspected, not guessed at.
  • The whole project compiles cleanly under strict mode, with zero implicit anys and no bare any anywhere in code you wrote yourself.
  • A small demo (a command-line script or a browser page) that calls your client and logs a result whose type you can hover in your editor and confirm is specific — not any and not unknown.
Suggested approach
  1. Pick a public API with a small, predictable, well-documented JSON response, and inspect one real response (in a browser, curl, or Postman) before writing a single type.
  2. Write interfaces matching that real response shape first, directly from what you inspected — resist the urge to guess at an idealized shape.
  3. Build the generic fetch helper next, keeping it one small, type-parameterized function rather than a separate hand-written fetch call duplicated per endpoint.
  4. Add narrowing once basic fetching works: wrap failures and successes in a discriminated union result type so callers can't accidentally use data from a failed call.
  5. Reach for a utility type only once you notice a concrete, repeated shape it would remove — apply Partial, Pick, Omit, or Record where it actually simplifies something, not everywhere you technically could.
Stretch goals
  • Add a small in-memory cache typed as Record<string, ApiResponse>, keyed by the request URL (or URL plus parameters), and confirm a repeated call reads from the cache instead of hitting the network again.
  • Support at least two different endpoints on the same API through your one generic function, rather than writing a second, near-duplicate fetch function for each.
  • Add a small retry helper that wraps your generic fetch call and retries on failure, typed generically so it works with any of your typed calls without you needing to write it twice.
