Generics

TypeScript · part of the free zero-to-hero guide

Generics let a function, interface, or class work with any type while still preserving type information — instead of writing the same logic three times for strings, numbers, and objects (or giving up and typing everything any), you write it once with a placeholder type parameter that gets filled in differently at each call site.

The convention is a single capital letter like T for the type parameter, though descriptive names like TItem or TResult help readability in more complex generic functions with several independent type parameters, the same way a descriptive variable name helps over a single letter once a function gets complicated.

TypeScript can usually infer the generic type argument automatically from how the function is actually called, without you writing it out — passing an array of strings to a generic function that takes T[] infers T as string on the spot. Explicit type arguments (firstItem<string>([...])) are only needed when inference genuinely can't determine the type from the arguments alone, which is relatively rare.

The crucial difference between a generic function and one typed with any is that a generic preserves the relationship between input and output types: firstItem called with a string[] returns a string | undefined, not any, so everything downstream of the call stays fully type-checked. An any-based version of the same function would compile identically but silently give up all of that downstream safety.

Generic interfaces and classes work the same way as generic functions — a generic interface like a Box holding a value of type T lets you write one interface that's reused for a box of strings, a box of numbers, or a box of any other type, each instance remembering its own specific T.

Multiple type parameters are common in functions that combine two independent generic inputs — a function that merges two objects, for instance, typically needs a separate type parameter for each argument so the result type can correctly reflect the combination of both, rather than forcing both arguments to share a single type.

generics.ts
function firstItem<T>(items: T[]): T | undefined {
  return items[0];
}

const firstNumber = firstItem([1, 2, 3]);       // inferred as number
const firstName = firstItem(["a", "b", "c"]);  // inferred as string
generic-interface-and-multiple-params.ts
interface Box<T> {
  value: T;
}

const numberBox: Box<number> = { value: 42 };
const stringBox: Box<string> = { value: "hi" };

function merge<T, U>(a: T, b: U): T & U {
  return { ...a, ...b };
}

const combined = merge({ name: "Amina" }, { age: 27 });
// combined is inferred as { name: string } & { age: number }
generic-vs-any.ts
function identityAny(value: any): any {
  return value;
}
const a = identityAny("hello");
a.toFixed(2); // no compile error — but this crashes at runtime

function identityGeneric<T>(value: T): T {
  return value;
}
const b = identityGeneric("hello");
// b.toFixed(2); // Error: string has no toFixed — caught before running
Key points
  • Generics preserve the specific type through a function, rather than widening everything to any and losing downstream safety.
  • TypeScript can usually infer the generic type argument from how the function is called — you rarely need to specify it explicitly.
  • Generic interfaces work the same way as generic functions, with each instance remembering its own specific type argument.
  • Multiple type parameters are common when a function combines two or more independently-typed inputs into one result.
  • A generic function called with a concrete type still gives every caller full, type-specific checking on the result — unlike an any-based equivalent.
  • Descriptive type parameter names (TItem, TResult) are worth using once a generic function has more than one or two type parameters.
  • Explicit type arguments are only needed on the rare occasions inference genuinely can't determine the type from the call site alone.
Try it yourself

Write a generic function called wrapInArray that takes a value of any type and returns a one-element array containing it, then call it with a string, a number, and an object and confirm each result is correctly and specifically typed. Then write a generic Box-style interface and create two instances of it holding different types.
