01 Zero stage capstone

Your JavaScript to-do list, rebuilt with types

TypeScript · ties together everything in the Zero stage

The five Zero-stage topics — basic types, type annotations, interfaces and type aliases, tsconfig.json basics, and compiling TS to JS — all exist to answer one question: can you take code that already works and make the compiler actively help you, instead of getting in your way? This project answers that directly by taking a small JavaScript program you already understand (ideally the console to-do list from the JavaScript track, or any small script of similar size) and porting it to TypeScript, line by line.

The constraint that makes this a real test rather than busywork: the ported program's behavior must not change at all. Every type you add should describe what the code was already doing, not redesign it — which forces you to actually understand what each function and variable was doing well enough to name its type correctly, rather than copying types you don't fully understand.

By the end you'll have a working tsconfig.json, a file that compiles cleanly with tsc, and a first real feel for the moment strict mode starts catching mistakes your original JavaScript was quietly letting through.

  • Basic types: string, number, boolean, array, any
  • Type annotations on variables and functions
  • Interfaces and type aliases
  • tsconfig.json basics
  • Compiling TS to JS
Requirements
  • Your original JavaScript file's behavior is fully preserved — the compiled output still does exactly what the JavaScript version did, with no new or changed features.
  • At least one interface (for example, describing a single to-do item's shape) used everywhere that shape appears, replacing loose, untyped object literals.
  • Every function parameter and every function's return type is explicitly annotated — no unannotated parameter left to silently become any.
  • Arrays are typed using the T[] element-type syntax consistently (for example string[], or your interface name followed by []), never left as an untyped or any[] array.
  • A tsconfig.json with "strict": true, a reasonable target, and an include pointing at your source — and the project compiles with zero errors under it.
  • One deliberate, clearly-commented experiment: a single function given an intentionally any-typed parameter, called once with a wrong-shaped argument, with a comment noting exactly where the mistake actually surfaced at runtime — then reverted back to a properly typed parameter before you call the project finished.
Suggested approach
  1. Copy your working JavaScript file to a .ts extension and run tsc --init in the project folder — read through the generated tsconfig.json before changing anything.
  2. Get the file compiling as-is first, with implicit any allowed everywhere, and confirm the compiled output still runs exactly like the original JavaScript did.
  3. Define your interface for the program's core data shape, and replace loose object literals and array declarations with values that match it.
  4. Annotate every function's parameters and return type next, fixing whatever errors that surfaces one at a time rather than all at once.
  5. Turn on strict mode last, and work through the new errors it reveals — this is usually where the real, previously-invisible bugs show up.
Stretch goals
  • Add a small status-style field using a type alias for a fixed set of string literals (the same pattern shown in the interfaces-and-type-aliases lesson), and update every place that field is assigned so it only ever uses one of the allowed values.
  • Turn on just noImplicitAny first, before flipping on full strict mode, and compare how many errors each one reports on the same file.
  • Enable "sourceMap": true and step through the compiled JavaScript in your browser or Node's inspector while watching the original TypeScript source line light up.
