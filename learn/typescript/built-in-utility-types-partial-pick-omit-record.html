Built-in utility types (Partial, Pick, Omit, Record)

TypeScript · part of the free zero-to-hero guide

TypeScript ships a set of generic utility types that transform existing types instead of requiring you to redefine them from scratch. The version of a type wrapped with Partial makes every property optional — perfect for an 'update' function that only changes some fields of an entity, without needing a completely separate interface just for that partial payload.

The Pick and Omit utilities create a new type from a subset (or everything except a subset) of another type's properties, letting narrower, purpose-built types stay derived from one source of truth rather than being hand-copied and risking drifting out of sync as the original type changes over time.

The Record utility builds an object type mapping a set of keys to a consistent value type — it's the idiomatic way to type an object used purely as a lookup map or dictionary, and reads more clearly than the equivalent index signature syntax for the common case of a known or generic key type.

Required is the direct opposite of Partial: it strips optionality from every property, forcing every field to be present. This is genuinely useful after validating an input object, when you want the rest of your code to be able to rely on every field actually being there without repeated undefined checks.

Readonly wraps every property with the readonly modifier, which is useful for representing a value that should never be mutated after creation — though it's worth remembering this is a shallow, compile-time-only guarantee: it doesn't deep-freeze nested objects, and nothing stops a runtime caller who ignores the type error from mutating the object anyway.

These utility types are not special compiler magic — they're just generics defined using mapped types and conditional types you can write yourself, and TypeScript's own standard library source for them (in lib.es5.d.ts) is genuinely short and readable, making it a great next step once these become comfortable to use.

utilityTypes.ts
interface User {
  id: number;
  name: string;
  email: string;
}

function updateUser(id: number, changes: Partial<User>) { /* ... */ }

type UserPreview = Pick<User, "id" | "name">;
type UserWithoutId = Omit<User, "id">;
type UsersById = Record<number, User>;
required-and-readonly.ts
interface DraftEvent {
  title?: string;
  date?: string;
}

function publish(event: Required<DraftEvent>) {
  // safe to use event.title and event.date directly, no undefined checks
  console.log(`${event.title} on ${event.date}`);
}

const config: Readonly<{ retries: number }> = { retries: 3 };
// config.retries = 5; // Error: cannot assign to a readonly property
combining-utilities.ts
interface Product {
  id: number;
  name: string;
  price: number;
  description: string;
}

// Combine utilities: an update payload that's a partial version
// of everything except the immutable id field
type ProductUpdate = Partial<Omit<Product, "id">>;

function updateProduct(id: number, changes: ProductUpdate) { /* ... */ }
Key points
  • The Partial utility makes every property optional; the Required utility does the opposite, making every property mandatory.
  • Pick selects specific keys from a type; Omit excludes them — often used together across an app's derived types.
  • Record is the idiomatic way to type an object used as a lookup map, mapping a set of keys to a consistent value type.
  • Readonly prevents reassignment of top-level properties at compile time — it's a shallow guarantee, not a deep freeze.
  • Utility types can be composed together, like a Partial wrapped around an Omit, to express precise derived shapes.
  • These utility types are just generics defined using mapped and conditional types you already have access to — nothing about them is special compiler magic.
  • Deriving narrower types from one source interface (via Pick/Omit) keeps related types in sync automatically as the source evolves.
Try it yourself

Given a User interface, define UserPreview (a Pick of id and name), UpdatePayload (a Partial of the whole interface), and UsersById (a Record keyed by id) using the built-in utility types. Then combine two utilities together to express an update payload that excludes the id field entirely and makes every remaining field optional.
