ActiveRecord basics

Ruby · part of the free zero-to-hero guide

ActiveRecord is Rails' built-in ORM (object-relational mapper) — a Ruby class like Book maps directly to a books database table, and instances of that class map to individual rows, with no manual SQL required for common operations. It follows the Active Record architectural pattern its name comes from: each model object both represents a row of data and knows how to persist itself.

Migrations are version-controlled, incremental changes to your database schema, written in Ruby (translated into the appropriate SQL for whichever database you're using) and run with rails db:migrate. Each migration is timestamped and reversible where possible, keeping your schema's history in sync with your codebase's own git history, and letting a team apply the exact same sequence of schema changes in the same order on every machine.

Model.create, .find, .find_by, .where, .update, and .destroy cover the vast majority of everyday database work. .where in particular is lazy — it returns an ActiveRecord::Relation, not an already-executed query — which means you can keep chaining additional conditions onto it, and the actual SQL query only runs once you do something that needs the real data, like iterating over it or calling .to_a.

Validations (validates :title, presence: true) enforce data integrity at the model level, running automatically before a record is saved through ActiveRecord and rejecting invalid data before it ever reaches the database. It's important to understand that validations only run through ActiveRecord's own save path — a raw SQL update or a bulk operation like update_all bypasses them entirely, which is a common source of subtly invalid data slipping through.

ActiveRecord builds parameterized SQL queries for you internally, which means it is safe from SQL injection by default when used idiomatically (where(name: params[:name])). That safety disappears the moment you interpolate a raw value directly into a string passed to where or a similar method, so string interpolation inside a where clause is a red flag worth catching in code review.

Associations like belongs_to and has_many generate a family of convenience methods for you (book.author, author.books, author.books.build), and accessing them naively inside a loop is the classic source of the N+1 query problem — fetching one query for the outer collection, then one additional query per item for the association — which includes solves by loading everything in a small, fixed number of queries up front.

Using a model
book = Book.create(title: "Ruby Basics", author: "Amina")

Book.where(author: "Amina").each do |b|
  puts b.title
end

book.update(title: "Ruby Basics, 2nd Edition")
Migration + validation
# db/migrate/20240101000000_create_books.rb
class CreateBooks < ActiveRecord::Migration[7.0]
  def change
    create_table :books do |t|
      t.string :title, null: false
      t.string :author
      t.timestamps
    end
  end
end

class Book < ApplicationRecord
  validates :title, presence: true, length: { minimum: 2 }
end
Chained queries and the N+1 fix
# Lazy chaining -- one query fires at the very end
recent_by_amina = Book.where(author: "Amina")
                       .where("created_at > ?", 1.week.ago)
                       .order(created_at: :desc)

# N+1: 1 query for books, then 1 per book for its author
Book.all.each { |b| puts b.author.name }

# Fixed: 2 queries total, regardless of how many books there are
Book.includes(:author).each { |b| puts b.author.name }
Key points
  • Model.create, .find, .where, .update, .destroy cover the vast majority of everyday database work.
  • Migrations (rails generate migration) are how schema changes are made and tracked over time, in order, and shared across a whole team.
  • Validations (validates :title, presence: true) enforce data integrity at the model level before saving, but only through ActiveRecord's own save path.
  • .where returns a lazy ActiveRecord::Relation -- the SQL query doesn't actually run until the data is needed.
  • ActiveRecord builds SQL for you using parameterized queries internally -- safe from SQL injection by default when used idiomatically.
  • Bulk operations like update_all bypass both validations and callbacks, which is a deliberate tradeoff for speed that's easy to forget.
  • N+1 queries from unoptimized association access are a common Rails performance trap -- includes solves it by eager loading.
Try it yourself

Create a Rails model with a migration, add a presence validation on one field, and use the Rails console to create, find, and update a record. Then create a second, associated model with a has_many/belongs_to relationship, deliberately trigger an N+1 query by looping over the parent and accessing the association, and fix it with includes.
