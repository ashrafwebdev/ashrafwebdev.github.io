Rails deep dive: associations, validations, callbacks

Ruby · part of the free zero-to-hero guide

Builds on: Metaprogramming basics

Associations (has_many, belongs_to, has_and_belongs_to_many, has_many :through) declare relationships between models, letting ActiveRecord generate the methods and queries needed to navigate between related records naturally, like author.books or book.author. has_many :through in particular models a many-to-many relationship through an explicit join model, which is usually preferable to has_and_belongs_to_many the moment the relationship itself needs any attributes of its own, like a timestamp or a role.

The foreign key convention matters: belongs_to :author expects an author_id column on that model's own table by default, and belongs_to associations are required (must be present) by default in Rails 5 and later, meaning a record without its association fails validation unless you explicitly mark it optional: true.

Validations run automatically before saving a record through ActiveRecord's normal save path, rejecting invalid data before it reaches the database — common built-ins include presence, uniqueness, length, numericality, and format, and custom validations can be added as a method marked with validate :method_name for logic too specific for the built-in helpers to express.

Callbacks (before_validation, before_save, after_create, after_commit, and many more) hook into a record's lifecycle to run code at specific points automatically. They're useful for things like normalizing data before it's saved, but they run implicitly every time their trigger occurs anywhere in the codebase, which makes them easy to overuse into hidden, hard-to-trace behavior — a chain of several callbacks across a few models can make it genuinely difficult to answer 'what actually happens when I save this record?' just by reading the model itself.

after_commit is worth knowing specifically because it only fires once a database transaction has actually committed, unlike after_save, which fires inside the transaction and can end up running for a save that's later rolled back — this distinction matters a lot for callbacks that have external side effects, like sending an email or enqueuing a background job, since you generally don't want those to fire for a change that never actually persisted.

N+1 queries from unoptimized association access are one of the most common real-world Rails performance issues, and they get worse specifically because associations make accessing related data look so effortless — book.author.name inside a loop reads perfectly innocently, and includes (or eager_load for association-based where clauses) is the standard fix, loading the association data in a small, fixed number of additional queries instead of one per record.

models/author.rb + book.rb
class Author < ApplicationRecord
  has_many :books, dependent: :destroy
end

class Book < ApplicationRecord
  belongs_to :author
  validates :title, presence: true, uniqueness: { scope: :author_id }
  before_save :normalize_title

  private

  def normalize_title
    self.title = title.strip
  end
end
has_many :through -- a many-to-many with attributes
class Book < ApplicationRecord
  has_many :reviews
  has_many :reviewers, through: :reviews, source: :user
end

class Review < ApplicationRecord
  belongs_to :book
  belongs_to :user
  validates :rating, numericality: { in: 1..5 }
end

book.reviewers  # every User who reviewed this book, via Review
after_commit vs after_save
class Book < ApplicationRecord
  after_save   { Rails.logger.info("saved -- may still roll back!") }
  after_commit { NotifyLibraryJob.perform_later(id) }  # perform_later enqueues a background job (its own lesson later) -- only fires if the save really committed
end
Key points
  • has_many/belongs_to pairs must be declared on both sides of a relationship to work correctly.
  • belongs_to associations are required by default since Rails 5 -- mark one optional: true if it should be allowed to be blank.
  • has_many :through is usually the better choice over has_and_belongs_to_many once the join itself needs its own attributes.
  • Validations run on save/create, not automatically on direct database writes that bypass ActiveRecord.
  • Callbacks run implicitly whenever their trigger occurs -- overusing them can make it hard to trace what actually happens when a record saves.
  • after_commit only fires once a transaction truly commits, unlike after_save, which matters for side effects like emails or background jobs.
  • N+1 queries from unoptimized association access are a common Rails performance trap -- includes solves it by eager loading.
  • dependent: :destroy on a has_many controls what happens to child records when the parent is deleted -- easy to forget and leave orphaned rows otherwise.
Try it yourself

Add a has_many/belongs_to association between two models, a presence validation, and a before_save callback that normalizes one field. Then add a third model connected through has_many :through, write a custom validation method (not just a built-in helper) on one of the models, and add an after_commit callback that logs a message, verifying it does not fire when a save is deliberately rolled back inside a transaction.
