03 Advanced stage capstone

Turn RecipeBox into a tested, job-backed, API-ready service

Ruby · ties together everything in the Advanced stage

This project takes the RecipeBox app you built in the Learning stage and pushes it toward production quality, exercising every Advanced-stage topic in one connected piece of work rather than as isolated exercises: metaprogramming, deeper ActiveRecord associations with validations and callbacks, a real RSpec test suite, a background job, and an API-only surface alongside the existing web pages.

The unifying theme is trustworthiness under change: a test suite that actually catches regressions, background work that doesn't block the request cycle, and an API other clients could consume safely. None of this is about adding features for their own sake — it's about making the existing app resilient enough that you (or a future collaborator) could keep extending it without fear of quietly breaking something.

If you didn't build the Learning-stage RecipeBox, or want a clean slate, rebuild a small version of it first — this project assumes a Rails app with at least a Recipe model and basic CRUD already in place, since the point here is deepening what already exists, not starting from zero again.

  • Metaprogramming basics
  • Rails deep dive: associations, validations, callbacks
  • Testing with RSpec
  • Background jobs (Sidekiq/ActiveJob)
  • API-only Rails apps
Requirements
  • A second model associated with Recipe via has_many :through (for example, Recipe has_many :ratings, and ratings belong to a User), with at least one custom validation method beyond a built-in helper like presence or length.
  • A before_save or before_validation callback that normalizes some piece of recipe data (for example, trimming and titleizing the recipe title), plus an after_commit callback that logs or triggers a side effect, with a comment explaining why after_commit was chosen over after_save for that particular effect.
  • An RSpec suite with at least one model spec covering a validation, one request spec covering an index or show endpoint, and factories (via factory_bot) used instead of hand-built test objects.
  • A background job (ActiveJob, run with Sidekiq or the default async adapter) that performs a small piece of real work, like sending a Recipe's ingredients through an outbound notification or writing a digest to a log file, enqueued from a controller action with perform_later.
  • At least one deliberate use of metaprogramming — either a define_method-generated set of methods, or a method_missing implementation paired correctly with respond_to_missing? — applied somewhere it genuinely simplifies the code, with a code comment explaining the tradeoff you're making.
  • An API-only namespace under /api/v1 exposing recipes as JSON through a serializer (not raw render json: object), returning only the fields you deliberately chose to expose.
  • A deliberately introduced and then fixed N+1 query on the recipes-with-ratings view, demonstrated with a before/after comparison (for example, logging query counts, or using the bullet gem) showing includes fixing it.
Suggested approach
  1. Add the second model and its association first, along with the custom validation and callbacks, and confirm the association works correctly from the Rails console before writing any tests against it.
  2. Write the RSpec suite next, starting with model specs for the validations you just added, then a request spec for an existing endpoint — this locks in current behavior before you start changing more of the app.
  3. Add the background job, keeping its perform method small and idempotent, and write a spec for it using perform_now so the test stays fast and deterministic.
  4. Build the API namespace and serializer once the underlying model logic is stable, since the API is just another view onto data you've already validated works.
  5. Do the metaprogramming and the N+1 demonstration last — both are refinements on top of a working app, and they're easier to justify once you can see exactly what problem they're solving in your own code.
Stretch goals
  • Add request-level rate limiting or basic token authentication to the API namespace so it isn't fully open.
  • Write a benchmark-ips comparison between two different implementations of one piece of recipe-formatting logic, and keep whichever one measurably wins.
  • Add a system spec (using Capybara) that drives the recipe creation form through an actual simulated browser, in addition to the model and request specs.
