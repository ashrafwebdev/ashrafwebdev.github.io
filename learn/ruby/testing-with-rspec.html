Testing with RSpec

Ruby · part of the free zero-to-hero guide

RSpec is Ruby's most popular testing framework, favoring a readable, English-like syntax: describe groups related tests around a class or a specific behavior, context further groups examples by a particular condition or scenario, it defines an individual example with a description of the expected behavior, and expect(...).to makes the actual assertion.

Rails integrates deeply with RSpec through the rspec-rails gem, adding specialized spec types for each architectural layer — model specs for validations and business logic in isolation, request specs for full HTTP request/response cycles through the actual routing and controller stack, and system specs for full browser-driven end-to-end tests — each with helpers tailored to what that particular layer needs to verify.

Matchers are what make an assertion read naturally: expect(x).to eq(y) for exact equality, be_valid/be_truthy for predicate-style checks, include for collection membership, and raise_error for exceptions. RSpec also supports negation directly (expect(x).not_to eq(y)) rather than requiring a separate assertion style for the negative case.

Factories, most commonly built with the factory_bot gem, are the idiomatic way to build realistic test data instead of hand-writing static YAML fixtures. A factory defines sensible defaults for a model's attributes, and each spec can override only the specific attributes that matter for that particular test, keeping the setup code focused on what's actually relevant to what's being tested.

before hooks run shared setup code before each example (or once per group with before(:all), though per-example setup with before(:each), the default, is by far the more common and generally safer choice, since it avoids state leaking between tests). let and let! memoize a value lazily per example — let only actually creates the value the first time it's referenced inside an example, while let! forces it to be created eagerly before every example runs, whether it's referenced or not.

A well-organized spec suite tests behavior, not implementation — asserting on what a method returns or what side effect it produces, rather than exactly how it internally accomplishes that, which keeps the tests useful as a safety net during refactoring instead of becoming brittle and needing constant updates for changes that don't actually change the code's observable behavior.

spec/models/book_spec.rb
require "rails_helper"

RSpec.describe Book, type: :model do
  it "is invalid without a title" do
    book = Book.new(title: nil)
    expect(book).not_to be_valid
  end
end
spec/models/book_spec.rb -- factories and let
RSpec.describe Book, type: :model do
  let(:author) { create(:author) }
  let(:book)   { build(:book, author: author, title: "Ruby Basics") }

  context "with a valid title" do
    it "saves successfully" do
      expect { book.save! }.not_to raise_error
    end
  end

  context "without a title" do
    before { book.title = nil }

    it "is invalid" do
      expect(book).to be_invalid
      expect(book.errors[:title]).to include("can't be blank")
    end
  end
end
spec/requests/books_spec.rb
RSpec.describe "Books API", type: :request do
  it "returns a list of books" do
    create_list(:book, 3)
    get "/books.json"

    expect(response).to have_http_status(:ok)
    expect(JSON.parse(response.body).size).to eq(3)
  end
end
Key points
  • describe/context group examples; it defines one specific expected behavior.
  • expect(x).to eq(y) and its many matcher variants read close to natural English, including negation with not_to.
  • Factories (via the factory_bot gem) are the idiomatic way to build test data instead of hand-writing fixtures.
  • Request specs test full HTTP request/response cycles; model specs test validations and business logic in isolation.
  • let lazily memoizes a value the first time it's referenced in an example; let! creates it eagerly before every example.
  • before hooks run shared setup before each example -- per-example (:each) is the default and generally safer than per-group.
  • Good specs test observable behavior, not internal implementation, so they stay useful as a safety net through refactors.
Try it yourself

Write an RSpec model spec with two examples: one confirming a valid record saves, one confirming an invalid record (missing a required field) doesn't, using a factory_bot factory instead of hand-built objects. Then write a request spec that hits an index endpoint and asserts both the HTTP status and the number of records returned, using let to set up the test data.
