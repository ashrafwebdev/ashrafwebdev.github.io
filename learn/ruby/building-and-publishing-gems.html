Building and publishing gems

Ruby · part of the free zero-to-hero guide

bundle gem my_gem_name scaffolds a new gem's structure — a gemspec file for metadata, a lib folder for the actual code, and a spec (or test) folder ready to go, along with a README, license file, and CHANGELOG stub — a complete, conventional gem structure in one command, ready to build and publish to RubyGems.org.

A gemspec declares the gem's name, version, summary, author, license, runtime and development dependencies, and which files to actually include in the packaged gem. Getting the file list right matters: including test files or development-only assets bloats the published gem unnecessarily, while accidentally excluding a required file breaks it for every user who installs it.

Semantic versioning (MAJOR.MINOR.PATCH) genuinely matters once other projects depend on your gem in production — a patch release should only fix bugs without changing behavior anyone could reasonably depend on, a minor release adds functionality in a backward-compatible way, and a major release is the only place a breaking change belongs, since consumers commonly pin their Gemfile with the pessimistic operator specifically to avoid getting an unexpected major-version break.

gem build my_gem.gemspec packages the gem locally into a .gem file, which you can install and test directly with gem install ./my_gem-0.1.0.gem before ever publishing it — a good habit to catch packaging mistakes (like a missing file) before they reach real users.

gem push my_gem-0.1.0.gem publishes the built package to RubyGems.org, the canonical public registry, making it installable by anyone with gem install my_gem or addable to any project's Gemfile — publishing requires an account on RubyGems.org and, once published, a given version number can never be reused, even if you immediately yank it.

A clear README explaining what the gem does, a quick installation and usage example, and an up-to-date CHANGELOG documenting what changed in each release make a genuine difference in whether a published gem actually gets adopted and trusted — the code itself being good is necessary but nowhere near sufficient for a gem to gain real usage.

my_gem.gemspec
Gem::Specification.new do |spec|
  spec.name = "my_gem"
  spec.version = "0.1.0"
  spec.summary = "A short, clear description"
  spec.authors = ["Amina"]
  spec.license = "MIT"
  spec.files = Dir["lib/**/*.rb"] + ["README.md", "LICENSE.txt"]
  spec.add_dependency "activesupport", ">= 6.0"
  spec.add_development_dependency "rspec", "~> 3.0"
end
lib/my_gem.rb + a spec
# lib/my_gem.rb
module MyGem
  def self.shout(text)
    "#{text.upcase}!"
  end
end

# spec/my_gem_spec.rb
require "my_gem"

RSpec.describe MyGem do
  it "upcases and adds an exclamation mark" do
    expect(MyGem.shout("hello")).to eq("HELLO!")
  end
end
Terminal -- build, install locally, publish
$ gem build my_gem.gemspec
$ gem install ./my_gem-0.1.0.gem   # test it locally first
$ irb -r my_gem -e 'puts MyGem.shout("hi")'
$ gem push my_gem-0.1.0.gem        # publish to RubyGems.org
Key points
  • bundle gem name scaffolds a complete, conventional gem structure, including a test setup, in one command.
  • The gemspec's file list controls exactly what ships in the package -- get it wrong and you either bloat the gem or ship something broken.
  • Semantic versioning matters once other projects depend on your gem in production, especially since consumers often pin with the pessimistic operator.
  • gem build packages the gem locally, letting you test-install it before ever publishing, catching packaging mistakes early.
  • RubyGems.org is the canonical public registry -- gem push publishes there directly, and a published version number can never be reused.
  • A clear README and an up-to-date CHANGELOG make a real difference in whether a published gem actually gets adopted.
  • Development-only dependencies belong in add_development_dependency, not the main dependency list, so consumers of the gem don't install tools they'll never use.
Try it yourself

Scaffold a gem with bundle gem, implement one small utility method in it, write a test for it, and build it locally with gem build. Then install the built .gem file locally with gem install and confirm the method works from a fresh irb session, and write a gemspec entry declaring one runtime dependency with an appropriate semantic version constraint.
