Gems and Bundler

Ruby · part of the free zero-to-hero guide

A gem is a packaged Ruby library, installed with gem install or, more commonly in a real project, declared in a Gemfile and installed together with Bundler — Ruby's dependency manager, bundled with Ruby itself since version 2.6. Working directly with gem install for a project's dependencies is generally discouraged, because it gives you no record of exactly what a project needs to run.

Bundler resolves compatible versions for every gem a project needs — including the transitive dependencies of those gems — and records the exact resolved version of each one in Gemfile.lock. Committing that lock file means every developer, CI run, and production server installs identical gem versions, eliminating an entire class of 'works on my machine' bugs caused by subtly different dependency versions.

Version constraints in a Gemfile control how much freedom Bundler has when resolving a version: "7.0.0" pins an exact version, ">= 7.0" allows anything newer, and the pessimistic operator "~> 7.0" allows patch and minor updates (7.1, 7.0.5) but blocks an accidental jump to a new major version (8.0) that might break compatibility.

bundle exec command runs a command using the exact gem versions specified in the lock file, rather than whatever version happens to be installed globally on the system — this matters a lot when multiple projects on the same machine depend on different, conflicting versions of the same gem, since without bundle exec a command might silently pick up the wrong one.

Gems can be grouped in a Gemfile (group :development, :test do ... end), so that, for instance, testing and debugging tools are installed locally but excluded from a production deployment with bundle install --without development test, keeping the production install lighter and faster.

Beyond the public registry, Bundler can also pull a gem straight from a git repository or a local path — gem "my_gem", git: "..." or path: "../my_gem" — which is especially useful while developing a gem alongside the application that consumes it, before it's ready to be published.

Gemfile
source "https://rubygems.org"

gem "rails", "~> 7.0"
gem "pg"

group :development, :test do
  gem "rspec-rails"
  gem "pry"
end

# Terminal:
# bundle install
Terminal -- everyday Bundler commands
$ bundle install                      # resolve + install, write Gemfile.lock
$ bundle exec rspec                   # run rspec using the locked versions
$ bundle update rspec-rails           # bump only that gem, within constraints
$ bundle install --without development test  # production install
Gemfile -- git and local path sources
gem "my_gem", git: "https://github.com/me/my_gem", branch: "main"
gem "internal_tool", path: "../internal_tool"  # develop it alongside the app
Key points
  • bundle install reads the Gemfile, resolves versions, and writes/updates Gemfile.lock.
  • Always commit Gemfile.lock -- it guarantees everyone installs the exact same gem versions.
  • bundle exec command runs a command using the exact gem versions specified in the lock file, not whatever happens to be globally installed.
  • Version constraints like "~> 7.0" allow patch/minor updates but prevent an accidental major version jump.
  • Gemfile groups (group :development, :test) let you exclude non-production gems from a production install.
  • Bundler can install a gem directly from a git repository or a local path, useful when developing a gem alongside its consuming app.
  • Gemfile.lock also pins the transitive dependencies of your direct dependencies, not just the gems you listed yourself.
Try it yourself

Create a Gemfile requiring a small gem, run bundle install, and use the gem in a short script run with bundle exec. Then add a second gem inside a development-only group, run bundle install --without development to confirm it's skipped, and explain in a comment what Gemfile.lock changed between the two installs.
