API-only Rails apps

Ruby · part of the free zero-to-hero guide

Builds on: Background jobs (Sidekiq/ActiveJob)

Rails can run in API-only mode (rails new myapp --api), stripping out view-rendering, the asset pipeline, and other browser-facing middleware not needed when the app only returns JSON to a separate frontend, mobile app, or other service — the result is a smaller, leaner middleware stack tailored specifically to serving an API rather than rendering HTML pages.

Controllers in API mode render JSON directly rather than HTML views. render json: object serializes an ActiveRecord object (or a whole collection) to JSON automatically using its column names as keys, which is convenient to start with but gives you little explicit control over exactly which fields end up in the response — every column gets included by default, including ones you may not want exposed, like internal timestamps or a password digest.

A serializer gem — commonly active_model_serializers or the more actively maintained jsonapi-serializer (formerly fast_jsonapi) — gives explicit, deliberate control over exactly which fields appear in the JSON output and how associated records are nested or linked, rather than dumping every database column by default. This matters for both security (not leaking internal fields) and API stability (the JSON shape doesn't silently change whenever someone adds a new database column).

CORS (Cross-Origin Resource Sharing) configuration, typically via the rack-cors gem, is usually necessary the moment the API is consumed by a frontend running on a different domain or port than the API itself — without it, a browser will block the frontend's JavaScript from actually reading the API's response, even though the request itself succeeds at the network level, which is a confusing failure mode the first time you hit it.

Authentication in an API-only app typically differs from a traditional server-rendered Rails app, since there's no browser session or CSRF-protected form to rely on in the same way — token-based approaches (a JWT, or an opaque API token stored and checked against the database) sent in an Authorization header are the common pattern, verified on each request rather than relying on a server-side session.

Versioning an API early — even something as simple as namespacing routes and controllers under /api/v1/ — pays off once the API has real external consumers, since it gives you a clean way to introduce a breaking change in a new version without immediately forcing every existing client to update at the same time.

app/controllers/books_controller.rb (API mode)
class BooksController < ApplicationController
  def index
    render json: Book.all
  end

  def show
    render json: Book.find(params[:id])
  end
end
serializer + namespaced routes
# app/serializers/book_serializer.rb
class BookSerializer
  include JSONAPI::Serializer
  attributes :title, :author
end

# app/controllers/api/v1/books_controller.rb
class Api::V1::BooksController < ApplicationController
  def index
    render json: BookSerializer.new(Book.all).serializable_hash
  end
end

# config/routes.rb
namespace :api do
  namespace :v1 do
    resources :books, only: [:index, :show]
  end
end
config/initializers/cors.rb
Rails.application.config.middleware.insert_before 0, Rack::Cors do
  allow do
    origins "https://myfrontend.example.com"
    resource "/api/*",
      headers: :any,
      methods: [:get, :post, :patch, :delete]
  end
end
Key points
  • rails new --api configures a leaner middleware stack tailored specifically for JSON APIs.
  • render json: object serializes an ActiveRecord object (or array) to JSON automatically, including every column by default.
  • A serializer gem gives explicit, deliberate control over exactly which fields appear in the JSON output, rather than dumping every column.
  • CORS configuration (via the rack-cors gem) is usually necessary when the API is consumed by a separate frontend on a different domain.
  • Token-based authentication (JWT or an API token in an Authorization header) is the common pattern for API-only apps, in place of session cookies.
  • Namespacing routes and controllers under /api/v1/ early makes it much easier to introduce a breaking change later without disrupting existing clients.
  • Without correct CORS headers, a browser blocks the frontend from reading the response even though the request itself reaches the server successfully.
Try it yourself

Generate an API-only Rails app with one resourceful controller, and confirm index and show actions return correctly formatted JSON. Then add a serializer gem to explicitly control the returned fields, namespace the routes and controller under api/v1, and configure rack-cors to allow requests from a specific frontend origin.
