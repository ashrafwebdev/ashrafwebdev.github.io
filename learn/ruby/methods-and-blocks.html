Methods and blocks

Ruby · part of the free zero-to-hero guide

Methods are defined with def name(params) ... end. Ruby methods implicitly return the value of their last evaluated expression — an explicit return is entirely optional and is used mainly for early exits from inside a method body, such as guard clauses at the top.

Ruby supports default parameter values, keyword arguments, and splat arguments for variable-length argument lists. Keyword arguments (def greet(name:, greeting: "Hello")) are especially common in real-world Ruby and Rails code because they make call sites self-documenting — you can immediately see which value is which without checking the method's definition.

A block is a chunk of code passed to a method, written with do...end or curly braces, and it is central to idiomatic Ruby. Most collection operations — each, map, select, reduce — work by yielding each element to a block you supply, which is how Ruby achieves so much with so little explicit looping code.

A method receives a block implicitly; inside the method body, yield invokes whatever block the caller passed, and block_given? checks whether one was passed at all before trying to yield to it. A block can also be captured explicitly as a Proc object by prefixing the last parameter with &, which lets you store it, pass it along to another method, or call it later with .call.

Procs and lambdas are both ways to hold a block of code as a first-class value, but they differ subtly: a lambda enforces the exact number of arguments it was defined with and a return inside a lambda only exits the lambda itself, while a return inside a plain proc actually returns from the enclosing method — a distinction that trips up almost everyone the first time they hit it.

By convention, a method name ending in ? (like empty? or nil?) returns a boolean, and a method name ending in ! signals that it mutates the receiver or otherwise behaves more dangerously than its non-bang counterpart. Ruby doesn't enforce either convention mechanically — they are promises the method's author makes to callers, and well-behaved libraries stick to them closely.

methods.rb
def greet(name)
  "Hello, #{name}!"  # implicitly returned, no `return` needed
end

puts greet("Yusuf")

[1, 2, 3].each do |n|
  puts n * 2
end
args_and_yield.rb
def order_summary(item, qty: 1, **options)
  "#{qty}x #{item}" + (options.empty? ? "" : " (#{options})")
end

puts order_summary("Widget", qty: 3, gift_wrap: true)

def repeat(n)
  return enum_for(:repeat, n) unless block_given?

  n.times { |i| yield i }
end

repeat(3) { |i| puts "call ##{i}" }
proc_vs_lambda.rb -- the return gotcha
def uses_proc
  p = Proc.new { return 10 }
  p.call
  puts "never reached"  # proc's return exits the whole method
end

def uses_lambda
  l = lambda { return 10 }
  l.call
  puts "this DOES print"  # lambda's return only exits the lambda
end

Key points
  • The last evaluated expression in a method is returned automatically — explicit return is a stylistic choice for clarity or early exit.
  • do...end is conventional for multi-line blocks; { } is conventional for short, single-line blocks.
  • A method can accept a block implicitly and invoke it with yield; check block_given? before yielding if the block is optional.
  • Keyword arguments make call sites self-documenting and are the idiomatic default for methods with several optional parameters.
  • A return inside a lambda exits only the lambda; a return inside a plain Proc exits the enclosing method entirely.
  • Lambdas strictly check their argument count; procs are lenient and silently ignore extra or missing arguments.
  • Method names ending in ? (like empty?) conventionally return a boolean; names ending in ! conventionally signal a more dangerous or mutating variant.
  • Prefixing a parameter with & captures a passed block as an explicit Proc object you can store or forward.
