Designing distributed systems in Go

Go · part of the free zero-to-hero guide

Builds on: Performance profiling (pprof) and optimization

Go's lightweight goroutines, fast compilation, and small static binaries make it a common choice for the networked services that make up a distributed system — API gateways, message consumers, and internal RPC services alike — and its strong standard library for networking (net, net/http, net/rpc) means many building blocks don't require third-party dependencies at all.

For service-to-service communication, Go projects commonly choose between JSON over HTTP for simplicity, human-readability, and broad compatibility with any client language, or gRPC (with Protocol Buffers) for strongly-typed, efficient binary communication, built-in streaming support (unary, server-streaming, client-streaming, and bidirectional), and code generation that keeps client and server in sync as the API evolves.

Distributed systems must handle partial failure as the normal case, not an exception: any given dependency can be slow, unreachable, or returning errors at any moment, and a well-designed Go service degrades gracefully rather than cascading that failure — patterns like retries with exponential backoff (ideally with jitter added to avoid many clients retrying in lockstep) and circuit breakers (which stop calling a dependency that's clearly failing, giving it time to recover instead of piling on more load) are standard tools.

Idempotent request handling — often via an idempotency key the client generates and the server deduplicates on — is essential once retries are in play, since a retried request might actually have succeeded the first time and the response simply got lost in transit; without idempotency, a naive retry of a "charge this card" request could charge it twice.

Message queues and event streams (Kafka, NATS, RabbitMQ, or cloud-managed equivalents) decouple producers from consumers in time, letting a slow or temporarily-down consumer catch up later rather than blocking the producer, and Go's small memory footprint and fast startup make consumer processes cheap to run many of, horizontally scaling consumption by adding more instances reading from different partitions.

Consistent, structured logging with a correlation or trace ID threaded through every log line and every downstream call is what makes a distributed failure debuggable at all — without it, reconstructing what happened to one specific failed request across a dozen services means grepping timestamps and guessing, so this is worth setting up from day one rather than retrofitting under pressure.

retry.go
func callWithRetry(fn func() error, attempts int) error {
	var err error
	for i := 0; i < attempts; i++ {
		if err = fn(); err == nil {
			return nil
		}
		time.Sleep(time.Duration(i+1) * 200 * time.Millisecond)
	}
	return err
}
retry_with_jitter_and_ctx.go
package main

import (
	"context"
	"math/rand"
	"time"
)

func callWithBackoff(ctx context.Context, fn func() error, attempts int) error {
	var err error
	for i := 0; i < attempts; i++ {
		if err = fn(); err == nil {
			return nil
		}

		base := time.Duration(1<<i) * 100 * time.Millisecond
		jitter := time.Duration(rand.Int63n(int64(base) / 2))

		select {
		case <-time.After(base + jitter):
		case <-ctx.Done():
			return ctx.Err()
		}
	}
	return err
}
circuit_breaker_sketch.go
package main

import (
	"errors"
	"sync"
	"time"
)

var ErrCircuitOpen = errors.New("circuit breaker is open")

type CircuitBreaker struct {
	mu          sync.Mutex
	failures    int
	threshold   int
	openedAt    time.Time
	cooldown    time.Duration
}

func (cb *CircuitBreaker) Call(fn func() error) error {
	cb.mu.Lock()
	if cb.failures >= cb.threshold && time.Since(cb.openedAt) < cb.cooldown {
		cb.mu.Unlock()
		return ErrCircuitOpen
	}
	cb.mu.Unlock()

	err := fn()

	cb.mu.Lock()
	defer cb.mu.Unlock()
	if err != nil {
		cb.failures++
		cb.openedAt = time.Now()
	} else {
		cb.failures = 0
	}
	return err
}
Key points
  • Go's small binaries and cheap goroutines make it well suited to networked service workloads.
  • gRPC with Protocol Buffers offers typed, efficient, streaming-capable service-to-service communication; JSON over HTTP favors simplicity and compatibility.
  • Retries with exponential backoff and jitter, plus circuit breakers, keep services resilient to slow or failing dependencies.
  • Idempotency keys let a retried request be safely handled more than once without duplicate side effects.
  • Message queues decouple producers from consumers in time, and Go's cheap process footprint makes horizontal consumer scaling easy.
  • Distributed systems must treat partial failure as normal, not exceptional, and degrade gracefully rather than cascading it.
  • Structured logging with a correlation ID threaded through every service is what makes a distributed failure debuggable.

Write a callWithRetry helper that retries a failing function up to N times with increasing backoff, then use it to wrap a function that fails the first two times and succeeds on the third.
