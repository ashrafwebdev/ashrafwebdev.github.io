Architecting microservices at scale

Go · part of the free zero-to-hero guide

Go's fast startup time and small memory footprint make it well suited to running many independently-scaled microservices, often packaged as minimal Docker images built from a single static binary with CGO_ENABLED=0 and no runtime dependencies to install, sometimes down to a FROM scratch base image containing nothing but the binary itself and any required certificates.

At scale, service boundaries should align with team and data ownership, not just technical convenience: each service owns its own database and exposes a well-defined API, avoiding the trap of several services quietly sharing one database, which eventually makes every schema change a cross-team coordination problem and defeats the point of splitting services apart in the first place.

Observability — structured logging (typically JSON, so it's machine-parseable by a log aggregator), metrics (often via Prometheus client libraries exposing a /metrics endpoint scraped on an interval), and distributed tracing (via OpenTelemetry, propagating a trace ID across every service a request touches) — is not optional at this scale; without it, diagnosing which of dozens of services caused a slow or failed request becomes effectively impossible.

Service discovery and configuration management become explicit concerns once you have more than a handful of services: hardcoded hostnames give way to a service mesh, DNS-based discovery, or a platform like Kubernetes handling routing, and configuration moves from flags or files baked into an image to environment variables or a config service, so the same image can be promoted unchanged from staging to production.

Backward-compatible API evolution matters more as the number of services grows, since you can rarely deploy every consumer of a service at the same instant as the service itself: adding new fields to a response is safe, but removing or renaming a field, or changing a field's type, breaks any consumer still expecting the old shape — versioned APIs or careful, additive-only changes are the standard mitigation.

At true scale, a shared internal library (sometimes called a "platform" or "scaffolding" library) for cross-cutting concerns — standardized logging setup, HTTP middleware, health-check endpoints, graceful shutdown handling — keeps every service consistent without every team reinventing it, but has to be versioned and adopted carefully so a breaking change in that shared library doesn't simultaneously break every service that depends on it.

Dockerfile
FROM golang:1.22 AS build
WORKDIR /app
COPY . .
RUN CGO_ENABLED=0 go build -o server .

FROM scratch
COPY --from=build /app/server /server
ENTRYPOINT ["/server"]
graceful_shutdown.go
package main

import (
	"context"
	"log"
	"net/http"
	"os"
	"os/signal"
	"syscall"
	"time"
)

func main() {
	srv := &http.Server{Addr: ":8080"}

	go func() {
		if err := srv.ListenAndServe(); err != nil && err != http.ErrServerClosed {
			log.Fatal(err)
		}
	}()

	stop := make(chan os.Signal, 1)
	signal.Notify(stop, syscall.SIGINT, syscall.SIGTERM)
	<-stop // block until Kubernetes (or the OS) sends a shutdown signal

	ctx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
	defer cancel()
	if err := srv.Shutdown(ctx); err != nil {
		log.Println("forced shutdown:", err)
	}
	log.Println("server exited cleanly")
}
health_and_metrics.go
package main

import (
	"net/http"

	"github.com/prometheus/client_golang/prometheus/promhttp"
)

func main() {
	mux := http.NewServeMux()

	mux.HandleFunc("GET /healthz", func(w http.ResponseWriter, r *http.Request) {
		w.WriteHeader(http.StatusOK) // liveness probe target
	})
	mux.HandleFunc("GET /readyz", func(w http.ResponseWriter, r *http.Request) {
		// check downstream deps (db, cache) before reporting ready
		w.WriteHeader(http.StatusOK)
	})
	mux.Handle("/metrics", promhttp.Handler()) // scraped by Prometheus

	http.ListenAndServe(":8080", mux)
}
Key points
  • Static Go binaries with CGO_ENABLED=0 package neatly into minimal, fast-starting Docker images, often on a scratch base.
  • Each microservice should own its data; services should never silently share one database.
  • Structured (JSON) logging, metrics, and distributed tracing are essential once you have more than a few services.
  • Service discovery and externalized configuration replace hardcoded hostnames and baked-in config files at scale.
  • API changes must stay backward compatible since not every consumer deploys at the same instant as the service that changed.
  • Health-check endpoints (liveness and readiness) and graceful shutdown handling let an orchestrator like Kubernetes manage a service safely.
  • A shared internal platform library keeps cross-cutting concerns consistent across services, but must be versioned carefully to avoid breaking everyone at once.
