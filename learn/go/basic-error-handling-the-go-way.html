Basic error handling (the Go way)

Go · part of the free zero-to-hero guide

Builds on: Packages and go run/go build

Go has no exceptions for ordinary error handling. Instead, functions that can fail return an error as their last return value, and callers check it explicitly with if err != nil immediately after the call — there is no way to accidentally ignore an error silently while still compiling cleanly if you assign it, since an unused variable is itself a compile error.

error is just a built-in interface with one method, Error() string, so any type that implements that method can be used as an error — the built-in errors package provides errors.New for the common case of a simple, static string-based error.

fmt.Errorf with the %w verb lets you wrap an underlying error while adding context (fmt.Errorf("loading config: %w", err)), preserving the original for later inspection with errors.Is or errors.As, rather than losing it by converting it to a plain string with %v.

A common beginner mistake is checking err != nil against the wrong variable, or discarding an error with _ out of impatience during prototyping and forgetting to go back and handle it — go vet and linters like errcheck specifically catch unchecked errors, and it's worth running one in CI.

Panics are reserved for truly unrecoverable situations (a programming bug like an out-of-bounds index, not an expected failure like a missing file), and recover can catch a panic inside a deferred function to prevent a crash — but idiomatic Go code almost never uses panic/recover for routine control flow the way other languages use exceptions; that's what returned errors are for.

This explicit, no-magic style is a deliberate design choice: errors are just values, so they flow through the same control-flow constructs (if, return) as everything else in the language, with nothing hidden, and the repetitive if err != nil pattern — while it does add visible lines — makes every point where a function can fail impossible to miss during a code review.

main.go
package main

import (
	"errors"
	"fmt"
)

var ErrNotFound = errors.New("item not found")

func findItem(id int) error {
	if id != 1 {
		return fmt.Errorf("lookup failed for id %d: %w", id, ErrNotFound)
	}
	return nil
}

func main() {
	err := findItem(42)
	if errors.Is(err, ErrNotFound) {
		fmt.Println("not found:", err)
	}
}
custom_error_type.go
package main

import "fmt"

type RangeError struct {
	Value, Min, Max int
}

func (e *RangeError) Error() string {
	return fmt.Sprintf("%d is out of range [%d, %d]", e.Value, e.Min, e.Max)
}

func checkAge(age int) error {
	if age < 0 || age > 150 {
		return &RangeError{Value: age, Min: 0, Max: 150}
	}
	return nil
}

func main() {
	if err := checkAge(-5); err != nil {
		fmt.Println("validation error:", err)
	}
}
panic_recover.go
package main

import "fmt"

// safeDivide demonstrates recover as a last-resort safety net,
// NOT as a substitute for returning an error in normal code.
func safeDivide(a, b int) (result int, err error) {
	defer func() {
		if r := recover(); r != nil {
			err = fmt.Errorf("recovered from panic: %v", r)
		}
	}()
	return a / b, nil // panics on b == 0 (division by zero)
}

func main() {
	result, err := safeDivide(10, 0)
	if err != nil {
		fmt.Println("error:", err)
		return
	}
	fmt.Println(result)
}
Key points
  • Functions return an error as the last value; callers check it with if err != nil.
  • error is just an interface with an Error() string method — any type implementing it works as an error.
  • fmt.Errorf with %w wraps an error while preserving it for later inspection with errors.Is or errors.As.
  • errors.Is checks whether a wrapped error chain contains a specific sentinel error.
  • Panics are for unrecoverable programming bugs, not expected failures; expected failures should be returned errors, not panics.
  • recover inside a deferred function can catch a panic, but idiomatic Go rarely relies on this for routine control flow.
  • Errors are ordinary values in Go, not a separate control-flow mechanism like exceptions.
