03 Advanced stage capstone

linkcheck: a concurrent URL health-checking service, backed by a real database

Go · ties together everything in the Advanced stage

linkcheck is a small but genuinely production-shaped service: submit a batch of URLs over a REST API, a bounded worker pool checks each one concurrently, and the results land in a real SQL database rather than staying in memory. It's the first project in the roadmap where a slow or misbehaving dependency (a URL that never responds) is a first-class problem you have to design around, not an edge case you can ignore.

The service accepts a batch of URLs and returns immediately with a batch id, rather than making the caller wait for every check to finish — because a worker pool that blocks whoever calls it defeats the point of having a worker pool at all. Getting the concurrency, the database writes, and the API responses to all agree on the batch's current state is the real test of this stage's skills.

This project deliberately exercises every Advanced-stage topic together: a bounded worker pool coordinated with channels and select, per-check timeouts via context.Context, results persisted through database/sql (including a transaction for writing a batch's results together), a router (chi or gin) for the REST layer, and table-driven tests run under the race detector.

  • Concurrency patterns: worker pools, select statements
  • Testing with the built-in testing package
  • Building REST APIs with a router (chi/gin)
  • Working with databases (database/sql)
  • Context for cancellation and timeouts
Requirements
  • POST /checks accepts a JSON array of URLs, enqueues them, and responds immediately (202 Accepted) with a batch id — it must not block until every URL has actually been checked.
  • A worker pool of a fixed, configurable size processes queued URL checks by pulling from a shared channel; the number of workers is set once at startup and does not grow with the number of URLs submitted.
  • Each individual URL check runs under its own context.WithTimeout, so one slow or unreachable host cannot stall the rest of the batch.
  • Check results (URL, HTTP status code or error, and latency) are persisted to a real SQL database via database/sql, with a batch's results written inside a single transaction.
  • GET /checks/{id}, implemented as a chi or gin route, returns the batch's overall status (pending or complete) and every completed result as JSON.
  • At least one table-driven test, using named subtests via t.Run, covers the single-URL-check function in isolation — including a case where the context times out before the check completes.
  • The full test suite passes under go test -race, and go vet ./... reports no warnings.
Suggested approach
  1. Write and table-test the single-URL-check function first, entirely in isolation from HTTP and the database, including its timeout behavior — this is the piece every other requirement depends on being correct.
  2. Design the results table's schema and get database/sql reads and writes working against a local database, including the transaction that writes a whole batch's results together.
  3. Build the worker pool next: a job channel of URLs, a fixed number of worker goroutines, and a coordinator that uses select to know when every job in a batch has finished.
  4. Wire up the chi or gin routes: POST /checks enqueues jobs into the pool and returns immediately; GET /checks/{id} reads back whatever is currently persisted for that batch.
  5. Finish by running the whole suite under -race and go vet, and fix anything either one flags before considering the project done.
Stretch goals
  • Add a rate limiter so the whole worker pool respects a maximum requests-per-second ceiling across all workers combined, not just per worker.
  • Add a retry policy for checks that time out, with a capped number of attempts before a URL is marked permanently failed.
  • Add a polling-friendly progress field to GET /checks/{id} reporting how many of the batch's URLs are done so far, updated as each worker finishes.
