Testing with the built-in testing package

Go · part of the free zero-to-hero guide

Builds on: Concurrency patterns: worker pools, select statements

Go's standard library includes a testing framework with no extra dependency required: a test file is named *_test.go, lives alongside the code it tests in the same package, and each test function takes a *testing.T parameter and is named TestXxx where Xxx starts with a capital letter.

Failures are reported with t.Error/t.Errorf (record a failure and continue running the rest of the test) or t.Fatal/t.Fatalf (record a failure and stop the current test function immediately, useful when a later assertion would panic or be meaningless after an earlier one failed). Table-driven tests — a slice of input/expected-output cases looped over with a single test body — are the idiomatic way to cover many cases concisely, and each case is usually run as its own named subtest.

t.Run("case name", func(t *testing.T) { ... }) creates a named subtest, which can be run in isolation with go test -run TestAdd/negative and reports failures with the subtest's own name, making it immediately clear which specific table-driven case failed rather than just which test function did.

t.Parallel(), called at the start of a test or subtest, marks it as safe to run concurrently with other parallel tests, which can significantly speed up a large test suite — but only for tests with no shared mutable state, since parallel tests genuinely run at the same time.

Beyond plain tests, Go supports benchmarks (func BenchmarkXxx(b *testing.B), run via go test -bench=.) and fuzz tests (func FuzzXxx(f *testing.F), run via go test -fuzz=FuzzXxx, added in Go 1.18) which automatically generate randomized inputs to search for edge cases and crashes that hand-written table-driven cases might never think to try.

go test ./... runs all tests in a module, and go test -cover reports test coverage as a percentage, with go test -coverprofile=cover.out followed by go tool cover -html=cover.out producing a line-by-line HTML coverage view — both routinely wired into CI pipelines for Go projects, often with a minimum coverage threshold enforced.

calculator_test.go
package calculator

import "testing"

func TestAdd(t *testing.T) {
	cases := []struct {
		a, b, want int
	}{
		{2, 3, 5},
		{-1, 1, 0},
		{0, 0, 0},
	}

	for _, c := range cases {
		got := Add(c.a, c.b)
		if got != c.want {
			t.Errorf("Add(%d, %d) = %d, want %d", c.a, c.b, got, c.want)
		}
	}
}
subtests_test.go
package calculator

import "testing"

func TestDivide(t *testing.T) {
	cases := map[string]struct {
		a, b   int
		want   int
		wantErr bool
	}{
		"positive":   {a: 10, b: 2, want: 5},
		"by zero":    {a: 10, b: 0, wantErr: true},
	}

	for name, c := range cases {
		c := c
		t.Run(name, func(t *testing.T) {
			t.Parallel()
			got, err := Divide(c.a, c.b)
			if c.wantErr {
				if err == nil {
					t.Fatal("expected an error, got nil")
				}
				return
			}
			if got != c.want {
				t.Errorf("got %d, want %d", got, c.want)
			}
		})
	}
}
fuzz_test.go
package calculator

import "testing"

func FuzzReverse(f *testing.F) {
	f.Add("hello") // seed corpus
	f.Fuzz(func(t *testing.T, s string) {
		reversed := Reverse(s)
		if Reverse(reversed) != s {
			t.Errorf("double reverse of %q produced %q", s, Reverse(reversed))
		}
	})
}
Key points
  • Test functions live in *_test.go files, named TestXxx, taking *testing.T.
  • t.Error/t.Errorf reports a failure and continues; t.Fatal/t.Fatalf stops the test immediately.
  • Table-driven tests loop a single test body over a slice or map of input/expected-output cases.
  • t.Run("name", func(t *testing.T) {...}) creates a named subtest, runnable in isolation and clearly reported on failure.
  • t.Parallel() lets independent tests run concurrently for a faster suite, but only when they share no mutable state.
  • Benchmarks (BenchmarkXxx) and fuzz tests (FuzzXxx) go beyond fixed-case tests to measure performance and search for edge cases automatically.
  • go test -cover reports how much of the code the test suite actually exercises; go tool cover -html visualizes it line by line.
Try it yourself

Write a table-driven test for a function IsPalindrome(s string) bool covering a palindrome, a non-palindrome, and an empty string, using t.Run to name each case as its own subtest. Then add a FuzzIsPalindrome fuzz test that seeds a couple of known strings and asserts the function never panics on random input, and run go test -cover to check your coverage.
