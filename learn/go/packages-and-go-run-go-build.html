Packages and go run/go build

Go · part of the free zero-to-hero guide

Builds on: Slices and maps

Go organizes code into packages, one per directory, and every source file starts with a package declaration; all files in the same directory must declare the same package name. Names starting with a capital letter (func DoThing()) are exported and visible outside the package; lowercase names are private to it — there is no separate public/private keyword, capitalization alone controls visibility.

go run main.go compiles and runs a program in one step without leaving a binary behind, ideal for quick iteration during development. go build compiles a standalone, statically-linked binary without running it, which is what you'd deploy or distribute — running that binary requires no separate Go installation on the target machine.

A package's init() function, if present, runs automatically before main() — useful for one-time setup like registering database drivers, but a source of hidden control flow if overused, so idiomatic Go tends to reserve it for genuinely package-level initialization rather than general startup logic.

go fmt automatically reformats code to Go's single canonical style (spacing, brace placement, import grouping), removing an entire class of style debates that other language communities have, and go vet catches common mistakes statically (like a Printf call whose format verbs don't match its arguments) — both are run routinely as part of everyday Go development, not optional extras, and most editors run go fmt automatically on save.

Internal packages get special treatment: any package under a directory named internal/ can only be imported by code inside the module rooted at that internal directory's parent, which the compiler enforces — a lightweight way to expose an API to the rest of your own module while explicitly forbidding external modules from depending on it.

go install builds a binary and places it in $GOPATH/bin (or $HOME/go/bin by default), making it directly runnable from the shell's PATH — the standard way to install command-line tools written in Go, including many of the Go ecosystem's own developer tools.

terminal
$ go run main.go

$ go build -o myapp main.go
$ ./myapp

$ go fmt ./...
$ go vet ./...
mathutil/mathutil.go
package mathutil

// Add is exported: capitalized name.
func Add(a, b int) int {
	return a + b
}

// roundToEven is unexported: lowercase name, private to this package.
func roundToEven(x float64) int {
	return int(x + 0.5)
}
main.go
package main

import (
	"fmt"

	"github.com/you/myapp/mathutil"
)

func main() {
	fmt.Println(mathutil.Add(2, 3)) // OK, exported
	// fmt.Println(mathutil.roundToEven(2.5)) // compile error: unexported
}
Key points
  • Capitalized identifiers are exported (public); lowercase ones are package-private — visibility is purely about the first letter.
  • go run compiles and runs immediately without a lasting binary; go build produces a standalone, distributable binary.
  • A package's optional init() function runs automatically before main(), useful for setup but easy to overuse.
  • go fmt enforces one canonical formatting style across all Go code, ending style debates.
  • go vet statically flags likely bugs, such as mismatched Printf format verbs, before you even run the program.
  • Packages under an internal/ directory can only be imported from within the same module, enforced by the compiler.
  • go install builds and places a binary on your PATH, the standard way to install Go command-line tools.
Try it yourself

Create a small package with one exported and one unexported function, import it from main.go, and build it into a binary with go build. Then add an internal/ subpackage, import it successfully from within your module, and note in a comment what would happen if an outside module tried to import it.
