Error handling patterns in depth

Go · part of the free zero-to-hero guide

Beyond basic if err != nil checks, idiomatic Go often defines custom error types implementing the error interface's single Error() string method, letting callers extract structured information via type assertion or errors.As rather than parsing an error's message string, which is fragile and breaks the moment the wording changes.

errors.As checks whether an error chain contains an error of a specific concrete type and, if so, extracts it into a variable you can inspect — the structured-type counterpart to errors.Is's sentinel-value check. It walks the chain produced by repeated %w wrapping via the error's Unwrap() error method, which fmt.Errorf generates automatically when you use %w.

Go 1.20 added support for wrapping multiple errors in one value, either with errors.Join(err1, err2) or by using more than one %w verb in a single fmt.Errorf call — useful when several independent operations fail and you want to report all of them rather than only the first, such as when validating several fields of a form at once.

A common convention is to handle an error exactly once: either log it and stop, or add context and return it up the call stack — never both, which avoids the common bug of the same failure being logged repeatedly at every layer of a call stack, cluttering logs and making the actual failure point hard to find.

Sentinel errors (package-level var Err... = errors.New(...)) are simple but have a downside: they create a coupling where callers must import your package just to compare against your specific error value, and they can't carry dynamic data. Custom error struct types solve both problems by carrying fields and by letting errors.As match on type rather than on a specific shared variable.

When designing a package's error handling, decide up front which errors are part of its public contract (documented sentinel errors or types callers are expected to check for) versus purely internal failure details that should just be wrapped with context and treated as opaque by callers — exposing too much internal error detail as part of an API makes later refactoring a breaking change.

main.go
package main

import (
	"errors"
	"fmt"
)

type ValidationError struct {
	Field string
}

func (e *ValidationError) Error() string {
	return fmt.Sprintf("invalid field: %s", e.Field)
}

func validate(age int) error {
	if age < 0 {
		return &ValidationError{Field: "age"}
	}
	return nil
}

func main() {
	err := validate(-5)
	var ve *ValidationError
	if errors.As(err, &ve) {
		fmt.Println("validation failed on:", ve.Field)
	}
}
joined_errors.go
package main

import (
	"errors"
	"fmt"
)

func validateForm(name string, age int) error {
	var errs []error
	if name == "" {
		errs = append(errs, errors.New("name is required"))
	}
	if age < 0 {
		errs = append(errs, fmt.Errorf("age must not be negative, got %d", age))
	}
	return errors.Join(errs...) // nil if errs is empty
}

func main() {
	if err := validateForm("", -3); err != nil {
		fmt.Println(err) // prints both messages, one per line
	}
}
handle_once.go
package main

import (
	"fmt"
	"log"
)

func loadConfig() error {
	return fmt.Errorf("reading config.yaml: %w", fmt.Errorf("permission denied"))
}

func run() error {
	if err := loadConfig(); err != nil {
		// add context, DON'T also log here -- the caller decides what to do
		return fmt.Errorf("startup failed: %w", err)
	}
	return nil
}

func main() {
	if err := run(); err != nil {
		log.Fatal(err) // handled exactly once, at the top
	}
}
Key points
  • A custom error type just needs an Error() string method to satisfy the error interface.
  • errors.As extracts a specific concrete error type out of a (possibly wrapped) error chain, walking each Unwrap() step.
  • errors.Join (Go 1.20+) or multiple %w verbs let you combine several independent errors into one value.
  • Handle each error exactly once — either resolve/log it, or add context and propagate it, not both.
  • Sentinel errors are simple but couple callers to your package; custom error types carry data and match by type instead.
  • Structured errors let callers react programmatically instead of matching on message text.
  • Decide which errors are part of a package's public contract versus purely internal detail before publishing an API.
Try it yourself

Define a custom NotFoundError type with an Id field, return it from a lookup function for a missing id, and use errors.As in the caller to print a specific message. Then write a form-validation function that checks two fields and uses errors.Join to return all validation failures at once instead of stopping at the first one.
