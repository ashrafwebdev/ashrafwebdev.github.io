04 Hero stage capstone

Fanout: a horizontally-scalable, distributed job-processing platform

Go · ties together everything in the Hero stage

Fanout is the roadmap's own stated goal for this stage made concrete: a distributed, horizontally-scalable Go service, designed and deployed rather than just described. It's split into two independently deployable binaries — a stateless API service that accepts job submissions, and a worker binary that processes them — coordinating through nothing but a shared SQL job-queue table, so that running more copies of the worker binary genuinely increases throughput with zero code changes.

The interesting engineering is entirely in the coordination: multiple worker processes must be able to claim jobs from the same queue table without ever double-processing one, jobs must be safe to retry after a partial failure without being processed twice, and both binaries must start up, report their health, and shut down cleanly enough that an orchestrator could manage them without babysitting.

This project draws on the full width of what the Hero stage covers: distributed-systems patterns (idempotency keys, retries with backoff and jitter, a circuit breaker around a simulated downstream dependency) and microservices architecture at scale (minimal Docker images, health and readiness endpoints, graceful shutdown), closed out with real performance work — a pprof profile taken under load, and a benchmark-backed optimization of whatever it points to.

  • Designing distributed systems in Go

Requirements
  • Two independently deployable binaries (or one binary with two run modes) — a stateless API service and a worker — that coordinate only through a shared job-queue table in a real SQL database; no state is shared between instances any other way.
  • Workers claim jobs atomically from the shared queue (for example, a SELECT ... FOR UPDATE SKIP LOCKED query inside a transaction) such that running several worker processes against the same queue concurrently never lets two workers process the same job.
  • Every job carries a client-supplied idempotency key that the system deduplicates on at submission time, so resubmitting the same job never results in it being processed twice.
  • Job processing runs under a context.WithTimeout, retries transient failures with exponential backoff and jitter, and trips a circuit breaker around a downstream dependency you simulate, so a sustained failure stops hammering it instead of retrying forever.
  • Both binaries expose /healthz and /readyz endpoints and shut down gracefully on SIGTERM, letting in-flight work drain instead of being dropped mid-job.
  • Both binaries are packaged as minimal Docker images built from CGO_ENABLED=0 static binaries, and you can demonstrate horizontal scale-out concretely: run three or more worker containers against the same queue and show throughput increasing as workers are added.
  • At least one CPU or memory profile, captured with pprof while the workers are under load, leads to one specific, documented optimization justified by a go test -bench -benchmem comparison of before and after.
Suggested approach
  1. Design the shared job-queue schema first (status, idempotency key, payload, claimed-by, claimed-at) and get the SKIP LOCKED claim query correct and tested against a local database before writing either binary.
  2. Build the stateless API service: it accepts job submissions, enforces idempotency-key deduplication, and writes new jobs into the queue — nothing else.
  3. Build the worker binary: it claims jobs, processes them under a context timeout, and wraps the simulated downstream call in retry-with-backoff-and-jitter plus the circuit breaker.
  4. Add health, readiness, and graceful-shutdown handling to both binaries, then write a minimal Dockerfile for each and confirm both run correctly as containers.
  5. Run several worker containers against the same queue to confirm real horizontal scaling, then profile a worker under load with pprof, optimize the hottest path the profile points to, and back the improvement with a benchmark comparison.
Stretch goals
  • Add distributed tracing with a correlation id generated by the API service and threaded through every worker log line, so one job's full lifecycle is traceable across both binaries.
  • Swap the Postgres-backed queue for a real message broker (NATS or Kafka) and write a short comparison of the two coordination strategies' tradeoffs.
  • Add simple autoscaling logic that launches additional worker containers when queue depth crosses a threshold and retires them when it drops back down.
