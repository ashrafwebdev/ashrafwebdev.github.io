Performance profiling (pprof) and optimization

Go · part of the free zero-to-hero guide

Go's standard library includes net/http/pprof, which exposes live CPU, memory (heap), goroutine, and mutex-contention profiles over HTTP with a single blank import (import _ "net/http/pprof"), and the go tool pprof command analyzes the resulting profile data interactively or generates flame graphs and call-graph visualizations from it.

CPU profiling samples where the program spends its time by periodically interrupting execution and recording the call stack, giving a statistical picture of hot functions rather than an exact trace; memory profiling tracks where allocations happen (by size and call site), which in Go is often the more actionable lever since excessive allocation drives extra garbage-collection work that steals CPU time from the actual workload.

A goroutine profile (/debug/pprof/goroutine) dumps the stack trace of every currently running goroutine, which is invaluable for diagnosing a goroutine leak in production — a steadily climbing goroutine count over time, visible in this profile or in a simple metric, is the classic symptom.

As in any language, the discipline is to profile first, then optimize the specific hot path the data points to, rather than guessing — Go's benchmark functions (func BenchmarkXxx(b *testing.B), run via go test -bench=. -benchmem) make it easy to verify an optimization actually helped, and -benchmem specifically reports allocations per operation, which often matters more than raw nanoseconds.

Common, well-known Go performance patterns include preallocating a slice's capacity with make([]T, 0, n) when the final size is roughly known (avoiding repeated reallocation as append grows it), using strings.Builder instead of repeated + string concatenation (which would otherwise allocate a new string on every operation, since strings are immutable), and reusing buffers via sync.Pool for short-lived objects allocated in a hot loop.

The Go runtime's garbage collector is a concurrent, low-latency collector tuned to keep pause times short rather than to minimize total CPU overhead, and it's tunable via the GOGC environment variable (or debug.SetGCPercent) which controls how much the heap is allowed to grow between collections — raising it trades higher memory usage for less GC CPU overhead, useful for latency-sensitive services with memory to spare.

import _ "net/http/pprof"
// exposes profiles at /debug/pprof/ once the server is running

$ go tool pprof http://localhost:8080/debug/pprof/profile?seconds=30
$ go tool pprof http://localhost:8080/debug/pprof/heap
$ go test -bench=. -benchmem ./...
string_builder_bench_test.go
package strutil

import (
	"strings"
	"testing"
)

func concatPlus(words []string) string {
	result := ""
	for _, w := range words {
		result += w // allocates a new string every iteration
	}
	return result
}

func concatBuilder(words []string) string {
	var b strings.Builder
	for _, w := range words {
		b.WriteString(w) // reuses an internal growable buffer
	}
	return b.String()
}

var words = []string{"go", "is", "fast", "and", "simple"}

func BenchmarkConcatPlus(b *testing.B) {
	for i := 0; i < b.N; i++ {
		concatPlus(words)
	}
}

func BenchmarkConcatBuilder(b *testing.B) {
	for i := 0; i < b.N; i++ {
		concatBuilder(words)
	}
}
preallocate.go
package main

// slow: append reallocates repeatedly as the slice outgrows its capacity
func buildSlow(n int) []int {
	var out []int
	for i := 0; i < n; i++ {
		out = append(out, i)
	}
	return out
}

// fast: capacity is known up front, so append never reallocates
func buildFast(n int) []int {
	out := make([]int, 0, n)
	for i := 0; i < n; i++ {
		out = append(out, i)
	}
	return out
}
Key points
  • net/http/pprof exposes CPU, heap, goroutine, and mutex profiles over HTTP with one import.
  • go tool pprof analyzes profile data and can render flame graphs and call graphs of hot paths.
  • Excess allocation is often the real cost in Go programs, since it drives more GC work — memory profiles pinpoint where allocations happen.
  • A goroutine profile dumping every running goroutine's stack is the standard tool for diagnosing goroutine leaks in production.
  • Benchmark functions (BenchmarkXxx, run with -bench -benchmem) verify whether an optimization actually improved speed and allocations.
  • Preallocating slice capacity, using strings.Builder over repeated concatenation, and pooling short-lived objects with sync.Pool are common wins.
  • GOGC tunes how much the heap grows between collections, trading memory for less GC CPU overhead.

Write a Benchmark function for a string-concatenation helper, run it with go test -bench -benchmem, then rewrite the helper using strings.Builder and compare the benchmark results including allocations per operation. Then write a second pair of benchmarks comparing a slice built with append from a nil slice against one preallocated with make([]T, 0, n), and note the difference in allocation counts.
