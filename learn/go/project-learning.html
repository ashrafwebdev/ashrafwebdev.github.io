02 Learning stage capstone

A REST task tracker built with nothing but net/http

Go · ties together everything in the Learning stage

This project is a small, real REST API for tracking tasks — create, list, fetch, and delete — built entirely on the standard library, with a twist that forces you to actually understand goroutines and channels rather than skip past them: the in-memory data store's state may only ever be touched by one dedicated goroutine, which every HTTP handler talks to over channels. No handler is allowed to read or write the underlying map directly.

That constraint exists because Learning-stage Go hasn't covered sync.Mutex yet — that's Advanced-stage material. Instead, you'll build the store the way Go's own philosophy suggests: "share memory by communicating." A single goroutine owns the data; everyone else sends it a request and waits for a reply on a channel.

Alongside the concurrency constraint, this project ties together structs and interfaces (a Task struct, a Store interface satisfied implicitly), a real Go module with its own go.mod, and error-handling patterns beyond a bare if err != nil — a custom validation error type surfaced as a proper HTTP 400 response.

  • Structs and interfaces
  • Goroutines and channels basics
  • Error handling patterns in depth
  • Working with modules (go.mod)
  • Building a basic HTTP server with net/http
Requirements
  • A real Go module: go mod init run at the project root, building cleanly with go build.
  • A Task struct with JSON tags (id, title, done, etc.) and a Store interface declaring Create, Get, List, and Delete methods, implemented by exactly one in-memory type.
  • The in-memory store's state is owned and mutated by a single dedicated goroutine; every HTTP handler communicates with it only by sending a request value (with a reply channel embedded in it) over a shared channel — no handler reads or writes the store's map directly.
  • HTTP routes, using Go 1.22's method-and-pattern http.ServeMux syntax, for at least: GET /tasks (list all), POST /tasks (create), GET /tasks/{id} (fetch one), and DELETE /tasks/{id} (delete).
  • Correct JSON encoding and decoding (encoding/json) on every route, with the right status code for each outcome: 201 for a successful create, 200 for a successful read/list/delete, 404 for an unknown id.
  • A custom ValidationError type (implementing the error interface) returned when a task's title is empty, detected in the handler with errors.As and turned into a 400 response with a clear message.
  • The server is started from an explicit http.Server value with ReadTimeout, WriteTimeout, and IdleTimeout set, not the bare http.ListenAndServe shortcut.
Suggested approach
  1. Run go mod init and get the barest possible server running — a single health-check route, started via an explicit http.Server with timeouts set — before writing any task logic.
  2. Define the Task struct and the Store interface first, on paper if you have to, before writing a single handler; this is the contract everything else builds against.
  3. Implement the channel-based store: design the request messages it accepts (each carrying its own reply channel), write the goroutine's central for { select { ... } } loop, and test it with a few calls from a throwaway main before wiring up HTTP at all.
  4. Add the four HTTP routes one at a time, translating each incoming request into a message sent to the store goroutine and its reply into a JSON response with the right status code.
  5. Add the ValidationError type and wire it into the create-task path last, once the happy path for every route already works.
Stretch goals
  • Add a PUT /tasks/{id} route to mark a task done, and confirm it round-trips correctly through the channel-based store.
  • Add a request-logging middleware (a function wrapping an http.Handler) that prints each request's method, path, and duration, applied to every route.
  • Swap the reply-channel pattern for a version using context.Context to time out a request if the store goroutine takes too long to respond, even though you haven't formally covered context yet — see how far you get reading the standard library docs.
