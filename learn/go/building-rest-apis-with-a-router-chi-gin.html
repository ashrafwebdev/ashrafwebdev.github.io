Building REST APIs with a router (chi/gin)

Go · part of the free zero-to-hero guide

Builds on: Testing with the built-in testing package

While net/http covers the basics, routers like chi and gin add convenient features on top: path parameters (/users/{id}), middleware chains, route grouping, and automatic request binding/validation, without straying far from idiomatic Go.

gin is a full-featured, high-performance framework with built-in JSON binding and validation via struct tags (binding:"required"), a custom gin.Context that bundles the request, response writer, and helper methods together, and its own middleware and error-handling conventions — popular for its speed and low-friction API for building an API quickly.

chi is a lightweight, fully net/http-compatible router: its handlers are plain func(w http.ResponseWriter, r *http.Request), so any existing net/http middleware or handler works with chi unmodified, which makes it a natural fit for teams who want just routing and grouping without a broader framework's opinions layered on top.

Both let you group related routes and apply shared middleware (logging, authentication, rate limiting) to a whole group at once, which keeps route definitions readable as an API grows — for example, mounting an /admin group behind an authentication middleware while leaving /public routes open.

Middleware in both frameworks runs in the order it's registered, wrapping the eventual handler like layers of an onion: a logging middleware registered first runs its pre-handler code first and its post-handler code last, so request-scoped setup (like attaching a request ID) belongs early in the chain and response-shaping code belongs later.

For a small API, plain net/http with Go 1.22's pattern-based ServeMux is often sufficient and keeps dependencies minimal; reaching for chi or gin becomes worthwhile once you need consistent middleware layering, structured request binding, or the ecosystem of plugins those frameworks provide.

main.go (gin)
package main

import "github.com/gin-gonic/gin"

type Product struct {
	ID    int     `json:"id"`
	Name  string  `json:"name"`
	Price float64 `json:"price"`
}

func main() {
	r := gin.Default()
	r.GET("/products/:id", func(c *gin.Context) {
		id := c.Param("id")
		c.JSON(200, Product{ID: 1, Name: "Widget", Price: 9.99})
		_ = id
	})
	r.Run(":8080")
}
main.go (gin binding + group)
package main

import "github.com/gin-gonic/gin"

type CreateProductRequest struct {
	Name  string  `json:"name" binding:"required"`
	Price float64 `json:"price" binding:"required,gt=0"`
}

func main() {
	r := gin.Default()

	api := r.Group("/api")
	{
		api.POST("/products", func(c *gin.Context) {
			var req CreateProductRequest
			if err := c.ShouldBindJSON(&req); err != nil {
				c.JSON(400, gin.H{"error": err.Error()})
				return
			}
			c.JSON(201, req)
		})
	}
	r.Run(":8080")
}
main.go (chi)
package main

import (
	"net/http"

	"github.com/go-chi/chi/v5"
	"github.com/go-chi/chi/v5/middleware"
)

func main() {
	r := chi.NewRouter()
	r.Use(middleware.Logger)

	r.Route("/tasks", func(r chi.Router) {
		r.Get("/", listTasks)
		r.Get("/{id}", getTask) // plain net/http-style handler, no framework Context needed
	})

	http.ListenAndServe(":8080", r)
}

func listTasks(w http.ResponseWriter, r *http.Request) { w.Write([]byte("[]")) }

func getTask(w http.ResponseWriter, r *http.Request) {
	id := chi.URLParam(r, "id")
	w.Write([]byte("task " + id))
}
Key points
  • Routers like chi and gin add path parameters, middleware, and route grouping on top of net/http.
  • gin favors speed and built-in JSON binding/validation via a custom Context; chi favors staying with plain net/http handler signatures.
  • Struct tags like json:"name" and binding:"required" control serialization and, in gin, request validation.
  • Middleware applied to a route group runs for every route inside that group automatically, in registration order.
  • chi's handlers are ordinary net/http handlers, so existing standard-library middleware works with it unmodified.
  • Middleware wraps a handler in layers: pre-handler code runs in registration order, post-handler code runs in reverse.
  • Reach for a router framework once you need consistent middleware layering or structured binding beyond what net/http offers directly.
