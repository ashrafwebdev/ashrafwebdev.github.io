Working with databases (database/sql)

Go · part of the free zero-to-hero guide

Go's standard library defines a common interface for SQL databases in database/sql, and a specific driver (like github.com/lib/pq for Postgres, github.com/go-sql-driver/mysql for MySQL, or the newer github.com/jackc/pgx for Postgres) implements it underneath, imported purely for its side-effecting init() registration with a blank _ import.

sql.Open doesn't actually connect immediately; it lazily manages a pool of connections and validates the driver name and connection string syntax only, so a typo'd password or unreachable host won't surface until the first real query. db.Ping() is the idiomatic way to verify connectivity eagerly at startup instead of discovering the problem on a user's first request.

Queries use placeholder parameters (? for MySQL, $1, $2 for Postgres, depending on the driver) rather than string concatenation, which is essential for preventing SQL injection; QueryRow, Query, and Exec cover single-row, multi-row, and no-result-set statements (inserts, updates, deletes) respectively.

Rows returned by Query must be closed — typically with defer rows.Close() right after checking the error — and iterated with for rows.Next() { ... }, scanning each row into destination variables with rows.Scan(&a, &b); forgetting to close rows or check rows.Err() after the loop are two of the most common database/sql bugs, since a leaked, unclosed result set can exhaust the connection pool.

The connection pool's behavior is tunable via db.SetMaxOpenConns, db.SetMaxIdleConns, and db.SetConnMaxLifetime — leaving these at their (effectively unbounded) defaults is a common cause of exhausting a database's own connection limit under load, especially in a horizontally-scaled deployment with many service instances each opening their own pool.

Multi-statement operations that must succeed or fail together belong in a db.Begin() transaction: run each statement against the returned *sql.Tx instead of db directly, then call tx.Commit() on success or tx.Rollback() on any error — a common pattern is to defer tx.Rollback() immediately after beginning, since calling Rollback after a successful Commit is a safe no-op, guaranteeing cleanup on every exit path.

main.go
package main

import (
	"database/sql"
	"fmt"

	_ "github.com/lib/pq"
)

func main() {
	db, err := sql.Open("postgres", "postgres://user:pass@localhost/mydb")
	if err != nil {
		panic(err)
	}
	defer db.Close()

	var name string
	err = db.QueryRow("SELECT name FROM users WHERE id = $1", 1).Scan(&name)
	if err != nil {
		panic(err)
	}
	fmt.Println(name)
}
query_rows_and_pool.go
package main

import (
	"database/sql"
	"fmt"
	"time"
)

type User struct {
	ID   int
	Name string
}

func listActiveUsers(db *sql.DB) ([]User, error) {
	rows, err := db.Query("SELECT id, name FROM users WHERE active = $1", true)
	if err != nil {
		return nil, fmt.Errorf("querying users: %w", err)
	}
	defer rows.Close()

	var users []User
	for rows.Next() {
		var u User
		if err := rows.Scan(&u.ID, &u.Name); err != nil {
			return nil, fmt.Errorf("scanning row: %w", err)
		}
		users = append(users, u)
	}
	return users, rows.Err() // check for errors encountered during iteration
}

func configurePool(db *sql.DB) {
	db.SetMaxOpenConns(25)
	db.SetMaxIdleConns(25)
	db.SetConnMaxLifetime(5 * time.Minute)
}
transaction.go
package main

import (
	"database/sql"
	"fmt"
)

func transferFunds(db *sql.DB, fromID, toID int, amount float64) error {
	tx, err := db.Begin()
	if err != nil {
		return fmt.Errorf("beginning transaction: %w", err)
	}
	defer tx.Rollback() // no-op if Commit succeeds below

	if _, err := tx.Exec("UPDATE accounts SET balance = balance - $1 WHERE id = $2", amount, fromID); err != nil {
		return fmt.Errorf("debiting account: %w", err)
	}
	if _, err := tx.Exec("UPDATE accounts SET balance = balance + $1 WHERE id = $2", amount, toID); err != nil {
		return fmt.Errorf("crediting account: %w", err)
	}

	return tx.Commit()
}
Key points
  • database/sql is a driver-agnostic interface; a specific driver package is imported for its side effects with a blank _ import.
  • sql.Open is lazy and doesn't verify connectivity — use db.Ping() at startup to fail fast instead of on a user's first request.
  • Always use placeholder parameters instead of string concatenation to prevent SQL injection.
  • QueryRow, Query, and Exec map to single-row, multi-row, and no-result statements.
  • Always defer rows.Close() and check rows.Err() after a Query loop — leaked rows can exhaust the connection pool.
  • Tune SetMaxOpenConns/SetMaxIdleConns/SetConnMaxLifetime rather than leaving the pool at its effectively unbounded defaults.
  • Multi-statement operations that must succeed or fail together belong in a db.Begin() transaction, committed or rolled back explicitly.
  • defer tx.Rollback() right after Begin is a safe pattern since it's a no-op after a successful Commit.
Try it yourself

Write Go code that opens a database/sql connection, queries a users table with a parameterized WHERE clause, and scans the results into a slice of structs using rows.Next() and rows.Scan(), remembering to defer rows.Close(). Then write a transferFunds function that debits one account and credits another inside a single db.Begin() transaction, rolling back on any error.
