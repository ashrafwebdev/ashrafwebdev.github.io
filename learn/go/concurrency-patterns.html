Concurrency patterns: worker pools, select statements

Go · part of the free zero-to-hero guide

Builds on: Building a basic HTTP server with net/http

A worker pool launches a fixed number of goroutines that all read tasks from a shared input channel and send results to an output channel, bounding concurrency instead of spawning an unbounded goroutine per task — important when tasks involve a limited resource like a database connection pool or an external API's rate limit, where unlimited concurrency would overwhelm the downstream system rather than speed things up.

The select statement waits on multiple channel operations at once, proceeding with whichever is ready first — essential for patterns like implementing timeouts (racing a real channel against time.After) or handling cancellation alongside normal work. A select with a default case never blocks: it takes the default branch immediately if no channel operation is ready, which is how you implement a non-blocking send or receive.

sync.WaitGroup is the standard way to wait for a group of goroutines to finish: call wg.Add(1) before launching each one, defer wg.Done() inside it, and wg.Wait() in the coordinating goroutine to block until all of them have called Done. It's commonly paired with a worker pool to know when all results have been produced, so the output channel can be safely closed.

sync.Mutex protects shared state that isn't naturally expressed as channel communication — incrementing a shared counter from multiple goroutines, for instance. Go's philosophy favors channels for coordinating goroutines and passing ownership of data, but reaches for a mutex without hesitation when protecting a small piece of genuinely shared state is simpler and clearer than routing it through a channel.

The Go race detector (go run -race or go test -race) instruments the program to catch data races — concurrent unsynchronized access to the same memory, at least one of which is a write — at runtime. It doesn't catch every possible race (only ones that actually occur during the run being tested), but running the full test suite under -race in CI is standard practice for any concurrent Go code.

Combining a worker pool with a context.Context (covered in a later lesson) for cancellation, plus select for timeouts, is the standard toolkit for writing robust, bounded concurrent Go code that doesn't leak goroutines or hang indefinitely when something downstream goes wrong.

main.go
package main

import "fmt"

func worker(id int, jobs <-chan int, results chan<- int) {
	for j := range jobs {
		results <- j * j
	}
}

func main() {
	jobs := make(chan int, 5)
	results := make(chan int, 5)

	for w := 1; w <= 3; w++ {
		go worker(w, jobs, results)
	}
	for j := 1; j <= 5; j++ {
		jobs <- j
	}
	close(jobs)

	for a := 1; a <= 5; a++ {
		fmt.Println(<-results)
	}
}
select_timeout.go
package main

import (
	"fmt"
	"time"
)

func slowWork() <-chan string {
	ch := make(chan string)
	go func() {
		time.Sleep(2 * time.Second)
		ch <- "done"
	}()
	return ch
}

func main() {
	select {
	case result := <-slowWork():
		fmt.Println(result)
	case <-time.After(1 * time.Second):
		fmt.Println("timed out waiting for slowWork")
	}
}
waitgroup_and_mutex.go
package main

import (
	"fmt"
	"sync"
)

func main() {
	var wg sync.WaitGroup
	var mu sync.Mutex
	total := 0

	for i := 1; i <= 100; i++ {
		wg.Add(1)
		go func(n int) {
			defer wg.Done()
			mu.Lock()
			total += n // shared state -- must be protected
			mu.Unlock()
		}(i)
	}

	wg.Wait()
	fmt.Println("total:", total) // 5050
}
Key points
  • A worker pool bounds concurrency to a fixed number of goroutines pulling from a shared job channel.
  • close(channel) signals no more values will be sent, letting range loops over it terminate.
  • select proceeds with whichever of several channel operations becomes ready first; a default case makes it non-blocking.
  • sync.WaitGroup (Add/Done/Wait) is the standard way to know when a group of goroutines has all finished.
  • sync.Mutex protects shared state that isn't naturally routed through channel communication.
  • Buffered channels (make(chan int, 5)) let sends succeed without an immediate receiver, up to their capacity.
  • The race detector (-race) catches concurrent unsynchronized access to shared memory and should run in CI for concurrent code.
  • Pairing a worker pool with context.Context cancellation and select-based timeouts avoids leaked or hung goroutines.
Try it yourself

Build a worker pool of 3 goroutines processing 10 jobs from a buffered jobs channel, collecting all results with a sync.WaitGroup, and use select with time.After to add a 2-second overall timeout. Then run your program with go run -race to confirm there are no data races, and add a sync.Mutex-protected counter that tracks how many jobs each worker processed.
