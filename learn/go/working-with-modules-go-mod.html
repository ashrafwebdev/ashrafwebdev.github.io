Working with modules (go.mod)

Go · part of the free zero-to-hero guide

Builds on: Error handling patterns in depth

Go modules are the standard dependency management system, defined by a go.mod file at the project root that declares the module's own import path, the minimum Go version it requires, and its dependencies with exact versions. Modules replaced the older GOPATH-based workflow, and any project outside of a single-file script should be a module.

go mod init module-name creates a new module, and simply importing a package and running go build, go test, or go mod tidy automatically adds it to go.mod and records exact resolved versions in the accompanying go.sum lock file — you rarely edit either file by hand.

Go uses semantic import versioning: a dependency's major version above v1 is part of its import path (github.com/foo/bar/v2), so two different major versions of the same library can even be imported side by side in the same program without conflict, since Go treats them as genuinely different packages.

go.sum records cryptographic checksums of every dependency's exact contents, not just its version number, so a build is reproducible and tamper-evident — if a dependency's published code ever changes without its version number changing, go build will refuse to proceed rather than silently using different code than last time.

go mod tidy also removes unused dependencies and adds any missing ones the code actually imports, keeping the module file an accurate, minimal reflection of what the code actually uses — a routine step to run before committing changes, and one that CI pipelines often verify was run (by checking that go mod tidy produces no diff).

For local development across multiple modules that depend on each other, a replace directive in go.mod (replace github.com/you/lib => ../lib) points an import at a local filesystem path instead of a published version, letting you test unpublished changes to a dependency without needing to push and tag a release first.

terminal
$ go mod init github.com/you/myapp
$ go get github.com/gin-gonic/gin@latest
$ go mod tidy
$ cat go.mod
module github.com/you/myapp

go 1.22

require github.com/gin-gonic/gin v1.9.1
terminal-versioning
$ go get github.com/some/pkg@v1.4.0    # pin an exact version
$ go get github.com/some/pkg@latest    # upgrade to latest
$ go get github.com/some/pkg@none      # remove the dependency
$ go list -m all                       # list the full resolved module graph

# a v2+ major version lives at a versioned import path:
$ go get github.com/some/pkg/v2@latest
import "github.com/some/pkg/v2"
go.mod (with replace)
module github.com/you/myapp

go 1.22

require (
	github.com/gin-gonic/gin v1.9.1
	github.com/you/shared-lib v1.2.0
)

// use the local checkout instead of the published version while developing
replace github.com/you/shared-lib => ../shared-lib
Key points
  • go.mod declares a module's own path, its required Go version, and its dependency versions.
  • go.sum pins exact resolved checksums (not just versions), ensuring reproducible, tamper-evident builds.
  • go get adds, upgrades, pins, or removes a dependency; go mod tidy reconciles go.mod with actual imports.
  • Major versions v2 and above are part of the import path itself (/v2), so multiple majors can coexist in one build.
  • Modules let Go projects depend on precise, verifiable versions of external packages.
  • CI pipelines often check that go mod tidy produces no diff, catching a forgotten dependency update.
  • A replace directive points an import at a local path for testing unpublished changes to a dependency.
Try it yourself

Initialize a new Go module, add one external dependency with go get, run go mod tidy, and inspect the resulting go.mod and go.sum files. Then simulate developing two modules together by adding a replace directive that points one module at a local relative path, and explain in a comment when you'd remove that directive before shipping.
