Keyframe animations and transform performance

CSS · part of the free zero-to-hero guide

Builds on: Custom properties (CSS variables) and theming

@keyframes defines a named animation sequence with any number of steps (not just a start and end like transition), specified as percentages of the animation's total duration, which you then apply to an element with the animation shorthand.

The animation shorthand packs several sub-properties together: name, duration, timing-function, delay, iteration-count, direction, fill-mode, and play-state. animation-iteration-count: infinite loops forever; animation-fill-mode: forwards keeps the styles from the final keyframe applied after the animation completes, instead of snapping back to the element's original styles.

Not all properties animate equally cheaply. transform and opacity can often run entirely on the GPU compositor without triggering layout or paint on the main thread, making them dramatically smoother than animating width, top, or margin, which force the browser to recompute layout on every single frame of the animation.

Multiple transform functions (translate, scale, rotate) can be combined in one declaration, and their order matters — transform: translateX(20px) rotate(45deg) rotates around the already-translated position, while rotate(45deg) translateX(20px) translates along the newly rotated axis, producing a visibly different result.

animation-play-state: paused lets you freeze an animation via CSS alone (often toggled by a class from JavaScript on hover or click), which is a lighter-weight alternative to tearing the animation down and restarting it.

Chrome DevTools' Performance panel (and the 'Rendering' tab's paint-flashing / layout-shift overlays) show exactly which animated properties are triggering expensive layout or paint work, which is how you verify an animation is actually running smoothly rather than guessing from how it looks on your own fast development machine.

styles.css
@keyframes pulse {
  0%   { transform: scale(1); opacity: 1; }
  50%  { transform: scale(1.05); opacity: 0.8; }
  100% { transform: scale(1); opacity: 1; }
}

.notification-dot { animation: pulse 1.5s ease-in-out infinite; }
styles.css (fill-mode and play-state)
@keyframes slide-in {
  from { transform: translateX(-100%); opacity: 0; }
  to   { transform: translateX(0); opacity: 1; }
}

.toast {
  animation: slide-in 0.4s ease-out forwards; /* stays at 'to' state after finishing */
}
.toast.paused { animation-play-state: paused; } /* freeze via a toggled class */
common mistake: animating layout properties
/* Janky: top/left trigger layout recalculation every frame */
@keyframes bad-move {
  from { top: 0; left: 0; }
  to   { top: 100px; left: 50px; }
}

/* Smooth: transform runs on the compositor, no layout recalculation */
@keyframes good-move {
  from { transform: translate(0, 0); }
  to   { transform: translate(50px, 100px); }
}
Key points
  • @keyframes name { 0% {...} 100% {...} } defines the sequence; animation: name duration timing iteration; applies it.
  • Prefer animating transform and opacity for smooth, GPU-accelerated performance.
  • animation-fill-mode: forwards keeps the final keyframe's styles after the animation ends, instead of reverting.
  • The order of chained transform functions changes the result — translate then rotate differs from rotate then translate.
  • animation-play-state: paused freezes an animation via CSS alone, without restarting it from the beginning.
  • Chrome DevTools' Performance panel shows exactly which animated properties are triggering expensive layout/paint.
  • animation-iteration-count: infinite loops forever; a finite number stops after that many repeats.
Try it yourself

Build a subtle pulsing notification dot with @keyframes, using only transform and opacity so it stays smooth. Then build a second animation using top/left instead, record both in DevTools' Performance panel while scrolling, and compare the layout/paint cost between the two.
