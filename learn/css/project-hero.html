04 Hero stage capstone

A design-token system and starter framework for a team

CSS · ties together everything in the Hero stage

This is the capstone of the CSS track: design and ship a small, genuinely reusable CSS foundation — a layered design-token system plus a handful of framework-grade components — built the way a real internal design system or a small open-source CSS framework would be, not the way a single page would be.

The bar is different here than in earlier stages. It's not "does this work on my page" — it's "could a team that has never talked to me adopt this, understand what's safe to change, and not be surprised six months later." That means documentation, versioning discipline, and layout code that doesn't quietly assume a single browser width, a single writing direction, or a single screen.

You'll draw on the full CSS toolkit from every stage: subgrid or advanced Grid for structural layout, container queries so components adapt to where they're dropped rather than to the viewport, and performance techniques (content-visibility, deliberate contain) applied somewhere they're actually justified by a real cost, not sprinkled in speculatively.

  • Container queries and intrinsic responsive design
  • Subgrid and advanced Grid layouts
  • Performance: critical CSS, containment, will-change
  • Building and maintaining a design system used by other teams
  • Authoring or contributing to a CSS framework
Requirements
  • A layered token file: primitive tokens (raw values) feeding semantic tokens (purpose-named values components actually consume), documented in a README explaining the difference and why the indirection exists.
  • At least one component using container-type/@container so it adapts to the width of whatever container it's placed in, demonstrated by placing the same component in two differently-sized containers on one demo page and showing each adapts independently.
  • At least one structural layout built with grid-template-areas and, where genuinely useful, subgrid to align nested content (e.g. a row of cards whose internal title/body/footer line up across the row even when one card's title wraps).
  • At least one deliberate, measured performance technique (content-visibility: auto with a sensible contain-intrinsic-size, or contain: layout paint on a repeated list) applied where you can show a before/after difference in DevTools' Performance panel, not applied everywhere by default.
  • Logical properties (margin-inline, padding-block, and friends) used instead of physical ones (margin-left, padding-top) throughout every component, verified by testing at least one page with dir="rtl" set on <html> and confirming the layout mirrors correctly.
  • A versioned CHANGELOG documenting at least one breaking change (a token rename or a component default change) with a stated migration path for consumers, not just a silent update.
  • A README a stranger could follow: what each token layer is for, which values are safe to override locally, and installation/usage instructions with no prior context assumed.
Suggested approach
  1. Design the token layers first, on paper or in a token file, before writing any component CSS — decide what's primitive versus semantic, since retrofitting that distinction later is much harder than starting with it.
  2. Build the structural layout (the page-level grid, subgrid alignment) next, since your components will need somewhere real to live in order to test container queries meaningfully.
  3. Build components one at a time, each consuming only semantic tokens and using logical properties from the start, rather than writing physical properties and converting them later.
  4. Add container queries and any performance techniques only once the core system works, and only where you can point to a specific reason (a component that's genuinely reused in differently-sized contexts, or a list that's genuinely long) — treat both as targeted fixes, not defaults.
  5. Write the README and CHANGELOG as you go rather than at the end, and test the RTL flip and the two-container-size container-query demo last, since both are the easiest things to silently break as you keep adding components.
Stretch goals
  • Register one of your custom properties with @property so it can be smoothly transitioned or animated, and use that for a real UI detail (like an animated progress value).
  • Find a real open-source CSS framework's "good first issue" list, pick one related to logical properties, RTL support, or a token, and submit a fix or a detailed report.
  • Publish your token file and components as an installable package (npm, or at minimum a public repo with clear install instructions) and have someone outside the project try to use it from just your README, with no help from you.
