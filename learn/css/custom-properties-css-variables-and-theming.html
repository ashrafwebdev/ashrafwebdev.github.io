Custom properties (CSS variables) and theming

CSS · part of the free zero-to-hero guide

Custom properties (commonly called CSS variables) let you name a value once and reuse it everywhere, defined with a -- prefix and read with var(). Unlike Sass variables, which are resolved once at build time and vanish from the compiled output, custom properties are live in the browser — they can change at runtime via media queries, JavaScript, or even per-component overrides, without recompiling anything.

Custom properties cascade and inherit like any other CSS property: a variable defined on :root is available everywhere, but redefining that same variable name on a more specific selector overrides it only within that subtree — which is exactly how per-component theming (like a 'danger' variant of a card) works without a completely separate set of classes.

var(--name, fallback) supplies a fallback value used whenever the variable is undefined or invalid, which makes components more resilient to being dropped into a page that hasn't defined every token yet. Note that an invalid value for a variable (not just a missing one) causes the property using it to fall back to its own initial value, not silently ignore the whole declaration — a subtlety worth testing when debugging.

Custom properties are readable and writable from JavaScript via element.style.setProperty('--name', value) and getComputedStyle(element).getPropertyValue('--name'), which is what makes them the standard bridge between JavaScript-driven interactivity (like a color picker or a drag-resize handle) and pure CSS styling.

Defining a palette of custom properties on :root is the foundation of theming: swap a handful of variable values (for dark mode, a rebrand, or a per-tenant theme) and the entire site updates without touching a single other rule — this is the single biggest practical win custom properties unlocked over the old copy-hex-codes-everywhere approach.

Unlike ordinary properties, custom properties don't have a defined type or syntax by default — --gap: 16px and --gap: red are both technically valid custom property values. The newer @property rule lets you register a custom property with an explicit syntax, initial value, and inheritance behavior, which also unlocks smoothly animating/transitioning custom properties, something plain var() usage can't do on its own.

styles.css
:root {
  --brand: #1F4E44;
  --text: #1A231F;
}

.btn { background: var(--brand); }
.btn:hover { background: color-mix(in srgb, var(--brand) 85%, white); }
styles.css (per-component override + JS bridge)
:root { --card-accent: #1F4E44; }

.card { border-top: 3px solid var(--card-accent); }
.card.danger { --card-accent: #B3261E; } /* overrides only within this card */

/* JavaScript can read/write the same variable: */
// document.querySelector('.card').style.setProperty('--card-accent', '#C1832E');
styles.css (@property for animatable custom properties)
@property --progress {
  syntax: '<percentage>';
  initial-value: 0%;
  inherits: false;
}

.bar {
  width: var(--progress);
  transition: --progress 0.3s ease; /* only smoothly animatable once registered */
}
.bar.loaded { --progress: 100%; }
Key points
  • Custom properties cascade and inherit like any other CSS property — they can be overridden per component or subtree.
  • var(--name, fallback) supplies a fallback if the variable isn't defined, but an invalid (not missing) value falls back to the property's own initial value instead.
  • Unlike Sass variables, custom properties are live at runtime and readable/writable from JavaScript via element.style.setProperty().
  • A well-designed token set (colors, spacing, radii) is the backbone of any real design system.
  • @property lets you register a type and initial value for a custom property, which also enables smoothly transitioning/animating it.
  • Custom properties have no built-in type checking by default — a variable meant for a color can technically hold any valid CSS token.
  • Redefining a variable name on a more specific selector overrides it only within that subtree, which is the mechanism behind per-component theming.
Try it yourself

Define a small palette of custom properties on :root and refactor an existing page to use var() instead of hardcoded color values. Then add a 'danger' variant of one component that overrides just that component's accent color variable, and confirm the rest of the page is unaffected.
