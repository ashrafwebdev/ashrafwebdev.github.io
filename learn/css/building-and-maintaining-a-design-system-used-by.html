Building and maintaining a design system used by other teams

CSS · part of the free zero-to-hero guide

At this level, CSS work stops being about a single page and starts being about a shared system: a documented set of design tokens (colors, spacing, type scale), reusable component styles, and clear usage guidelines that other teams adopt without needing to ask you questions.

The hard part isn't the CSS itself — it's governance: versioning changes without breaking every consumer, deprecating old patterns gracefully, and deciding what belongs in the system versus what's a one-off exception a team should own themselves.

A token file other teams import
:root {
  /* spacing scale */
  --space-1: 4px; --space-2: 8px; --space-3: 16px; --space-4: 24px;
  /* type scale */
  --text-sm: 0.875rem; --text-base: 1rem; --text-lg: 1.25rem;
}
Key points
  • A design system is documentation and governance as much as it is CSS — undocumented tokens don't get adopted.
  • Semantic versioning matters once other teams depend on your styles in production.
  • Design tokens (spacing, color, type scales) should be the foundation every component is built from, not an afterthought.
  • Collect real usage feedback from consuming teams — a design system built in isolation drifts from what people actually need.
Try it yourself

Define a small token set (4-5 spacing values, 3-4 type sizes, a color palette) and write one page of usage documentation for a hypothetical consuming team.
