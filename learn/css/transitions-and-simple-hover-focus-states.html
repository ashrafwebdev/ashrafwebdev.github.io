Transitions and simple hover/focus states

CSS · part of the free zero-to-hero guide

Builds on: Positioning: relative, absolute, fixed, sticky

Transitions animate a property smoothly from one value to another over time, instead of jumping instantly — the difference between a button that feels responsive and one that feels dead. They only run when the property's value actually changes, whether from a state change like :hover, a class toggled by JavaScript, or even a media-query switch.

The full shorthand is transition: property duration timing-function delay;. Always name the specific property (or a comma-separated list of them) rather than the keyword all — all forces the browser to watch every animatable property for changes, which is measurably slower and can accidentally animate properties you never intended to.

Pair transitions with interaction states: :hover for mouse users, and always :focus-visible too — a button that only responds to :hover is completely invisible to anyone navigating by keyboard. :focus-visible (rather than plain :focus) is preferred because it lets the browser suppress the focus ring for mouse clicks while still showing it for keyboard tabbing, matching what users expect from each input method.

Not every property animates equally cheaply. Transitioning transform and opacity is cheap because the browser can often handle them on the GPU compositor without recalculating layout; transitioning width, height, top, or margin forces the browser to recompute layout on every frame, which is measurably more expensive and can visibly stutter on lower-end devices.

The timing-function shapes how the transition accelerates: ease (the default) starts and ends gently; linear moves at a constant rate and often feels mechanical for UI; cubic-bezier() lets you define a fully custom curve. Small UI feedback (hover, focus) usually reads best with a short duration, roughly 150–250ms — much longer starts to feel sluggish rather than smooth.

Always account for prefers-reduced-motion: some users have explicitly told their OS they get discomfort or distraction from motion, and CSS lets you respect that preference by disabling or shortening transitions inside a matching media query rather than ignoring it.

styles.css
.btn {
  background: #1F4E44;
  transition: background 0.2s ease, transform 0.2s ease;
}
.btn:hover, .btn:focus-visible {
  background: #2E6B5E;
  transform: translateY(-1px);
}
styles.css (respecting reduced motion)
.btn { transition: background 0.2s ease, transform 0.2s ease; }

@media (prefers-reduced-motion: reduce) {
  .btn { transition-duration: 0.01ms; }
}
common mistake: transitioning 'all' and layout properties
/* Slow: watches every property, and animates width/margin which
   triggers layout recalculation on every single frame */
.card {
  transition: all 0.3s ease;
}
.card:hover {
  width: 320px;
  margin-top: -4px;
}

/* Fix: animate only transform/opacity, name properties explicitly */
.card {
  transition: transform 0.2s ease, box-shadow 0.2s ease;
}
.card:hover {
  transform: translateY(-4px);
  box-shadow: 0 8px 20px rgba(0,0,0,0.15);
}
Key points
  • transition: property duration easing; — always name the property, don't rely on all for performance.
  • Pair :hover with :focus-visible so keyboard users get the same feedback mouse users do.
  • Transitioning transform and opacity is cheap for the browser; transitioning width/height/margin is expensive because it triggers layout.
  • Respect prefers-reduced-motion for users who've asked their OS for less animation.
  • Short durations (roughly 150–250ms) read as responsive; much longer starts to feel sluggish for simple UI feedback.
  • Transitions only fire when a watched property's value actually changes — a state change, a JS-toggled class, or a media query switch.
  • :focus-visible shows the ring for keyboard navigation while suppressing it for mouse clicks, matching user expectations for each input type.
Try it yourself

Add a smooth background-color and slight upward transform transition to a button on both hover and keyboard focus, keeping the duration under 250ms. Then wrap the transition in a prefers-reduced-motion media query that shortens it to near-zero, and verify the effect by toggling 'reduce motion' in DevTools' rendering emulation.
