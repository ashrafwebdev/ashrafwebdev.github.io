Performance: critical CSS, containment, will-change

CSS · part of the free zero-to-hero guide

Critical CSS means inlining just the styles needed for the visible, above-the-fold content directly in the HTML head, so the browser can paint immediately without waiting on an external stylesheet round-trip — the rest of the CSS (for content the user hasn't scrolled to yet) loads afterward, typically via a non-blocking or deferred link.

contain tells the browser an element's internals won't affect layout, paint, size, or style outside its own boundary, letting the browser skip recalculating the rest of the page whenever that element changes. contain: layout paint is a strong, low-risk performance win for long, repeated lists of independent items, like a social feed or a large table, where each row genuinely doesn't affect its neighbors.

content-visibility: auto goes a step further than contain alone: it lets the browser entirely skip rendering work (layout and paint) for elements that are off-screen, only doing that work once the element scrolls into view. This is one of the single biggest wins available for very long pages, but it requires reserving approximate space with contain-intrinsic-size so the page doesn't jump around as off-screen content is realized.

will-change hints to the browser that a property is about to change (usually right before an animation starts), letting it prepare an optimized rendering path ahead of time. But it has a real cost: each element with will-change set typically gets promoted to its own GPU layer, which consumes memory — applying it to many elements, or leaving it on permanently, can actually slow a page down rather than speed it up.

The correct pattern for will-change is to add it via JavaScript immediately before the animation begins and remove it once the animation finishes, rather than baking it into the stylesheet permanently — this way the browser only pays the preparation cost during the brief window it's actually needed.

None of these techniques should be applied speculatively — Lighthouse and the Performance panel in Chrome DevTools are how you verify a given change actually reduced layout/paint time or improved a real metric like Largest Contentful Paint, rather than assuming an optimization helped because it sounds like it should.

styles.css
.widget-list-item {
  contain: layout paint;
}

.drawer.opening {
  will-change: transform;
}
styles.css (content-visibility for long pages)
.feed-item {
  content-visibility: auto;
  contain-intrinsic-size: 0 220px; /* reserved placeholder height, avoids layout jumps */
}
script.js (applying will-change only when needed)
const drawer = document.querySelector('.drawer');

drawer.addEventListener('pointerdown', () => {
  drawer.style.willChange = 'transform'; // set right before the animation
});
drawer.addEventListener('transitionend', () => {
  drawer.style.willChange = 'auto'; // remove once it's done, free the layer
});
Key points
  • Critical CSS trades a small inline block for a faster first paint — most useful on content-heavy landing pages.
  • contain: layout paint is a strong performance win for long, repeated lists of independent items.
  • content-visibility: auto skips rendering work for off-screen content entirely, but needs contain-intrinsic-size to avoid layout jumps.
  • Apply will-change only right before an animation starts, and remove it after — permanent use wastes GPU memory across many elements.
  • Each element with will-change typically gets its own GPU layer, which has a real memory cost, not just a benefit.
  • Lighthouse and the Performance panel in DevTools are how you verify these techniques actually helped, rather than guessing.
  • None of these optimizations are free — each one trades some resource (memory, complexity, or a reserved-space guess) for rendering speed, so apply them where profiling shows a real cost, not everywhere.
Try it yourself

Add contain: layout paint to items in a long repeated list (like a feed) and use the Performance panel to compare scrolling before and after. Then apply content-visibility: auto with a reasonable contain-intrinsic-size to the same list, and measure whether it further reduces initial rendering time.
