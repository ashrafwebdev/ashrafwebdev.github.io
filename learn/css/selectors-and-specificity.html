Selectors and specificity

CSS · part of the free zero-to-hero guide

A CSS rule pairs a selector (what to style) with a block of declarations (how to style it). The simplest selectors target a tag name (p), a class (.card), or an id (#header) — and combinators let you narrow further: a descendant selector (nav a), a direct child (nav > a), or a sibling relationship (h2 + p for 'immediately after', h2 ~ p for 'any later sibling').

When two rules target the same element with conflicting values, specificity decides the winner. It's calculated as a four-part tuple: inline styles, then ID selectors, then class/attribute/pseudo-class selectors, then type selectors and pseudo-elements. Each column outranks every combination of the columns to its right, no matter how many of them there are.

Pseudo-classes like :hover and :nth-child() count in the same column as classes. Pseudo-elements like ::before and ::after count as type selectors, the lowest tier. The universal selector * and combinators like > or + contribute nothing to specificity at all.

The modern selectors :is() and :where() handle grouping differently: :is() takes on the specificity of whichever argument inside it is most specific, while :where() always contributes zero specificity regardless of what's inside it — which makes :where() ideal for writing low-priority defaults that any later, ordinary rule can override without a fight.

When specificity ties exactly, the cascade falls back to source order: whichever rule was declared last (or was loaded last, for separate stylesheets) wins. This is why the order of your <link> tags and the order of rules within a file both matter.

In practice, the healthiest approach is to keep specificity as flat as possible: style almost everything with single classes, avoid ID selectors for styling entirely (ids are for JavaScript hooks and anchors), and treat !important as something you reach for only when overriding CSS you truly cannot edit, like third-party widget styles.

styles.css
p { color: black; }               /* specificity: 0-0-0-1 */
.highlight { color: orange; }     /* specificity: 0-0-1-0, wins over p */
#hero p.highlight { color: red; } /* specificity: 0-1-1-1, wins over both */
styles.css (is vs where)
/* :is() takes the specificity of its most specific argument */
:is(#sidebar, .panel) p { color: navy; }   /* behaves like #sidebar p → 0-1-0-1 */

/* :where() always contributes zero specificity */
:where(#sidebar, .panel) p { color: navy; } /* behaves like p → 0-0-0-1, trivially overridable */

/* a later, ordinary rule can now beat the :where() version without !important */
.panel p { color: teal; }
common mistake: fighting specificity with !important
/* Someone reached for !important instead of fixing the real problem */
#main .content .card p { color: gray !important; }

/* Now every future override needs its own !important, and the war escalates */
.card p.note { color: red !important; }

/* Better: lower the original selector's specificity so normal rules can override it */
.card p { color: gray; }
.card p.note { color: red; }
Key points
  • Specificity is a four-part tuple (inline, id, class/attribute/pseudo-class, type/pseudo-element) — higher columns always beat lower ones, regardless of source order.
  • Reach for !important only as an absolute last resort — it breaks the normal cascade for everyone who edits the file after you.
  • Overly specific selectors (deeply nested, id-based) make a stylesheet harder to override later and often lead to specificity wars.
  • When specificity ties exactly, the rule appearing later in the cascade (or later in load order) wins.
  • :where() always contributes zero specificity; :is() takes on the specificity of its most specific argument — pick the one that fits your intent.
  • Pseudo-elements (::before) count as type selectors; pseudo-classes (:hover) count as classes.
  • Combinators (>, +, ~) and the universal selector * add zero specificity by themselves.
  • Use the browser DevTools' 'Computed' panel to see exactly which declared rule won and why when styles don't apply as expected.
Try it yourself

Write three CSS rules of increasing specificity that all target the same paragraph, predict which color wins, then verify it in DevTools. Afterward, rewrite the most specific rule using :where() so an ordinary class selector can override it, and confirm the winner changes.
