Ownership and borrowing in depth

Rust · part of the free zero-to-hero guide

Borrowing lets you access a value without taking ownership of it, using references: &value for an immutable (read-only) borrow, or &mut value for a mutable borrow. This avoids the constant moving and returning of values that pure ownership alone would require.

The borrow checker enforces one core rule at compile time: for any value, you may have either any number of immutable borrows, or exactly one mutable borrow, but never both at the same time. This single rule is what prevents data races and iterator-invalidation bugs without needing a runtime lock.

Lifetimes (written 'a) let the compiler verify that a reference never outlives the data it points to; most of the time lifetimes are inferred automatically, and you only write them explicitly in a handful of situations, like a function returning a reference derived from two different input references.

Modern Rust uses non-lexical lifetimes (NLL): the borrow checker tracks a reference's last actual use in the code, not merely the end of its enclosing lexical scope, so a borrow is considered "finished" as soon as it's no longer needed. This makes many intuitively-safe patterns compile that would have been rejected by the borrow checker in early versions of Rust.

Returning a reference to a value created locally inside a function is a compile error, because that local value's memory does not survive the function returning — the reference would immediately dangle. The fix is almost always to return an owned value (like a String instead of a &str pointing into a local buffer) so ownership transfers cleanly to the caller instead.

A common borrow-checker surprise: holding an immutable reference into a Vec while separately trying to .push() onto that same Vec in the same scope is rejected, even though it might look harmless. The reason is that push can trigger a reallocation that moves every existing element to a new memory address, which would leave the earlier reference dangling — the borrow checker rejects the pattern outright rather than trying to prove it's safe in this particular case.

main.rs
fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() > y.len() { x } else { y }
}

fn add_one(n: &mut i32) {
    *n += 1;
}

fn main() {
    let mut value = 10;
    add_one(&mut value);
    println!("{}", value);

    let a = String::from("hello");
    let b = String::from("hi");
    println!("{}", longest(&a, &b));
}

}
vec_borrow_gotcha.rs
fn main() {
    let mut numbers = vec![1, 2, 3];
    let first = &numbers[0];

    // numbers.push(4); // ERROR: cannot borrow `numbers` as mutable
    //                  // while it is also borrowed as immutable (`first`)
    println!("first: {}", first);

    // after `first`'s last use, the borrow ends (thanks to NLL)
    numbers.push(4); // fine here
    println!("{:?}", numbers);
}
Key points
  • &value borrows immutably; &mut value borrows mutably; you can never mix the two at once.
  • The borrow checker enforces these rules entirely at compile time, with no runtime cost.
  • Lifetime annotations like 'a tell the compiler how long a reference must stay valid.
  • Most lifetimes are inferred automatically; explicit annotations are the exception, not the rule.
  • Non-lexical lifetimes track a reference's last real use, not just its enclosing scope's end.
  • Returning a reference to a function-local value is a compile error; return an owned value instead.
  • Holding a reference into a Vec while pushing to it is rejected, since push can reallocate and invalidate it.
  • A reference can never outlive the data it points to — the borrow checker's entire job is proving this.
Try it yourself

Write a function that takes a mutable reference to a Vec of i32 and doubles every element in place, then call it and print the resulting vector. Then write (and comment out) an attempted function that tries to return a reference to a String created inside its own body, and add a comment explaining exactly why the compiler rejects it.
