04 Hero stage capstone

A benchmarked ring buffer, published as a real crate

Rust · ties together everything in the Hero stage

This is the capstone of the Rust track: design, build, benchmark, and publish a small, genuinely useful crate — a fixed-capacity ring buffer (circular buffer) — that solves a real performance-sensitive problem: storing the last N items of a stream without ever reallocating. It's a project small enough to finish, and serious enough to put on a resume as proof you can write, profile, and ship real systems-level Rust.

The bar here isn't "it compiles." It's "a stranger could add this to their Cargo.toml, trust the safety of its internals, and see the benchmark numbers that justify using it over a naive Vec-based version." That means unsafe code used deliberately and justified with SAFETY comments, a measured (not assumed) performance story, and packaging that looks like every other real crate on crates.io.

Two of this stage's other topics show up as tools in service of the main goal rather than the goal itself: a small macro to cut repetition in your own tests, and the same contribution etiquette (formatting, linting, a real README, a documented MSRV) you'd expect from any crate you'd trust enough to depend on yourself.

  • Unsafe Rust and when it's actually needed
  • Advanced macro programming
  • Building performance-critical systems software
  • Contributing to the Rust compiler or ecosystem crates
Requirements
  • A generic RingBuffer type supporting push and pop with wraparound, implemented with zero heap allocation after construction, using unsafe internals (raw pointers or MaybeUninit) where index arithmetic alone isn't enough — with every unsafe block accompanied by a SAFETY comment explaining exactly what invariant it depends on.
  • A fully safe public API: no sequence of calls a caller makes through the public methods can trigger undefined behavior, no matter how the buffer is used.
  • A benchmark suite using criterion comparing your ring buffer's push/pop performance against a naive Vec-based reference implementation, with the actual numbers written up in the README.
  • A test suite covering edge cases specifically — popping from an empty buffer, pushing into a full buffer, and a push/pop sequence that wraps across the underlying array's boundary — plus at least one doctest demonstrating typical usage on your crate's main type.
  • A small macro_rules! macro that removes real repetition from your own tests or examples (e.g. asserting a buffer's contents equal a given slice in one line).
  • cargo miri test runs against your unsafe code with zero reported issues.
  • The crate is packaged like a real one: complete Cargo.toml metadata (description, license, repository), a README with usage examples and your benchmark results, and a successful cargo publish --dry-run (or an actual publish to crates.io if you're ready to make it public).
Suggested approach
  1. Start with a safe-but-slower implementation — index arithmetic over a Vec of Option of T, no unsafe at all — and get the API and its test suite fully correct before optimizing anything.
  2. Once the tests pass, replace the internal storage with a raw allocation or a MaybeUninit array and rewrite push/pop using unsafe, keeping the public method signatures identical so your existing tests keep validating correctness through the rewrite.
  3. Run cargo miri test after every unsafe change you make, not just once at the end, so any undefined behavior gets caught close to the change that introduced it.
  4. Add the criterion benchmark comparing your buffer against the naive version, and only write performance claims in the README after you have real numbers in hand.
  5. Write the test-helper macro, fill in Cargo.toml metadata and the README, and finish with cargo publish --dry-run.
Stretch goals
  • Generalize the buffer to work correctly with non-Copy types, handling Drop for elements still sitting in the buffer when it's dropped.
  • Implement the Iterator trait for your ring buffer so it works with for loops and iterator adapter chains.
  • Set up a CI matrix testing against your crate's documented MSRV alongside stable and beta, following the same conventions covered in this stage's lesson on contributing to the Rust ecosystem.
