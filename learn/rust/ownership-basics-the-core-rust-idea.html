Ownership basics (the core Rust idea)

Rust · part of the free zero-to-hero guide

Ownership is Rust's central idea: every value has exactly one owner variable, and when that owner goes out of scope, Rust automatically frees the value's memory — no garbage collector, no manual free(), and no dangling pointers, enforced entirely at compile time.

Assigning a heap-allocated value like a String to another variable moves ownership rather than copying it; the original variable becomes invalid, and using it afterward is a compile error. This is different from simple types like integers, which implement the Copy trait and are duplicated cheaply instead of moved.

This one rule — one owner, memory freed automatically when it goes out of scope — is what lets Rust guarantee memory safety without runtime overhead, and understanding it is the single most important step in learning the language.

Cleanup itself is handled by the Drop trait, an implementation of the RAII (Resource Acquisition Is Initialization) pattern: when an owner goes out of scope, Rust automatically calls its drop method, which is how file handles get closed and heap memory gets freed without you writing any cleanup code. You can implement Drop yourself for custom cleanup logic, but you can never call .drop() directly — use std::mem::drop(value) if you need to force early cleanup.

Passing a value into a function by value moves it in exactly the same way an assignment does: unless the function hands it back as its return value, the caller permanently loses access to it. This is precisely the inconvenience that borrowing (covered in a later lesson) exists to solve, letting code access a value temporarily without taking ownership at all.

When you genuinely need two independent copies of a heap value, .clone() performs an explicit deep copy. Rust deliberately does not clone automatically the way it copies simple stack types, so the cost of duplicating a potentially large heap allocation is always visible directly in the source code rather than hidden behind an innocuous-looking assignment.

main.rs
fn main() {
    let s1 = String::from("hello");
    let s2 = s1; // ownership moves to s2
    // println!("{}", s1); // would not compile: s1 is no longer valid
    println!("{}", s2);

    let x = 5;
    let y = x; // integers implement Copy, so both are valid
    println!("{} {}", x, y);
}
drop_and_functions.rs
struct Connection {
    name: String,
}

impl Drop for Connection {
    fn drop(&mut self) {
        println!("closing connection: {}", self.name);
    }
}

fn take_ownership(s: String) -> String {
    println!("got: {}", s);
    s // handed back to the caller
}

fn main() {
    let a = Connection { name: String::from("db") };
    let b = Connection { name: String::from("cache") };

    let greeting = String::from("hi");
    let greeting = take_ownership(greeting);
    println!("{}", greeting);

    // a and b drop in reverse declaration order: b, then a
}
clone_rescue.rs
fn main() {
    let original = String::from("important data");
    let backup = original.clone(); // explicit deep copy

    let moved_away = original; // original is now invalid, but backup is untouched
    println!("{}", moved_away);
    println!("{}", backup);
}
Key points
  • Every value has exactly one owner; memory is freed automatically when the owner goes out of scope.
  • Assigning a heap value like String moves ownership; the old variable becomes invalid.
  • Types implementing the Copy trait (like integers) are duplicated instead of moved.
  • These rules are enforced entirely at compile time, with zero runtime garbage-collection cost.
  • The Drop trait implements RAII: cleanup code runs automatically when an owner leaves scope.
  • Passing a value into a function by value moves it, unless the function returns it back.
  • .clone() performs an explicit deep copy, keeping the cost of duplication visible in the code.
  • std::mem::drop(value) forces early cleanup instead of calling .drop() directly.
Try it yourself

Write a function that takes ownership of a String, prints it, and returns a new String; call it and observe which variables remain valid afterward. Then define a struct with a Drop implementation that prints a message on cleanup, create two instances of it, and observe the order in which the drop messages print relative to their declaration order.
