Advanced macro programming

Rust · part of the free zero-to-hero guide

Builds on: Unsafe Rust and when it's actually needed

Rust has two kinds of macros: declarative macros (macro_rules!), which match against patterns in the token stream and expand into code, similar to a sophisticated find-and-replace; and procedural macros, which are Rust functions that run at compile time and can generate or transform arbitrary code, most commonly used for #[derive(...)].

A macro_rules! macro can accept a variable number of arguments using repetition patterns ($($x:expr),*), which is exactly how the standard library's own vec! macro is implemented under the hood.

Procedural macros come in three flavors — derive macros, attribute macros, and function-like macros — and are commonly used to eliminate boilerplate, such as #[derive(Serialize, Deserialize)] automatically generating serialization code for a struct.

macro_rules! macros are hygienic by default: an identifier introduced inside the macro's expansion (like a temporary local variable) cannot accidentally collide with an identically-named variable at the call site, which is a meaningful safety guarantee that naive C preprocessor-style textual substitution simply doesn't provide.

Each $variable inside a macro_rules! pattern is annotated with a fragment specifier describing what kind of Rust syntax it's allowed to capture: expr for an expression, ident for an identifier, ty for a type, block for a brace-delimited block, and tt (token tree) as a catch-all for a single token or bracketed group. These specifiers are what let the macro system report a reasonably clear error instead of simply failing to parse.

Writing an actual procedural macro requires its own separate crate marked proc-macro = true in Cargo.toml, since proc macros operate directly on token streams rather than pattern-matching source text. Almost every real-world proc macro relies on the syn crate to parse the incoming tokens into a proper syntax tree, and the quote crate to generate the output tokens back out, which is why syn and quote are considered close to standard tooling for this kind of macro.

main.rs
macro_rules! max {
    ($a:expr, $b:expr) => {
        if $a > $b { $a } else { $b }
    };
}

fn main() {
    println!("{}", max!(3, 7));
    println!("{}", max!(10.5, 2.1));
}
sum_macro.rs
macro_rules! sum {
    ($($x:expr),*) => {
        {
            let mut total = 0;
            $(total += $x;)*
            total
        }
    };
}

fn main() {
    println!("{}", sum!(1, 2));
    println!("{}", sum!(1, 2, 3));
    println!("{}", sum!(1, 2, 3, 4));
}
hygiene.rs
macro_rules! double_it {
    ($x:expr) => {
        {
            let total = $x * 2; // this `total` is hygienic
            total
        }
    };
}

fn main() {
    let total = 100; // this `total` is a completely separate binding
    let doubled = double_it!(21);
    println!("{} {}", total, doubled); // 100 42, no collision
}
Key points
  • Declarative macros (macro_rules!) pattern-match token streams and expand into code at compile time.
  • Procedural macros are compile-time Rust functions that generate or transform code, powering derive macros.
  • Repetition patterns let a macro accept a variable number of arguments, as vec! itself does.
  • Derive macros like #[derive(Serialize)] eliminate large amounts of otherwise-repetitive boilerplate.
  • macro_rules! macros are hygienic: identifiers they introduce don't collide with the call site's identifiers.
  • Fragment specifiers (expr, ident, ty, block, tt) control what kind of syntax each $variable may capture.
  • Procedural macros live in their own crate marked proc-macro = true in Cargo.toml.
  • syn parses proc-macro input into a syntax tree; quote generates the output tokens — the de facto standard toolkit.
Try it yourself

Write a macro_rules! macro called sum that accepts a variable number of expressions using a repetition pattern and expands to their total, testing it with two, three, and four arguments. Then add a comment explaining which fragment specifier you used for the repeated argument and why an ident or ty specifier would not have worked there.
