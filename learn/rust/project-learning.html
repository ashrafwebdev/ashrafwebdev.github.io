02 Learning stage capstone

Your terminal to-do list, saved to disk between runs

Rust · ties together everything in the Learning stage

This project takes the CLI habit you built at Zero and pushes it somewhere genuinely useful: a task manager that remembers your tasks after the program exits. It's the first project where the data actually has to survive, which forces you to confront ownership and borrowing for real instead of just avoiding the compiler's complaints by accident.

You'll model each task as a struct stored in a collection, look tasks up by id, and use Result and Option everywhere something can genuinely fail or be absent — a missing task id, a corrupted save file, a bad command — rather than reaching for .unwrap() as a default habit. Persistence itself comes from a crates.io package, which means this is also your first real experience adding and using an external dependency.

The constraint that makes this a genuine test of the stage: no task manager state is allowed to live only in memory. Every mutation — adding, completing, deleting a task — has to be written back to disk before the program exits, and reloaded correctly the next time it starts.

  • Ownership and borrowing in depth
  • Result and Option for error handling
  • Traits and generics basics
  • Collections (Vec, HashMap)
  • Working with crates.io packages
Requirements
  • A Task struct with at minimum an id, a description, and a done flag, deriving Debug, Clone, and PartialEq.
  • A collection of tasks stored in a struct (e.g. TaskList) backed by a HashMap keyed by task id, so looking up a specific task by id doesn't require scanning a Vec.
  • Command-line subcommands for at least add, list, complete, and delete (e.g. cargo run -- add "buy milk", cargo run -- done 3).
  • Tasks are saved to a JSON file using serde and serde_json (added with cargo add), loaded on startup and written back after every mutating command.
  • Every fallible operation — file I/O, parsing a task id from a string, finding a task that might not exist — returns a Result or Option and is propagated with the ? operator rather than unwrapped blindly.
  • Looking up a task that doesn't exist (e.g. completing task id 99 when it doesn't exist) prints a clear "no such task" message instead of panicking.
  • A custom trait (e.g. a Summarize trait implemented for Task) is used at least once to produce the text shown by the list command, rather than formatting it inline.
Suggested approach
  1. Build the in-memory version first: Task struct, a HashMap-backed TaskList, and hard-coded add/list/complete calls in main with no command-line parsing or persistence at all.
  2. Add command-line subcommand parsing next, still entirely in-memory, so you can confirm add/list/done/delete each do the right thing before persistence enters the picture.
  3. Add #[derive(Serialize, Deserialize)] to Task, and write save/load functions that return Result, using ? throughout — get a round-trip (save, then load, then confirm the tasks match) working before wiring it into the rest of the program.
  4. Wire save-after-every-mutation and load-at-startup into main, and go back over every .unwrap() you wrote earlier, replacing the ones on genuinely fallible operations with proper Result/Option handling.
  5. Add the Summarize trait last, once the data model is stable, and use it in your list command's output.
Stretch goals
  • Add a due-date field using a date-handling crate from crates.io, and sort the list output by due date.
  • Add a filter flag to the list command (e.g. only pending, or only completed tasks).
  • Support multiple named task lists stored in separate files, selected with a flag.
