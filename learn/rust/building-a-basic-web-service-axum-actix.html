Building a basic web service (axum/actix)

Rust · part of the free zero-to-hero guide

axum and actix-web are the two most popular async web frameworks in Rust, both built on tokio. axum favors composability and integrates tightly with tower's middleware ecosystem; actix-web favors raw performance and has been a long-standing benchmark leader.

In axum, routes are declared with a Router, mapping a path and HTTP method to an async handler function; handler parameters implementing axum's extractor traits (like Json or Path) automatically parse the relevant part of the request.

Returning a type that implements axum's IntoResponse trait (a plain String, a tuple of status code and body, or a Json wrapper) is enough to produce a proper HTTP response, with serialization handled automatically for JSON.

Real handlers usually need access to shared resources, such as a database connection pool or an in-memory cache. axum's State extractor, paired with .with_state(...) on the Router, is the idiomatic way to give every handler access to the same shared value, typically wrapped in an Arc so cloning it into each handler stays cheap.

Cross-cutting behavior — logging, CORS headers, request timeouts, response compression — is added with tower's Layer trait rather than woven into every handler individually. Calling .layer(...) on a Router wraps every route with that middleware, and the tower-http crate ships a large set of ready-made layers covering the common cases.

A handler doesn't have to return a fixed success type: returning a Result whose error type implements IntoResponse lets you centralize how a domain error (like "not found" or "invalid input") turns into the right HTTP status code and body, rather than hand-matching the error in every single handler that could produce it.

main.rs
use axum::{routing::get, Router, extract::Path};

async fn hello() -> &'static str {
    "Hello, axum!"
}

async fn greet(Path(name): Path<String>) -> String {
    format!("Hello, {}!", name)
}

#[tokio::main]
async fn main() {
    let app = Router::new()
        .route("/", get(hello))
        .route("/greet/:name", get(greet));

    let listener = tokio::net::TcpListener::bind("0.0.0.0:8080").await.unwrap();
    axum::serve(listener, app).await.unwrap();
}
shared_state.rs
use axum::{routing::{get, post}, Router, extract::State, Json};
use std::sync::{Arc, Mutex};

#[derive(Clone)]
struct AppState {
    counter: Arc<Mutex<i32>>,
}

async fn increment(State(state): State<AppState>) -> Json<i32> {
    let mut count = state.counter.lock().unwrap();
    *count += 1;
    Json(*count)
}

async fn current(State(state): State<AppState>) -> Json<i32> {
    Json(*state.counter.lock().unwrap())
}

#[tokio::main]
async fn main() {
    let state = AppState { counter: Arc::new(Mutex::new(0)) };

    let app = Router::new()
        .route("/increment", post(increment))
        .route("/count", get(current))
        .with_state(state);

    let listener = tokio::net::TcpListener::bind("0.0.0.0:8080").await.unwrap();
    axum::serve(listener, app).await.unwrap();
}
handler_errors.rs
use axum::{response::{IntoResponse, Response}, http::StatusCode};

enum ApiError {
    NotFound,
}

impl IntoResponse for ApiError {
    fn into_response(self) -> Response {
        match self {
            ApiError::NotFound => (StatusCode::NOT_FOUND, "not found").into_response(),
        }
    }
}

async fn get_item(id: u32) -> Result<String, ApiError> {
    if id == 1 {
        Ok(String::from("widget"))
    } else {
        Err(ApiError::NotFound)
    }
}
Key points
  • axum and actix-web are the two dominant async web frameworks in Rust, both built on tokio.
  • axum routes map a path and method to an async handler using a Router.
  • Extractor types like Path and Json automatically parse relevant parts of the incoming request.
  • Returning any IntoResponse-implementing type is enough to produce a valid HTTP response.
  • The State extractor with .with_state(...) gives handlers access to shared, typically Arc-wrapped resources.
  • tower's Layer trait adds cross-cutting middleware (logging, CORS, timeouts) without touching handler logic.
  • A handler returning Result of T, E where E implements IntoResponse centralizes error-to-response mapping.
  • tower-http ships ready-made layers, avoiding the need to hand-roll common middleware.
Try it yourself

Extend a small axum app with an Arc-wrapped in-memory counter as shared State, add a POST route that increments it and a GET route that returns the current value as JSON. Then add one tower-http layer (such as request tracing) to the router, and write a custom error enum implementing IntoResponse for a route that can fail.
