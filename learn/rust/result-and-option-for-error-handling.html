Result and Option for error handling

Rust · part of the free zero-to-hero guide

Builds on: Ownership and borrowing in depth

Rust has no exceptions and no null. Instead, a value that might be absent is wrapped in Option, with variants Some(value) or None; a fallible operation returns Result, with variants Ok(value) or Err(error). Both are ordinary enums the compiler forces you to handle explicitly.

The ? operator is Rust's concise error-propagation shortcut: inside a function returning Result, writing some_call()? either unwraps the Ok value or immediately returns the Err to the caller, avoiding deeply nested manual error checks.

Because both types must be explicitly matched, unwrapped, or propagated, it is structurally impossible to accidentally use a missing or errored value as if it were valid — the compiler simply won't allow it.

Both types offer a rich set of combinators for transforming values without a full match: .map() transforms the inner value if present, .and_then() chains together operations that themselves return Option or Result, and .unwrap_or(default) / .unwrap_or_else(|| ...) supply a fallback value. These keep code concise while remaining just as total (every case still handled) as an explicit match.

.unwrap() and .expect("message") immediately panic the whole program if called on a None or Err. They're genuinely useful in prototypes, tests, and cases you've already proven can't fail, and .expect's custom message makes debugging a panic much easier — but reaching for either in production logic that should handle failure gracefully is a common code-review flag.

Real applications frequently define their own error enum (implementing std::error::Error, often with help from crates like thiserror or anyhow) so a function can return one unified error type instead of leaking whichever specific library's error type happened to fail underneath. The ? operator can automatically convert between error types along the way, as long as a From implementation exists describing how to convert one into the other.

main.rs
use std::num::ParseIntError;

fn parse_and_double(input: &str) -> Result<i32, ParseIntError> {
    let n: i32 = input.parse()?;
    Ok(n * 2)
}

fn main() {
    match parse_and_double("21") {
        Ok(value) => println!("Doubled: {}", value),
        Err(e) => println!("Failed to parse: {}", e),
    }
}
combinators.rs
fn safe_divide(a: f64, b: f64) -> Option<f64> {
    if b == 0.0 { None } else { Some(a / b) }
}

fn main() {
    let result = safe_divide(10.0, 2.0)
        .map(|v| v * 100.0)
        .unwrap_or(0.0);
    println!("{}", result);

    let failed = safe_divide(10.0, 0.0)
        .map(|v| v * 100.0)
        .unwrap_or(-1.0);
    println!("{}", failed);
}
custom_error.rs
use std::fmt;

#[derive(Debug)]
enum AppError {
    Parse(String),
    Empty,
}

impl fmt::Display for AppError {
    fn fmt(&self, f: &mut fmt::Formatter) -> fmt::Result {
        match self {
            AppError::Parse(s) => write!(f, "could not parse: {}", s),
            AppError::Empty => write!(f, "input was empty"),
        }
    }
}

fn parse_positive(input: &str) -> Result<i32, AppError> {
    if input.is_empty() {
        return Err(AppError::Empty);
    }
    input.parse::<i32>().map_err(|_| AppError::Parse(input.to_string()))
}

fn main() -> Result<(), AppError> {
    let n = parse_positive("42")?;
    println!("parsed: {}", n);
    Ok(())
}
Key points
  • Option models a value that may or may not exist; Result models an operation that may fail.
  • The ? operator propagates an Err or unwraps an Ok in a single character.
  • The compiler forces every Option and Result to be handled, eliminating null-reference-style bugs entirely.
  • match, unwrap_or, and if let are common ways to work with these types.
  • Combinators like .map() and .and_then() transform and chain values without a full match.
  • .unwrap()/.expect() panic on None/Err; use them deliberately, not as a default habit.
  • Custom error enums let a function return one unified error type instead of leaking a dependency's error type.
  • The ? operator can convert between error types automatically via a From implementation.
Try it yourself

Write a function that parses a string to an i32, returning a Result, then use the ? operator inside a caller function and handle both success and error with a match. Then write a second function returning Option of f64 that safely divides two numbers, chaining .map() and .unwrap_or() to produce a default value instead of a full match.
