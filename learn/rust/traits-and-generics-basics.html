Traits and generics basics

Rust · part of the free zero-to-hero guide

A trait defines shared behavior a type can implement, similar to an interface: trait Summary { fn summarize(&self) -> String; } declares a method any implementing type must provide, using impl Summary for MyType.

Generics let you write a function or struct once that works with any type: a generic function using a type parameter T, and trait bounds like T: PartialOrd restrict which types are allowed while granting access to that trait's methods inside the function.

Traits and generics combine constantly in Rust: impl Trait as a return type, or a where clause with multiple bounds, are common ways to write flexible code that the compiler still fully type-checks and can often optimize as if it were hand-written for each concrete type.

Trait methods can supply a default implementation: a method body written directly in the trait definition is used automatically by any implementor that doesn't override it, which is a natural way to share common behavior across many implementors while still allowing individual ones to customize just the parts that differ.

When a function needs several capabilities from its generic type at once, bounds combine with +, as in T: Display + Clone, or move into a separate where clause once the parameter list starts getting long or involves multiple type parameters — purely a readability convention, not a difference in meaning.

#[derive(...)] covers common, mechanical trait implementations (Debug, Clone, PartialEq, PartialOrd), but a manual impl is needed whenever the behavior isn't simply "do the obvious thing field by field" — a custom Display implementation for user-facing output is a typical example, kept deliberately separate from the developer-facing Debug output.

main.rs
trait Summary {
    fn summarize(&self) -> String;
}

struct Article {
    title: String,
}

impl Summary for Article {
    fn summarize(&self) -> String {
        format!("Article: {}", self.title)
    }
}

fn print_summary(item: &impl Summary) {
    println!("{}", item.summarize());
}

fn main() {
    let a = Article { title: String::from("Rust Ownership") };
    print_summary(&a);
}
default_methods_and_bounds.rs
trait Greet {
    fn name(&self) -> String;

    fn greet(&self) -> String {
        format!("Hello, {}!", self.name()) // default implementation
    }
}

struct Person { name: String }
struct Robot { id: u32 }

impl Greet for Person {
    fn name(&self) -> String { self.name.clone() }
    // uses the default greet()
}

impl Greet for Robot {
    fn name(&self) -> String { format!("Unit-{}", self.id) }
    fn greet(&self) -> String { format!("BEEP BOOP {}", self.name()) }
}

fn largest<T: PartialOrd + Copy>(items: &[T]) -> T {
    let mut max = items[0];
    for &item in items {
        if item > max { max = item; }
    }
    max
}

fn main() {
    println!("{}", Person { name: String::from("Sumaya") }.greet());
    println!("{}", Robot { id: 7 }.greet());
    println!("{}", largest(&[3, 7, 2, 9, 4]));
}
custom_display.rs
use std::fmt;

struct Temperature { celsius: f64 }

impl fmt::Display for Temperature {
    fn fmt(&self, f: &mut fmt::Formatter) -> fmt::Result {
        write!(f, "{:.1}\u{00B0}C", self.celsius)
    }
}

fn main() {
    let t = Temperature { celsius: 21.5 };
    println!("current: {}", t); // uses our Display impl
}
Key points
  • A trait declares behavior a type must implement, similar to an interface in other languages.
  • Generic functions and structs use a type parameter that gets filled in when they're used.
  • Trait bounds restrict a generic type parameter while granting access to that trait's methods.
  • impl Trait as a parameter or return type is shorthand for a common generic pattern.
  • Default trait method implementations are shared automatically unless an implementor overrides them.
  • Multiple bounds combine with +, or move into a where clause for readability.
  • #[derive(...)] covers mechanical trait impls; write Display/custom traits manually otherwise.
  • Display is for user-facing output; Debug is for developer-facing inspection — they're separate on purpose.
Try it yourself

Define a trait Greet with a default greet() method, override it for one struct and accept the default for another, then write a generic function largest of T with a PartialOrd bound that returns the largest element of a slice. Also implement a custom Display for one of your structs and print an instance with {} to see it used.
