Advanced traits and generics

Rust · part of the free zero-to-hero guide

Builds on: Working with crates.io packages

Associated types let a trait define a placeholder type that each implementor fills in, such as the Iterator trait's type Item, which avoids needing a separate generic parameter for every implementation of the trait.

Trait objects (dyn Trait, usually behind Box of dyn Trait) allow storing different concrete types that share a trait in the same collection, resolved via dynamic dispatch at runtime, as opposed to generics which are resolved at compile time via monomorphization (a separate specialized copy generated per concrete type).

Choosing between generics and trait objects is a real design decision: generics give zero-cost, compile-time-specialized code at the cost of larger binaries; trait objects give a single shared implementation and heterogeneous collections at the cost of a small runtime dispatch overhead.

Rust lets you overload operators like +, -, and == for your own types by implementing the corresponding trait from std::ops — implementing Add for a custom vector type lets two instances be summed with plain + syntax instead of a named method, which reads far more naturally in mathematical code.

A supertrait relationship, written trait B: A, requires that anything implementing B must also implement A, letting B's own methods freely call methods from A since the compiler guarantees they'll always be available together. This is a common way to build layered trait hierarchies without duplicating requirements.

A blanket implementation implements a trait for every type that satisfies some other bound at once — for instance, the standard library implements ToString for every type that already implements Display, so you get .to_string() for free the moment you write a Display implementation. It's a powerful pattern for extending a trait across an entire family of types with a single block of code, though it's worth noting that not every trait can be turned into a trait object: dyn Trait requires the trait to be "object safe," which rules out methods that return Self by value or that are themselves generic.

main.rs
trait Shape {
    fn area(&self) -> f64;
}

struct Circle { radius: f64 }
struct Square { side: f64 }

impl Shape for Circle {
    fn area(&self) -> f64 { 3.14159 * self.radius * self.radius }
}
impl Shape for Square {
    fn area(&self) -> f64 { self.side * self.side }
}

fn main() {
    let shapes: Vec<Box<dyn Shape>> = vec![
        Box::new(Circle { radius: 2.0 }),
        Box::new(Square { side: 3.0 }),
    ];
    for s in &shapes {
        println!("{}", s.area());
    }
}
operator_overload.rs
use std::ops::Add;

#[derive(Debug, Clone, Copy)]
struct Vector2D { x: f64, y: f64 }

impl Add for Vector2D {
    type Output = Vector2D;

    fn add(self, other: Vector2D) -> Vector2D {
        Vector2D { x: self.x + other.x, y: self.y + other.y }
    }
}

fn main() {
    let a = Vector2D { x: 1.0, y: 2.0 };
    let b = Vector2D { x: 3.0, y: 4.0 };
    println!("{:?}", a + b); // uses our Add impl
}
supertrait_and_blanket.rs
use std::fmt::Debug;

trait Named: Debug {
    fn name(&self) -> String;

    fn describe(&self) -> String {
        format!("{} ({:?})", self.name(), self) // relies on Debug from the supertrait
    }
}

#[derive(Debug)]
struct Item { label: String }

impl Named for Item {
    fn name(&self) -> String { self.label.clone() }
}

fn main() {
    let item = Item { label: String::from("widget") };
    println!("{}", item.describe());
}
Key points
  • Associated types let a trait define a per-implementor placeholder type, as the Iterator trait does.
  • Trait objects (dyn Trait) enable heterogeneous collections resolved via dynamic dispatch.
  • Generics are monomorphized at compile time; trait objects share one implementation at runtime.
  • Choose generics for zero-cost specialization, trait objects for heterogeneous collections.
  • Implementing std::ops traits like Add lets custom types use operators like + naturally.
  • A supertrait (trait B: A) guarantees A's methods are always available wherever B is implemented.
  • Blanket implementations extend a trait across every type satisfying some bound, like ToString via Display.
  • dyn Trait requires object safety; methods returning Self by value or generic methods disqualify a trait.
Try it yourself

Create a Vec of Box of dyn Shape holding at least two different shape types, iterate over it, and print the total combined area. Then implement std::ops::Add for a custom Vector2D struct so two vectors can be summed with plain +, and define a supertrait Named requiring Debug so its default describe() method can rely on debug formatting.
