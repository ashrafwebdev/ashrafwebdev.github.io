Async Rust (tokio basics)

Rust · part of the free zero-to-hero guide

Builds on: Concurrency: threads and message passing

Rust's async/await syntax lets you write non-blocking code that reads sequentially, but unlike some languages, Rust's standard library provides only the language feature — an actual async runtime like tokio is needed to actually execute async code, since Rust deliberately keeps the runtime out of the language core.

An async fn returns a Future that does nothing until it's .awaited or driven by the runtime; #[tokio::main] is the common way to turn fn main() into an async entry point backed by tokio's runtime.

tokio::spawn runs a future concurrently as a lightweight task, and tokio::join! or tokio::select! let you run multiple futures concurrently and either wait for all of them or react to whichever finishes first.

Async tasks are cooperatively scheduled, unlike OS threads: a task only yields control back to the runtime at an .await point. A long CPU-bound loop written inside an async function with no .await anywhere inside it will run to completion without ever yielding, starving every other task scheduled on that same worker thread in the meantime — CPU-heavy work belongs in tokio::task::spawn_blocking or a dedicated OS thread instead.

Anything passed to tokio::spawn must be 'static and Send, because a spawned task may be moved to and run on any of the runtime's worker threads and can outlive the function that spawned it. This is why capturing a borrowed reference (rather than an owned value) into a spawned task is a common compile error for newcomers.

It's worth being realistic about when async actually helps: it shines for I/O-bound workloads with many concurrent waits — network requests, file access, database queries — where a task spends most of its time waiting rather than computing. For CPU-bound work, plain OS threads or a data-parallelism library like rayon are usually a better fit; async by itself does not make computation faster.

main.rs
use tokio::time::{sleep, Duration};

async fn fetch_data() -> String {
    sleep(Duration::from_millis(500)).await;
    String::from("data loaded")
}

#[tokio::main]
async fn main() {
    println!("fetching...");
    let result = fetch_data().await;
    println!("{}", result);
}
spawn_and_join.rs
use tokio::time::{sleep, Duration};

async fn worker(id: u32, delay_ms: u64) -> String {
    sleep(Duration::from_millis(delay_ms)).await;
    format!("worker {} done", id)
}

#[tokio::main]
async fn main() {
    let handles = vec![
        tokio::spawn(worker(1, 300)),
        tokio::spawn(worker(2, 100)),
        tokio::spawn(worker(3, 200)),
    ];

    for handle in handles {
        println!("{}", handle.await.unwrap());
    }
}
spawn_blocking.rs
fn cpu_heavy_work() -> u64 {
    (1..=40u64).product() // pretend this is expensive
}

#[tokio::main]
async fn main() {
    // WRONG: putting cpu_heavy_work() directly in an async fn with
    // no .await would block the whole worker thread's other tasks.
    let result = tokio::task::spawn_blocking(cpu_heavy_work)
        .await
        .unwrap();
    println!("{}", result);
}
Key points
  • Rust's async/await is a language feature; an executor like tokio is required to actually run futures.
  • An async fn returns a Future that only runs once awaited or polled by the runtime.
  • #[tokio::main] sets up a tokio runtime around an async main function.
  • tokio::spawn, join!, and select! run and coordinate multiple futures concurrently.
  • Async tasks are cooperatively scheduled and only yield at .await points, unlike preemptive OS threads.
  • A CPU-bound loop with no .await inside an async function can starve every other task on its thread.
  • Tasks passed to tokio::spawn must be 'static and Send, since they may outlive the caller and move threads.
  • Async shines for I/O-bound waiting; CPU-bound work belongs on spawn_blocking or dedicated threads.
Try it yourself

Write three async functions that each simulate an I/O delay with sleep and return a distinct value, run them concurrently with tokio::spawn, and collect all three results via their JoinHandles. Then add a comment explaining why placing a long CPU-bound loop directly inside one of those functions (with no await inside it) would block the entire runtime thread's other tasks.
