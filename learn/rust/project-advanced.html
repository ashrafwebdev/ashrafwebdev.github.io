03 Advanced stage capstone

A URL-shortener API with a background analytics logger

Rust · ties together everything in the Advanced stage

This project is a small but real async web service: a URL shortener with an axum backend, shared in-memory state, and — the part that makes it more than a tutorial clone — a dedicated background OS thread that logs every visit and creation event, fed by a channel from your async handlers. That combination forces you to use both concurrency models this stage teaches: tokio's cooperative async tasks for the web layer, and a genuine OS thread with message passing for the background work, in the same program.

It also has to hold up under the stage's other big theme: doing errors properly. Every handler that can fail needs to return a real HTTP error response, not a panic, which means a custom error type and a trait implementation tying it into axum's response system.

The constraint that makes this a genuine test of the stage, not just a copy-pasted axum starter: the background logging thread has to be a plain std::thread receiving over an mpsc channel, kept entirely separate from tokio's runtime, so you have to reason clearly about which parts of your program are async tasks and which are OS threads.

  • Advanced traits and generics
  • Concurrency: threads and message passing
  • Async Rust (tokio basics)
  • Testing and documentation
  • Building a basic web service (axum/actix)
Requirements
  • An axum (or actix-web) REST API with at least three routes: create a short code for a submitted URL, redirect or look up a URL by its short code, and list every URL that's been shortened so far.
  • The URL mapping lives behind shared state (e.g. Arc of Mutex of a HashMap), wired through axum's State extractor and .with_state(...) exactly as covered in this stage's lessons.
  • A custom error enum implements axum's IntoResponse trait, and at least one handler returns a Result whose error variant maps to a correct, specific HTTP status code (e.g. 404 for an unknown short code).
  • A dedicated std::thread, separate from the tokio runtime, receives creation and lookup events over an mpsc channel from your handlers and appends them to a log file.
  • At least one tower/tower-http middleware layer is applied to the router (e.g. request tracing or logging).
  • A trait defines what a URL store must support (e.g. get and insert methods), implemented for your concrete in-memory store, so the storage logic isn't hard-wired directly into your handlers.
  • A test suite covering the core store logic (shorten, lookup, handle a missing code) that runs with cargo test without needing a running server, plus at least one doctest on a public function.
Suggested approach
  1. Build and test the core logic in isolation first: a plain struct implementing your store trait around a HashMap, with unit tests for shortening and lookup, and no web framework or threads involved yet.
  2. Wrap that store in Arc of Mutex, wire up the three axum routes with State, and confirm you can create and look up short codes with curl before adding anything else.
  3. Add the mpsc channel and the background logging thread, sending one event per handler call, and confirm entries actually land in the log file while the server keeps responding normally.
  4. Replace ad-hoc .unwrap() calls in handlers with your custom error enum and its IntoResponse implementation, checking with curl that a missing short code now returns a proper 404 instead of a 500 or a panic.
  5. Add the tower-http layer and the remaining tests (or doctests) last, once the routes and error handling are stable.
Stretch goals
  • Add TTL-based expiration for short codes, cleaned up periodically by a background task.
  • Add a second store implementation and use a dyn Trait so the router can be built against either one interchangeably.
  • Add a basic rate-limiting layer so a single client can't create unlimited short codes per minute.
