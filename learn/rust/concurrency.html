Concurrency: threads and message passing

Rust · part of the free zero-to-hero guide

Rust's standard library spawns OS threads with std::thread::spawn, and the borrow checker's ownership rules extend directly into concurrency: data moved into a thread closure can no longer be used by the spawning thread, which prevents data races at compile time rather than catching them at runtime.

Channels (std::sync::mpsc) let threads communicate by sending owned values rather than sharing mutable memory directly, embodying the same message-passing philosophy popularized by Go, with Rust's ownership system providing the additional guarantee that a sent value can never be accessed by two threads simultaneously.

When threads genuinely need to share state, Arc (atomic reference counting, for shared ownership across threads) combined with Mutex (for safe mutable access) is the standard pattern, and Rust's type system enforces that you cannot access the data inside a Mutex without holding its lock.

thread::spawn returns a JoinHandle, and calling .join() on it blocks the current thread until the spawned thread finishes, returning its final value (or the panic payload, wrapped in an Err, if it panicked). Forgetting to join a handle isn't a compile error, but it means you have no guarantee the spawned work finished before the program moves on — the main thread exiting can end the whole process regardless of what background threads were still doing.

The Send and Sync marker traits describe thread-safety at the type level: a type is Send if it's safe to move to another thread, and Sync if it's safe to access from multiple threads through a shared reference. The compiler derives both automatically for most types and, critically, rejects at compile time any attempt to move a non-Send type like Rc across a thread boundary — which is exactly why threaded code reaches for Arc (the thread-safe counterpart to Rc) instead.

It's worth being clear about what these guarantees do and don't cover: Rust's ownership and type system prevent data races entirely, but they say nothing about deadlocks. Acquiring two mutexes in inconsistent order across different threads can still hang a Rust program forever, exactly as in any other language — Rust's promise is memory safety, not liveness.

main.rs
use std::sync::mpsc;
use std::thread;

fn main() {
    let (tx, rx) = mpsc::channel();

    for i in 1..=3 {
        let tx = tx.clone();
        thread::spawn(move || {
            tx.send(i * i).unwrap();
        });
    }
    drop(tx);

    for value in rx {
        println!("{}", value);
    }
}
join_handles.rs
use std::thread;

fn main() {
    let handles: Vec<_> = (1..=3)
        .map(|i| thread::spawn(move || i * i))
        .collect();

    let results: Vec<i32> = handles
        .into_iter()
        .map(|h| h.join().expect("thread panicked"))
        .collect();

    println!("{:?}", results);
}
arc_mutex_counter.rs
use std::sync::{Arc, Mutex};
use std::thread;

fn main() {
    let counter = Arc::new(Mutex::new(0));
    let mut handles = vec![];

    for _ in 0..5 {
        let counter = Arc::clone(&counter);
        handles.push(thread::spawn(move || {
            let mut num = counter.lock().unwrap();
            *num += 1;
        }));
    }

    for h in handles {
        h.join().unwrap();
    }

    println!("final count: {}", *counter.lock().unwrap());
    // using Rc instead of Arc here would fail to compile:
    // Rc is not Send, so it cannot be moved into another thread
}
Key points
  • Ownership rules extend into threads: the compiler prevents data races, not just detects them at runtime.
  • Channels (mpsc) let threads communicate by sending owned values instead of sharing memory.
  • Arc provides thread-safe shared ownership; Mutex provides safe mutable access.
  • The type system enforces that Mutex-protected data can only be accessed while holding its lock.
  • thread::spawn returns a JoinHandle; .join() waits for completion and retrieves the result.
  • The Send and Sync marker traits let the compiler reject unsafe cross-thread moves at compile time.
  • Rc is not thread-safe and won't compile across threads; Arc is its thread-safe counterpart.
  • Rust prevents data races, but not deadlocks — inconsistent lock ordering can still hang a program.
