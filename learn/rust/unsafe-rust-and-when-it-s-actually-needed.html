Unsafe Rust and when it's actually needed

Rust · part of the free zero-to-hero guide

The unsafe keyword unlocks five specific capabilities the compiler cannot otherwise verify as safe: dereferencing raw pointers, calling unsafe functions, accessing mutable statics, implementing unsafe traits, and accessing union fields. Everything else in Rust remains exactly as safe as normal, even inside an unsafe block.

unsafe does not turn off the borrow checker or type checking — it only grants access to those five specific operations, and the programmer takes on the responsibility of manually upholding the invariants the compiler would normally enforce, such as never producing a dangling raw pointer.

In practice, unsafe is needed for FFI (calling C libraries), building certain low-level data structures the borrow checker can't reason about directly (like some intrusive linked lists), and performance-critical code; well-written unsafe code is typically wrapped in a small, carefully-audited safe API so the rest of the program never needs to reason about it.

It's worth being precise about what happens when an unsafe invariant is actually violated: it isn't guaranteed to crash right away. Dereferencing a dangling pointer or creating two conflicting mutable references through raw pointers is undefined behavior, meaning the compiler is free to assume it never happens and can miscompile code around it in ways that only surface later, on a different platform, or under a different optimization level. This is exactly why unsafe code demands more discipline than safe Rust's "the compiler will catch it" mindset encourages, not less.

Calling into C code requires an extern "C" block declaring the foreign function's signature, and every call into such a function is itself unsafe by default, since Rust has no way to verify that the foreign code upholds Rust's own invariants. The same extern "C" and #[no_mangle] attributes work in reverse too, exposing a Rust function so it can be called from C.

Miri, an experimental interpreter for Rust's mid-level intermediate representation, can catch many categories of undefined behavior in unsafe code — out-of-bounds access, use-after-free, invalid pointer aliasing — while running your test suite, catching bugs the compiler itself has no way to detect. Running cargo miri test is a genuinely valuable habit whenever a project contains a meaningful amount of hand-written unsafe code.

main.rs
fn main() {
    let mut num = 5;
    let r1 = &num as *const i32;
    let r2 = &mut num as *mut i32;

    unsafe {
        println!("r1 is: {}", *r1);
        *r2 = 10;
        println!("r1 is now: {}", *r1);
    }
}
ffi.rs
// declares a C function's signature so Rust can call it
extern "C" {
    fn abs(input: i32) -> i32;
}

// exposes this Rust function to be called from C
#[no_mangle]
pub extern "C" fn rust_double(x: i32) -> i32 {
    x * 2
}

fn main() {
    unsafe {
        println!("abs(-4) = {}", abs(-4)); // calling into C is unsafe
    }
}
safe_wrapper.rs
// SAFETY: caller must guarantee `slice` is non-empty.
// Violating this reads out of bounds, which is undefined behavior.
fn first_or_default(slice: &[i32], default: i32) -> i32 {
    if slice.is_empty() {
        return default;
    }
    unsafe { *slice.get_unchecked(0) } // skips the bounds check
}

fn main() {
    println!("{}", first_or_default(&[10, 20, 30], -1));
    println!("{}", first_or_default(&[], -1));
}
Key points
  • unsafe unlocks exactly five operations; it does not disable the borrow checker.
  • The programmer, not the compiler, guarantees safety invariants inside an unsafe block.
  • Common legitimate uses: FFI with C libraries, specialized data structures, and performance-critical code.
  • Idiomatic unsafe code is wrapped in a small, well-audited safe API for the rest of the program to use.
  • Violating an unsafe invariant is undefined behavior, not a guaranteed crash — the compiler may miscompile around it.
  • extern "C" blocks declare foreign function signatures; calling them is unsafe by default.
  • #[no_mangle] extern "C" fn exposes a Rust function to be called from C code.
  • Miri (cargo miri test) catches many forms of undefined behavior in unsafe code that rustc cannot.
Try it yourself

Write a small safe wrapper function first_or_default that uses an unsafe block internally with get_unchecked to read the first element of a slice without a bounds check when the caller has already verified the slice is non-empty. Add a SAFETY comment explaining exactly what invariant the caller must uphold for this to remain sound, and test it against both an empty and a non-empty slice.
